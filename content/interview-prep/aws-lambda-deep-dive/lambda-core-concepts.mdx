<SimpleDefinition>

AWS Lambda is a serverless, event-driven compute service where you upload just your function code and AWS handles provisioning, patching, and scaling the underlying servers, billing you only for the milliseconds your code actually runs.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Sabse pehli galti jo log karte hain: "serverless" sunke sochte hain server exist hi nahi karta. Aisa nahi hai — server hai, AWS ke kisi data center me physical/virtual machine chal rahi hai, bas wo machine **aapki responsibility nahi hai**. Aap uska OS patch nahi karte, uska capacity plan nahi karte, uska monitoring setup nahi karte. Aap sirf ek cheez dete ho: **function code**. Baaki sab AWS ka kaam hai.

### Function, handler, aur runtime — teen alag cheezein

**Function** ek deployment unit hai — code, configuration (memory, timeout, environment variables), aur permissions (IAM role) ka bundle. **Handler** us function ke andar wo specific entry point hai jise AWS invoke karta hai jab event aata hai — jaise Node.js me `exports.handler = async (event, context) => {...}`, ya Python me `def lambda_handler(event, context):`. Handler ka naam configuration me specify hota hai (`fileName.exportName` format), isliye galat naam dena ek common deploy-time mistake hai — function exist karega lekin invoke pe "handler not found" error dega.

**Runtime** wo environment hai jisme code chalta hai — Node.js, Python, Java, Go, Ruby, .NET, ya phir **custom runtime** (Runtime API ke through — koi bhi language jo Linux binary bana sake, jaise Rust). AWS managed runtimes automatically patch hote hain (minor security updates), lekin ek din wo runtime **deprecate** ho jaata hai aur naye function creation block ho jaata hai — isliye purani runtime pe chal rahe production functions ko periodically upgrade karna padta hai, warna ek din surprise breakage milta hai.

### Event-driven invocation model

Lambda **kabhi khud se nahi chalta** — koi na koi event source usse trigger karta hai. Ye teen tareeke se ho sakta hai: **synchronous** (caller response ka wait karta hai — jaise API Gateway), **asynchronous** (caller sirf event queue kar deta hai aur aage badh jaata hai — jaise S3 ObjectCreated), ya **poll-based** (Lambda service khud kisi source ko poll karti hai — jaise SQS queue). Har invocation ko ek `event` object milta hai (JSON — jo bhi trigger ne bheja) aur ek `context` object (request ID, remaining time, memory limit jaisi metadata). Ye distinction agle topic me detail me aayega, lekin core idea abhi samajhna zaroori hai: **Lambda passive hai, event active hai** — jab tak koi event nahi aata, code execute hi nahi hota, aur na hi koi cost lagti hai.

### Billing — pay-per-millisecond, high-level

Do cheezon ka paisa lagta hai: **number of requests** (per-invocation flat charge, bahut chhota) aur **duration × memory** (GB-second — jitni der function chala, uska memory allocation ke saath multiply hota hai). Milestone samajhna zaroori hai: agar function nahi chal raha, **zero cost** — EC2 ke ulat, jahan idle instance bhi paisa leta hai. Isi wajah se Lambda spiky ya low-traffic workloads (contact form, cron job, event processing) ke liye financially bahut sense banata hai, lekin **sustained high-throughput** workload (24×7 heavy traffic) ke liye kabhi kabhi EC2/Fargate sasta pad jaata hai — exact numbers (pricing, free tier, GB-second math) doosre topics me aayenge jahan memory/timeout configuration discuss hoga.

### Kab use karo, kab nahi

Lambda best fit hai jab: workload event-driven hai, traffic unpredictable/spiky hai, ya operational overhead minimize karna priority hai. Lambda **galat choice** hai jab: workload long-running hai (batch job jo ghanton chale — max timeout 15 minute hai), consistently high sustained CPU/memory chahiye (containers/EC2 sasta padega), ya aapko underlying OS/kernel level control chahiye (custom networking, specific kernel modules). Ek real gotcha: agar function bahut heavy dependencies use karta hai (large ML models, native binaries), package size aur cold start dono badh jaate hain — us case me container-based Lambda (up to 10 GB image) ya Fargate better fit ho sakta hai.

</Hinglish>

<Callout type="tip">

Interview me "serverless ka matlab kya hai" pucha jaaye to sirf "no server management" mat bolo — explicitly kaho "server exists, but provisioning/patching/scaling AWS ki responsibility hai, aap sirf code aur configuration dete ho." Ye distinction interviewer ko dikhata hai ki aap surface-level buzzword nahi, actual mental model samajhte ho.

</Callout>

## Real World Example

<RealWorld company="A Production AWS Project">

Ek startup apni image-resize pipeline Lambda pe banata hai kyunki traffic unpredictable hai — kabhi din me 5 uploads, kabhi marketing campaign ke time 5,000. EC2 pe ek dedicated instance rakhte to 99% waqt idle capacity ka paisa jaata. Function ka handler simple hai: S3 se image event le, PIL/Sharp se resize kare, output alag bucket me daale. Runtime Python 3.12, code sirf ~80 lines ka, aur poori infrastructure management team ka time image-processing logic pe jaata hai, server patching pe nahi.

</RealWorld>

## Numbers That Matter

<Numbers>

<ul>
<li>Supported managed runtimes: Node.js, Python, Java, Go, Ruby, .NET, plus custom runtimes via Runtime API</li>
<li>Billing granularity: 1 millisecond (historically 100ms blocks, changed years ago)</li>
<li>Free tier (perpetual, every AWS account): 1 million requests/month + 400,000 GB-seconds/month compute</li>
<li>Max function timeout: 900 seconds (15 minutes) — not built for long-running batch jobs</li>
<li>Deployment package size: 50 MB zipped via console/CLI upload, 250 MB unzipped including layers; container images up to 10 GB</li>
</ul>

</Numbers>

## Interview Angle

<InterviewAngle>

The very first question in almost any Lambda discussion is "what is serverless, really" — a weak answer just says "no servers to manage," a strong answer explicitly separates "server exists, not your concern" from "you only ship code + config." Interviewers also probe whether you know the difference between function, handler, and runtime as distinct concepts — mixing them up (calling the runtime a "handler," for instance) signals shallow familiarity. A classic follow-up: "when would you NOT use Lambda" — the strong answer names concrete disqualifiers (15-minute timeout ceiling, sustained high-throughput cost, need for OS-level control) rather than a vague "for big things."

</InterviewAngle>

## Common Mistakes

<Mistake>

Sochna ki "serverless" ka matlab server exist nahi karta — actually server hai, bas AWS manage karta hai. Interview me ye galat framing turant weak candidate jaisa lagta hai.

</Mistake>

<Mistake>

Handler naming format galat dena (fileName.exportName mismatch) — deploy to ho jaata hai lekin pehli invocation pe hi "handler not found" runtime error milta hai, jo confusing lagta hai kyunki build/deploy successful dikha tha.

</Mistake>

<Mistake>

Lambda ko har workload ke liye default choice samajhna — long-running batch jobs (15 min se zyada) ya sustained heavy-traffic services ke liye EC2/Fargate/ECS zyada sense banata hai, cost aur design dono angle se.

</Mistake>

<Mistake>

Deprecated runtime pe production function chhod dena — AWS ek din naya function creation us runtime pe block kar deta hai aur eventually existing functions bhi force-upgrade ki deadline milti hai, jo last-minute scramble bana deta hai.

</Mistake>

## Quick Revision

<QuickRevision>

<ul>
<li>Serverless does not mean no server — it means the server is AWS's responsibility, not yours</li>
<li>Function = code + config + IAM role bundle; Handler = specific entry point invoked; Runtime = language environment code runs in</li>
<li>Lambda is purely event-driven — it never runs on its own, only in response to a trigger</li>
<li>Three invocation styles exist: synchronous, asynchronous, and poll-based (covered in depth in the next topic)</li>
<li>Billing is per-millisecond duration times memory (GB-seconds) plus a small per-request charge — zero cost when idle</li>
<li>Max timeout is 900 seconds — Lambda is not designed for long-running batch processing</li>
<li>Managed runtimes get patched automatically but eventually deprecate — stale runtimes are an operational risk</li>
</ul>

</QuickRevision>
