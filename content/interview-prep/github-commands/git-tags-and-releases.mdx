<SimpleDefinition>

A git tag is a fixed pointer to a specific commit, typically used to mark release points (v1.0.0, v2.3.1) that, unlike branches, never move forward as new commits are added, and comes in two flavors -- lightweight (a bare pointer) and annotated (a full Git object with author, date, and message, plus GPG-signing support).

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Branch aur tag dono commit ko point karte hain, lekin fundamental difference hai: branch ek **moving** pointer hai -- naya commit karo, branch automatically aage badh jaati hai. Tag ek **frozen** pointer hai -- ek baar laga do, wo hamesha usi commit ko point karega, chahe repo me baad me kitne bhi commits aa jaayein. Yehi property tags ko release marking ke liye perfect banati hai: "v2.3.1 exactly ye commit tha" -- ye statement kabhi change nahi hoga.

### Lightweight vs annotated tags

**Lightweight tag** bas ek naam hai jo directly ek commit SHA pe point karta hai -- koi extra metadata nahi, koi separate Git object nahi banta:

```bash
git tag v1.0.0-lw
```

**Annotated tag** apna khud ka Git object banata hai jisme tagger ka naam, email, date, aur ek message store hota hai -- basically ek chhota commit-jaisa object jo khud commit ko point karta hai:

```bash
git tag -a v1.0.0 -m "Release 1.0.0 -- initial stable release"
```

`-a` flag "annotated" ke liye hai, `-m` message deta hai (na diya to editor khulega, commit message jaisa). Annotated tags **GPG-signed** bhi ho sakte hain (`git tag -s v1.0.0 -m "..."`) taaki verify ho sake ye tag genuinely authorized person ne banaya, kisi ne repo access mil jaane pe fake release tag nahi push kiya.

**Practical rule: releases ke liye hamesha annotated tags use karo.** Lightweight tags casual/temporary bookmarking ke liye theek hain (jaise "yaha ek baar dekh lena"), lekin release ka permanent record chahiye jisme pata ho kisne, kab, kyun tag banaya -- wo sirf annotated tag deta hai. `git describe` command bhi annotated tags ko prefer karta hai jab wo nearest tag dhoondta hai commit history me.

### Pushing tags

Bahut important gotcha: **tags automatically push nahi hote** normal `git push` se. Explicitly push karna padta hai:

```bash
git push origin v1.0.0          # ek specific tag push karo
git push --tags                 # saare local tags ek saath push karo
git push origin --tags          # explicit remote ke saath saare tags
```

`git push --tags` convenient hai lekin risky bhi -- agar aapke paas koi local experimental/temp tags hain jo aap share nahi karna chahte, wo bhi push ho jaayenge. Isliye teams me convention hota hai: sirf explicit `git push origin <tagname>` use karo release tags ke liye, `--tags` avoid karo jab tak sab tags genuinely shareable na hon.

### Semantic versioning convention

Real-world me tags almost hamesha **SemVer** (`MAJOR.MINOR.PATCH`, jaise `v2.3.1`) follow karte hain:

- **MAJOR** badhta hai jab breaking change ho (backward-incompatible API change)
- **MINOR** badhta hai jab naya feature add ho, backward-compatible tareeke se
- **PATCH** badhta hai jab bug fix ho, koi naya feature nahi

`v` prefix convention hai (`v1.0.0` not `1.0.0`), though universal rule nahi hai -- kuch orgs bina `v` ke bhi karte hain. Pre-release tags `v2.0.0-beta.1` ya `v2.0.0-rc.1` jaisa naming use karte hain.

### Tags triggering release pipelines

CI/CD systems (GitHub Actions included) tag push ko ek trigger event ke roop me use karte hain -- jaise koi tag jo `v*` pattern match kare push hote hi, automatically ek release pipeline chal jaaye: build artifact banao, changelog generate karo, GitHub Release create karo, package registry (npm/NuGet/Docker Hub) pe publish karo. Ye pattern isliye clean hai kyunki tagging ek explicit, deliberate human action hai -- "ye commit officially release-ready hai" -- jo normal commit pushes se alag hai jo continuously ho rahe hote hain.

### Deleting a tag

Local aur remote dono jagah se alag command chahiye:

```bash
git tag -d v1.0.0-typo               # local se delete
git push origin --delete v1.0.0-typo # remote se delete
# older/alternate syntax for remote delete:
git push origin :refs/tags/v1.0.0-typo
```

</Hinglish>

<Callout type="warning">

Agar ek tag already kisi CI/CD pipeline ne consume kar liya hai (build published ho chuka, ya kisi ne wo tag pull karke deploy kar diya), delete karke usi naam se dobara alag commit pe tag lagana bahut confusing hota hai -- log/artifact mismatch ho jaata hai. Release tags ko treat karo jaise wo immutable hain, ek baar publish ho gaye to.

</Callout>

## Real World Example

<RealWorld company="GitHub">

Open-source projects par maintainers `v1.4.0` jaisa annotated tag push karte hain jab release-ready commit ready ho jaata hai. GitHub Actions workflow `on: push: tags: ["v*"]` trigger pe automatically build karta hai, binaries attach karta hai, aur GitHub Releases page pe changelog ke saath publish kar deta hai -- sab kuch us ek `git push origin v1.4.0` command se shuru hota hai.

</RealWorld>

<RealWorld company="Microsoft">

.NET NuGet package publishing pipelines me tag push (`v3.2.0`) hi wo signal hota hai jo package version number decide karta hai -- CI script tag name se version extract karke usi version se NuGet package pack aur publish karta hai, taaki Git history aur published package version hamesha sync me rahein.

</RealWorld>

## Numbers That Matter

<Numbers>

<ul>
<li>SemVer format has exactly 3 numeric parts: MAJOR.MINOR.PATCH</li>
<li>Annotated tags create a real Git object (like a commit); lightweight tags create zero extra objects</li>
<li>Two separate commands needed to fully delete a tag: one for local, one for remote</li>
<li>`git push` alone pushes zero tags by default -- always requires an explicit tag push command</li>
<li>Common CI trigger pattern: `tags: ["v*"]` matches any tag starting with v</li>
</ul>

</Numbers>

## Interview Angle

<InterviewAngle>

"Lightweight aur annotated tag me fundamental difference kya hai, aur releases ke liye kaunsa use karoge?" -- strong answer: annotated tag ek full Git object hai jisme tagger, date, message store hota hai (aur GPG-signable hai), jabki lightweight tag sirf ek bare pointer hai. Releases ke liye hamesha annotated -- production-grade audit trail chahiye. "Agar `git push` ke baad tag remote pe nahi dikh raha, kya wajah ho sakti hai?" -- strong answer: tags normal push ke saath automatically nahi jaate, explicit `git push origin <tagname>` ya `git push --tags` chahiye. Ek scenario question aata hai: "release pipeline kaise trigger karoge sirf specific commits pe, har push pe nahi?" -- strong answer: tag-based trigger (`on push tags: v*`) use karo, taaki deliberate tagging hi release ka signal ho, continuous commits nahi.

</InterviewAngle>

## Common Mistakes

<Mistake>

`git push` chala ke assume karna ki tag bhi push ho gaya -- tags ko explicitly push karna padta hai, ye normal commits ke saath automatically nahi jaate.

</Mistake>

<Mistake>

Casual lightweight tags use karna releases ke liye -- audit trail (kisne, kab, kyun) missing rehta hai, jo production incident investigation me problem create karta hai.

</Mistake>

<Mistake>

`git push --tags` blindly use karna -- ye saare local tags push kar deta hai including temporary/experimental ones jo shayad share karne ka irada hi nahi tha.

</Mistake>

<Mistake>

Ek already-published release tag ko delete karke usi naam se dusre commit pe re-tag karna -- ye downstream consumers (CI artifacts, deployed builds) ke liye version-commit mismatch create karta hai jo debug karna mushkil hota hai.

</Mistake>

<Mistake>

SemVer convention ignore karna aur random naming (`final-build`, `latest-fix`) use karna -- isse automation tools (jo `v*` pattern match karte hain) tag ko detect hi nahi kar paate.

</Mistake>

## Quick Revision

<QuickRevision>

<ul>
<li>`git tag v1.0.0-lw` -- lightweight tag, bare pointer, no extra metadata</li>
<li>`git tag -a v1.0.0 -m "message"` -- annotated tag, full object with author/date/message, use this for releases</li>
<li>`git tag -s v1.0.0 -m "message"` -- GPG-signed annotated tag</li>
<li>`git push origin v1.0.0` -- push one specific tag (safest, explicit)</li>
<li>`git push --tags` -- push all local tags at once (use with caution)</li>
<li>`git tag -d v1.0.0` then `git push origin --delete v1.0.0` -- delete local then remote</li>
<li>SemVer: MAJOR.MINOR.PATCH -- breaking change, new feature, bug fix respectively</li>
<li>CI/CD pipelines commonly trigger release builds on `tags: ["v*"]` push events</li>
</ul>

</QuickRevision>
