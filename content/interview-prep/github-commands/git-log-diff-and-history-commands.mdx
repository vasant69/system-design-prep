<SimpleDefinition>

git log, git diff, git blame, and git show are Git's core history-inspection commands — they let you view commit history, compare changes between working states or commits, trace which commit last changed a specific line, and inspect the full content of a single commit.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Jab bhi tumhe samajhna ho "yahan kya hua tha," "yeh line kyun change hui," ya "in do branches mein kya farak hai" — Git ke history commands yeh sab answer dete hain. Yeh commands data ko delete ya modify nahi karte, sirf inspect karte hain, isliye experiment karne mein koi risk nahi hai.

### git log — commit history dekhna

Plain `git log` bahut verbose hota hai — full commit hash, author, date, aur poora message har commit ke liye. Real-world mein useful flags ke saath use karte hain:

```bash
git log                            # full verbose history
git log --oneline                  # ek line per commit — hash (short) + message
git log --oneline --graph          # + ASCII graph dikhata hai branches/merges ka
git log --oneline --graph --all    # sab branches ka graph, sirf current branch nahi
git log --author="Priya"           # sirf Priya ke commits
git log -p                         # -p = --patch, har commit ka actual diff bhi dikhao
git log -5                         # sirf last 5 commits
git log --since="2 weeks ago"      # time-based filter
git log -- path/to/file.js         # sirf us specific file ko touch karne wale commits
```

`--oneline --graph --all` combo daily use mein sabse zyada helpful hai — ek glance mein pura branch structure aur merge history dikh jaata hai, especially jab team confused ho ki "yeh feature branch kahan se diverge hua tha."

### git diff — changes compare karna

`git diff` teen alag comparisons kar sakta hai, aur confusion yahi hota hai ki bina argument ke yeh exactly kya compare kar raha hai:

```bash
git diff                           # working directory vs staging area (UNSTAGED changes)
git diff --staged                  # staging area vs last commit (STAGED changes) — also --cached
git diff HEAD                      # working directory vs last commit (staged + unstaged dono)
git diff main..feature-branch      # do branches ke beech farak
git diff HEAD~3 HEAD                # last 3 commits mein kya changed
git diff -- file.js                # sirf ek specific file ka diff
```

Yeh teen-way distinction interview mein bahut common hai: plain `git diff` sirf woh dikhata hai jo abhi tak `git add` nahi hua; `--staged` woh dikhata hai jo staged hai lekin commit nahi hua; `HEAD` ke against dono combine karke dikhata hai. Agar `git add` kar diya aur phir `git diff` chalao, kuch nahi dikhega — kyunki woh changes ab staged hain, unstaged nahi — is confusion mein naye developers phas jaate hain.

### git blame — kisne, kab, kyun change kiya

`git blame` ek file ki har line ke against woh commit dikhata hai jisne last us line ko modify kiya — author, date, aur commit hash ke saath.

```bash
git blame file.js                          # poori file, line-by-line attribution
git blame -L 10,25 file.js                 # sirf line 10 se 25 tak
git blame -w file.js                       # whitespace changes ignore karo (formatting commits skip)
git blame --ignore-rev <commit-hash> file.js  # ek specific "noise" commit (jaise bulk reformat) ignore karo
```

Real use-case: production mein ek bug dikha, aur tumhe pata karna hai "yeh weird logic kisne aur kyun likha." `git blame` us line ka commit hash de dega, jisse `git show` se poora context (commit message, related changes) mil jaata hai. Ek common frustration yeh hai ki agar beech mein koi bulk formatting commit (jaise Prettier run) aa gaya ho, toh blame us formatting commit ko point karta hai, actual logic-author ko nahi — is scenario ke liye `--ignore-rev` ya ek `.git-blame-ignore-revs` file use karte hain.

### git show — ek commit ka poora detail

```bash
git show <commit-hash>             # us commit ka message + full diff
git show HEAD                      # sabse recent commit
git show HEAD~2                    # 2 commits pehle
git show <commit-hash>:path/file.js  # us commit ke time file ka poora content dikhao
```

`git show` `git log -p` ka single-commit version samjho — jab tumhe pata hai exactly kaunsa commit dekhna hai (jaise `git blame` se mila hash), `git show <hash>` seedha us commit ka poora context de deta hai.

### In sab ko saath mein use karna — ek real debugging flow

1. `git log --oneline --graph -- api/payment.js` — payment.js ko touch karne wale sab commits dekho
2. Ek suspicious commit dikha — `git show <hash>` se uska poora diff aur message padho
3. Confirm karne ke liye `git blame -L 40,60 api/payment.js` se exact line trace karo
4. `git diff main..hotfix-branch -- api/payment.js` se apne fix ko compare karo before pushing

</Hinglish>

## Real World Example

<RealWorld company="Microsoft">

Large teams commonly configure a `.git-blame-ignore-revs` file listing bulk formatting/linting commit hashes, so `git blame` (with `--ignore-rev` or a configured ignore-revs file) skips straight past cosmetic reformatting commits to the actual author of the logic.

</RealWorld>

<RealWorld company="GitHub">

Code review tooling on GitHub itself is essentially a rendered `git diff` between a feature branch and its target branch (`git diff main..feature-branch`) — understanding this underlying command makes it much easier to reason about why a PR diff shows what it shows, including unexpected changes from an out-of-date branch.

</RealWorld>

## Numbers That Matter

<Numbers>

<ul>
<li>git diff has three distinct comparison modes depending on arguments — no args, --staged, and against HEAD</li>
<li>git log --oneline typically compresses a 6-line verbose commit entry down to a single line</li>
<li>git blame -L limits output to a specific line range instead of scanning an entire file, useful on files with thousands of lines</li>
<li>A commit hash is a 40-character SHA-1 string, but git log --oneline shows only the first 7 characters by default — almost always unique enough to reference</li>
</ul>

</Numbers>

## Interview Angle

<InterviewAngle>

**"How would you find out who introduced a specific bug and why?"** The model answer chains commands: `git log -- <file>` or `git blame` to narrow down candidate commits, then `git show <hash>` to read the full diff and commit message for context. A strong candidate also mentions the blame-noise problem — a bulk reformat commit can mask the real author — and how `--ignore-rev` or a `.git-blame-ignore-revs` file solves it, which signals real production debugging experience.

</InterviewAngle>

## Common Mistakes

<Mistake>

`git add` karne ke baad plain `git diff` chalana aur confuse ho jaana ki "kuch changes dikh hi nahi rahe" — staged changes dekhne ke liye `git diff --staged` chahiye, plain `git diff` sirf unstaged dikhata hai.

</Mistake>

<Mistake>

`git log` ka verbose default output daily use mein use karna — `--oneline --graph` jaise flags ke bina history scan karna practically unusable hai bade repos mein.

</Mistake>

<Mistake>

`git blame` ke result ko bina verify kiye trust kar lena jab beech mein ek bulk formatting commit ho — actual logic author ki jagah formatting-commit-author ko blame kar dena.

</Mistake>

<Mistake>

`git diff branch1..branch2` aur `git diff branch1...branch2` (three dots) ko same samajhna — two-dot direct diff karta hai, three-dot common ancestor se compare karta hai, dono ka result different ho sakta hai jab branches diverge ho chuki hon.

</Mistake>

## Quick Revision

<QuickRevision>

<ul>
<li>git log --oneline --graph --all — best daily-use command for scanning history and branch structure</li>
<li>git diff — unstaged changes only (working dir vs staging area)</li>
<li>git diff --staged (or --cached) — staged changes only (staging area vs last commit)</li>
<li>git diff HEAD — everything not yet committed, staged and unstaged combined</li>
<li>git blame -L 10,25 file.js — trace who last changed lines 10-25</li>
<li>git blame --ignore-rev &lt;hash&gt; — skip a noisy bulk-reformat commit when tracing blame</li>
<li>git show &lt;hash&gt; — full message + diff for one specific commit</li>
<li>git log --author="name" / --since="2 weeks ago" — filter history by author or time</li>
</ul>

</QuickRevision>
