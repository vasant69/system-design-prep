<SimpleDefinition>

State management in Angular is the set of patterns used to store, share, and synchronize application data across components, ranging from a simple service holding a BehaviorSubject for small apps, to a structured library like NgRx for large apps with complex cross-cutting state, to the newer Signals API as a lighter-weight reactive primitive built into the framework itself.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Jaise jaise Angular app badi hoti hai, ek sawaal repeatedly aata hai: **"is data ka source of truth kahan hai, aur usse kaise sync karein multiple components ke beech?"** Component ke apne local `@Input`/`@Output` se kaam chal jaata hai jab data ek parent-child chain me flow karta hai, lekin jab do sibling components ko same data chahiye, ya deeply nested components ko kisi far-away ancestor ka data chahiye, tab "state management" ka sawaal khada hota hai.

### Level 1 — Service + BehaviorSubject (chhoti/medium apps ke liye)

Angular me sabse simple aur sabse common pattern hai ek **injectable service** banana jisme ek `BehaviorSubject` hota hai (kyunki ye current value hold karta hai aur naye subscriber ko turant deta hai):

```typescript
@Injectable({ providedIn: "root" })
export class CartService {
  private itemsSubject = new BehaviorSubject<CartItem[]>([]);
  items$ = this.itemsSubject.asObservable();

  addItem(item: CartItem) {
    const current = this.itemsSubject.value;
    this.itemsSubject.next([...current, item]);
  }
}
```

Koi bhi component `items$` ko `async` pipe se template me subscribe kar sakta hai, aur Angular ki singleton service (`providedIn: "root"`) automatically ensure karti hai ki har component same instance use kare — isliye state naturally shared ho jaata hai. Ye pattern chhoti se medium apps ke liye kaafi hota hai — simple, kam boilerplate, koi extra library nahi.

### Ye pattern kab break hone lagta hai

Jaise jaise app badi hoti hai, ye kuch problems dikhati hai:

- **Debugging mushkil ho jaati hai** — state kahin bhi, kisi bhi service method se mutate ho sakta hai, isliye "state kyun change hua" trace karna time-consuming ho jaata hai jab bahut saare services interact kar rahe hon.
- **Cross-cutting concerns duplicate hote hain** — loading states, error handling, caching logic har service me alag-alag likhna padta hai.
- **Time-travel debugging, undo/redo jaisi cheezein** possible nahi hoti bina extra kaam ke.

Isi gap ko **NgRx** fill karta hai.

### Level 2 — NgRx (bade apps, complex shared state ke liye)

NgRx **Redux pattern** ka Angular-flavored implementation hai — poore app ka state ek **single, immutable store** me rehta hai, aur us store ko modify karne ka sirf ek tareeka hai: **actions dispatch karke**.

- **Actions** — plain objects jo "kya hua" describe karte hain (`[Cart] Add Item`).
- **Reducers** — pure functions jo `(currentState, action) => newState` compute karte hain — koi side effect nahi, sirf naya state return karte hain.
- **Selectors** — store se specific slice of state read karne ke liye memoized functions.
- **Effects** — side effects (HTTP calls, jaise) yahan handle hote hain, actions ko listen karke naye actions dispatch karte hain.

```typescript
// action
export const addItem = createAction("[Cart] Add Item", props<{ item: CartItem }>());

// reducer
export const cartReducer = createReducer(
  initialState,
  on(addItem, (state, { item }) => ({ ...state, items: [...state.items, item] }))
);

// selector
export const selectCartItems = createSelector(selectCartState, state => state.items);

// component
items$ = this.store.select(selectCartItems);
addToCart(item: CartItem) {
  this.store.dispatch(addItem({ item }));
}
```

Ye structure predictability deta hai — state ka har change ek traceable action se aata hai, Redux DevTools me poori history dekh sakte ho, time-travel debugging possible hai. Lekin cost bhi hai: **boilerplate zyada hai** (action, reducer, selector, effect — ek simple feature ke liye bhi 4 files), aur team ko Redux mental model seekhna padta hai.

### Level 3 — Angular Signals (naya, lightweight reactive primitive)

Angular 16+ me **Signals** introduce hui — ye ek naya reactive primitive hai jo RxJS se simpler hai specific use cases ke liye. Ek signal ek wrapped value hai jo apne readers ko automatically notify karta hai jab change hota hai, bina explicit subscribe/unsubscribe ke:

```typescript
@Injectable({ providedIn: "root" })
export class CartService {
  private itemsSignal = signal<CartItem[]>([]);
  items = this.itemsSignal.asReadonly();

  addItem(item: CartItem) {
    this.itemsSignal.update(current => [...current, item]);
  }
}
```

Template me `{{ cartService.items().length }}` likhkar directly use kar sakte ho — koi `async` pipe nahi chahiye, koi unsubscribe ki zaroorat nahi (signals automatically cleanup hote hain jab consuming context destroy hoti hai). Signals `computed()` (derived state) aur `effect()` (side effects on change) bhi provide karte hain. Signals RxJS ko replace nahi karte — asynchronous streams (HTTP, websockets, debouncing) ke liye RxJS abhi bhi better fit hai — lekin simple synchronous shared state ke liye Signals kaafi lightweight aur ergonomic option hain.

### Kab kya use karein — honest guidance

- **Chhoti/medium app, simple shared state**: service + BehaviorSubject (ya ab Signals) — sufficient hai, kam complexity.
- **Bahut saari teams, complex cross-cutting state, heavy debugging/audit needs (jaise ek large fintech dashboard)**: NgRx ka structure aur predictability worth hai.
- **NgRx tab mat lao jab**: app chhoti hai, ek-do developer maintain kar rahe hain, ya state mostly local/component-scoped hai. NgRx ko "hum bade enterprise app bana rahe hain" ke naam pe har project me daal dena ek bahut common over-engineering mistake hai — extra boilerplate, slower onboarding, bina real fayde ke.

</Hinglish>

## Real World Example

<RealWorld company="Microsoft">

Bade enterprise Angular apps me (jaise complex internal dashboards with dozens of interacting widgets), NgRx aksar isliye chuna jaata hai kyunki multiple teams parallel me same state pe kaam karte hain — actions/reducers ka strict contract merge conflicts aur "kisne ye state kyun change kiya" jaisi confusion kam karta hai. Lekin chhote greenfield projects me same teams often simple service-based pattern se hi shuru karte hain, aur NgRx sirf tab introduce karte hain jab actual complexity justify kare.

</RealWorld>

## Numbers That Matter

<Numbers>

- Angular Signals were introduced as developer preview in Angular 16 (2023), stabilized in Angular 17
- A typical NgRx feature slice (action + reducer + selector + effect) is often 4-plus files versus 1 service file for the BehaviorSubject approach
- BehaviorSubject always holds exactly 1 current value, delivered immediately to any new subscriber
- NgRx DevTools can replay full action history for time-travel debugging in development

</Numbers>

## Interview Angle

<InterviewAngle>

"When would you use NgRx over a simple service?" is the single most common state-management question — the strong answer avoids "NgRx is always better for big apps" and instead names concrete signals: many components mutating the same state unpredictably, need for time-travel debugging, multiple teams needing a strict contract. A frequent trap question is "explain the difference between Signals and RxJS Observables" — the strong answer says Signals are for synchronous, glitch-free state with automatic dependency tracking, while RxJS remains the right tool for async streams, and the two interoperate (`toSignal`/`toObservable`). Expect to be asked to sketch an NgRx action/reducer/effect flow on a whiteboard.

</InterviewAngle>

## Common Mistakes

<Mistake>

Har naye Angular project me by default NgRx add kar dena "best practice hai" soch kar — bina actual complexity ke, ye sirf unnecessary boilerplate aur slower onboarding leke aata hai.

</Mistake>

<Mistake>

Service ke andar `BehaviorSubject` ki value ko directly `.value` se mutate karna (jaise array push karke) instead of `.next()` se naya reference emit karna — isse change detection aur subscribers ko notification miss ho sakta hai.

</Mistake>

<Mistake>

NgRx reducer ke andar side effects (HTTP calls, async kaam) likhna — reducers pure functions hone chahiye; side effects ka sahi jagah Effects hai.

</Mistake>

<Mistake>

Signals aur RxJS ko ek-dusre ka complete replacement samajhna — Signals synchronous state ke liye best hain, complex async streams (debounce, switchMap, combineLatest) abhi bhi RxJS ka domain hai.

</Mistake>

<Mistake>

Async pipe use karte waqt bhi manually subscribe karke fir unsubscribe bhool jaana — jab `| async` available hai to manual subscription avoid karna hi behtar hai, ye khud cleanup handle karta hai.

</Mistake>

## Quick Revision

<QuickRevision>

- Service + BehaviorSubject: simplest shared-state pattern, good for small/medium apps
- NgRx: Redux pattern for Angular — actions describe what happened, reducers are pure functions computing new state, selectors read state, effects handle side effects
- NgRx gives predictability and time-travel debugging but adds real boilerplate
- Signals (Angular 16+, stable 17+): lightweight reactive primitive, no subscribe/unsubscribe, great for synchronous state
- Signals do not replace RxJS for async streams — the two interoperate
- Don't reach for NgRx by default — justify it with real cross-cutting complexity or multi-team needs
- Never mutate BehaviorSubject's current value directly — always emit a new value via next()
- Reducers must stay pure; side effects belong in NgRx Effects

</QuickRevision>
