<SimpleDefinition>

Angular offers two form-building approaches: reactive forms, which define the form model explicitly in the component class using FormGroup and FormControl, and template-driven forms, which infer the form model implicitly from ngModel directives written directly in the template.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Angular me forms banane ke do fundamentally different tareeke hain — aur interview me "kaunsa use karoge aur kyun" almost guaranteed pooche jaate hain.

### Reactive Forms — model class me define hota hai

Reactive forms me poora form structure **TypeScript class ke andar** explicitly banaya jaata hai, `FormGroup`, `FormControl`, aur `FormBuilder` use karke:

```typescript
this.signupForm = this.fb.group({
  email: ["", [Validators.required, Validators.email]],
  password: ["", [Validators.required, Validators.minLength(8)]],
});
```

Template me sirf binding hoti hai — `formGroup`, `formControlName` directives:

```html
<form [formGroup]="signupForm">
  <input formControlName="email" />
  <input formControlName="password" />
</form>
```

Form ka **source of truth component class me hai**, template sirf display layer hai. Ye immutable, synchronous data model deta hai — `signupForm.value` ya `signupForm.get("email")?.errors` kabhi bhi synchronously read kar sakte ho, koi surprise nahi.

### Template-Driven Forms — template me infer hota hai

Template-driven forms me `ngModel` directive template me likhte ho aur Angular khud background me FormControl objects create karta hai:

```html
<form #signupForm="ngForm">
  <input name="email" ngModel required email />
</form>
```

Yahan form model **implicitly, template se derive** hota hai — component class ko form structure pata bhi nahi hota jab tak `ngForm` reference expose na ki jaye. Ye simpler dikhta hai chhote forms ke liye kyunki HTML jaisa lagta hai, kam boilerplate.

### Built-in validators

Dono approaches same built-in validators use kar sakte hain: `required`, `minLength`, `maxLength`, `pattern`, `email`. Reactive me ye function calls hain (`Validators.required`), template-driven me HTML attributes (`required`, `email`).

### Custom validators — sync aur async

Custom sync validator ek plain function hai jo `ValidationErrors | null` return karta hai:

```typescript
function forbiddenNameValidator(forbidden: string): ValidatorFn {
  return (control: AbstractControl): ValidationErrors | null => {
    return control.value === forbidden ? { forbiddenName: true } : null;
  };
}
```

Async validator same shape hai lekin `Observable<ValidationErrors | null>` ya `Promise` return karta hai — jaise server pe check karna ki username already taken hai ya nahi. Ye third argument ke roop me `FormControl` me pass hota hai: `new FormControl("", syncValidators, asyncValidators)`. Async validators automatically debounce nahi hote — agar server call har keystroke pe firing rok ni hai, `updateOn: "blur"` ya manual debounce logic lagani padti hai.

### Kab kya use karo

Reactive forms **complex forms, dynamic form arrays (add/remove fields), unit testing** ke liye behtar hain — kyunki form logic component class me hai, bina DOM render kiye test kar sakte ho. Template-driven forms **simple forms** (login, contact form, 2-3 fields) ke liye theek hain jaha form ka structure kabhi change nahi hoga aur testing ki depth zaroori nahi.

Real teams me almost hamesha **reactive forms** dominant choice hoti hai enterprise apps me — kyunki forms grow karte hain waqt ke saath (naye fields, conditional validation, dynamic arrays), aur reactive approach us growth ko bina refactor kiye handle kar leta hai.

</Hinglish>

## Real World Example

<RealWorld company="Infosys">

Banking/insurance domain ke client-facing Angular apps (KYC forms, loan applications) hamesha reactive forms use karte hain kyunki form ka structure business rules ke hisaab se dynamically change hota hai — "agar loan amount 10 lakh se zyada hai to extra documents field dikhao" jaisa conditional logic template-driven approach me maintain karna almost impossible ho jaata, jabki reactive forms me ye sirf `FormGroup` ko runtime pe modify karna hai.

</RealWorld>

## Numbers That Matter

<Numbers>

- Reactive forms module: import `ReactiveFormsModule` (or standalone equivalent providers)
- Template-driven forms module: import `FormsModule`
- A form with 15+ fields and conditional validation typically takes 2-3x longer to build correctly with template-driven approach vs reactive
- Async validators commonly debounced at 300-500ms to avoid firing an API call on every keystroke

</Numbers>

## Interview Angle

<InterviewAngle>

"Reactive vs template-driven, which do you prefer and why" is near-universal — the strong answer isn't "reactive is always better," it's naming the actual trade-off: template-driven is fine for a 2-3 field static form, reactive wins once there's dynamic structure, cross-field validation, or a testing requirement. A common trap question: "how would you validate that password and confirmPassword match" — this requires a cross-field (group-level) validator attached to the FormGroup itself, not to either individual control, and candidates who only know per-control validators often stumble here. Expect a follow-up on async validator debouncing — naming `updateOn: blur` or a manual `debounceTime` in the async validator's observable chain shows real experience, not textbook knowledge.

</InterviewAngle>

## Common Mistakes

<Mistake>

Cross-field validation (password === confirmPassword) ko individual FormControl pe validator laga ke solve karne ki koshish karna — ye kaam nahi karega kyunki ek control ko doosre control ki value ka access nahi hota. Group-level validator FormGroup pe lagana chahiye.

</Mistake>

<Mistake>

Async validator me debounce na lagana — har keystroke pe server ko API call jaana, unnecessary load aur bad UX (fields "pending" state me flicker karte rehte hain).

</Mistake>

<Mistake>

Template-driven form me business logic ko heavily template ke andar likhna (`*ngIf` conditions ke through validation control karna) — ye jaldi unmanageable ho jaata hai jaise hi form thoda bhi complex hota hai.

</Mistake>

<Mistake>

Reactive form me `FormGroup` ka structure component class me hardcode kar dena jab requirement dynamic fields ki thi — `FormArray` use karna chahiye tha add/remove fields ke liye instead of manually managing individual FormControls.

</Mistake>

## Quick Revision

<QuickRevision>

- Reactive forms: model defined explicitly in component class (`FormGroup`/`FormControl`/`FormBuilder`), template only binds
- Template-driven forms: model inferred from `ngModel` directives in the template, component class stays mostly unaware
- Reactive forms import `ReactiveFormsModule`, template-driven import `FormsModule`
- Reactive forms are synchronously testable without rendering the DOM — better for complex/enterprise forms
- Custom sync validator returns `ValidationErrors | null`; async validator returns `Observable`/`Promise` of the same
- Cross-field validation (e.g. password match) needs a group-level validator, not a per-control one
- Use template-driven for small static forms, reactive for anything dynamic, growing, or heavily validated

</QuickRevision>
