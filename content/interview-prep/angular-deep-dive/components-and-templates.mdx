<SimpleDefinition>

A component in Angular is a TypeScript class decorated with @Component that pairs a template (HTML) and optional styles to render a piece of UI, and templates use a small set of syntax extensions — interpolation, property binding, and reference variables — to connect that class to the DOM.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Pichle topic me humne dekha ki component = class + template + styles. Ab is topic me hum us `@Component` decorator ke andar actually kya-kya hota hai, aur template me jo syntax use hota hai, wo detail me dekhenge.

### @Component decorator ki anatomy

`@Component` ek TypeScript decorator hai jo ek plain class ko Angular component me convert karta hai. Isme kuch metadata properties hoti hain jo har interview me poochhi jaati hain:

```typescript
@Component({
  selector: "app-product-card",
  templateUrl: "./product-card.component.html",
  styleUrls: ["./product-card.component.scss"],
  encapsulation: ViewEncapsulation.Emulated,
})
export class ProductCardComponent {
  productName = "Wireless Mouse";
}
```

- **selector** — custom HTML tag ka naam jisse ye component doosri jagah use hota hai, jaise `<app-product-card></app-product-card>`. Convention hai ki isme app ka prefix (`app-`) hota hai taaki naming clash na ho browser ke native elements se.
- **templateUrl vs template** — `templateUrl` ek separate `.html` file point karta hai. Chhote components ke liye `template` property me hi inline HTML likh sakte ho — string ya backtick template literal ke through. Bade templates ke liye separate file behtar hai (syntax highlighting, readability).
- **styleUrls vs styles** — same pattern, separate SCSS/CSS file ya inline styles array.

### View Encapsulation

Default me Angular har component ke styles ko **scope** kar deta hai — matlab ek component ka CSS doosre component ko affect nahi karta, chahe class names same ho. Ye `ViewEncapsulation.Emulated` (default) ke through hota hai — Angular har element pe ek unique attribute (jaise `_ngcontent-xyz`) add karta hai aur styles ko usi attribute se scope karta hai. Do aur options hain: `ViewEncapsulation.None` (styles global ho jaate hain, koi scoping nahi) aur `ViewEncapsulation.ShadowDom` (browser ka native Shadow DOM use karta hai, sabse strict isolation). Interview me `Emulated` hi default samjho aur `None` sirf tab use karo jab jaan-boojh kar global styles chahiye (jaise ek theming component).

### Template syntax basics

Template ke andar Angular kuch special syntax provide karta hai jo plain HTML se alag hai:

**Interpolation** — double curly braces me ek expression daal ke uska value text ke roop me render karte hain:

```html
<h2>{{ productName }}</h2>
<p>Price: {{ price * quantity }}</p>
```

Interpolation ke andar sirf simple expressions likhne chahiye — assignment, loops, `new` jaisi cheezein allowed nahi hain. Complex logic template me nahi, component class me getter ya method ke roop me hona chahiye.

**Property binding** — square brackets `[ ]` se ek DOM element ki property ko component ke field se bind karte hain:

```html
<img [src]="productImageUrl" [alt]="productName" />
<button [disabled]="isOutOfStock">Add to Cart</button>
```

Ye one-way binding hai — component se DOM ki taraf. Note karo: `[disabled]="isOutOfStock"` attribute binding nahi, DOM *property* binding hai — dono me farak hota hai jab attribute aur property sync me nahi rehte (jaise `value` attribute vs property in inputs).

**Template reference variables** — hash `#` se ek DOM element ya component instance ko template ke andar hi ek naam de dete ho, jisse doosri jagah reference kar sakte ho:

```html
<input #emailInput type="text" />
<button (click)="submitEmail(emailInput.value)">Submit</button>
```

Yahan `#emailInput` us `<input>` DOM element ko refer karta hai, aur `emailInput.value` uska current value nikaal leta hai — bina component class me koi extra property banaye. Ye chhote, local use-cases ke liye handy hai; bade forms ke liye Reactive Forms (`FormControl`) behtar approach hai.

### Kab inline template use karein, kab separate file

Chhote, throwaway ya bahut simple components (jaise ek loading spinner, do line ka wrapper) ke liye inline `template` acceptable hai — file count kam rehta hai. Lekin production codebase me convention yahi hai ki `templateUrl` use karo har real component ke liye — IDE support (HTML syntax highlighting, autocomplete) sirf `.html` files me pura milta hai, TypeScript string literal ke andar nahi.

</Hinglish>

## Real World Example

<RealWorld company="Amazon">

Ek large e-commerce dashboard team (jaisa Amazon internal seller-tools jaisa setup) me har widget — price card, inventory badge, order status chip — apna khud ka component hota hai with scoped styles. Isse designers freely reuse kar sakte hain ek `.badge` class naam multiple widgets me bina darr ke ki ek component ka style doosre ko todd de, kyunki Emulated encapsulation har component ke CSS ko isolate rakhta hai.

## Numbers That Matter

<Numbers>

- ViewEncapsulation.Emulated has been Angular's default since version 2 (2016) — has not changed since
- A typical mid-size component's template stays under 100-150 lines before it's a signal to split into child components
- Interpolation expressions in Angular templates cannot exceed simple property/method access — no assignment operators (=, +=) allowed by the template parser
- ShadowDom encapsulation mode requires native browser Shadow DOM support (all modern evergreen browsers, near 100% coverage as of 2024)

</Numbers>

## Interview Angle

<InterviewAngle>

A very common opener is "explain what happens when you write `@Component`" — the strong answer names the three metadata pillars (selector, template, styles) and mentions encapsulation without being asked, since that's what separates a beginner answer from one with real experience. "What's the difference between interpolation and property binding" tests precision — the correct framing is interpolation is really syntactic sugar for a subset of property binding (it always binds to `textContent`-like string output), while property binding can target any DOM property with any type (boolean, object, array). Expect a follow-up on template reference variables versus a component field — the answer should note `#var` is purely a template-local, DOM/component-instance reference and never exists in the TypeScript class.

</InterviewAngle>

## Common Mistakes

<Mistake>

Interpolation ke andar complex logic likhna, jaise `{{ items.filter(i => i.active).length }}` — ye har change-detection cycle pe re-run hota hai aur performance issue create karta hai. Isko component class me ek getter ya computed property me move karna chahiye.

</Mistake>

<Mistake>

`[value]="userInput"` aur attribute `value="userInput"` (bina brackets) ko confuse karna — bina brackets ke `"userInput"` ek literal string ban jaata hai, binding nahi. Brackets missing hona ek bahut common beginner bug hai jo silently galat UI dikhata hai bina koi error diye.

</Mistake>

<Mistake>

Har chhote component ke liye inline `template` string use karna production code me — readability aur IDE tooling dono kharab ho jaate hain jab HTML TypeScript string ke andar embed hota hai.

</Mistake>

<Mistake>

`ViewEncapsulation.None` ko globally kisi bhi component pe laga dena "kyunki style apply nahi ho raha tha" — asal problem usually CSS specificity ka hota hai, encapsulation off karna sirf global style leaks create karta hai poore app me.

</Mistake>

## Quick Revision

<QuickRevision>

- `@Component` metadata = selector + templateUrl/template + styleUrls/styles + encapsulation
- `ViewEncapsulation.Emulated` (default) scopes CSS per component via unique attributes; `None` = global; `ShadowDom` = native browser isolation
- Interpolation `{{ expr }}` renders text, only simple expressions allowed, no assignments
- Property binding `[prop]="expr"` binds any DOM property (not just strings) one-way from class to DOM
- Template reference variables `#name` give a local handle to a DOM element or component instance, scoped to that template only
- Prefer `templateUrl`/`styleUrls` (separate files) for real components; inline only for trivial ones
- Keep interpolation/binding expressions simple — move complex logic to getters/methods in the class

</QuickRevision>
