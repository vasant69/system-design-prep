<SimpleDefinition>

SQL query design is the practice of writing queries that correctly express the business question being asked — using joins to combine related tables, subqueries or CTEs to break complex logic into readable steps, and aggregations to summarize data — while keeping in mind how the query will actually execute against the underlying schema and indexes.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Schema design sahi ho tab bhi, agar query galat likhi jaaye to ya to galat result aata hai ya production mein slow query se poora system affect hota hai. Yeh topic ER modeling aur constraints ke baad natural next step hai — ab jo schema banaya, usse actually query kaise karein.

### Joins — kab kaunsa use karo

- **INNER JOIN** — sirf woh rows jo dono tables mein match karti hain. BFSI example: "un sab customers ki list do jinke paas kam se kam ek Account hai" — Customer INNER JOIN Account.
- **LEFT JOIN** — left table ki saari rows, chahe right side match mile ya na mile. Example: "sab customers ki list do, chahe unka account ho ya na ho" — yeh onboarding-status check jaise use-cases mein common hai (naya customer jisne abhi tak account activate nahi kiya).

Interview mein confuse hona common hai — agar tumhe "sab X do, chahe Y ho ya na ho" sunai de, seedha LEFT JOIN samjho.

### Subqueries vs CTEs (WITH clause)

Dono se complex logic ko chhote pieces mein todte hain. CTE (Common Table Expression, `WITH` clause) generally zyada readable hota hai jab query mein multiple steps hon — jaise pehle "har account ka is month ka total spend nikaalo" (ek CTE), phir "un accounts ko filter karo jinka spend ek threshold se zyada hai" (main query CTE ko use karke). Nested subqueries wahi kaam kar sakti hain, lekin deeply nested ho to padhna mushkil ho jaata hai — CTE isi readability problem ko solve karta hai, performance same reh sakta hai (optimizer par depend karta hai).

### Aggregations — GROUP BY ka sahi use

`COUNT`, `SUM`, `AVG` jaise aggregate functions `GROUP BY` ke saath mil ke summarize karte hain. BFSI example: "har branch ka is quarter ka total transaction volume" — `SELECT branch_id, SUM(amount) FROM Transaction WHERE ... GROUP BY branch_id`. Common mistake: `SELECT` list mein ek non-aggregated column daal dena jo `GROUP BY` mein nahi hai — yeh ya to error deta hai (strict SQL mode mein) ya undefined/arbitrary value return karta hai (loose mode mein) — dono hi production mein dangerous hain financial reports ke liye.

### Query likhte waqt schema ko dhyan mein rakho

Yeh sabse important practical point hai: query sirf "correct" hona kaafi nahi, usse yeh bhi pata hona chahiye ki underlying table pe kaunsa index hai. Agar `WHERE account_id = ?` likh rahe ho aur `account_id` pe index nahi hai, query correct result degi lekin production mein bahut slow ho sakti hai bade table pe (full table scan) — yeh agle module (Indexing & Query Performance) mein detail mein cover hoga, lekin query design ke time hi yeh soch lena chahiye.

### N+1 query problem

Ek aur common mistake application code mein: ek list of accounts fetch karo, phir HAR account ke liye alag se ek query chalao uske transactions fetch karne ke liye (loop ke andar query) — agar 100 accounts hain to 101 queries chal jaati hain (1 + 100). Sahi approach: ek single JOIN ya ek `WHERE account_id IN (...)` query se sab kuch ek baar mein fetch karo. Yeh application-level mistake hai lekin query design ki samajh se hi avoid hoti hai.

</Hinglish>

<Callout type="trap">

Agar `GROUP BY` query mein aggregate na ho lekin `SELECT` list mein ek extra column dikhe jo group-by mein nahi hai — turant flag karo. Financial reporting query mein yeh silently galat number de sakta hai.

</Callout>

## Real World Example

<RealWorld company="HDFC Bank">

Ek branch performance dashboard query typically Account aur Transaction tables ko JOIN karke, branch ke hisaab se GROUP BY karke, is month ka total deposit/withdrawal volume nikaalti hai. Yeh exact query pattern hai jo agar galat likhi jaaye (jaise galat JOIN type se kuch accounts silently drop ho jaayein), management ko galat business numbers dikha sakta hai.

</RealWorld>

<RealWorld company="Amazon">

Order history page jaisa feature — "customer ke sab orders, har order ke items ke saath" — classic N+1 trap hai agar naively likha jaaye (ek query orders ke liye, phir loop mein har order ke items ke liye alag query). Production-grade implementation ek single JOIN (ya batched IN query) use karti hai taaki database round-trips minimum rahein.

</RealWorld>

## Numbers That Matter

<Numbers>

- N+1 query problem: 100 rows ke liye naive loop approach = 101 queries vs 1 optimized JOIN/IN query
- A single unindexed WHERE clause on a 100M+ row table can turn a sub-10ms query into a multi-second full table scan
- CTEs vs subqueries: readability improves significantly beyond 2-3 levels of nesting, performance is usually optimizer-dependent (not always different)
- Typical branch/reporting aggregation query: scans a bounded date range (indexed), not the full table

</Numbers>

## Interview Angle

<InterviewAngle>

Interviewer aksar ek "write a query that..." prompt dete hain aur dekhte hain ki tum kaunsa JOIN type choose karte ho aur kyun. Model answer shape: pehle clarify karo ki "chahiye ya na ho" wali cheez hai kya (LEFT JOIN signal), phir query likho, phir khud se bolo "is query ko fast chalane ke liye humein `X` column pe index chahiye hoga" — yeh proactive index-awareness ek strong senior-level signal hai, chahe interviewer ne indexing explicitly na poocha ho.

</InterviewAngle>

## Common Mistakes

<Mistake>

INNER JOIN aur LEFT JOIN mein confuse ho jaana — "sab X do chahe Y ho ya na ho" sunte hi LEFT JOIN yaad rakho.

</Mistake>

<Mistake>

GROUP BY query mein ek non-aggregated column SELECT list mein daal dena jo group-by mein nahi hai — silently galat ya undefined result de sakta hai.

</Mistake>

<Mistake>

Application code mein N+1 query pattern likhna — loop ke andar ek-ek karke queries chalana instead of ek batched JOIN/IN query.

</Mistake>

<Mistake>

Query ko sirf "correctness" ke liye likhna, underlying index ka khayal na rakhna — production mein slow query se poora system affect ho sakta hai.

</Mistake>

## Quick Revision

<QuickRevision>

- INNER JOIN = only matching rows both sides; LEFT JOIN = all left rows, matched or not
- CTEs (WITH clause) improve readability over deeply nested subqueries for multi-step logic
- GROUP BY: every non-aggregated SELECT column must be in the GROUP BY clause, or results are unreliable
- Always think about the index a query needs while writing it, not after it's slow in production
- N+1 problem: loop-based per-row queries — fix with a single JOIN or WHERE ... IN (...) batch query
- Proactively mention indexing needs in interviews even if not asked — shows production awareness

</QuickRevision>
