<SimpleDefinition>

C# offers a traditional `switch` statement alongside the newer `switch` expression (C# 8), and a rich family of pattern kinds — type patterns, property patterns, relational patterns, logical patterns (`and`/`or`/`not`), and list patterns (C# 11) — that let a single `switch` concisely express conditions that would otherwise require nested `if-else` chains.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

C# ka `switch` sirf ek "multiple `if-else` ka shortcut" nahi raha — C# 7 se pattern matching aana shuru hua, aur C# 8 me switch EXPRESSION aaya jo poora control-flow-writing style badal deta hai. Interview me isko sirf syntax ki tarah nahi, "kab kaunsa use karna chahiye" ki tarah samjhaana zaroori hai.

### `switch` statement — purana, familiar

```csharp
switch (shape)
{
    case Circle c:
        Console.WriteLine($"Circle, radius {c.Radius}");
        break;
    case Square s:
        Console.WriteLine($"Square, side {s.Side}");
        break;
    default:
        Console.WriteLine("Unknown shape");
        break;
}
```

Har `case` ek statement block hai, `break` mandatory (ya `return`/`throw`), fall-through by default disallowed (C# me implicit fall-through allowed nahi, jo C/Java se ek deliberate difference hai — accidental fall-through bugs avoid karne ke liye).

### `switch` EXPRESSION (C# 8) — concise, value-returning

```csharp
string description = shape switch
{
    Circle c => $"Circle, radius {c.Radius}",
    Square s => $"Square, side {s.Side}",
    _ => "Unknown shape",
};
```

Ye **expression** hai, statement nahi — direct ek value produce karta hai, kisi variable ko assign hone ke liye. `_` discard pattern `default` ki jagah leta hai. Ye syntax tab shine karta hai jab goal genuinely "input ko ek value me map karna" ho, na ki "har case me alag-alag multi-line action perform karna."

**Jab har case ek complex multi-statement action ho** (logging, database call, etc.), traditional `switch` statement zyada readable rehta hai. Jab har case sirf "ek value return karo," switch expression zyada concise aur declarative hai. Ye trade-off interview me poochne layak hai.

### Type Patterns

```csharp
object obj = GetValue();
if (obj is int i)
{
    Console.WriteLine($"It's an int: {i}");
}
```

`is` pattern matching (C# 7) type-check + cast + variable-binding ek saath karta hai — purana style `(int)obj` explicit cast + separate variable tha.

### Property Patterns (C# 8)

```csharp
string category = order switch
{
    { Total: > 10000 } => "High Value",
    { Status: "Cancelled" } => "Cancelled Order",
    { Customer.IsVip: true } => "VIP Order",
    _ => "Regular Order",
};
```

Properties ke andar directly match karta hai — `{ Total: > 10000 }` object ke `Total` property pe relational pattern apply karta hai, nested property (`Customer.IsVip`) bhi directly access ho sakti hai.

### Relational Patterns (C# 9)

`>`, `<`, `>=`, `<=` — direct comparison operators pattern ke roop me:

```csharp
string sizeCategory = age switch
{
    < 13 => "Child",
    < 20 => "Teenager",
    < 60 => "Adult",
    _ => "Senior",
};
```

### Logical Patterns (C# 9) — `and`, `or`, `not`

```csharp
bool isValidAge = age switch
{
    >= 18 and <= 60 => true,
    _ => false,
};

bool isNotNullOrEmpty = str is not (null or "");
```

`and`/`or`/`not` patterns ko combine karte hain — `>= 18 and <= 60` ek range check ko ek line me express karta hai, bina do separate comparisons ko `&&` se manually jodne ke.

### List Patterns (C# 11)

```csharp
int[] numbers = { 1, 2, 3 };

string result = numbers switch
{
    [] => "Empty",
    [var single] => $"Single element: {single}",
    [var first, .., var last] => $"First: {first}, Last: {last}",
    _ => "Other",
};
```

`[]` empty array, `[var x]` exactly-one-element, `..` (slice pattern) "beech me kuch bhi ho sakta hai" — array/list ki shape ko directly match karna, bina manual `.Length` checks ke.

### Combining kai pattern kinds ek switch me

Real interview-worthy example — sab kuch ek saath:

```csharp
string Classify(object input) => input switch
{
    null => "Null value",
    int n and > 0 => $"Positive int: {n}",
    int n and < 0 => $"Negative int: {n}",
    int => "Zero",
    string s when s.Length > 100 => "Long string",
    string { Length: 0 } => "Empty string",
    string s => $"String: {s}",
    List<int> { Count: > 0 } list => $"Non-empty list of {list.Count}",
    _ => "Unrecognized",
};
```

`when` clause ek extra boolean condition attach karta hai pattern ke upar — pattern match hone ke baad bhi ek additional guard check.

</Hinglish>

<Callout type="tip">

Rule of thumb: agar switch ka goal "input ko seedha ek value me convert karna" hai, expression form use karo (concise, declarative). Agar har case me multiple statements/side-effects hain, statement form use karo (readable, imperative). Dono mix mat karo ek hi switch me.

</Callout>

## Real World Example

<RealWorld company="Microsoft">

.NET ke apne source code me (jaise `System.Text.Json` ke internal type-handling code) switch expressions ke saath type patterns heavily use hote hain — ek value ke runtime type ke basis pe serialization strategy choose karne ke liye, jo purane `if (x is TypeA) {...} else if (x is TypeB) {...}` chains se kaafi zyada readable hai.

</RealWorld>

<RealWorld company="An Indian Insurance Claims System">

Ek claims-processing engine me, claim ki `(Amount, Status, PolicyType)` combination ke basis pe routing decide karna ek classic property-pattern use case hai: `claim switch { { Amount: > 500000, Status: "Pending" } => RouteToSeniorReview, { PolicyType: "Health", Status: "Pending" } => RouteToHealthTeam, _ => RouteToStandardQueue }` — nested `if-else` ki jagah ek readable decision table jaisa dikhta hai.

</RealWorld>

## Numbers That Matter

<Numbers>

- Type patterns (`is Type x`) — C# 7.0 (2017)
- switch expression, property patterns — C# 8.0 (2019)
- Relational (`>`, `<`) aur logical (`and`/`or`/`not`) patterns — C# 9.0 (2020)
- List patterns (`[]`, `..`) — C# 11.0 (2022)
- C# switch statement me implicit fall-through DISALLOWED hai (compile error) — C/Java jaisi accidental fall-through bug is language-level impossible
- `_` discard pattern `default` ka switch-expression equivalent hai

</Numbers>

## Common Mistakes

<Mistake>

Switch expression me `_` discard pattern (catch-all) miss kar dena — agar koi case handle nahi hota aur `_` bhi nahi hai, runtime pe `SwitchExpressionException` throw hota hai jab koi unmatched value aaye. Har switch expression me exhaustiveness ensure karo, ya `_` explicitly add karo.

</Mistake>

<Mistake>

Type pattern (`is int i`) ke baad us variable `i` ko us scope ke bahar bhi use karne ki koshish karna — pattern-matched variable ka scope us `if`/`case` block tak hi limited hai (kuch cases me thoda wider, lekin generally block-scoped hi treat karo safety ke liye).

</Mistake>

<Mistake>

`when` clause aur pattern ke beech confusion — `case int n when n > 0:` me pattern match (`int n`) pehle hota hai, phir `when` guard check hota hai. Agar pattern match fail ho, `when` evaluate hi nahi hota — order samajhna zaroori hai complex cases debug karte waqt.

</Mistake>

<Mistake>

Deeply-nested `if-else` chains ko force-fit karna ek switch expression me jab actual logic multi-statement/side-effect-heavy ho — readability ke liye switch statement (ya simple if-else) zyada appropriate hota hai aise cases me, expression form nahi.

</Mistake>

## Quick Revision

<QuickRevision>

- switch statement = imperative, multi-statement branches, `break`/`return` needed, no implicit fall-through
- switch expression (C# 8) = declarative, each arm returns a value, `_` replaces `default`
- Type patterns (C# 7): `is Type x` — check + cast + bind in one
- Property patterns (C# 8): `{ Prop: value }`, nested props supported (`{ A.B: x }`)
- Relational (C# 9): `< 13`, `>= 18` as patterns directly
- Logical (C# 9): `and`/`or`/`not` combine patterns
- List patterns (C# 11): `[]`, `[x]`, `[first, .., last]` match collection shape
- Missing `_` in an exhaustive-looking switch expression risks a runtime `SwitchExpressionException`

</QuickRevision>
