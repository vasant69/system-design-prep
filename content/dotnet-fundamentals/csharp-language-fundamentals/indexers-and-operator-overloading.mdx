<SimpleDefinition>

An indexer (`this[int i]`) lets a custom type be accessed with array-like square-bracket syntax; operator overloading lets a type redefine what standard operators like `+`, `==`, and `<` mean for its own instances, most commonly used for value-like types (e.g. a `Money` type) where arithmetic-style syntax genuinely improves readability.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Dono features "apne custom type ko built-in types jaisa syntactically feel karwana" ke around hain — indexers array-jaisa `[]` access dete hain, operator overloading arithmetic/comparison syntax dete hain. Powerful hain, lekin overuse se code confusing ban sakta hai — discipline zaroori hai.

### Indexers — `this[int i]`

```csharp
public class WeekSchedule
{
    private readonly string[] _days = new string[7];

    public string this[int dayIndex]
    {
        get => _days[dayIndex];
        set => _days[dayIndex] = value;
    }
}

var schedule = new WeekSchedule();
schedule[0] = "Monday: Team standup"; // set accessor
Console.WriteLine(schedule[0]);        // get accessor
```

Indexer `this[parameter]` syntax se define hoti hai — bilkul property jaisa `get`/`set` accessor, bas parameter square brackets me pass hota hai. Custom type ko array/dictionary jaisa `[]` access dena, jab underlying implementation array na bhi ho.

**String-keyed indexer bhi possible hai** (dictionary-jaisa):

```csharp
public class Settings
{
    private readonly Dictionary<string, string> _values = new();

    public string this[string key]
    {
        get => _values.TryGetValue(key, out var v) ? v : null;
        set => _values[key] = value;
    }
}

var settings = new Settings();
settings["theme"] = "dark";
Console.WriteLine(settings["theme"]); // "dark"
```

**Multiple indexers (overloaded)** ek hi class me ho sakti hain, different parameter types ke saath — jaise ek `int` indexer aur ek `string` indexer.

### Operator Overloading

`+`, `-`, `==`, `!=`, `<`, `>` jaise operators ko custom types ke liye redefine karna, `static` methods ke through:

```csharp
public readonly struct Money
{
    public decimal Amount { get; }
    public string Currency { get; }

    public Money(decimal amount, string currency)
    {
        Amount = amount;
        Currency = currency;
    }

    public static Money operator +(Money a, Money b)
    {
        if (a.Currency != b.Currency)
            throw new InvalidOperationException("Cannot add different currencies");
        return new Money(a.Amount + b.Amount, a.Currency);
    }

    public static bool operator ==(Money a, Money b) => a.Amount == b.Amount && a.Currency == b.Currency;
    public static bool operator !=(Money a, Money b) => !(a == b);

    public override bool Equals(object obj) => obj is Money m && this == m;
    public override int GetHashCode() => HashCode.Combine(Amount, Currency);
}

var total = new Money(100, "INR") + new Money(50, "INR");
Console.WriteLine(total.Amount); // 150
```

**Important rule: `==`/`!=` overload karte waqt `Equals()`/`GetHashCode()` bhi override karna chahiye** — inconsistency (`==` kuch aur bolta hai, `Equals()` kuch aur) confusing aur buggy behavior deta hai, especially collections (`Dictionary`, `HashSet`) me jo internally `Equals()`/`GetHashCode()` use karte hain, `==` nahi.

**Operators ke pairs saath overload karne zaroori hain** — `==` overload karo to `!=` bhi karna hoga (compiler enforce karta hai), `<` overload karo to `>` bhi expected hai (convention, hard-enforced nahi lekin strongly expected).

### Kab use karna sahi hai, kab overkill

Operator overloading tab genuinely sahi hai jab type **value-like** hai aur arithmetic/comparison semantics domain me naturally fit karti hain — `Money`, `Vector2D`, `Complex` numbers, `Duration`. Ye tab GALAT hai jab operator ka meaning ambiguous ya surprising ho — jaise `Employee + Employee` ka koi natural meaning nahi hai, aisi jagah operator overload karna sirf confusion badhata hai, normal named methods (`employee.PromoteWith(other)`) zyada clear hote hain.

</Hinglish>

## Real World Example

<RealWorld company="Microsoft">

.NET BCL me `Dictionary<TKey,TValue>`, `List<T>`, `string` sab indexers use karte hain (`dict[key]`, `list[index]`, `str[charIndex]`). Operator overloading `DateTime`/`TimeSpan` (`date1 - date2` returns a `TimeSpan`), `decimal`/numeric types me heavily use hoti hai — ye .NET ke apne types me operator overloading ka canonical real-world example hai.

</RealWorld>

<RealWorld company="An Indian Fintech Ledger System">

Ek ledger-balancing system me ek `Money` struct (upar jaisa example) operator overloading use karta hai taaki `balance += transactionAmount` jaisa natural-reading code likha ja sake, lekin currency-mismatch ko runtime exception ke through explicitly reject kare — accidental cross-currency arithmetic bugs ko silently allow karne ke bajaye loudly fail karta hai.

</RealWorld>

## Numbers That Matter

<Numbers>

- Indexer syntax — `this[parameter]`, C# 1.0 se
- Multiple indexers ek class me overload ho sakte hain (different parameter types)
- `==` overload karne par `!=` overload karna compiler-mandatory hai (pair requirement)
- `==` overload karte waqt `Equals()`/`GetHashCode()` bhi override karna strongly recommended (consistency ke liye)
- Comparison operators (`<`,`>`,`<=`,`>=`) overload karne ke liye typically `IComparable<T>` bhi implement karna best practice hai

</Numbers>

## Interview Angle

<InterviewAngle>

"Operator overloading kab use karna chahiye, kab nahi?" ka strong answer: "Jab type genuinely value-like ho aur domain me arithmetic/comparison semantics naturally fit karti ho — jaise ek `Money` ya `Vector2D` type, jahan `+` ka meaning obvious hai. Jab type ek entity/behavior-driven object ho jiske liye `+` ka koi natural meaning nahi hai — jaise `Employee + Employee` — operator overloading avoid karni chahiye, ek clearly-named method zyada readable hota hai. Aur jab bhi `==` overload karta hoon, main hamesha `Equals()` aur `GetHashCode()` ko bhi consistently override karta hoon, taaki collections (Dictionary, HashSet) me behavior surprising na ho." Follow-up: "indexer kab use karoge property/method ke bajaye?" — jab type conceptually ek collection/sequence jaisa access pattern rakhta ho.

</InterviewAngle>

## Common Mistakes

<Mistake>

`==` operator overload karna lekin `Equals()`/`GetHashCode()` ko consistent na rakhna — is se `Dictionary`/`HashSet` (jo `Equals()`/`GetHashCode()` use karte hain) aur direct `==` comparisons ka behavior alag-alag ho sakta hai, ek subtle, confusing bug.

</Mistake>

<Mistake>

Operator overloading ko non-value-types pe use karna jahan operator ka meaning genuinely ambiguous/surprising ho — jaise `Customer + Order` — is se code readability improve nahi hoti, ulta kam ho jaati hai.

</Mistake>

<Mistake>

Indexer ke andar heavy computation ya side-effects daalna — `[]` syntax caller ko expect karwata hai ki access fast/lightweight hai (array-jaisa), agar indexer ke andar database call ya complex logic ho, ye caller ke expectation se mismatch hota hai.

</Mistake>

<Mistake>

`<`/`>` overload karna bina `IComparable<T>` implement kiye jab type genuinely sortable hona chahiye — sorting/ordering-related BCL methods (`Sort()`, `OrderBy()`) `IComparable<T>` pe rely karte hain, sirf operator overload karna unke saath automatically integrate nahi hota.

</Mistake>

## Quick Revision

<QuickRevision>

- Indexer: `this[param] { get; set; }` — array/dictionary-like `[]` access on a custom type
- Multiple indexers can be overloaded by parameter type in the same class
- Operator overloading: `static ReturnType operator +(Type a, Type b)` — redefines what an operator means for a type
- `==`/`!=` must be overloaded as a pair (compiler-enforced); keep them consistent with `Equals()`/`GetHashCode()`
- Best fit: value-like types (Money, Vector) — worst fit: entity/behavior types with no natural operator meaning
- Comparison operators should typically pair with `IComparable<T>` for BCL sort/order integration

</QuickRevision>
