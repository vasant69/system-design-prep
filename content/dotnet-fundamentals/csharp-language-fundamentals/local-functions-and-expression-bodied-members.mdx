<SimpleDefinition>

Local functions (C# 7) are methods defined inside another method, useful for recursion helpers and logic that only makes sense in one place without the closure-allocation cost a lambda would have; expression-bodied members use the `=>` shorthand to write single-expression methods, properties, and constructors more concisely.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Dono features unrelated hain ek doosre se, lekin dono "code ko concise aur locally-scoped rakhna" ke around hain — isliye ek topic me saath cover karna sensible hai.

### Local Functions (C# 7.0)

Ek method ke andar defined ek doosra method — sirf outer method ke andar hi callable, bahar se invisible:

```csharp
public int Factorial(int n)
{
    if (n < 0) throw new ArgumentException("n must be non-negative");

    return Calculate(n);

    int Calculate(int number) // local function
    {
        return number <= 1 ? 1 : number * Calculate(number - 1);
    }
}
```

**Kyun useful hai:**
1. **Recursion helpers** — jaise upar `Calculate` — argument-validation ko ek baar top pe karke, recursive part ko clean rakhna
2. **Encapsulation** — ye helper method sirf `Factorial` ke andar hi meaningful hai, bahar expose karne ki koi zarurat nahi — local function ise `Factorial` ke bahar completely invisible bana deti hai
3. **Lambda se better performance in some cases** — agar ek equivalent `Func<int,int>` lambda use karte (`Func<int,int> calculate = null; calculate = n => n <= 1 ? 1 : n * calculate(n-1);`), aur wo lambda outer variables capture kare, compiler ek **closure object heap pe allocate** karta hai. Local functions, agar wo koi outer variable capture nahi karte (ya sirf `readonly`-jaisi simple capture), no-allocation ya minimal-allocation rehte hain — genuinely lighter-weight hote hain jab heavy recursion/hot-path code me use ho.

**Local function vs Lambda — kab kaunsa:**

```csharp
// Local function — better readability, potential no-allocation, supports recursion naturally
int Add(int a, int b) => a + b;

// Lambda — jab function ko value ki tarah pass karna ho (Func/Action parameter, LINQ predicate)
Func<int, int, int> add = (a, b) => a + b;
numbers.Where(n => n > 5);
```

Rule of thumb: agar function ko sirf current method ke andar call karna hai (kabhi kisi parameter ki tarah pass nahi karna), local function prefer karo. Agar function ko value ki tarah kahin pass karna hai (LINQ, callback, delegate parameter), lambda/`Func`/`Action` chahiye hoga.

### Expression-Bodied Members (C# 6 methods/properties, C# 7 constructors/finalizers)

`=>` shorthand — jab body genuinely ek single expression ho:

```csharp
// Method
public int Square(int x) => x * x;

// Read-only property
public string FullName => $"{FirstName} {LastName}";

// Property with both getter and setter (C# 7)
private string _name;
public string Name
{
    get => _name;
    set => _name = value ?? throw new ArgumentNullException(nameof(value));
}

// Constructor (C# 7)
public class Point
{
    private readonly int _x, _y;
    public Point(int x, int y) => (_x, _y) = (x, y);
}
```

Ye purely **readability/conciseness** feature hai — semantically block-body (`{ return x * x; }`) se koi runtime difference nahi hai, compiler equivalent IL generate karta hai. Ye feature tab shine karta hai jab logic genuinely ek line me fit ho — force-fit karna multi-statement logic ko `=>` me (jaise ternary chains ke andar ternary) readability kharab kar deta hai, discipline zaroori hai.

</Hinglish>

<Callout type="tip">

Local functions vs private helper methods: agar helper method sirf ek hi outer method ke context me meaningful hai (kahin aur reuse nahi hoga), local function usko class-level namespace se hata kar sahi jagah scope karti hai — class ka public/private method-list clutter nahi hota.

</Callout>

## Numbers That Matter

<Numbers>

- Local functions — C# 7.0 (2017)
- Expression-bodied methods/properties — C# 6.0 (2015); constructors, finalizers, get/set accessors — C# 7.0 (2017)
- Local function jo koi outer variable capture nahi karta — koi closure allocation nahi (lambda se lighter)
- `=>` syntax purely compile-time sugar — same IL as equivalent `{ }` block body

</Numbers>

## Interview Angle

<InterviewAngle>

"Local function aur lambda me kab kaunsa choose karoge?" ka strong answer: "Agar function sirf current method ke andar hi call hoga, kabhi value ki tarah pass nahi hoga (delegate parameter, LINQ predicate), main local function prefer karta hoon — better readability, recursion ke liye natural syntax, aur agar koi outer variable capture na ho to koi closure-allocation overhead bhi nahi. Agar function ko genuinely value ki tarah treat karna hai — jaise `Where(predicate)` me pass karna — tab lambda/`Func`/`Action` zaroori hai, kyunki local function khud ek 'value' nahi hai jise directly pass kiya ja sake without wrapping in a delegate." Follow-up: "expression-bodied members ka koi runtime performance benefit hai?" — answer: nahi, purely syntactic sugar hai, same IL generate hota hai.

</InterviewAngle>

## Common Mistakes

<Mistake>

Local function ko lambda ki tarah directly kisi `Func<>`/`Action<>` parameter me pass karne ki koshish karna bina explicit conversion ke — local function khud ek delegate value nahi hai, use ek delegate me wrap karna padta hai agar value ki tarah pass karna ho (`Func<int,int> f = LocalFunctionName;`).

</Mistake>

<Mistake>

Expression-bodied members me multi-statement logic force-fit karna nested ternary operators ke through — ye technically compile hota hai lekin readability seriously kharab kar deta hai; agar logic ek line se zyada complex ho, block body (`{ }`) use karo.

</Mistake>

<Mistake>

Har chhota helper method ko local function bana dena, chahe wo genuinely multiple jagah reusable ho — agar logic sach me kai methods me reuse hoti hai, ek proper class-level private method zyada sahi hai, local function nahi (jo sirf ek method tak scoped rehti hai).

</Mistake>

<Mistake>

Local function jo heavily outer variables capture karti hai use assume karna ki wo "always zero-allocation" hai — closure allocation tab bhi ho sakta hai agar meaningful variable capture ho, sirf no-capture case guaranteed lightweight hai.

</Mistake>

## Quick Revision

<QuickRevision>

- Local function (C# 7) — method inside a method, callable only within the enclosing method
- Best for: recursion helpers, single-use logic, avoiding class-level namespace clutter
- No closure allocation if it captures no outer variables — lighter than an equivalent capturing lambda
- Cannot be passed as a delegate value directly without wrapping — use a lambda/Func/Action for that
- Expression-bodied members (`=>`) — C# 6/7, methods/properties/constructors/accessors
- Purely syntactic sugar, zero runtime difference from an equivalent `{ }` block body
- Don't force multi-statement logic into `=>` — readability suffers

</QuickRevision>
