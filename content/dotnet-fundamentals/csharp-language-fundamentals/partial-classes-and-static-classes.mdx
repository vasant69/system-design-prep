<SimpleDefinition>

A `partial` class lets one class's definition span multiple files (most commonly to separate designer/scaffolded-generated code from hand-written code); a `static` class cannot be instantiated at all, exists purely as a container for static members, and is the standard pattern for stateless utility/helper functionality.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

`partial class`/`partial method` ka mechanism aur EF Core scaffolding use-case pehle se `oops-dotnet`'s `sealed-partial-nested-classes` topic me cover ho chuka hai — wahan padho agar poora partial-class mechanism revise karna hai. Yahan sirf ek quick recap, aur is topic ka main focus: **static classes** — jo genuinely alag concept hai aur bahut zyada interview-relevant hai utility/helper-class design ke context me.

### Quick recap — partial class

```csharp
// GeneratedCode.cs — tool-generated, mat touch karo
public partial class Product
{
    public int Id { get; set; }
    public string Name { get; set; }
}

// Product.cs — hand-written business logic
public partial class Product
{
    public decimal CalculateDiscountedPrice(decimal discountPercent)
    {
        return Price - (Price * discountPercent / 100);
    }
}
```

`partial` keyword ek class ki definition ko multiple files me split karne deta hai — compile-time pe compiler sab pieces ko join kar ke ek single class treat karta hai. Classic use-case: **generated code + hand-written code ko alag files me rakhna** (EF Core scaffolding, WinForms designer files) — taaki tool re-generate hone par hand-written logic overwrite na ho.

### Static Classes — is topic ka asli focus

```csharp
public static class MathHelpers
{
    public const double Pi = 3.14159;

    public static double CircleArea(double radius) => Pi * radius * radius;
    public static bool IsEven(int number) => number % 2 == 0;
}

// Usage — koi instance nahi banti
double area = MathHelpers.CircleArea(5);
```

**Static class ke strict rules:**
1. **Instantiate NAHI ho sakti** — `new MathHelpers()` COMPILE ERROR deta hai. Static class ka poora point hi ye hai ki koi instance kabhi zaroori nahi hai.
2. **Sirf static members** rakh sakti hai — koi instance field, instance method, instance property allowed nahi. Compiler enforce karta hai — agar galti se ek non-static member add kar do, compile error aata hai.
3. **Inherit nahi ki ja sakti, aur kisi se inherit bhi nahi kar sakti** (implicitly `sealed` hai) — ek static class na base class ban sakti hai, na koi (non-`object`) base class extend kar sakti hai.
4. **Constructor nahi ho sakta** (instance constructor) — sirf ek static constructor allowed hai, jo automatically first-use se pehle ek baar run hota hai (static field initialization ke liye).

**Kab static class use karna sahi hai:**
- **Stateless utility/helper functions** — jaise `Math`, `Console`, `File` (.NET BCL ke apne examples) — inka koi meaningful "instance" concept hi nahi hai
- **Extension methods** — extension methods MANDATORY static class ke andar honi chahiye
- **Constants ka grouping** — related constants ko ek logical namespace-jaisa group dena

**Kab static class GALAT choice hai:**
- Jab type genuinely state rakhta hai jo instance-to-instance vary karta hai — static class me sirf ek shared, global state hoti hai (agar static fields use ho), jo testability aur thread-safety ke liye dangerous ho sakta hai
- Jab dependency injection/mocking chahiye ho testing ke liye — static classes ko mock karna genuinely mushkil hai (koi interface implement nahi kar sakte), jo unit-testing me friction badhata hai

</Hinglish>

## Real World Example

<RealWorld company="Microsoft">

.NET BCL ke `Math`, `Console`, `File`, `Directory`, `Convert` — sab static classes hain. In sab me common pattern hai: koi meaningful "instance" concept nahi hai (`Math` ka do instances banana kya matlab rakhta), aur functionality poori tarah stateless, input-output based hai.

</RealWorld>

<RealWorld company="An Indian Logistics Platform">

Ek shipment-tracking system me `partial class ShipmentDbContext` (EF Core scaffolded part + hand-written `OnModelCreating` fluent config part alag files me) aur ek `static class DistanceCalculator` (pure geo-distance math functions, koi state nahi) dono ek saath dikhte hain — do genuinely alag design patterns, dono apni jagah sahi.

</RealWorld>

## Numbers That Matter

<Numbers>

- `partial` keyword — C# 2.0 (2005); `partial method` bhi C# 2.0 se, extended C# 8/9 me
- `static class` — C# 1.0 se hi maujood, implicitly `sealed` (kabhi inherit nahi ho sakti)
- Static class me instance constructor allowed NAHI — sirf ek static constructor allowed hai
- .NET BCL ke `Math`/`Console`/`Convert`/`Directory` sab static classes ke canonical examples hain
- Extension methods MANDATORY ek static class ke andar honi chahiye (language requirement)

</Numbers>

## Interview Angle

<InterviewAngle>

"Static class kab use karoge, kab regular class better hai?" ka strong answer: "Static class tab jab type genuinely stateless hai aur koi meaningful 'instance' concept hi nahi hai — jaise math utility functions, extension methods ka container, ya related constants ka grouping. Regular class tab jab type ka koi genuine state ho jo instance-se-instance differ karta ho, ya jab dependency injection/mocking chahiye ho testing ke liye — static classes ko interface implement nahi karwa sakte, isliye unit tests me mock karna genuinely mushkil hai. Modern ASP.NET Core codebases me is wajah se pure-utility logic ke alawa static classes ka use limited rakha jaata hai, taaki testability maintain rahe." Follow-up: "partial class ka main real-world use-case kya hai?" — generated code (EF scaffolding, designer files) ko hand-written code se alag rakhna.

</InterviewAngle>

## Common Mistakes

<Mistake>

Static class me mutable static fields daal dena jo request-to-request ya call-to-call state maintain karti hain — ye ek hidden global/shared state ban jaata hai jo multi-threaded ASP.NET Core environment me thread-safety bugs de sakta hai, aur unit testing me tests ek doosre ko affect karne lag jaate hain (test isolation break ho jaata hai).

</Mistake>

<Mistake>

Business logic ya domain services ko static classes bana dena "convenience" ke liye — ye testability seriously kharab karta hai kyunki static classes ko dependency-injected interfaces ke through mock nahi kiya ja sakta, jo unit testing ko mushkil bana deta hai.

</Mistake>

<Mistake>

Partial class ke pieces ko bina clear naming convention ke split karna (jaise dono files ka naam similar rakh dena) — bina discipline ke, ye confusion badhata hai ki kaunsi file generated hai (touch mat karo) aur kaunsi hand-written hai (safe to edit).

</Mistake>

<Mistake>

Static class me accidentally `sealed`/inheritance try karna — static class already implicitly sealed hai, use kisi cheez se inherit karne ya usse inherit karwane ki koshish compile error deti hai; ye rule bhoolna beginners ke liye confusing hota hai.

</Mistake>

## Quick Revision

<QuickRevision>

- `partial class` (C# 2.0) — splits one class's definition across files, compiler joins at compile time
- Classic partial use-case: separating generated code (EF scaffolding, designer files) from hand-written code
- `static class` — cannot be instantiated, only static members allowed, implicitly sealed
- Best fit for static class: stateless utilities (Math-like), extension method containers, constant grouping
- Worst fit for static class: anything needing DI/mocking for testability, or genuine per-instance state
- Mutable static state is a hidden global — thread-safety and test-isolation risk

</QuickRevision>
