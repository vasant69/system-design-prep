<SimpleDefinition>

Deconstruction (`var (a, b) = point;`) unpacks a tuple or any type exposing a `Deconstruct` method into separate variables in one statement; discards (`_`) let code explicitly ignore a value it doesn't need; `nameof()` gives back the string name of a variable, type, or member in a refactor-safe way that updates automatically when the symbol is renamed.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Teen chhote lekin genuinely useful features — inka common thread hai "code ko cleaner aur refactor-safe banana."

### Deconstruction — `var (a, b) = ...`

**Tuples ke saath** (sabse common use):

```csharp
(string name, int age) GetPerson() => ("Amit", 30);

var (name, age) = GetPerson();
Console.WriteLine($"{name} is {age} years old");
```

Ek method jo tuple return karta hai, uske result ko ek statement me multiple named variables me unpack kar sakte ho — `var result = GetPerson(); var name = result.name; var age = result.age;` jaisi 3-line boilerplate ki jagah ek line.

**Custom types ke saath bhi** — koi bhi type jo ek `Deconstruct` method expose karta hai:

```csharp
public class Point
{
    public int X { get; }
    public int Y { get; }
    public Point(int x, int y) { X = x; Y = y; }

    public void Deconstruct(out int x, out int y)
    {
        x = X;
        y = Y;
    }
}

var point = new Point(3, 4);
var (x, y) = point; // Deconstruct method automatically call hota hai
```

`Deconstruct` method (naam exactly ye hona zaroori hai) `out` parameters use karta hai — compiler `var (x, y) = point;` ko dekh kar automatically `point.Deconstruct(out x, out y);` call karta hai. **`record` types me `Deconstruct` automatically compiler-generated hoti hai** (positional records ke liye), isliye records ke saath deconstruction "bina kuch likhe" kaam karta hai.

### Discards — `_`

Jab ek value ki zarurat hi nahi, sirf ignore karni hai:

```csharp
var (name, _) = GetPerson(); // age ignore kar diya, sirf name chahiye

if (int.TryParse(input, out _)) // result value nahi chahiye, sirf success/fail check
{
    Console.WriteLine("Valid number");
}

_ = SomeMethodThatReturnsValueButIDontCare(); // return value explicitly discard
```

`_` compiler ko batata hai "ye value genuinely use nahi hogi" — koi actual variable allocate nahi hoti (multiple `_` ek scope me bhi conflict nahi karte, jabki `int a, int a` conflict karta). Ye code ka intent clear karta hai — "maine is value ko IGNORE kiya hai, bhoola nahi hai."

**Pattern matching me bhi discard pattern common hai:**

```csharp
object obj = GetValue();
if (obj is int _) // sirf type check, value nahi chahiye
{
    Console.WriteLine("It's an int, don't care about the value");
}
```

### `nameof()` — refactor-safe string names

```csharp
public void SetAge(int age)
{
    if (age < 0)
        throw new ArgumentException("Age cannot be negative", nameof(age));
}
```

`nameof(age)` compile-time pe `"age"` string me resolve hota hai — lekin ye ek **magic string nahi hai**, ye `age` parameter ko genuinely reference karta hai. Agar kal ko parameter ka naam `age` se `yearsOld` rename ho jaaye (IDE rename-refactor use karke), `nameof(age)` automatically compile error dega (kyunki `age` ab exist hi nahi karta), jo developer ko turant batayega ki string bhi update karni hai. **Plain hardcoded string** (`"age"`) is protection ke bina silently stale reh jaata, koi compile error nahi aata, aur exception message galat parameter naam bataata rehta.

```csharp
// Bad — hardcoded string, rename-unsafe
throw new ArgumentException("...", "age");

// Good — nameof, rename-safe
throw new ArgumentException("...", nameof(age));
```

`nameof()` sirf exceptions ke liye nahi — logging (`_logger.LogInformation($"{nameof(ProcessOrder)} started")`), property-changed events (`OnPropertyChanged(nameof(Name))`), aur kahin bhi jahan ek symbol ka STRING naam chahiye, sabme useful hai.

</Hinglish>

<Callout type="tip">

Rule of thumb jo teeno features ko jodta hai: sab "compiler ko apna intent explicitly batana" ke around hain — deconstruction "mujhe ye specific parts chahiye", discard "mujhe ye value nahi chahiye", `nameof()` "mujhe is symbol ka naam chahiye, hardcoded string nahi."

</Callout>

## Real World Example

<RealWorld company="Microsoft">

.NET ke apne `ArgumentNullException.ThrowIfNull(value, nameof(value))`-jaisi guard-clause patterns me `nameof()` universal convention hai — .NET analyzers (jaise `CA1507`) explicitly warning dete hain jab koi hardcoded string parameter-name ki jagah use ki jaaye jahan `nameof()` honi chahiye thi.

</RealWorld>

<RealWorld company="An Indian Real-Estate Listings API">

Ek listings-search API me `(decimal minPrice, decimal maxPrice) ParsePriceRange(string input)` jaisa method deconstruction ke saath directly consume hota hai — `var (min, max) = ParsePriceRange(query);` — bina ek intermediate tuple-variable ke through dono values access karne ki zarurat.

</RealWorld>

## Numbers That Matter

<Numbers>

- Tuple deconstruction, discards — C# 7.0 (2017)
- `nameof()` — C# 6.0 (2015)
- Positional `record` types automatically ek compiler-generated `Deconstruct` method paate hain
- `Deconstruct` method naam exactly yahi hona chahiye — compiler is naam se hi ise recognize karta hai
- Multiple `_` discards ek hi scope me conflict-free hain (unlike naming a real variable twice)

</Numbers>

## Interview Angle

<InterviewAngle>

"`nameof()` ka use kyun better hai hardcoded string se, especially exception messages me?" ka strong answer: "`nameof(parameterName)` compile-time pe string me resolve hota hai, lekin ye genuinely us symbol ka reference hai — agar parameter ka naam rename ho jaaye (refactoring ke dauraan), `nameof()` automatically compile error dega agar purana naam ab exist nahi karta, jo developer ko force karta hai reference update karne ke liye. Hardcoded string (`\"age\"`) is protection ke bina silently stale reh sakta hai — parameter rename ho jaaye lekin exception message purana naam batata rahe, jo debugging ko confusing bana deta hai." Follow-up: "custom type me deconstruction kaise enable karoge?" — ek `public void Deconstruct(out Type1 a, out Type2 b)` method add karke.

</InterviewAngle>

## Common Mistakes

<Mistake>

Exception messages ya logging me hardcoded parameter-name strings use karna (`nameof()` ke bajaye) — refactoring ke baad ye silently stale ho jaate hain, koi compile error nahi aata, sirf runtime pe confusing/misleading messages milte hain.

</Mistake>

<Mistake>

Deconstruction ke liye custom `Deconstruct` method ka naam galat rakhna (jaise `Deconstruct2` ya `ToTuple`) — compiler specifically `Deconstruct` naam hi recognize karta hai, koi doosra naam automatically kaam nahi karega.

</Mistake>

<Mistake>

Discard (`_`) ko genuinely-needed values ke liye bhi habitually use karna, sirf typing bachaane ke liye — agar value future me kabhi zarurat pad sakti hai, ek meaningful naam dena better hai, discard "main ise permanently ignore kar raha hoon" ka signal deta hai.

</Mistake>

<Mistake>

`nameof(SomeClass.SomeProperty)` aur `nameof(SomeProperty)` (class ke andar se) ke beech confusion — dono valid syntax hain lekin context-dependent, aur galat context me use karne se compile error ya unexpected resolved-name aa sakta hai.

</Mistake>

## Quick Revision

<QuickRevision>

- Deconstruction (C# 7): `var (a, b) = source;` — works for tuples and any type with a `Deconstruct(out ..., out ...)` method
- Positional `record` types get `Deconstruct` auto-generated by the compiler
- Discards (`_`, C# 7): explicitly ignore a value — in deconstruction, `out` params, pattern matching
- `nameof()` (C# 6): compile-time, refactor-safe symbol-to-string — breaks the build if the symbol is renamed away, unlike a hardcoded string
- Use `nameof()` for exception parameter names, logging, and property-changed notifications

</QuickRevision>
