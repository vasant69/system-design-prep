<SimpleDefinition>

C# 9-10 introduced three ceremony-reducing features: top-level statements remove the need for an explicit `Main` method and enclosing class for simple programs, global usings share common `using` directives across every file in a project from one place, and file-scoped namespaces remove one level of indentation by letting a namespace apply to an entire file without braces.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Teeno features ek hi goal share karte hain — **repetitive, low-value ceremony ko hataana**, bina language ki expressiveness kam kiye. Interview me ye poocha jaata hai "in features ka exact kya hota hai peeche" — ye samajhna zaroori hai ki ye sirf syntax sugar hai, semantics same hi rehti hai.

### Top-Level Statements (C# 9.0)

**Pre-C#9 style — mandatory boilerplate:**

```csharp
using System;

namespace MyApp
{
    class Program
    {
        static void Main(string[] args)
        {
            Console.WriteLine("Hello World");
        }
    }
}
```

**C# 9+ top-level statements:**

```csharp
using System;

Console.WriteLine("Hello World");
```

Bas itna — koi `class Program`, koi `static void Main`, koi explicit `namespace` block. Compiler khud IL level pe ek hidden `Program` class aur `Main` method generate karta hai — **runtime behavior bilkul identical hai**, sirf source-level ceremony gayab ho gayi hai. `args` (command-line arguments) bhi automatically available hai top-level statements ke context me, bina explicitly declare kiye.

**Kab useful hai:** Chhote console apps, scripts, quick prototypes, ya modern ASP.NET Core `Program.cs` (jahan `WebApplication.CreateBuilder(args)` jaisa setup code seedha top-level likha jaata hai). Bade, multi-file production apps me bhi ye ek entry-point file ke liye normal hai — sirf `Program.cs` top-level style me, baaki files normal class-based rehte hain.

### Global Usings (C# 10.0)

**Pre-C#10 — har file me repeat karna padta tha:**

```csharp
// Every .cs file needed this at the top
using System;
using System.Collections.Generic;
using System.Linq;
using System.Threading.Tasks;
```

**C# 10+ — ek jagah declare karo, poore project me apply ho:**

```csharp
// GlobalUsings.cs (ya koi bhi file, convention hai ek dedicated file rakhna)
global using System;
global using System.Collections.Generic;
global using System.Linq;
global using System.Threading.Tasks;
```

`global using` ek baar likhne ke baad, us namespace ka `using` **poore project ke har `.cs` file me automatically apply hota hai**, bina har file me repeat kiye. Compile-time pe compiler har file ko treat karta hai jaise wo `using` waha bhi likha ho — koi runtime difference nahi, purely compile-time convenience.

**Implicit Usings** (`.csproj` me `<ImplicitUsings>enable</ImplicitUsings>`, .NET 6+ SDK templates ka default) is concept ko aur aage le jaata hai — project type (Console, Web, etc.) ke basis pe SDK khud commonly-needed namespaces (`System`, `System.Linq`, etc. Console ke liye; `Microsoft.AspNetCore.Builder` etc. Web ke liye) ko automatically global-using kar deta hai, bina developer ko kuch likhne ki zarurat.

### File-Scoped Namespaces (C# 10.0)

**Pre-C#10 — block-scoped, ek extra indentation level:**

```csharp
namespace MyApp.Services
{
    public class OrderService
    {
        // ... poori class body ek extra indent level pe
    }
}
```

**C# 10+ — file-scoped, no braces, no extra indent:**

```csharp
namespace MyApp.Services;

public class OrderService
{
    // ... normal indentation, no extra nesting level
}
```

`namespace X;` (semicolon, no braces) ka matlab hai "is poori file ka namespace `X` hai" — koi block/brace zaroori nahi, aur poori file ek indentation level kam use karti hai. **Ek file me sirf ek file-scoped namespace ho sakta hai** — agar ek file me genuinely do alag namespaces me classes rakhni hon (rare case), traditional block-syntax use karni padegi.

</Hinglish>

<Callout type="tip">

Sab teen features **purely compile-time/source-level convenience** hain — koi runtime behavior change nahi hota, koi performance impact nahi hai. Interview me ye clarify karna important hai: naya syntax = kam typing, same IL output.

</Callout>

## Real World Example

<RealWorld company="Microsoft">

.NET 6+ ke saare project templates (`dotnet new console`, `dotnet new webapi`) by default top-level statements, implicit usings, aur file-scoped namespaces use karte hain — `Program.cs` sirf kuch lines ka hota hai jahan pehle 15-20 lines boilerplate hota tha. Ye .NET team ka deliberate push tha "getting started" experience ko simplify karne ke liye.

</RealWorld>

<RealWorld company="An Indian Startup's Microservices Codebase">

Ek microservices-based backend me team ne project-wide `GlobalUsings.cs` file convention adopt ki — har service project me ek single file jisme saare commonly-needed namespaces (`System`, `System.Linq`, `Microsoft.Extensions.Logging`, apna domain namespace) global-declared hain, jisse individual service/controller files sirf apne domain-specific `using` statements rakhte hain, boilerplate kam hota hai code-review me bhi.

</RealWorld>

## Numbers That Matter

<Numbers>

- Top-level statements — C# 9.0 (2020)
- Global usings, file-scoped namespaces, implicit usings — C# 10.0 / .NET 6 (2021)
- `<ImplicitUsings>enable</ImplicitUsings>` — .NET 6+ SDK templates ka default setting
- Ek file me sirf EK file-scoped namespace declaration allowed hai
- Top-level statements: sirf EK file per project me allowed hain (jahan `Main`-equivalent code hai)

</Numbers>

## Interview Angle

<InterviewAngle>

"Top-level statements ka runtime pe kya effect hota hai?" ka strong answer: "Bilkul koi runtime difference nahi — compiler internally still ek `Program` class aur `Main` method generate karta hai, exactly waisa hi jaisa traditional syntax se hota. Top-level statements purely source-level ceremony reduce karte hain, IL output effectively same hota hai. Ye .NET team ka deliberate push tha getting-started experience simplify karne ke liye — .NET 6+ ke saare project templates ab by default top-level statements, implicit usings, aur file-scoped namespaces use karte hain." Follow-up: "kya global using kisi file-specific using ko override kar sakta hai, ya conflict ho sakta hai?" — global using project-wide default hai, agar ek specific file me alag namespace ka same-named type chahiye, file-local `using` alias ya fully-qualified naam use karna padega — koi automatic override nahi hota, ambiguous-reference compile error aayega agar genuinely conflict ho.

</InterviewAngle>

## Common Mistakes

<Mistake>

Ek project me do files me top-level statements likhne ki koshish karna — sirf EK entry-point file allowed hai top-level statements ke saath; doosri file me try karne se compile error aata hai ("only one compilation unit can have top-level statements").

</Mistake>

<Mistake>

File-scoped namespace (`namespace X;`) ke baad galti se braces bhi add kar dena — ye compile error deta hai, file-scoped syntax semicolon-based hai, traditional block-syntax nahi mix ho sakta ek hi declaration me.

</Mistake>

<Mistake>

Implicit usings (`<ImplicitUsings>enable</ImplicitUsings>`) ke baare me confuse hona ki exactly kaunse namespaces automatically include hain — ye project type (Console vs Web vs Worker) ke basis pe differ karta hai; bina samjhe assume karna ki har namespace automatically available hai, missing-using compile errors de sakta hai.

</Mistake>

<Mistake>

Global usings ko overuse karna — bahut saare unrelated namespaces ko globally declare karna, jinme se kuch sirf 1-2 files me use hote hain, discoverability kam kar sakta hai (kisi file me code padhte waqt clear nahi hota kaunsa type kahan se aa raha hai bina explicit local using ke).

</Mistake>

## Quick Revision

<QuickRevision>

- Top-level statements (C# 9): no explicit Main/class needed, compiler generates them behind the scenes — identical runtime behavior
- Only ONE file per project can have top-level statements
- Global usings (C# 10): `global using X;` applies that using to every file in the project
- Implicit usings (.NET 6+ SDK default): auto-adds common namespaces based on project type
- File-scoped namespaces (C# 10): `namespace X;` (no braces) applies to the whole file, one less indentation level
- Only one file-scoped namespace allowed per file
- All three are purely compile-time/source-level — zero runtime performance impact

</QuickRevision>
