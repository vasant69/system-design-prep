<SimpleDefinition>

`Func`, `Action`, and `Predicate` are built-in generic delegate types that eliminate the need to declare a custom delegate for most everyday cases — `Func` represents a method that returns a value, `Action` represents one that returns `void`, and `Predicate` represents a method that takes one argument and returns a `bool`, most commonly used for filtering.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Pichhle topic me humne dekha custom delegate kaise declare karte hain — `public delegate int MathOperation(int a, int b);`. Practically, har baar naya delegate type declare karna repetitive hota — isliye .NET Framework 3.5 se, `System` namespace me **pehle se-defined generic delegate types** aa gaye jo 99% cases cover kar dete hain: `Func<>`, `Action<>`, aur `Predicate<>`.

### `Func<T1, T2, ..., TResult>` — jo kuch return karta hai

`Func<>` ek method represent karta hai jo **value return karta hai**. Last type parameter hamesha return type hota hai, baaki sab input parameters:

```csharp
Func<int, int, int> add = (a, b) => a + b;
int result = add(5, 3); // 8

Func<string, int> getLength = s => s.Length;
int len = getLength("hello"); // 5

Func<int> getRandom = () => new Random().Next(); // no input, sirf return
```

### `Action<T1, T2, ...>` — jo kuch return NAHI karta (void)

`Action<>` ek method represent karta hai jo `void` return karta hai — koi return type parameter nahi hota, sab type parameters input hote hain:

```csharp
Action<string> print = msg => Console.WriteLine(msg);
print("Hello"); // "Hello" print hota hai, kuch return nahi

Action<int, int> logSum = (a, b) => Console.WriteLine($"Sum: {a + b}");
logSum(3, 4); // "Sum: 7"

Action noArgs = () => Console.WriteLine("No parameters at all");
```

### `Predicate<T>` — jo bool return karta hai (filtering ke liye)

`Predicate<T>` ek specialized case hai — bilkul `Func<T, bool>` jaisa hi behave karta hai, lekin ek dedicated naam ke saath, filtering/condition-checking scenarios ke liye:

```csharp
Predicate<int> isEven = n => n % 2 == 0;
bool result = isEven(4); // true

List<int> numbers = new() { 1, 2, 3, 4, 5, 6 };
List<int> evens = numbers.FindAll(isEven); // [2, 4, 6]
```

### Type-parameter limits

`Func<>` overloads `TResult` ke saath **0 se 16 input parameters** tak support karte hain (`Func<TResult>`, `Func<T1, TResult>`, ... `Func<T1, ..., T16, TResult>`). `Action<>` similarly **0 se 16 parameters** tak (`Action`, `Action<T1>`, ... `Action<T1, ..., T16>`). `Predicate<T>` sirf **ek** parameter leta hai — ye generalize nahi hota, sirf single-argument, bool-returning case ke liye hai.

### Kab kaunsa use karo — decision guide

- **Return value chahiye?** → `Func<...>`
- **Kuch return nahi karna, sirf action perform karni hai** (logging, printing, side-effect) → `Action<...>`
- **Ek value ko test karke true/false decide karna hai, especially filtering context me** → `Predicate<T>` (though `Func<T, bool>` bhi functionally identical hai — `Predicate<T>` sirf legacy `List<T>` methods jaise `FindAll`/`RemoveAll`/`Find` ke saath zyada dikhta hai; naya LINQ code mostly `Func<T, bool>` use karta hai, e.g. `Where(x => ...)`)

Practically, modern C# code me `Predicate<T>` kam dikhta hai — LINQ ke `Where`, `Any`, `All` sab `Func<T, bool>` expect karte hain, `Predicate<T>` nahi. `Predicate<T>` mostly `List<T>` ke older methods (`FindAll`, `Find`, `RemoveAll`, `Exists`) ke signature me reh gaya hai, historical reasons se.

### Custom delegate ki zaroorat kab padti hai

Agar tumhe `ref`/`out` parameters chahiye, ya delegate ka naam khud documentation ki tarah kaam kare (jaise `public delegate bool ValidationRule(Order order)` — naam se hi samajh aata hai ye kya karta hai), tab custom delegate declare karna better hai. Warna, `Func<>`/`Action<>` almost hamesha sufficient hain, aur naya custom type declare karna unnecessary boilerplate hai.

</Hinglish>

## Real World Example

<RealWorld company="Microsoft">

LINQ poora ka poora `Func<>` delegates ke upar built hai — `Where(Func<T, bool> predicate)`, `Select(Func<T, TResult> selector)`, `OrderBy(Func<T, TKey> keySelector)`. Microsoft ne LINQ design karte waqt custom delegate types (jaise `WherePredicate<T>`) declare karne ke bajaye consistently `Func<>` use kiya — isse poori LINQ API surface ek predictable, familiar pattern follow karti hai.

</RealWorld>

<RealWorld company="An Indian E-commerce Backend">

Ek order-processing service me, ek `List<Order>.FindAll(Predicate<Order>)` call use ho raha tha purane codebase me — jab team ne LINQ `Where(Func<Order, bool>)` me migrate kiya performance aur consistency ke liye, dono syntactically almost identical lambda accept karte the (`o => o.Status == "Pending"`), sirf return type ka wrapper alag tha. Ye migration bina kisi business-logic change ke ho gayi, kyunki `Predicate<T>` aur `Func<T, bool>` functionally equivalent hain.

</RealWorld>

## Numbers That Matter

<Numbers>

- `Func<>`: 0 se 16 input parameters tak overloads (`Func<TResult>` se `Func<T1...T16, TResult>` tak)
- `Action<>`: similarly 0 se 16 parameters tak (`Action` se `Action<T1...T16>` tak)
- `Predicate<T>`: sirf 1 parameter, hamesha `bool` return — generalize nahi hota
- Sab .NET Framework 3.5 (2007) se available hain, `System` namespace me
- `Predicate<T>` functionally identical `Func<T, bool>` ke — sirf naam/history alag hai
- LINQ ke almost sab methods `Func<>` expect karte hain, `Predicate<T>` sirf legacy `List<T>` methods me dikhta hai

</Numbers>

## Interview Angle

<InterviewAngle>

"`Func`, `Action`, aur `Predicate` me kya fark hai?" ka crisp answer: "Teeno built-in generic delegates hain jo custom delegate declare karne ki zaroorat khatam karte hain. `Func<..., TResult>` value return karta hai — last type parameter return type hai. `Action<...>` `void` return karta hai — sab type parameters input hain, koi return-type slot nahi. `Predicate<T>` `Func<T, bool>` ka special-named version hai, sirf ek parameter leta hai, filtering ke liye — mostly `List<T>`'s legacy methods (`FindAll`, `Find`) me dikhta hai, jabki modern LINQ code `Func<T, bool>` directly use karta hai (`Where`)." Likely follow-up: "kab custom delegate banaoge in built-ins ke bajaye?" — answer: jab `ref`/`out` chahiye, ya method signature khud self-documenting hona chahiye (jaise domain-specific naam).

</InterviewAngle>

## Common Mistakes

<Mistake>

`Func<>` ke type parameters ka order galat samajhna — last parameter hamesha return type hai, ye bhoolna aur socha `Func<int, int, int>` ka pehla parameter return type hai.

</Mistake>

<Mistake>

`Action<>` ke saath kuch return karne ki koshish karna — `Action` sirf `void`-returning methods ke liye hai, agar return value chahiye to `Func<>` use karna zaroori hai.

</Mistake>

<Mistake>

`Predicate<T>` ko multi-parameter banane ki koshish karna — `Predicate<T>` sirf single-argument case ke liye design hua hai, generalize nahi hota jaise `Func<>`/`Action<>`.

</Mistake>

<Mistake>

Har jagah `Func<>`/`Action<>` use karna chahe method signature domain-specific naam se zyada readable hota — bahut generic parameter lists (jaise `Func<decimal, decimal, decimal, bool>`) khud kuch explain nahi karte, ek named delegate ya method group better hota interview-quality code ke liye.

</Mistake>

## Quick Revision

<QuickRevision>

- `Func<T1, ..., TResult>` — returns a value, last type parameter is the return type, 0-16 inputs supported
- `Action<T1, ...>` — returns void, all type parameters are inputs, 0-16 supported
- `Predicate<T>` — single parameter, always returns bool, functionally same as `Func<T, bool>`
- All three are built-in `System` namespace generic delegates since .NET Framework 3.5
- LINQ methods (`Where`, `Select`, `OrderBy`) use `Func<>`; `Predicate<T>` mostly survives in `List<T>`'s legacy methods
- None of the three support `ref`/`out` parameters — declare a custom delegate if you need those
- Prefer a custom named delegate when the signature is domain-specific enough that a name adds real clarity

</QuickRevision>
