<SimpleDefinition>

`Queue<T>` is a FIFO (first-in-first-out) collection with `O(1)` `Enqueue`/`Dequeue`; `Stack<T>` is a LIFO (last-in-first-out) collection with `O(1)` `Push`/`Pop`; `LinkedList<T>` is a doubly-linked list offering `O(1)` insertion/removal at any known node, trading away `List<T>`'s `O(1)` indexed access for that middle-of-the-sequence flexibility.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Teen aur collections jo bahut common hain, especially algorithmic aur systems-level interview questions me — `Queue<T>`, `Stack<T>`, aur `LinkedList<T>`. In teeno ka common thread hai: ordering semantics jo `List<T>` explicitly nahi deta.

### `Queue<T>` — FIFO, "pehle aaya, pehle gaya"

Ek line me lagne jaisa — jo pehle line me lagta hai, wahi pehle serve hota hai.

```csharp
Queue<string> tickets = new Queue<string>();
tickets.Enqueue("Ticket-1");
tickets.Enqueue("Ticket-2");
tickets.Enqueue("Ticket-3");

string next = tickets.Dequeue(); // "Ticket-1" — jo pehle aaya
Console.WriteLine(tickets.Peek()); // "Ticket-2" — dekh lo bina remove kiye
Console.WriteLine(tickets.Count);  // 2
```

`Enqueue`/`Dequeue` dono `O(1)` hain (internally ek circular buffer array use hota hai — na to front se shift karna padta hai, na naya allocate karna padta hai har baar). Real use case: task processing queues, print queues, BFS (Breadth-First Search) graph traversal, message queues ka in-memory equivalent.

### `Stack<T>` — LIFO, "aakhri aaya, pehle gaya"

Plates ke dher jaisa — sabse upar wali plate (jo sabse aakhri rakhi gayi) sabse pehle uthai jaati hai.

```csharp
Stack<string> history = new Stack<string>();
history.Push("Page A");
history.Push("Page B");
history.Push("Page C");

string back = history.Pop(); // "Page C" — jo sabse aakhri gaya
Console.WriteLine(history.Peek()); // "Page B"
```

`Push`/`Pop` dono `O(1)`. Real use case: browser back-button history, undo/redo functionality, function call stack (compiler/runtime khud stack use karta hai), DFS (Depth-First Search) graph traversal, expression evaluation (parentheses matching).

### `LinkedList<T>` — doubly-linked, O(1) middle insertion/deletion

`List<T>` array-based hai — kisi bhi element ko beech me insert/remove karna `O(n)` hai (baaki sab elements shift karne padte hain). `LinkedList<T>` bilkul alag data structure hai — har element (`LinkedListNode<T>`) ke paas apne agle aur pichhle node ka reference hota hai. Agar tumhare paas already kisi node ka reference hai, us jagah insert/remove `O(1)` hai — koi shifting nahi.

```csharp
LinkedList<int> ll = new LinkedList<int>();
LinkedListNode<int> first = ll.AddFirst(10);
LinkedListNode<int> second = ll.AddAfter(first, 20);
ll.AddBefore(second, 15);
// Sequence: 10 -> 15 -> 20

ll.AddLast(30);
// 10 -> 15 -> 20 -> 30

ll.Remove(second); // O(1) — sirf pointers relink karne padte hain, koi shifting nahi
// 10 -> 15 -> 30
```

**Trade-off:** `LinkedList<T>` me index-based access (`list[i]`) exist hi nahi karta — kisi bhi position tak pahunchne ke liye front (ya back) se traverse karna padta hai, `O(n)`. Ye `List<T>` ke bilkul ulta trade-off hai — `List<T>` fast indexed access deta hai lekin slow middle-insertion, `LinkedList<T>` fast middle-insertion deta hai (agar node reference already ho) lekin koi indexed access hi nahi.

### Kab `LinkedList<T>` genuinely use karna chahiye

Practically, interview me sabse honest answer ye hai: **zyaadatar business applications me `LinkedList<T>` rarely actually needed hota hai.** `List<T>` ka amortized-O(1) `Add` (end me) aur cache-friendly contiguous memory usually better real-world performance deta hai chhote-medium datasets pe, chahe theoretical complexity `LinkedList<T>` favor kare. `LinkedList<T>` genuinely tab valuable hai jab: frequent insertions/deletions ho rahi hon KNOWN positions pe (node reference already hath me ho), aur dataset itna bada ho ki `List<T>`'s O(n) shifting genuinely bottleneck ban rahi ho.

</Hinglish>

## Real World Example

<RealWorld company="Microsoft">

.NET ka `System.Threading.Channels` (producer-consumer messaging) aur ASP.NET Core ka internal request-processing pipeline dono FIFO-ordering-dependent scenarios me `Queue<T>`-jaisi semantics use karte hain — jaha order preserve karna functionally zaroori hai (jaise incoming HTTP requests ko unke arrival order me hi process karna kai middleware scenarios me expected hai).

</RealWorld>

<RealWorld company="An Indian Food Delivery App">

Ek delivery-assignment service me incoming orders ko FIFO order me riders ko assign karna tha (fairness ke liye — jo order pehle aaya, use pehle assign priority milni chahiye). Team ne `Queue<Order>` use kiya jo exactly ye guarantee deta hai. Alag se, app ke andar "recently viewed restaurants" feature ke liye `Stack<Restaurant>`-jaisi LIFO logic use hui — sabse recently viewed restaurant sabse upar dikhta hai, jo natural Push/Pop semantics se match karta hai.

</RealWorld>

## Numbers That Matter

<Numbers>

- `Queue<T>.Enqueue()`/`Dequeue()` — both `O(1)`, internally circular buffer array
- `Stack<T>.Push()`/`Pop()` — both `O(1)`, internally a resizable array (top-of-stack at the end)
- `LinkedList<T>` insertion/removal at a KNOWN node — `O(1)`
- `LinkedList<T>` indexed access — does not exist as a direct operation; traversal to a position is `O(n)`
- `List<T>` insertion/removal in the middle — `O(n)` (shifting), vs `LinkedList<T>`'s `O(1)` at a known node
- `Peek()` on Queue/Stack — `O(1)`, does not remove the element

</Numbers>

## Interview Angle

<InterviewAngle>

"`Queue<T>` aur `Stack<T>` me kya fark hai, aur `LinkedList<T>` inse kaise alag hai?" ka strong answer: "`Queue<T>` FIFO hai — jo pehle aaya wahi pehle nikalta hai, `Enqueue`/`Dequeue` dono O(1). `Stack<T>` LIFO hai — jo aakhri aaya wahi pehle nikalta hai, `Push`/`Pop` dono O(1). Dono ke API deliberately restricted hain — sirf ends pe access allowed hai, jo unki respective ordering guarantee ko enforce karta hai. `LinkedList<T>` in dono se alag hai — ye ek general-purpose doubly-linked sequence hai jahan kisi bhi KNOWN node par O(1) insertion/removal ho sakta hai, lekin index-based access List ki tarah exist nahi karta — kisi position tak pahunchne ke liye traverse karna padta hai." Follow-up jo aksar aata hai: "practically `LinkedList<T>` kab use karoge?" — honest answer: rarely, kyunki `List<T>` ka contiguous memory usually better real-world performance deta hai; `LinkedList<T>` sirf tab valuable hai jab frequent known-position insertions ho aur dataset genuinely bada ho.

</InterviewAngle>

## Common Mistakes

<Mistake>

`Queue<T>`/`Stack<T>` me beech ke element ko directly access/modify karne ki koshish karna — ye API deliberately restricted hai, sirf `Peek`/`Dequeue`/`Pop` (ends pe) allowed hain. Beech ka access chahiye to ye galat data structure hai.

</Mistake>

<Mistake>

`LinkedList<T>` ko `List<T>` se hamesha "better" samajh lena kyunki O(1) insertion deta hai — ye sirf KNOWN-position insertion ke liye true hai. Real-world me `List<T>`'s cache locality aur amortized-O(1) end-append usually behtar performance deta hai chhote-medium data pe.

</Mistake>

<Mistake>

Empty `Queue<T>`/`Stack<T>` pe `Dequeue()`/`Pop()` call karna bina `Count > 0` check kiye ya `TryDequeue`/`TryPop` use kiye — `InvalidOperationException` throw hoga.

</Mistake>

<Mistake>

`LinkedList<T>` me index se access karne ki koshish karna (`linkedList[2]` jaisa syntax) — `LinkedList<T>` indexer support hi nahi karta, sirf `First`/`Last`/traversal (foreach) available hai.

</Mistake>

<Mistake>

`Stack<T>` ko FIFO samajh lena (Queue jaisa) — ye ek common naming-confusion hai. Stack LIFO hai, Queue FIFO hai — dono opposite ordering dete hain.

</Mistake>

## Quick Revision

<QuickRevision>

- `Queue<T>` — FIFO, `Enqueue`/`Dequeue`/`Peek`, all `O(1)`
- `Stack<T>` — LIFO, `Push`/`Pop`/`Peek`, all `O(1)`
- `LinkedList<T>` — doubly-linked, `O(1)` insert/remove at a known node, but no indexed access (`O(n)` traversal)
- `List<T>` shifts elements on middle insert/remove (`O(n)`); `LinkedList<T>` just relinks pointers (`O(1)` at a known node)
- Use `TryDequeue`/`TryPop` to avoid `InvalidOperationException` on an empty collection
- Real use cases: Queue for BFS/task processing, Stack for DFS/undo-redo/browser history
- `LinkedList<T>` is rarely the right first choice in typical business code — `List<T>`'s cache locality usually wins in practice

</QuickRevision>
