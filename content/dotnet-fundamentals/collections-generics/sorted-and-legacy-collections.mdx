<SimpleDefinition>

`SortedList`, `SortedDictionary`, and `SortedSet` automatically maintain elements in sorted key/value order (`O(log n)` operations, tree or hybrid-array-backed internally); `ArrayList` and `Hashtable` are the pre-generics, non-generic collections that store everything as `object`, forcing value types to box on every insert and losing all compile-time type safety — avoided in new code.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Is topic me do genuinely alag families cover karenge — sorted collections (jo aaj bhi useful hain) aur legacy non-generic collections (jo aaj bilkul avoid karni chahiye, lekin interview me "in me kya galat hai" poocha jaata hai).

### Sorted collections — automatic order maintenance

`Dictionary`/`HashSet` koi ordering guarantee nahi dete. Jab tumhe key ya value ke basis pe hamesha-sorted order chahiye ho — bina manually `OrderBy` call kiye har baar — teen options hain.

**`SortedDictionary<TKey,TValue>`** — internally ek self-balancing binary search tree (red-black tree). Insert/lookup/delete sab `O(log n)`.

```csharp
var scores = new SortedDictionary<string, int>();
scores["Charlie"] = 70;
scores["Alice"] = 95;
scores["Bob"] = 80;

foreach (var kvp in scores) // Automatically key-order me: Alice, Bob, Charlie
{
    Console.WriteLine($"{kvp.Key}: {kvp.Value}");
}
```

**`SortedList<TKey,TValue>`** — internally do parallel ARRAYS (keys aur values), sorted maintained rakhe jaate hain. Insert/delete `O(n)` (kyunki array me sahi sorted position pe insert karna shifting maangta hai), lekin index-based access (`GetByIndex`) `O(log n)` binary search se ho sakta hai, aur memory footprint `SortedDictionary` se kam hai (tree-node overhead nahi).

**`SortedSet<T>`** — `HashSet` ka sorted version, internally bhi tree-based, `O(log n)` operations, automatic uniqueness bhi.

**Kab kaunsa:** `SortedDictionary` — frequent inserts/deletes ho rahe hon (tree insert `O(log n)` hai, array-shift nahi). `SortedList` — mostly read-heavy after initial population, aur memory footprint priority ho (array-based, less per-item overhead). `SortedSet` — sorted unique elements chahiye, koi associated value nahi.

### Legacy non-generic collections — `ArrayList` aur `Hashtable`

Ye C# 1.0 (generics se pehle) ke collections hain. Dono **`object`** store karte hain, kisi bhi specific type ke bajaye.

```csharp
ArrayList list = new ArrayList();
list.Add(5);      // int -> object: BOXED (heap allocation)
list.Add("text"); // string -> object: no boxing needed (already reference type)
list.Add(5.5);    // double -> object: BOXED

int x = (int)list[0]; // Manual cast REQUIRED — compiler doesn't know the type
```

**Do genuine problems, dono interview me poochhe jaate hain:**

1. **Boxing overhead.** Jab bhi ek value type (`int`, `double`, `struct`) `ArrayList`/`Hashtable` me store hota hai, wo heap pe box hota hai — ek extra allocation, extra indirection, extra GC pressure. `List<int>` me ye zero hai — value directly, unboxed store hoti hai.
2. **No compile-time type safety.** `ArrayList` me kisi bhi type ko daala ja sakta hai — compiler kabhi warn nahi karega agar tum galti se `int` list me `string` daal do. Runtime pe cast karte waqt `InvalidCastException` milta hai — bahut late pakda jaata hai bug.

`Hashtable` bhi same problem — key aur value dono `object` hain, isliye same boxing aur type-safety issues.

```csharp
Hashtable table = new Hashtable();
table["age"] = 30; // int boxed
int age = (int)table["age"]; // manual cast, runtime risk agar galat type ho
```

### Aaj in legacy collections ka use kab hota hai (rare cases)

Practically, naya code kabhi bhi `ArrayList`/`Hashtable` se shuru nahi hota — generics ke aane ke baad (C# 2.0, 2005) inka koi valid new-code use case nahi bacha. Interview me isse zyada ye poocha jaata hai "kyun avoid karna chahiye," na ki "kab use karna chahiye." Ek genuinely valid case: bahut purana legacy codebase jisme already `ArrayList`/`Hashtable` use ho raha hai aur interop maintain karna hai — us case me bhi long-term goal generics me migrate karna hi hota hai.

</Hinglish>

## Real World Example

<RealWorld company="Microsoft">

.NET Framework 1.0/1.1 (pre-generics era, 2002-2003) ka poora BCL `ArrayList`/`Hashtable` pe based tha — is era ke legacy enterprise .NET applications me aaj bhi ye collections dikhti hain. Microsoft ne generics (C# 2.0, 2005) aane ke turant baad `List<T>`/`Dictionary<TKey,TValue>` ko default guidance bana diya, aur `ArrayList`/`Hashtable` ko effectively "legacy, avoid in new code" mark kar diya — docs me explicitly ye recommendation likhi hai.

</RealWorld>

<RealWorld company="An Indian Insurance Legacy System Migration">

Ek 15-saal purani .NET Framework 1.1 se migrated insurance policy system me `Hashtable`-based policy-lookup code tha. Migration ke time, har `Hashtable` ko `Dictionary<string, Policy>` me convert karne se do fayde hue: (1) sabhi manual casts (`(Policy)table[key]`) khatam ho gaye, compile-time type safety mil gayi, jisse migration ke dauraan hi kai latent type-mismatch bugs pakde gaye; (2) production me measurable GC pressure kam hua kyunki high-volume lookups me boxing khatam ho gayi.

</RealWorld>

## Numbers That Matter

<Numbers>

- `SortedDictionary<TKey,TValue>` — red-black tree, `O(log n)` insert/lookup/delete
- `SortedList<TKey,TValue>` — two parallel sorted arrays, `O(n)` insert/delete, `O(log n)` indexed lookup (binary search)
- `SortedSet<T>` — tree-based, `O(log n)` operations, automatic uniqueness
- `ArrayList`/`Hashtable` — introduced .NET 1.0 (2002), effectively superseded by generics (C# 2.0, 2005)
- Every value-type `Add` into `ArrayList`/`Hashtable` — one extra heap allocation (boxing)
- Type mismatch: generic collection = compile error; `ArrayList`/`Hashtable` = runtime `InvalidCastException`

</Numbers>

## Interview Angle

<InterviewAngle>

"`ArrayList`/`Hashtable` ko aaj kyun avoid karna chahiye?" ka strong answer: "Do genuine problems hain — pehla, ye `object` store karte hain, isliye har value type add karne par boxing hoti hai, jo extra heap allocation aur GC pressure add karta hai; generic collections (`List<T>`) me ye zero hai. Doosra, koi compile-time type safety nahi — kisi bhi type ko kisi bhi `ArrayList` me daala ja sakta hai, mismatch sirf runtime pe `InvalidCastException` ke roop me pakda jaata hai, jo bahut late hai. Generics (C# 2.0) ne dono problems solve kar diye, isliye naya code kabhi in legacy collections se shuru nahi hota." Follow-up: "`SortedList` aur `SortedDictionary` me kab kaunsa?" — answer: frequent inserts/deletes ke liye `SortedDictionary` (tree-based, O(log n) insert), memory-conscious read-heavy scenarios ke liye `SortedList` (array-based, kam overhead).

</InterviewAngle>

## Common Mistakes

<Mistake>

Naye C# code me `ArrayList`/`Hashtable` use karna "purane habit" ki wajah se — in dono ka koi valid reason nahi bacha hai generics ke baad, sirf legacy-interop scenarios chhod kar.

</Mistake>

<Mistake>

`SortedList` ko frequent-insertion-heavy scenario me use karna — iska insert `O(n)` hai (array shifting), `SortedDictionary` (tree-based, `O(log n)` insert) us case me better fit hai.

</Mistake>

<Mistake>

Ye maan lena ki `Dictionary`/`HashSet` bhi sorted order maintain karte hain "kyunki mostly aisa dikhta hai" — ye guaranteed nahi hai. Sorted order chahiye to explicitly `SortedDictionary`/`SortedSet` use karo.

</Mistake>

<Mistake>

`ArrayList` se cast karte waqt galat type assume karna — `(int)list[0]` agar actual element `string` nikla to `InvalidCastException` runtime pe aayega, compiler kuch nahi bata sakta pehle se.

</Mistake>

<Mistake>

Boxing ke performance impact ko underestimate karna — high-volume, tight-loop scenarios me `ArrayList`/`Hashtable` ka boxing overhead genuinely measurable GC pressure create kar sakta hai, sirf "theoretical" concern nahi hai.

</Mistake>

## Quick Revision

<QuickRevision>

- `SortedDictionary<TKey,TValue>` — red-black tree, `O(log n)` all core operations
- `SortedList<TKey,TValue>` — parallel sorted arrays, `O(n)` insert/delete, `O(log n)` indexed lookup, lower memory overhead
- `SortedSet<T>` — sorted, unique, tree-based, `O(log n)`
- `ArrayList`/`Hashtable` — pre-generics, store `object`, box every value type, zero compile-time type safety
- Type mismatch: `List<T>`/`Dictionary` catch it at compile time; `ArrayList`/`Hashtable` throw `InvalidCastException` at runtime
- `Dictionary`/`HashSet` do NOT guarantee sorted or stable order — use the Sorted* variants when order matters
- New code should never start with `ArrayList`/`Hashtable` — generics fully supersede them

</QuickRevision>
