<SimpleDefinition>

`IEnumerable<T>` is the minimal, read-only, forward-only iteration contract; `ICollection<T>` adds `Count` and mutation (`Add`/`Remove`/`Clear`); `IList<T>` adds index-based access and insertion — each interface in this chain is a strict superset of capability over the one before it, and `IQueryable<T>` is a separate branch built for expression-tree-based query providers like EF Core rather than in-memory iteration.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

`List<T>` khud implement karta hai `IList<T>`, `ICollection<T>`, `IEnumerable<T>` — sab ek saath. Interview me poocha jaata hai ki inme se **kaunsa interface method parameter ke roop me accept karna chahiye**, aur kyun. Ye "accept the least-specific interface you need" principle ka concrete C# example hai.

### `IEnumerable<T>` — sabse basic, sirf iterate karo

Sirf ek method deta hai: `GetEnumerator()`. Isse tum sirf `foreach` kar sakte ho — read-only, forward-only, ek baar me ek element.

```csharp
public interface IEnumerable<T> : IEnumerable
{
    IEnumerator<T> GetEnumerator();
}
```

Koi `Count`, koi index access, koi mutation — sirf iteration. Ye sabse LEAST capable interface hai collection chain me.

### `ICollection<T>` — iteration + count + mutation

`IEnumerable<T>` ko extend karta hai, plus `Count`, `Add`, `Remove`, `Clear`, `Contains` deta hai.

```csharp
public interface ICollection<T> : IEnumerable<T>
{
    int Count { get; }
    bool IsReadOnly { get; }
    void Add(T item);
    bool Remove(T item);
    void Clear();
    bool Contains(T item);
}
```

Ab tum size jaan sakte ho aur mutate kar sakte ho, lekin abhi bhi koi index-based access nahi — `collection[2]` valid nahi hai `ICollection<T>` type ke variable pe.

### `IList<T>` — index-based access aur insertion

`ICollection<T>` ko extend karta hai, plus indexer (`this[int index]`) aur `Insert`/`RemoveAt` deta hai.

```csharp
public interface IList<T> : ICollection<T>
{
    T this[int index] { get; set; }
    int IndexOf(T item);
    void Insert(int index, T item);
    void RemoveAt(int index);
}
```

Ab poori `List<T>`-jaisi capability hai — index se read/write, position-based insert/remove.

### `IQueryable<T>` — ek alag branch, expression trees ke liye

`IQueryable<T>` `IEnumerable<T>` extend karta hai, lekin fundamentally alag purpose ke liye — ye **expression trees** build karta hai (code as data) jo ek query provider (jaise EF Core) SQL me translate karta hai, execution database pe hoti hai. `IEnumerable<T>` LINQ (LINQ to Objects) memory me filter karta hai, delegates ke through. Ye topic `linq-fundamentals` module me detail se cover hota hai — yahan sirf itna samajhna kaafi hai ki `IQueryable<T>` collection-hierarchy ka mutation-capability branch nahi hai, ek query-capability branch hai.

### "Accept the least-specific interface you need" — ye interview ka asli point hai

Method parameter type choose karte waqt, jo interface tumhare method ko genuinely chahiye, sirf wahi accept karo — no more.

```csharp
// GALAT — zaroorat se zyada specific, caller ko force karta hai ek List<T> hi pass kare
public void PrintAll(List<string> items)
{
    foreach (var item in items) Console.WriteLine(item);
}

// SAHI — sirf iteration chahiye, isliye sabse kam-specific interface accept karo
public void PrintAll(IEnumerable<string> items)
{
    foreach (var item in items) Console.WriteLine(item);
}
```

`PrintAll(IEnumerable<string> items)` ab `List<string>`, `string[]`, `HashSet<string>`, `Queue<string>`, ya ek LINQ query result — sab accept kar sakta hai, kyunki ye sab `IEnumerable<T>` implement karte hain. Agar method ne `List<T>` maanga, caller forcefully ek `List<T>` allocate/convert karne pe majboor hota, chahe uske paas already ek `array` ya `HashSet` ho.

Ulta bhi sach hai — agar method ko genuinely `Add`/`Remove` chahiye, `ICollection<T>` accept karo, sirf `IEnumerable<T>` mat lo (jo mutate nahi karne deta). Sahi interface **exactly utni capability expose karta hai jitni method ko chahiye** — na kam, na zyada.

</Hinglish>

<Tradeoff
  pros={["Accepting a less-specific interface (IEnumerable<T>) maximizes caller flexibility — any collection type works", "Accepting a more-specific interface (IList<T>) when genuinely needed gives compile-time guarantees for indexing/mutation"]}
  cons={["Too-generic a parameter type (IEnumerable<T>) when you actually need Count or indexing forces awkward workarounds (like calling .Count() repeatedly, an O(n) LINQ operation, vs a cheap .Count property)", "Too-specific a parameter type (List<T>) unnecessarily restricts what callers can pass"]}

## Real World Example

<RealWorld company="Microsoft">

.NET ki LINQ extension methods (`Where`, `Select`, `OrderBy`, etc.) sab `IEnumerable<T>` (ya `IQueryable<T>`) pe defined hain, `List<T>` ya kisi specific collection type pe nahi — ye exactly is principle ka sabse bada real-world example hai: LINQ ko sirf iteration capability chahiye, isliye ye sabse kam-specific interface accept karta hai, jisse ye literally kisi bhi collection type pe kaam kar jaata hai.

</RealWorld>

<RealWorld company="An Indian Logistics Reporting Service">

Ek reporting module me ek `GenerateReport(List<Shipment> shipments)` method tha. Jab team ne isse `GenerateReport(IEnumerable<Shipment> shipments)` me refactor kiya, kai jagah caller code simplify ho gaya — jahan pehle `.ToList()` explicitly call karna padta tha sirf method-signature satisfy karne ke liye (chahe caller ke paas already ek `IQueryable<Shipment>` from EF Core ho), ab directly pass ho sakta tha, aur kai cases me unnecessary premature database materialization bhi avoid ho gayi.

</RealWorld>

## Numbers That Matter

<Numbers>

- Hierarchy: `IEnumerable<T>` → `ICollection<T>` → `IList<T>` — each is a strict superset of the one before
- `IEnumerable<T>` — 1 method (`GetEnumerator`), the minimal contract
- `ICollection<T>` — adds `Count`, `Add`, `Remove`, `Clear`, `Contains`, `IsReadOnly`
- `IList<T>` — adds indexer, `IndexOf`, `Insert`, `RemoveAt`
- `IQueryable<T>` — separate branch, expression-tree-based, used by EF Core and other out-of-process query providers
- `List<T>` implements all three (`IEnumerable<T>`, `ICollection<T>`, `IList<T>`) simultaneously

</Numbers>

## Interview Angle

<InterviewAngle>

"Method parameter ke liye `IEnumerable<T>`, `ICollection<T>`, ya `IList<T>` — kaunsa accept karoge?" ka strong answer: "Principle simple hai — accept the least-specific interface tumhare method ko genuinely chahiye. Agar sirf iterate karna hai, `IEnumerable<T>` lo — ye caller ko maximum flexibility deta hai, koi bhi collection type (array, List, HashSet, ya LINQ query result) pass ho sakta hai bina conversion ke. Agar `Count` ya mutation chahiye, `ICollection<T>` lo. Agar index-based access ya position-based insert chahiye, `IList<T>` lo. `List<T>` ko directly parameter type banana over-restrictive hai — caller ko forcefully convert karna padta hai chahe uske paas already koi doosra compatible collection ho." Follow-up jo aksar aata hai: "`IQueryable<T>` `IEnumerable<T>` se kaise alag hai?" — answer: `IEnumerable<T>` in-memory delegate-based filtering karta hai, `IQueryable<T>` expression trees banata hai jo ek provider (jaise EF Core) SQL me translate karta hai.

</InterviewAngle>

## Common Mistakes

<Mistake>

Method parameters ko hamesha `List<T>` banana, chahe method ko sirf iteration chahiye ho — ye caller ki flexibility unnecessarily restrict karta hai, forcing conversions jo avoidable thi.

</Mistake>

<Mistake>

`IEnumerable<T>` type ke variable pe `.Count` property access karne ki koshish karna — `IEnumerable<T>` me `Count` exist hi nahi karta (LINQ ka `.Count()` extension method hai, jo poori collection enumerate karke count karta hai, `O(n)`, `ICollection<T>`'s `.Count` property jitna fast nahi jo typically `O(1)`).

</Mistake>

<Mistake>

`IEnumerable<T>` ko multiple baar enumerate karna bina samjhe ki underlying source ek deferred LINQ query ho sakta hai — har enumeration re-execute ho sakta hai (especially `IQueryable<T>` ke saath, jahan har enumeration ek naya database round-trip ho sakta hai).

</Mistake>

<Mistake>

`IQueryable<T>` aur `IEnumerable<T>` ko interchangeable samajhna — dono `IEnumerable<T>`-compatible dikhte hain lekin execution model bilkul alag hai (in-memory vs provider-translated).

</Mistake>

<Mistake>

Ek method ko `ICollection<T>` accept karwana jabki wo sirf iterate karta hai, kabhi mutate nahi karta — ye bhi over-specification hai, sirf ulti direction me (bahut kam-specific interfaces ki tarah bahut zyada-specific bhi galat hai).

</Mistake>

## Quick Revision

<QuickRevision>

- `IEnumerable<T>` — minimal, read-only, forward-only iteration (`GetEnumerator` only)
- `ICollection<T>` — adds `Count`, `Add`, `Remove`, `Clear`, `Contains`
- `IList<T>` — adds indexer, `IndexOf`, `Insert`, `RemoveAt`
- `IQueryable<T>` — separate branch, expression-tree-based, for providers like EF Core (SQL translation), not in-memory mutation
- Accept the LEAST-specific interface your method genuinely needs — maximizes caller flexibility
- `IEnumerable<T>` has no `.Count` property — LINQ's `.Count()` on it is `O(n)`, unlike `ICollection<T>.Count` which is typically `O(1)`
- `List<T>` implements `IEnumerable<T>`, `ICollection<T>`, and `IList<T>` all at once

</QuickRevision>
