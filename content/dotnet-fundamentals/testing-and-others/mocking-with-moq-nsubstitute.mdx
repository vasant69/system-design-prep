<SimpleDefinition>

Moq and NSubstitute are the two most widely used .NET mocking libraries for creating fake implementations of interfaces at test time — they solve the same problem (substituting a real dependency with a controllable fake), differing mainly in syntax style: Moq's explicit Setup/Verify API versus NSubstitute's more natural, direct-call-style syntax.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

`unit-testing-oop-moq-xunit` topic me already dekha ki DI aur interfaces mocking ko possible banate hain, aur Moq ka basic usage dikhaya gaya. Yahan focus hai — Moq vs NSubstitute same mock setup ko kaise likhte hain, aur teams ek ke bajaye doosra kyun choose karti hain.

### Same scenario — dono libraries se

Socho ek `IEmailService` interface hai jise `OrderService` use karta hai. Test me hume ye verify karna hai ki `SendConfirmation` call hua jab order place hua.

**Moq — explicit Setup/Verify style:**

```csharp
var mockEmailService = new Mock<IEmailService>();
mockEmailService
    .Setup(x => x.SendConfirmation(It.IsAny<string>()))
    .Returns(true);

var orderService = new OrderService(mockEmailService.Object);
orderService.PlaceOrder(order);

mockEmailService.Verify(x => x.SendConfirmation(order.CustomerEmail), Times.Once);
```

Moq me tumhe explicitly `.Object` property access karke actual instance nikalni padti hai (mock khud `IEmailService` nahi hai, `Mock<IEmailService>` hai — `.Object` uska underlying fake implementation deta hai), `Setup` se behavior define karte ho, `Verify` se interaction assert karte ho.

**NSubstitute — direct call-style syntax:**

```csharp
var emailService = Substitute.For<IEmailService>();
emailService.SendConfirmation(Arg.Any<string>()).Returns(true);

var orderService = new OrderService(emailService);
orderService.PlaceOrder(order);

emailService.Received(1).SendConfirmation(order.CustomerEmail);
```

NSubstitute me `Substitute.For<IEmailService>()` seedha ek object return karta hai jo `IEmailService` hi hai (koi `.Object` wrapper nahi chahiye), setup ek natural method-call jaisa dikhta hai (`emailService.SendConfirmation(...).Returns(...)`), aur verification `Received(1)` ke through hoti hai — syntax jo real method call jaisa padhta hai.

### Konsa prefer karein — mostly readability aur team taste

Functionally dono equally capable hain — same features (return values, exceptions throw karwana, call-count verification, argument matchers, callback support) dono deti hain. Difference primarily **syntax philosophy** me hai:

- **Moq**: explicit, verbose, thoda zyada "ceremony" (`.Object`, `Setup`, `It.IsAny<T>()`) — lekin ye explicitness kabhi kabhi clarity deti hai ki "ye ek mock hai," especially bade teams me jo naye developers onboard karte rehte hain.
- **NSubstitute**: concise, "reads like real code" — kam boilerplate, lekin kuch developers ko lagta hai ki mock aur real call visually kam distinguishable hai, jo confusion create kar sakta hai bade test files me.

Real-world me ye choice almost hamesha **existing codebase convention** follow karti hai — naya project shuru karte waqt team lead/senior engineers decide karte hain, aur phir consistency maintain ki jaati hai. Interview me "Moq better hai ya NSubstitute" jaisa absolute answer expect nahi hota — trade-off samajhna important hai.

### Mock vs Stub vs Fake — terminology jo aksar confuse hoti hai

Technically **mock** wo hai jiske against tum interactions **verify** karte ho (call hua ya nahi, kitni baar) — jaisa upar `Verify`/`Received` examples me. **Stub** sirf predetermined values return karta hai, koi interaction verification nahi. Practically Moq aur NSubstitute dono se tum dono cheezein kar sakte ho (isliye "mocking library" ek loose umbrella term ban gaya hai), lekin precise terminology interview me appreciate hoti hai — "maine is object ko stub kiya, sirf value return karne ke liye" vs "maine mock kiya, kyunki mujhe verify karna tha ki method call hua."

</Hinglish>

## Numbers That Matter

<Numbers>

- Moq: `new Mock<T>()`, `.Object` for the fake instance, `Setup(...)` for behavior, `Verify(...)` for interaction checks
- NSubstitute: `Substitute.For<T>()` returns the fake directly, `Returns(...)` chained naturally, `Received(n)` for interaction checks
- Both support argument matchers (`It.IsAny<T>()` in Moq, `Arg.Any<T>()` in NSubstitute), callbacks, and exception-throwing setups
- Both are NuGet packages, framework-agnostic — work with xUnit, NUnit, and MSTest equally
- Mock = verifies interactions happened; Stub = only returns canned values, no verification

</Numbers>

## Common Mistakes

<Mistake>

Moq me `mock.Object` bhoolna aur seedha `mock` ko dependency ki tarah pass karne ki koshish karna — `Mock<T>` khud `T` nahi hai, `.Object` property hi actual fake instance deti hai.

</Mistake>

<Mistake>

Setup na kiye gaye method call pe Moq se real value expect karna — agar `Setup` nahi kiya, Moq default (type ka default value, jaise `int` ke liye `0`, reference type ke liye `null`) return karta hai, exception nahi deta — ye silently wrong test results de sakta hai.

</Mistake>

<Mistake>

"Mock" aur "Stub" ko loosely interchange karna interview me — technically different concepts hain (verification vs sirf value-return), precise terminology use karna interview me better impression deta hai.

</Mistake>

<Mistake>

Over-mocking — har single dependency ko mock karna, chhote value objects (jaise DTOs) tak, jab unhe real instance banake use karna zyada simple aur readable hota.

</Mistake>

## Quick Revision

<QuickRevision>

- Moq: `new Mock<T>().Object`, `Setup(...)`, `Verify(...)` — explicit, verbose
- NSubstitute: `Substitute.For<T>()`, chained `Returns(...)`, `Received(n)` — concise, call-style
- Both are functionally equivalent — same core capabilities, different syntax philosophy
- Choice is team convention, not a technical limitation of either library
- Mock = verifies interactions; Stub = only returns canned values, no verification check
- Unsetup method calls in Moq silently return default values, not exceptions — a common source of false-passing tests

</QuickRevision>
