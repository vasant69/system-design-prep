<SimpleDefinition>

Arrange-Act-Assert (AAA) is the standard structure for writing a readable unit test — set up inputs, execute the behavior under test, then verify the outcome; .NET has three mainstream test frameworks (xUnit, NUnit, MSTest) that differ mainly in attribute naming, setup/teardown conventions, and parameterized-test syntax, not in the underlying testing philosophy.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

`oops-dotnet` section me `unit-testing-oop-moq-xunit` topic already cover kar chuka hai ki DI aur interfaces unit testing ko possible banate hain, aur Moq ke saath xUnit ka basic usage. Ye topic uska prerequisite maanta hai — yahan focus do cheezon pe hai jo wahan nahi cover hui: teeno mainstream frameworks ka comparison, aur AAA pattern ko ek general testing principle ki tarah, sirf OOP-mocking ke context se bahar.

### AAA — har achhe unit test ka skeleton

**Arrange** — test ke liye zaroori inputs, objects, mocks set up karo. **Act** — jo behavior test karna hai, wo ek single call/action execute karo. **Assert** — expected outcome verify karo. Ye teeno sections clearly separate rakhna (blank line se bhi) test ko turant readable banata hai — koi bhi developer test padh ke samajh sakta hai "kya test ho raha hai, kaise, aur kya expect kiya ja raha hai" bina poora business logic dobara trace kiye.

```csharp
[Fact]
public void Add_TwoPositiveNumbers_ReturnsSum()
{
    // Arrange
    var calculator = new Calculator();

    // Act
    var result = calculator.Add(2, 3);

    // Assert
    Assert.Equal(5, result);
}
```

Ek test me sirf EK logical assertion-group hona chahiye — agar test failure message se "kya specifically toota" clear na ho, test bahut kuch ek saath test kar raha hai.

### Teeno frameworks — same philosophy, alag syntax

**xUnit** — is site ke `oops-dotnet` examples me already use ho chuka hai, aur naye .NET projects me sabse common default hai. `[Fact]` (parameterless test) aur `[Theory]` + `[InlineData(...)]` (parameterized test) — koi separate `[TestClass]`/`[SetUp]` attribute nahi chahiye, constructor har test se pehle chalta hai (fresh instance per test, isolation built-in), aur `IDisposable.Dispose()` teardown ke liye.

```csharp
public class CalculatorTests
{
    private readonly Calculator _calculator = new(); // constructor = "setup"

    [Theory]
    [InlineData(2, 3, 5)]
    [InlineData(-1, 1, 0)]
    public void Add_VariousInputs_ReturnsExpectedSum(int a, int b, int expected)
    {
        Assert.Equal(expected, _calculator.Add(a, b));
    }
}
```

**NUnit** — purana, mature, `[TestFixture]` class-level attribute chahiye, `[Test]` (parameterless) aur `[TestCase(...)]` (parameterized — xUnit ke `[Theory]`/`[InlineData]` jaisa hi concept, alag naam), `[SetUp]`/`[TearDown]` methods explicitly define karne padte hain (shared instance across tests by default, xUnit ke fresh-instance-per-test se ulta assumption).

```csharp
[TestFixture]
public class CalculatorTests
{
    private Calculator _calculator;

    [SetUp]
    public void Setup() => _calculator = new Calculator();

    [TestCase(2, 3, 5)]
    [TestCase(-1, 1, 0)]
    public void Add_VariousInputs_ReturnsExpectedSum(int a, int b, int expected)
    {
        Assert.That(_calculator.Add(a, b), Is.EqualTo(expected));
    }
}
```

**MSTest** — Microsoft ka own framework, Visual Studio ke saath deeply integrated, `[TestClass]` + `[TestMethod]`, `[DataRow(...)]` parameterization ke liye, `[TestInitialize]`/`[TestCleanup]` setup/teardown ke liye. Enterprise/legacy Microsoft-stack shops me common milta hai, especially jahan Visual Studio Test Explorer ka deep integration priority ho.

```csharp
[TestClass]
public class CalculatorTests
{
    private Calculator _calculator;

    [TestInitialize]
    public void Setup() => _calculator = new Calculator();

    [DataRow(2, 3, 5)]
    [DataRow(-1, 1, 0)]
    [DataTestMethod]
    public void Add_VariousInputs_ReturnsExpectedSum(int a, int b, int expected)
    {
        Assert.AreEqual(expected, _calculator.Add(a, b));
    }
}
```

### Konsa use kare — mostly team convention, kuch genuine differences

xUnit aaj new .NET projects (especially open-source aur greenfield API work) me sabse popular default hai — cleaner attribute model, per-test isolation by default (koi shared mutable state accidentally leak nahi hoti test-to-test), community momentum. NUnit sabse feature-rich assertion library deta hai (`Assert.That` ka fluent constraint model) aur bahut purane .NET Framework codebases me already deeply embedded hai. MSTest ka pick mostly organizational — agar company already Microsoft-stack-first hai aur VS-native tooling priority hai.

Interview me ye batana kaafi hai ki teeno "same job karte hain, syntax/convention alag hai" — deep framework-internals knowledge nahi poocha jaata, lekin "aapki team konsa use karti hai aur kyun" jaisa practical question common hai.

</Hinglish>

<Callout type="tip">

Naming convention jo interview me bhi appreciate hoti hai: `MethodName_Scenario_ExpectedBehavior` (jaise `Add_TwoPositiveNumbers_ReturnsSum`) — test failure list padh ke hi pata chal jaata hai kya specifically break hua, bina test body kholے.

</Callout>

## Numbers That Matter

<Numbers>

- xUnit: `[Fact]` / `[Theory]` + `[InlineData]`, fresh class instance per test (isolation by default)
- NUnit: `[TestFixture]` + `[Test]` / `[TestCase]`, `[SetUp]`/`[TearDown]` explicit
- MSTest: `[TestClass]` + `[TestMethod]` / `[DataRow]` + `[DataTestMethod]`, `[TestInitialize]`/`[TestCleanup]`
- AAA structure: Arrange (setup) → Act (single action) → Assert (verify outcome)
- All three run via `dotnet test` and integrate with Visual Studio Test Explorer / VS Code Test Explorer

</Numbers>

## Interview Angle

<InterviewAngle>

"xUnit, NUnit, aur MSTest me kya difference hai?" ka strong answer: "Teeno same testing philosophy follow karte hain — attributes aur setup/teardown convention me differ karte hain. xUnit `[Fact]`/`[Theory]` use karta hai aur constructor-based setup ke saath per-test isolation deta hai; NUnit `[TestFixture]`/`[Test]`/`[TestCase]` aur explicit `[SetUp]`/`[TearDown]` use karta hai; MSTest `[TestClass]`/`[TestMethod]`/`[DataRow]` use karta hai. Choice mostly team convention hai — xUnit naye greenfield .NET projects me sabse common default hai." Follow-up jo aata hai: "AAA pattern kyun important hai?" — jawaab: readability aur maintainability, ek clear structure jisse failure ka reason turant samajh aaye.

</InterviewAngle>

## Common Mistakes

<Mistake>

Ek hi test method me multiple unrelated behaviors assert karna — test fail hone par exactly pata nahi chalta kya toota, kyunki AAA structure violate ho gayi (multiple "Act"s ek test me).

</Mistake>

<Mistake>

NUnit me `[SetUp]` ko forget karna aur assume karna ki xUnit jaisa constructor-based setup automatically ho jaayega — NUnit explicit `[SetUp]` method maangta hai, warna fields uninitialized rahenge.

</Mistake>

<Mistake>

Generic test names (`Test1`, `TestAdd`) use karna instead of `MethodName_Scenario_ExpectedBehavior` — test suite badi hone par failure list se kuch pata nahi chalta.

</Mistake>

<Mistake>

Ye maan lena ki ek framework "better" hai objectively — reality me sab feature-comparable hain, decision team convention aur existing codebase pe depend karta hai, interview me isko absolute claim ki tarah mat present karo.

</Mistake>

## Quick Revision

<QuickRevision>

- AAA = Arrange (setup) → Act (one action) → Assert (verify) — keep each section visually separate
- xUnit: `[Fact]`/`[Theory]`+`[InlineData]`, constructor-based setup, fresh instance per test
- NUnit: `[TestFixture]`+`[Test]`/`[TestCase]`, explicit `[SetUp]`/`[TearDown]`
- MSTest: `[TestClass]`+`[TestMethod]`/`[DataRow]`+`[DataTestMethod]`, `[TestInitialize]`/`[TestCleanup]`
- xUnit is the most common default for new .NET projects; NUnit and MSTest remain common in existing/legacy codebases
- Name tests `MethodName_Scenario_ExpectedBehavior` for readable failure lists
- Framework choice is team convention, not a hard technical superiority claim

</QuickRevision>
