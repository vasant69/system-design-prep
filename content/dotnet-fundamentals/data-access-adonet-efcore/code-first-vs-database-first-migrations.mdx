<SimpleDefinition>

Code-First lets EF Core generate the database schema from C# entity classes via Migrations, keeping the schema's history versioned alongside application code; Database-First (scaffolding) reverses the direction — an existing database is inspected and C# entity classes plus a `DbContext` are generated from it. The two approaches suit different project realities: a greenfield project vs. an existing, DBA-owned database.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Interview me "Code-First vs Database-First" ko sirf do naam ki tarah mat treat karo — asli sawal hai "database schema ka source of truth kaun hai: C# code, ya database khud?" Ye ek genuine architectural decision hai, project ki reality pe depend karta hai.

### Code-First — C# classes source of truth hain

Code-First me, tum entity classes likhte ho, EF Core us se schema **generate** karta hai Migrations ke through:

```csharp
public class Product
{
    public int Id { get; set; }
    public string Name { get; set; } = string.Empty;
    public decimal Price { get; set; }
}
```

Phir CLI se migration generate karte ho:

```
dotnet ef migrations add InitialCreate
dotnet ef database update
```

`migrations add` ek migration file generate karta hai (`Up()`/`Down()` methods ke saath — schema ko forward ya rollback karne ke liye C# code), aur `database update` use actually database pe apply karta hai. Har baar jab entity class change hoti hai (naya property, naya entity), naya migration generate karte ho — schema history **version-controlled, code ke saath committed** rehta hai, jo team collaboration aur deployment ke liye bahut valuable hai (kisi bhi environment pe "current schema state" reproduce ho sakta hai migrations replay karke).

### Database-First — database source of truth hai, code generate hota hai

Database-First (jise EF Core CLI me "scaffolding" kehte hain) reverse direction hai — database **already exist** karta hai (shayad DBA ne design kiya, ya legacy system hai), aur tum EF Core ko batate ho use inspect karke entity classes + `DbContext` generate karne ke liye:

```
dotnet ef dbcontext scaffold "Server=...;Database=...;" Microsoft.EntityFrameworkCore.SqlServer -o Models
```

Ye command existing tables, columns, foreign keys, indexes ko inspect karta hai aur matching C# classes + `OnModelCreating` configuration automatically generate karta hai. Is workflow me, agar database schema change hota hai (kisi aur tool/DBA se), tumhe **scaffolding dobara run karni padti hai** naye code ke liye — ya to poora regenerate karo, ya manually sync karo.

### Kab kaunsa approach fit baithta hai

**Code-First fits jab:**
- Greenfield project hai — koi existing database nahi.
- Development team hi schema design ko drive kar rahi hai.
- Schema evolution application development ke saath tightly coupled honi chahiye (naya feature = naya migration, ek hi PR me).
- CI/CD pipelines me automated schema deployment chahiye (`database update` deployment step ban sakta hai).

**Database-First fits jab:**
- Ek existing, mature database already hai (legacy system, ya ek DBA-owned enterprise database jahan multiple applications same DB share karte hain).
- Database schema application code se **independently** evolve hota hai — DBAs schema changes karte hain apne process se, application team ko sirf "current schema ke against kaam karna hai."
- Application sirf ek consumer hai kai systems me se ek jo isi database ko access karte hain — application ko schema "own" karne ka koi sense nahi banta.

### Real-world nuance — hybrid approach bhi common hai

Bade enterprise systems me, ek pure approach rarely hota hai. Common pattern: initial scaffold Database-First se generate karo (existing schema se start), phir usko Code-First workflow me "adopt" kar lo — ab aage se changes migrations ke through control karte ho, chahe original source database-first tha. Ye especially useful hai jab team gradually legacy database ko better-managed, versioned schema evolution ki taraf move karna chahti hai.

</Hinglish>

<Callout type="tip">

Ek-line distinction jo interview me clearly bolna chahiye: "Code-First me C# code database ko drive karta hai; Database-First me database C# code ko drive karta hai." Baaki sab (workflow commands, use cases) is ek line se follow karta hai.

</Callout>

## Real World Example

<RealWorld company="Microsoft">

Microsoft ki EF Core documentation aur default project templates dono Code-First ko default-recommended workflow ki tarah present karte hain naye projects ke liye — `dotnet new webapi` jaisa scaffolding, jab EF Core add kiya jaata hai, migrations-based Code-First setup expect karta hai. Database-First explicitly ek "existing database ke saath integrate karne" ka scenario-specific tool ki tarah documented hai, default nahi.

</RealWorld>

<RealWorld company="A Multi-Application Enterprise Database">

Ek typical bade Indian enterprise (jaise ek insurance ya banking group company) me, ek central "customer master" database kai alag-alag applications (claims processing, policy management, reporting) share karta hai, aur ek dedicated DBA team schema ko govern karti hai apne independent change-control process ke through. Har application team Database-First scaffolding use karti hai apna khud ka `DbContext` generate karne ke liye current schema ke against — koi bhi application team unilaterally schema change nahi kar sakti, kyunki wo shared resource hai multiple consumers ke saath.

</RealWorld>

## Numbers That Matter

<Numbers>

- `dotnet ef migrations add <Name>` — naya migration generate karta hai; `dotnet ef database update` — use apply karta hai
- `dotnet ef dbcontext scaffold` — existing database se entities + DbContext reverse-generate karta hai
- Migrations har ek me `Up()` (forward) aur `Down()` (rollback) methods hoti hain — schema evolution dono directions me controlled hai
- Code-First: schema history git-versioned, code ke saath committed
- Database-First: schema truth database me rehta hai, code re-scaffold hokar sync hota hai

</Numbers>

## Interview Angle

<InterviewAngle>

"Code-First aur Database-First me kab kya use karoge?" ka strong answer: "Code-First tab jab main greenfield project pe hoon aur schema evolution application development ke saath tightly coupled honi chahiye — migrations schema history ko code ke saath version-control me rakhte hain. Database-First tab jab ek existing, ya multiple applications se shared database already hai jise ek DBA team independently govern karti hai — main scaffolding se current schema ke against C# classes generate karta hoon, aur schema change hone par dobara scaffold karta hoon." Follow-up jo common hai: "kya dono ko mix kar sakte ho?" — jawaab: haan, ek common pattern hai database ko initially scaffold karke, phir aage migrations-based Code-First workflow adopt karna.

</InterviewAngle>

## Common Mistakes

<Mistake>

Ye maan lena ki Code-First hamesha "better" hai aur Database-First "outdated" hai — dono genuinely alag project realities ke liye design kiye gaye hain, ek universal "best" nahi hai.

</Mistake>

<Mistake>

Database-First scaffold karne ke baad, generated files ko manually edit karna aur phir schema change hone par dobara scaffold karna, jisse manual edits overwrite ho jaate hain — agar customization chahiye, partial classes ya separate configuration files use karo jo scaffolding overwrite na kare.

</Mistake>

<Mistake>

Production database pe seedha `dotnet ef database update` chalana bina migration script review kiye — generated migration me destructive operations (column drop, data type narrowing) ho sakte hain jo production data loss cause kar sakte hain. Migration SQL script generate karke (`dotnet ef migrations script`) review karna safer hai production ke liye.

</Mistake>

<Mistake>

Multiple developers ek saath conflicting migrations create karna bina coordinate kiye (parallel branches me alag-alag migrations) — merge conflicts aur schema drift create karta hai; team convention (jaise "migrations ko main branch se turant baad rebase karo") zaroori hai.

</Mistake>

## Quick Revision

<QuickRevision>

- Code-First: C# entity classes are the source of truth, `dotnet ef migrations add` + `dotnet ef database update` drive the schema
- Database-First (scaffolding): the existing database is the source of truth, `dotnet ef dbcontext scaffold` reverse-generates C# classes
- Code-First fits greenfield projects where the app team owns the schema
- Database-First fits existing/shared/DBA-governed databases where the app is just one consumer
- Migrations have `Up()` and `Down()` — forward and rollback support
- A hybrid pattern exists: scaffold once from an existing database, then adopt Code-First migrations going forward
- Never blindly run `database update` against production without reviewing the generated migration script first

</QuickRevision>
