<SimpleDefinition>

`record` (C# 9) introduced a third category in C#'s type system alongside class and struct — reference-type-by-default with compiler-generated value-based equality and non-destructive mutation via `with`-expressions; `record struct` (C# 10) applies the same equality/`with`-expression semantics to a value type, letting a team choose reference-type or value-type identity while keeping records' declarative equality model.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Is topic ka goal `record` ko full re-explain karna nahi hai — `record`/`record struct`/readonly struct ki poori deep-dive (Equals/GetHashCode auto-generation ki mechanics, `EqualityContract`, inheritance behavior) already `oops-dotnet` section me detail se cover ho chuki hai. Yahan focus hai: **C# ke type system me `record` kahan fit hota hai**, aur immutability genuinely kyun matter karti hai — ye angle wahan explicitly cover nahi hua tha.

### Type system me teesra category — class, struct, record

C# 9 se pehle, tumhare paas practically do fundamental type-categories the: **class** (reference type, mutable by convention, identity-based semantics by default) aur **struct** (value type, copy semantics). `record` in dono ke beech ek naya, teesra option add karta hai — by default ye ek **reference type** hai (heap-allocated, class ki tarah), lekin uska **equality behavior structurally value-based hai** (struct/value-semantics ki tarah), compiler dwara automatically generate kiya jaata hai:

```csharp
public record Person(string Name, int Age);

var p1 = new Person("Asha", 28);
var p2 = new Person("Asha", 28);
Console.WriteLine(p1 == p2);       // True — structural equality, chahe ye alag heap objects hon
Console.WriteLine(p1.Equals(p2));  // True — same reason
```

Ye class ke default behavior (reference equality) se seedha ulta hai — do alag `class` instances same field values ke saath default me `false` denge `==` pe, jabki `record` `true` dega, kyunki compiler ne poora Equals/GetHashCode/`==` overload contract khud generate kar diya.

### with-expressions — non-destructive mutation ka syntax

`record` ka doosra defining feature hai `with` — ek naya record instance banane ka tarika jo original ke saare properties copy karta hai, sirf jo tum specify karo wo change hote hain:

```csharp
var updated = p1 with { Age = 29 }; // naya Person("Asha", 29), p1 khud UNCHANGED
```

`p1` khud bilkul modify nahi hota — ye genuinely ek naya object hai. Ye pattern possible hai kyunki records ke properties by default `init`-only hote hain (ek baar set hone ke baad immutable), jo agle section ka topic hai.

### Immutability genuinely kyun matter karti hai — sirf "best practice" nahi

Interview me sirf "immutability achhi practice hai" bolna weak answer hai — do concrete, technical reasons hain:

1. **Thread-safety without locks.** Agar ek object ke fields kabhi change hi nahi hote object create hone ke baad, multiple threads usse safely simultaneously read kar sakte hain bina kisi `lock`/synchronization ke — koi race condition possible hi nahi hai, kyunki koi bhi thread kabhi kisi state ko modify nahi kar raha. Ye async/multi-threaded ASP.NET Core code me genuinely valuable hai.

2. **No aliasing bugs.** "Aliasing bug" tab hota hai jab ek reference multiple jagah share ho, aur kisi ek jagah se kiya gaya mutation baaki sab jagah unexpectedly dikhta hai — ek classic, hard-to-debug class of bugs. Agar object immutable hai, ye poora problem-class hi exist nahi karta — object ko jitni bhi jagah share karo, koi bhi jagah usse "accidentally" modify nahi kar sakti.

```csharp
// Mutable class ke saath aliasing bug:
var order = new OrderMutable { Total = 100 };
ProcessAsync(order); // agar ProcessAsync order.Total change kare, caller ko pata bhi nahi chalega
Console.WriteLine(order.Total); // ??? — kya hoga, code padhe bina pata nahi chalega

// record ke saath — ye class of bug hi impossible hai
var order = new OrderRecord(100);
var processed = ProcessAsync(order); // agar processing 'change' chahiye, naya record return hoga
Console.WriteLine(order.Total); // hamesha 100 — guaranteed, kyunki order khud kabhi change nahi ho sakta
```

### record struct — value-type identity chahiye to bhi record semantics

`record struct` (C# 10) exact wahi declarative equality/`with`-expression convenience deta hai, lekin underlying type **value type** hai — copy semantics, no heap allocation for the record itself (unless boxed). Choose karo jab data chhoti, short-lived, aur value-semantics-appropriate ho (jaisa `struct-vs-class-decision` topic detail me discuss karta hai).

</RealWorld>

## Numbers That Matter

<Numbers>

- `record` (C# 9, 2020) — reference type by default, compiler-generated structural equality
- `record struct` (C# 10, 2021) — value type variant, same declarative equality/`with` semantics
- Records auto-generate: `Equals`, `GetHashCode`, `ToString`, `==`/`!=` operators, a `Deconstruct` method, and `EqualityContract`
- `with`-expressions create a new instance, copying unspecified members — original is never mutated
- Immutable objects eliminate an entire bug class (aliasing/unexpected mutation) at the type-system level, not just by convention

</Numbers>

## Quick Revision

<QuickRevision>

- `record` (C# 9) is a third type-system category — reference type by default, structural equality compiler-generated
- Default `record` equality is value-based (`==`/`Equals` compare content), unlike `class`'s default reference equality
- `with { Property = newValue }` creates a new instance — the original is never mutated
- `record struct` (C# 10) gives the same equality/with-expression model on top of a value type
- Immutability isn't just style — it enables lock-free thread-safe reads and eliminates aliasing bugs at the type level
- Full Equals/GetHashCode mechanics and record-specific inheritance behavior — see the cross-linked prerequisite topic for the deep dive

</QuickRevision>
