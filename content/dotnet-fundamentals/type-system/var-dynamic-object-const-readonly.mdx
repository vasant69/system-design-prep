<SimpleDefinition>

`var`, `dynamic`, and `object` are often confused as synonyms but are three genuinely different things — `var` is compile-time type inference (still fully statically typed), `dynamic` defers type resolution to runtime via the DLR, and `object` is the universal static base type requiring explicit casting; separately, `const` is a compile-time constant baked directly into consuming assemblies' IL, while `readonly` is a runtime-settable-once-in-the-constructor field, and `static readonly` is a class-level value set once.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Ye topic do independent lekin dono hi "confuse-easily" concepts cover karta hai — pehla `var`/`dynamic`/`object` ka trio, doosra `const`/`readonly`/`static readonly` ka. Dono interview me alag-alag tarah se pakde jaate hain.

### var — compile-time inference, type STILL fixed hai

`var` ek bahut misunderstood keyword hai — naye developers isse "dynamically typed" samajh lete hain, jo bilkul galat hai. `var` sirf compiler ko batata hai "type ka naam tum khud figure out karo, right-hand side expression se" — lekin ek baar infer ho jaane ke baad, variable **utna hi strictly typed hai jitna explicit type declare karne se hota**:

```csharp
var name = "Asha";   // compiler infers: string
name = 42;            // Compile ERROR — name string hai, int assign nahi ho sakta
```

`var` sirf syntax sugar hai — `var name = "Asha";` aur `string name = "Asha";` compile hoke **identical IL** produce karte hain. Koi runtime difference nahi. `var` initializer ke bina use nahi ho sakta (compiler ko infer karne ke liye kuch chahiye), aur method parameters/return types me `var` allowed nahi hai.

### dynamic — runtime resolution, DLR ke through

`dynamic` (C# 4.0) genuinely alag hai — type-checking **compile-time pe skip** ho jaata hai, aur runtime pe DLR (Dynamic Language Runtime) resolve karta hai ki member exist karta hai ya nahi:

```csharp
dynamic obj = "hello";
Console.WriteLine(obj.Length);   // Runtime pe resolve hota hai — "hello" ek string hai, Length exist karta hai, works

obj = 42;
Console.WriteLine(obj.Length);   // Compiles FINE (koi compile-time check nahi) — Runtime pe RuntimeBinderException, kyunki int me Length nahi hota
```

Ye `var` se bilkul opposite hai — `var` compile-time type-safe hai, `dynamic` sirf runtime pe pata chalta hai ki kuch galat hai. `dynamic` genuinely useful hai jab COM interop, reflection-heavy code, ya truly dynamic data (jaise ExpandoObject, ya dynamic JSON parsing) ke saath kaam karna ho — general-purpose code me use karna maintainability aur compile-time safety dono kho deta hai.

### object — universal base, explicit cast chahiye

`object` (C# ka har type ka ultimate base) bhi kisi bhi value hold kar sakta hai, lekin `dynamic` se bilkul alag tareeke se — `object`-typed variable pe member access karne se **pehle explicit cast** karna hi padega, warna compile error:

```csharp
object obj = "hello";
Console.WriteLine(obj.Length);      // Compile ERROR — object type pe Length member exist nahi karta
Console.WriteLine(((string)obj).Length); // OK — explicit cast ke baad access allowed
```

### Teeno ka summary — ek hi table me

| | `var` | `dynamic` | `object` |
|---|---|---|---|
| Type resolve kab hota hai | Compile-time (inferred) | Runtime | Compile-time (base type) |
| Member access | Direct, type-checked | Direct, runtime-checked | Cast required first |
| Wrong-type bug kab pakda jaata hai | Compile-time | Runtime (RuntimeBinderException) | Compile-time (agar cast galat, runtime InvalidCastException) |

### const — compile-time constant, ek chhupi hui gotcha ke saath

`const` value **compile-time pe hi known honi chahiye**, aur compiler isse directly consuming code ke IL me **bake (embed)** kar deta hai — literal substitution jaisa:

```csharp
public class Config { public const int MaxRetries = 3; }
// Consumer code: if (attempts < Config.MaxRetries) — ye compile hoke "if (attempts < 3)" ban jaata hai, literally
```

**Real gotcha jo interview me poocha jaata hai:** agar `Config.MaxRetries` ki value badal ke library recompile ki jaaye (3 se 5), lekin consuming assembly recompile NAHI ki jaaye, consumer **purani value (3) use karta rahega** — kyunki value already unke IL me literal ke roop me bake ho chuki thi build time pe. Isliye `const` sirf tab use karo jab value **genuinely kabhi nahi badlegi** (jaise `Math.PI`), cross-assembly public constants ke liye risky hai.

### readonly — runtime-settable, constructor tak flexible

`readonly` field runtime pe set ho sakta hai — constructor ke andar (ya field declaration pe) — aur uske baad immutable ho jaata hai:

```csharp
public class Config
{
    public readonly int MaxRetries;
    public Config(int maxRetries) { MaxRetries = maxRetries; } // constructor me set — allowed
}
```

`readonly` cross-assembly recompile gotcha se safe hai — kyunki ye ek actual field access hai (IL me literal-embed nahi hota), consuming code hamesha latest value dekhta hai bina apna khud recompile kiye.

### static readonly — class-level, set-once

`static readonly` dono combine karta hai — class-level (ek hi copy sabke liye, instance-independent) aur ek baar hi set hota hai (static constructor me ya declaration pe). Ye tab use hota hai jab value compile-time constant nahi hai (jaise runtime pe compute hoti hai) lekin phir bhi kabhi badalni nahi chahiye:

```csharp
public class Config
{
    public static readonly DateTime AppStartTime = DateTime.UtcNow; // runtime pe compute hota hai, const nahi ho sakta
}
```

</Hinglish>

<Callout type="warning">

`const` ka cross-assembly recompile gotcha production me genuinely bug deta hai — agar tum kabhi ek shared library ka public `const` value change karo, **har consuming assembly ko bhi recompile karna zaroori hai**, warna wo purani value silently use karte rahenge. Jab bhi doubt ho ki value future me badal sakti hai, `static readonly` use karo, `const` nahi.

</Callout>

## Real World Example

<RealWorld company="Microsoft">

.NET BCL khud `const` ko sirf genuinely-immutable mathematical/physical constants ke liye use karta hai (`Math.PI`, `int.MaxValue` internally). Application-level configuration values — jo kabhi change ho sakti hain — hamesha `static readonly` ya configuration-system-driven values ke roop me expose ki jaati hain, exactly is recompile-gotcha se bachne ke liye.

</RealWorld>

<RealWorld company="An Indian SaaS Product Company">

Ek team ne apne shared NuGet package me `public const int DefaultPageSize = 20;` define kiya, jo 10+ consuming microservices use kar rahe the. Kuch mahine baad `DefaultPageSize` ko 50 karna pada — package version bump hua, lekin sirf 3 services ne apna dependency update kiya aur recompile kiya. Baaki services silently purani value (20) use karte rahe, jab tak team ne realize nahi kiya ki behavior inconsistent hai. Fix ke saath-saath, team ne guideline bana di: cross-package public values ke liye `const` kabhi use nahi karna, `static readonly` ya runtime configuration hi use karna.

</RealWorld>

## Numbers That Matter

<Numbers>

- `var`: compile-time inference, zero runtime difference from explicit typing — pure syntax sugar
- `dynamic`: C# 4.0 (2010), resolution deferred to runtime via the DLR
- `object`: available since C# 1.0, the universal base type, requires explicit casting for member access
- `const`: value baked into consuming assembly's IL at compile time — a recompile gotcha for cross-assembly changes
- `readonly`: settable at declaration or in the constructor, evaluated at runtime, no cross-assembly staleness risk
- `static readonly`: one value shared across all instances, set once (declaration or static constructor)

</Numbers>

## Common Mistakes

<Mistake>

`var` ko "dynamically typed" samajhna — `var` sirf compile-time inference hai, variable utna hi statically typed hai jitna explicit declaration se hota.

</Mistake>

<Mistake>

`dynamic` ko general-purpose code me overuse karna, sirf "flexibility" ke liye — compile-time safety poori tarah kho jaati hai, bugs sirf runtime pe pakde jaate hain.

</Mistake>

<Mistake>

`const` ko kisi bhi "value jo change nahi hoti" ke liye use karna, bina consider kiye ki wo cross-assembly consume ho rahi hai — future change par recompile na hone ki staleness bug create ho sakta hai.

</Mistake>

<Mistake>

`readonly` field ko constructor ke bahar (kisi normal method me) set karne ki koshish karna — compile error, `readonly` sirf declaration ya constructor ke andar set ho sakta hai.

</Mistake>

## Quick Revision

<QuickRevision>

- `var`: compile-time type inference, zero runtime difference — still fully statically typed
- `dynamic`: runtime type resolution via DLR — compile-time checks skipped, wrong usage throws `RuntimeBinderException`
- `object`: universal base type, requires explicit cast before member access
- `const`: compile-time constant, baked into consuming assemblies' IL — changing it needs every consumer recompiled
- `readonly`: runtime-evaluated, settable at declaration or in the constructor, no cross-assembly staleness risk
- `static readonly`: class-level, one shared value, set once — use when the value isn't a true compile-time constant
- Prefer `static readonly` over `const` for any public value that might change in a future version

</QuickRevision>
