<SimpleDefinition>

.NET Standard was a formal specification of APIs that every .NET implementation (Framework, Core, Xamarin) agreed to support, letting a library target multiple runtimes at once — mostly historical now that .NET 5+ unified everything into one implementation. The SDK is the full toolchain for developing (compiler, CLI, project templates, NuGet client); the Runtime is only what's needed to execute an already-built app — a distinction that matters the moment someone says "just install .NET."

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Ye topic do alag confusions ko clear karta hai jo beginners aur even 2-3 saal experience wale engineers ke beech bhi common hain: ".NET Standard kya hai" aur "SDK install karu ya Runtime."

### .NET Standard — ek "contract," implementation nahi

Pehle (2016 ke aas-paas) .NET ecosystem me multiple, genuinely alag implementations the: **.NET Framework** (Windows-only), **.NET Core** (cross-platform, naya), **Xamarin** (mobile), **Mono**. Problem ye thi — agar tum ek NuGet library banate ho (jaise ek logging library, ek utility library), to wo kis implementation ko target kare? Har implementation ki apni BCL (Base Class Library) surface thi, thoda alag.

**.NET Standard** iska solution tha — ek **specification**, actual implementation nahi. Ye batata hai "in APIs ka ye set — jaise `.NET Standard 2.0` — har implementation guarantee karegi." Agar library `.NET Standard 2.0` target karti hai, wo .NET Framework 4.6.1+, .NET Core 2.0+, Xamarin, sab pe chalegi — bina alag build ke.

```xml
<!-- Ek library jo Framework aur Core dono me consume ho sake -->
<TargetFramework>netstandard2.0</TargetFramework>
```

Ye numbering thoda confusing thi — `.NET Standard 2.0` ka matlab "version 2.0 ka runtime" nahi, balki "APIs ka wo set jo Standard 2.0 me commit kiya gaya." Higher Standard version = zyada APIs available, lekin fewer implementations support karti hain (kyunki sabko catch up karna padta hai).

**.NET 5+ ke baad ye largely historical ho gaya.** Jab Microsoft ne .NET Framework, .NET Core, Xamarin sabko ek hi implementation (.NET 5, phir 6, 7, 8...) me unify kar diya, to "multiple implementations ke beech common contract" wali problem hi khatam ho gayi — ab sirf **ek** .NET hai (Framework abhi bhi legacy support ke liye alag chal raha hai, lekin nayi development ke liye nahi). Naye projects ab `netstandard2.0` nahi, seedha `net8.0` (ya jo bhi current version) target karte hain, jab tak specifically .NET Framework ke saath compatibility nahi chahiye.

### SDK vs Runtime — "develop karna hai" vs "run karna hai"

Ye distinction abhi bhi 100% relevant hai, aur practical bhi — kisi bhi machine pe `.NET install karna hai` bolne se pehle poochna chahiye "develop karna hai ya sirf run?"

**Runtime** — sirf wo minimum jo ek already-compiled .NET app ko **chalane** ke liye chahiye: CLR (execution engine), JIT compiler, garbage collector, core BCL assemblies. Production server pe, ya kisi user ke machine pe jahan sirf app deploy ho rahi hai, sirf Runtime install hota hai — halka, chhota download.

```
dotnet-runtime-8.0    → ASP.NET Core app nahi chala sakta (missing ASP.NET-specific libs)
aspnetcore-runtime-8.0 → ASP.NET Core apps chalane ke liye (Runtime + web-specific libs)
```

**SDK (Software Development Kit)** — Runtime **plus** poora development toolchain: C# compiler (Roslyn), `dotnet` CLI (`dotnet build`, `dotnet run`, `dotnet test`, `dotnet publish`), project templates (`dotnet new`), NuGet client. Developer machine, CI/CD build agent — inhe SDK chahiye, kyunki inhe code **compile** karna hai, sirf run nahi.

```bash
dotnet --list-sdks       # installed SDKs
dotnet --list-runtimes   # installed runtimes (multiple runtime versions can coexist)
```

Practical impact: agar production server pe sirf Runtime hai (SDK nahi), `dotnet build`/`dotnet run` waha kaam nahi karenge — sirf already-published `.dll` ko `dotnet MyApp.dll` se run kiya ja sakta hai. Ye ek deliberate, security-and-size-conscious design hai — production machine ko compiler ki zaroorat hi nahi honi chahiye.

### Interview me ye kyun poocha jaata hai

Real-world scenario: "Production server pe deployment fail ho raha hai, `dotnet build` command not found ya kaam nahi kar raha" — iska ek common root cause hi ye hota hai ki server pe sirf Runtime install hai, SDK nahi (jaisa hona bhi chahiye — production server ko SDK ki zaroorat nahi). Isko samajhna deployment troubleshooting ka basic hai.

</Hinglish>

<Callout type="tip">

Quick mental model: SDK ⊃ Runtime (SDK includes a Runtime, plus everything to build). Dev machines aur CI agents → SDK. Production servers → sirf matching Runtime (`aspnetcore-runtime` for web apps).

</Callout>

## Real World Example

<RealWorld company="Microsoft">

.NET Standard ka evolution khud Microsoft ke docs me "deprecated in favour of .NET 5+" ke roop me documented hai — Microsoft explicitly recommend karta hai ki naye libraries `netstandard2.0` sirf tab target karein jab genuinely .NET Framework consumers support karna ho, warna directly `net8.0` (ya latest) target karo, kyunki .NET 5+ ka API surface bahut bada hai aur Standard usse artificially limit karta hai.

</RealWorld>

<RealWorld company="An Indian SaaS Company's CI Pipeline">

Ek team ka Docker-based production deployment fail hone laga jab kisi ne base image `mcr.microsoft.com/dotnet/sdk:8.0` se `mcr.microsoft.com/dotnet/aspnet:8.0` (runtime-only) me switch kiya production stage ke liye — image size kaafi chhoti ho gayi (achha change), lekin ek health-check script jo `dotnet build` internally call kar raha tha fail hone laga. Fix: multi-stage Docker build — SDK image sirf build stage me, final production image sirf Runtime image, aur health-check ko pre-built binary check karne ke liye badla gaya, `dotnet build` nahi.

</RealWorld>

## Numbers That Matter

<Numbers>

- .NET Standard introduced ~2016, effectively superseded by .NET 5 (Nov 2020) unification
- `netstandard2.0` — widest-compatible target for libraries still supporting .NET Framework consumers
- SDK download is significantly larger than Runtime-only (full compiler toolchain + templates + NuGet client)
- `aspnetcore-runtime` is a superset of `dotnet-runtime` — Web API/MVC apps need the ASP.NET-specific one
- Multiple SDK and Runtime versions can be installed side-by-side on the same machine (`dotnet --list-sdks`/`--list-runtimes`)

</Numbers>

## Interview Angle

<InterviewAngle>

"Kya .NET Standard abhi bhi relevant hai naye project ke liye?" — strong answer: "Generally nahi, jab tak library specifically .NET Framework consumers ke liye compatible honi chahiye. .NET 5+ ne Framework/Core/Xamarin ko ek implementation me unify kar diya, isliye 'multiple implementations ke beech common contract' wali original problem largely khatam ho gayi. Naye projects directly `net8.0` (ya current LTS) target karte hain." Follow-up almost hamesha: "SDK aur Runtime me practical difference?" — SDK = build karne ka poora toolchain (dev machine, CI), Runtime = sirf execute karne ke liye minimum (production server).

</InterviewAngle>

## Common Mistakes

<Mistake>

.NET Standard ko ek "version of .NET" samajhna, jaise .NET 6 ya .NET 8 hai — ye galat hai. Ye ek API specification/contract hai, khud koi runnable implementation nahi.

</Mistake>

<Mistake>

Production server pe SDK install karna "safe side" ke liye — unnecessary attack surface aur disk space badhata hai. Production ko sirf matching Runtime chahiye.

</Mistake>

<Mistake>

`dotnet-runtime` aur `aspnetcore-runtime` ko same samajh lena — ASP.NET Core Web API ko specifically `aspnetcore-runtime` chahiye, plain `dotnet-runtime` se web app run nahi hoga (missing Kestrel/hosting libs).

</Mistake>

<Mistake>

Har naye library project me bina soche `netstandard2.0` target kar dena — agar .NET Framework compatibility genuinely nahi chahiye, `net8.0` target karke bigger, modern API surface use karna better hai.

</Mistake>

## Quick Revision

<QuickRevision>

- .NET Standard = an API specification/contract, NOT a runnable implementation — largely historical after .NET 5+ unification
- `netstandard2.0` still used only when a library must support .NET Framework consumers
- SDK = compiler + CLI + templates + NuGet client + a Runtime — for developing/building
- Runtime = minimum needed to execute an already-built app — for production
- `aspnetcore-runtime` ≠ `dotnet-runtime` — web apps need the ASP.NET-specific one
- `dotnet --list-sdks` / `dotnet --list-runtimes` to inspect what's installed
- Production servers should have Runtime only, not SDK, as a matter of size and security hygiene

</QuickRevision>
