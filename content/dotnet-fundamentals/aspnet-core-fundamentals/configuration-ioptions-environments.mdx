<SimpleDefinition>

ASP.NET Core builds configuration from multiple layered providers (appsettings.json, environment-specific overrides, environment variables, command-line args, user secrets) applied in a fixed precedence order, and exposes strongly-typed access to that configuration through the IOptions family — `IOptions<T>`, `IOptionsSnapshot<T>`, and `IOptionsMonitor<T>` — each with different binding and reload semantics.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Har ASP.NET Core app ko configuration chahiye hoti hai — connection strings, API keys, feature flags, timeouts. Beginner-level candidates sirf "appsettings.json me hota hai" bol dete hain, lekin real interview me do cheezein poochi jaati hain: **providers ka precedence order** aur **strongly-typed config kaise consume karte hain**.

### Configuration providers aur unka precedence order

`WebApplication.CreateBuilder()` internally ek chain of configuration providers register karta hai, is order me (baad wala pehle wale ko **override** karta hai):

1. `appsettings.json` — base config, sab environments ke liye common
2. `appsettings.{Environment}.json` — jaise `appsettings.Development.json`, `appsettings.Production.json` — environment-specific overrides
3. User Secrets (sirf Development environment me, sensitive local values ke liye — repo me commit nahi hote)
4. Environment variables — deployment-time overrides, containers/Kubernetes me sabse common tarika
5. Command-line arguments — highest precedence, `dotnet run --ConnectionStrings:Default=...`

Ye order **matter karta hai**: agar `appsettings.json` me `"Timeout": 30` hai aur environment variable me `Timeout=60` set hai, runtime pe `60` hi use hoga — kyunki environment variables JSON files ke baad register hote hain, aur baad me register hone wala provider pehle wale ko override karta hai.

```json
// appsettings.json
{ "Timeout": 30, "Feature": { "Enabled": false } }

// appsettings.Production.json
{ "Timeout": 60 }
```

```bash
# Production environment variable — final override
Feature__Enabled=true   # ':' ki jagah '__' (double underscore) use hota hai env vars me
```

Nested keys ke liye JSON me `:` (colon) use hota hai (`Feature:Enabled`), lekin environment variables me colon most shells me problematic hai isliye `__` (double underscore) convention hai — ASP.NET Core dono ko same key treat karta hai.

### `ASPNETCORE_ENVIRONMENT` — kaunsa environment file load hoga

`ASPNETCORE_ENVIRONMENT` environment variable decide karta hai kaunsi `appsettings.{Environment}.json` file load hogi. Convention: `Development`, `Staging`, `Production` — lekin ye sirf strings hain, koi bhi custom naam use kar sakte ho. Local development me typically `launchSettings.json` me set hota hai; deployed environment me actual OS/container-level env var set hota hai.

```csharp
if (app.Environment.IsDevelopment())
{
    app.UseDeveloperExceptionPage();
}
```

`IWebHostEnvironment.IsDevelopment()`/`IsProduction()`/`IsEnvironment("Staging")` runtime pe check karne ke liye — jaise dev me detailed exception page dikhana, production me generic error page.

### Strongly-typed config — IOptions family

Raw `IConfiguration["Key:SubKey"]` string-based access error-prone hai — typo se silently `null` mil jaata hai. Better approach: ek POCO class banao, config section usme **bind** karo:

```csharp
public class SmtpSettings
{
    public string Host { get; set; } = "";
    public int Port { get; set; }
}

builder.Services.Configure<SmtpSettings>(
    builder.Configuration.GetSection("Smtp"));
```

Ab teen tareeke se inject kar sakte ho, aur inka behavior **genuinely alag** hai:

**`IOptions<T>`** — sabse simple, **Singleton** lifetime, config ek baar bind hoti hai app startup pe, **value change ho jaaye to bhi refresh nahi hoti** jab tak app restart na ho. Long-lived services (Singleton dependencies) me safe.

**`IOptionsSnapshot<T>`** — **Scoped** lifetime, har HTTP request ke liye fresh value recompute hoti hai config source se (agar underlying source — jaise `appsettings.json` with `reloadOnChange: true` — change ho gaya ho). Per-request consistency chahiye, aur change-detection bhi chahiye to isse use karo — Scoped/per-request services ke saath.

**`IOptionsMonitor<T>`** — **Singleton**, lekin `.CurrentValue` property **real-time updated** rehti hai jab bhi underlying source change ho, plus `.OnChange(callback)` se change-notification subscribe kar sakte ho. Singleton services ke andar bhi live-reloading config chahiye to isse use karo.

```csharp
public class EmailService
{
    private readonly IOptionsMonitor<SmtpSettings> _options;
    public EmailService(IOptionsMonitor<SmtpSettings> options)
    {
        _options = options;
        _options.OnChange(newSettings =>
            Console.WriteLine($"Smtp host changed to {newSettings.Host}"));
    }

    public void Send() => Console.WriteLine(_options.CurrentValue.Host);
}
```

Interview me exact table yaad rakhna helpful hai: `IOptions<T>` = Singleton, no reload; `IOptionsSnapshot<T>` = Scoped, reloads per-request; `IOptionsMonitor<T>` = Singleton, reloads live with change-notification.

</Hinglish>

## Real World Example

<RealWorld company="Microsoft">

ASP.NET Core ka configuration system deliberately **provider-agnostic** design hua hai — JSON files, environment variables, Azure Key Vault, Azure App Configuration, command line, sab same `IConfiguration` abstraction ke peeche hain. Ye Microsoft ka apna pattern hai jo cloud-native deployment ko support karta hai — same codebase local machine pe JSON files se chal sakta hai, aur Azure/Kubernetes me environment variables ya managed secret stores se, bina code change ke.

</RealWorld>

<RealWorld company="An Indian Banking Backend">

Ek typical BFSI backend me, database connection string kabhi bhi `appsettings.json` me commit nahi hoti — production connection string sirf environment variable (`ConnectionStrings__Default`) ke through, deployment pipeline (Azure DevOps/Jenkins) secrets vault se inject karta hai. Local dev ke liye developers `dotnet user-secrets set` use karte hain, jo repo ke bahar, user profile me store hota hai — accidental commit ka risk zero ho jaata hai. Ye exact precedence chain (env vars > JSON files) is workflow ko possible banati hai.

</RealWorld>

## Numbers That Matter

<Numbers>

- Configuration provider precedence (low to high): `appsettings.json` → `appsettings.{Env}.json` → User Secrets (dev only) → environment variables → command-line args
- Environment variable nested-key separator: `__` (double underscore) instead of JSON's `:`
- `IOptions<T>` = Singleton, bound once at startup, no reload
- `IOptionsSnapshot<T>` = Scoped, recomputed per HTTP request
- `IOptionsMonitor<T>` = Singleton, `.CurrentValue` live-updates + `.OnChange()` callback
- `reloadOnChange: true` on the JSON provider is what makes file-watching reload actually work — without it, even `IOptionsSnapshot`/`IOptionsMonitor` won't see file edits

</Numbers>

## Interview Angle

<InterviewAngle>

"IOptions, IOptionsSnapshot, aur IOptionsMonitor me kya fark hai?" — strong answer: "Teeno same config-binding pattern use karte hain, lekin lifetime aur reload behavior alag hai. `IOptions<T>` Singleton hai — startup pe ek baar bind hoti hai, kabhi refresh nahi hoti. `IOptionsSnapshot<T>` Scoped hai — har HTTP request ke start pe fresh recompute hoti hai, agar underlying source change ho gaya ho. `IOptionsMonitor<T>` bhi Singleton hai, lekin `.CurrentValue` hamesha latest value reflect karta hai real-time, aur `OnChange()` se explicit change-notifications bhi mil sakte hain — isliye Singleton services ke andar bhi live-reloading config chahiye to yahi use hota hai." Follow-up: "Singleton service me IOptionsSnapshot directly inject karoge to kya hoga?" — answer: DI container error dega (ya silent captive-dependency bug agar validation disabled ho) kyunki Scoped dependency ko Singleton me directly inject nahi kar sakte.

</InterviewAngle>

## Common Mistakes

<Mistake>

`IOptionsSnapshot<T>` ya `IOptionsMonitor<T>` ko IOptions<T>` ki jagah blindly use karna bina samjhe ki performance cost hai — `IOptionsSnapshot` har request pe recompute hoti hai, agar config binding expensive ho (rare, but possible with complex sections) to unnecessary overhead ban sakta hai.

</Mistake>

<Mistake>

Environment variable me nested key ke liye `:` (colon) use karna instead of `__` (double underscore) — Linux/most shells me colon environment variable names me valid nahi hota, silently value bind nahi hoti.

</Mistake>

<Mistake>

Production connection strings ya secrets ko `appsettings.json` me commit karna — should always come from environment variables, a secret manager (Azure Key Vault, AWS Secrets Manager), or user secrets in dev only.

</Mistake>

<Mistake>

`reloadOnChange: true` set kiye bina expect karna ki `IOptionsMonitor` file changes pick up karega — JSON provider ke liye ye explicitly enable karna padta hai (`AddJsonFile("appsettings.json", optional: true, reloadOnChange: true)`, jo `CreateBuilder` default me already true hoti hai, lekin custom-added JSON files me manually set karni padti hai).

</Mistake>

<Mistake>

`IOptionsSnapshot<T>` ko Singleton service me directly inject karne ki koshish karna — DI container is captive-dependency mismatch ko catch karta hai (scope validation enabled hone par exception deta hai startup pe hi).

</Mistake>

## Quick Revision

<QuickRevision>

- Precedence (low to high): `appsettings.json` -> `appsettings.{Env}.json` -> User Secrets (dev) -> env vars -> command-line args
- Env var nested keys use `__` not `:`
- `ASPNETCORE_ENVIRONMENT` picks which `appsettings.{Environment}.json` loads
- `IOptions<T>` = Singleton, bind-once
- `IOptionsSnapshot<T>` = Scoped, reload per request
- `IOptionsMonitor<T>` = Singleton, live `.CurrentValue` + `.OnChange()`
- Never commit secrets/connection strings in `appsettings.json`
- `reloadOnChange: true` is required for file-based reload to actually fire

</QuickRevision>
