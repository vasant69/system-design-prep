<SimpleDefinition>

**Scope** is the set of variables accessible at a given place in code. JavaScript uses **lexical (static) scope**: a function's access to outer variables is determined by **where the function is written**, not where it is called. A **closure** is the pairing of a function with the outer scope it was created in — the function keeps access to those outer variables **even after the outer function has returned**, because the engine keeps that scope alive as long as an inner function references it. Closures power private state, factory functions, callbacks that capture context, and memoization.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Closures JavaScript ka sabse zyada poocha jaane wala interview topic hai, aur real code mein — React hooks, event handlers, module pattern — har jagah chhupa hota hai. Samajhne ki kunji: **scope kahan likha hai se decide hota hai, kahan call hua se nahi.**

### Ye kya hai — scope

Scope = "is line pe kaunse variables dikh rahe hain". Teen levels:

- **Global scope** — file/script ke top level; har jagah dikhta hai.
- **Function scope** — function ke andar declared; sirf us function (aur andar wale) mein.
- **Block scope** — `{ }` ke andar `let`/`const`; sirf us block mein (`var` block scope nahi maanta).

### Ye kya hai — lexical scope aur scope chain

**Lexical scope** = function jahan *likha* gaya hai, wahan ke outer variables use kar sakta hai. Jab engine ko koi variable chahiye, wo pehle current scope dekhta hai, na mile to ek level bahar (jahan function likha tha), phir aur bahar — **scope chain** — global tak. Na mile to `ReferenceError`.

```javascript
const a = 1;
function outer() {
  const b = 2;
  function inner() {
    const c = 3;
    console.log(a, b, c); // 1 2 3 -- inner apne + outer + global se
  }
  inner();
}
```

Zaroori: `inner` ko `outer` ke `b` tak access isliye hai kyunki wo `outer` ke **andar likha** hai — chahe `inner` ko kahin aur le jaake call karo.

### Ye kya hai — closure

Jab ek inner function apne outer scope ke variables use karta hai, aur wo inner function outer function ke **return hone ke baad bhi zinda** rehta hai (return kiya gaya, event listener bana, `setTimeout` mein gaya), to wo apne saath us outer scope ko "band karke" le jaata hai. Isi combination ko **closure** kehte hain.

```javascript
function makeCounter() {
  let count = 0;
  return function () {
    count++;
    return count;
  };
}
const next = makeCounter();
next(); // 1
next(); // 2
next(); // 3
```

`makeCounter` kab ka return ho chuka, par `count` abhi zinda hai — kyunki lauta hua function usko reference kar raha hai.

### Ye kyun exist karta hai / kyun important hai

- **Private state** — `count` bahar se touch nahi ho sakta, sirf `next()` ke through. Ye JavaScript ka original "private variable" mechanism hai.
- **Callbacks context yaad rakhte hain** — event handler / `setTimeout` / promise callback jab baad mein chalta hai, closure use us waqt ke variables deta hai.
- **React hooks** poori tarah closures pe khade hain — `useState` ka setter, `useEffect` ka callback, sab render ke us waqt ke props/state ko close over karte hain.

### Internally kaise kaam karta hai

Normally jab function return hota hai, uska scope (local variables) garbage collect ho jaata hai. Lekin agar koi cheez (lauta hua function, listener) us scope ke kisi variable ko abhi bhi reference kar rahi hai, to engine wo scope **memory mein rakhta hai**. Function object ke andar ek chhupi hui reference hoti hai us outer environment ki — `[[Environment]]`. Jab tak function object zinda, us environment ke variables zinda.

### Simple real-life analogy

Ek employee (`inner`) office (`outer`) chhod deta hai, par uske paas office ki ek chaabi (closure) reh jaati hai jis se wo abhi bhi ek locker (`count`) khol sakta hai. Office band ho gaya (function returned) par wo ek locker sirf is chaabi ke kaaran maintain kiya ja raha hai.

### Code — line by line

```javascript
function once(fn) {
  let called = false;
  let result;
  return function (...args) {
    if (!called) {
      called = true;
      result = fn.apply(this, args);
    }
    return result;
  };
}
```

- `let called = false` — private flag, sirf lauta hua function isse padh/likh sakta hai.
- `return function (...args)` — ye closure banta hai `called`, `result`, `fn` ke upar.
- `if (!called)` — pehli call pe `true` hoke andar jaata hai; aage har call skip.
- `result = fn.apply(this, args)` — asli function ek hi baar chalta hai; result cache.
- Har baar wahi cached `result` return — `once` ka poora point.

### Day-to-day use

- Module pattern / private state (`makeCounter`, `once`, `memoize`).
- Factory functions — `createLogger(prefix)` jo prefix ko yaad rakhne wala logger deta hai.
- Event handlers / `setTimeout` jo surrounding variables capture karte hain.
- Currying / partial application (`add(1)(2)`).
- Memoization — cache object ko closure mein rakhna.

### Classic `var` loop-closure bug

```javascript
const fns = [];
for (var i = 0; i < 3; i++) {
  fns.push(function () { return i; });
}
fns[0](); fns[1](); fns[2](); // 3, 3, 3  -- sab ek hi i share karte hain
```

`var i` poore loop ke liye **ek** binding hai; teeno closures usi ko dekh rahe hain, aur loop khatam hone pe `i` `3` hai.

**Fix 1 — `let`:**

```javascript
for (let i = 0; i < 3; i++) {
  fns.push(function () { return i; });
}
// 0, 1, 2  -- let har iteration ka apna binding deta hai
```

**Fix 2 — IIFE (pre-`let` tarika):**

```javascript
for (var i = 0; i < 3; i++) {
  (function (j) {
    fns.push(function () { return j; });
  })(i);
}
// 0, 1, 2  -- har iteration ke liye naya scope (j)
```

### Memory / leak angle

Closure jitne der zinda, uska captured scope utni der zinda. Agar tumne ek **long-lived** listener register kiya jo ek **bada object** capture karta hai, wo object kabhi GC nahi hoga jab tak listener remove na ho.

```javascript
function attach(bigData) {
  window.addEventListener("resize", function () {
    console.log(bigData.length); // bigData ab window listener ke through zinda
  });
}
```

Fix: listener ko `removeEventListener` se hataao, ya closure mein sirf zaroori chhoti value capture karo (`const n = bigData.length;`).

### Kab closures use karne chahiye

- Private state chahiye bina class ke — counter, cache, one-time init.
- Factory jo config yaad rakhe.
- Callback ko surrounding context chahiye.

### Kab dhyan rakhna chahiye

- Long-lived closure + bada captured object = leak. Cleanup zaroori.
- Loop ke andar closure — `let` use karo, `var` nahi.
- Bahut deep nesting se scope chain lambi — readability girti hai; module/class better.

### Pros and cons

**Closures**

- Pros: true encapsulation (private vars), stateful functions bina class, callbacks context yaad rakhte hain, functional patterns (curry/memoize) enable.
- Cons: captured scope zinda rehta hai — leak risk agar cleanup na ho; debugging mein "ye value yahan kahan se aayi" trace karna mushkil; har factory call naya function object (memory).

### Alternatives

- **Class + `#private` fields** — encapsulation ka modern OO tarika; jab multiple methods shared state pe kaam karein.
- **Module-level variable** — file ke top pe `let cache` — single instance ke liye closure se simpler.
- **`WeakMap` for private data** — instance ke saath private data associate karna bina leak (keys weakly held).

### Interview mein "Closure kya hai / kahan use kiya?"

> "Closure ek function + uske creation scope ka combination hai — function apne outer variables ko access kar sakta hai outer function ke return hone ke baad bhi, kyunki engine wo scope tab tak zinda rakhta hai jab tak koi inner function usse reference kar raha ho. Maine isse `once()` aur `memoize()` helpers banaane mein use kiya — cache aur 'called' flag closure mein private rehte hain, bahar se tamper nahi ho sakte. Dhyan rakhna padta hai ki long-lived listener bade objects capture na kare, warna wo GC nahi honge."

</Hinglish>

<Callout type="tip">

Har baar jab tum `arr.map(x => x + offset)` likhte ho, wo callback `offset` ke upar ek closure hai. Closures exotic nahi — tum din mein sau baar banaate ho.

</Callout>

## Real World Example

<RealWorld company="React">

React ka `useState` closure ke bina kaam hi nahi karta. `const [count, setCount] = useState(0)` ke baad `useEffect(() => { const id = setInterval(() => setCount(count + 1), 1000); return () => clearInterval(id); }, [])` — yahaan interval callback `count` ke us render ke value pe closure banata hai. Isiliye "stale closure" bug famous hai: empty dependency array ke saath callback hamesha pehle render ka `count` (0) dekhta hai. Fix: functional update `setCount(c => c + 1)` ya `count` ko deps mein daalo.

</RealWorld>

<RealWorld company="Node.js / Express middleware">

Express middleware factories closures hain: `function requireRole(role) { return function (req, res, next) { if (req.user.role !== role) return res.status(403).end(); next(); }; }`. `requireRole('admin')` ek middleware return karta hai jo `'admin'` ko closure mein yaad rakhta hai. Ek hi factory se `requireRole('admin')`, `requireRole('editor')` — har ek apna `role` capture kiye hue.

</RealWorld>

## Numbers That Matter

<Numbers>

- Lexical scope JavaScript ke shuru se (1995) hai — `let`/`const` ne sirf **block** scope add kiya (ES2015).
- Scope chain lookup: current -> outer (jahan likha) -> ... -> global; na mile to `ReferenceError`.
- Har function object apne saath ek `[[Environment]]` reference rakhta hai — yahi closure ka mechanism hai.
- `var` loop mein **1** shared binding; `let` loop mein **har iteration** ka naya binding.
- Closure-captured scope tab tak GC nahi hota jab tak closure (function object) reachable hai.

</Numbers>

## Interview Angle

<InterviewAngle>

Do format: (1) "Closure define karo aur ek use batao" — conceptual; (2) ek `for`+`setTimeout`/`for`+array snippet ka output — trap.

Achhe jawaab ka shape:

1. **Definition** — "Function + uska lexical outer scope; outer return hone ke baad bhi access rehta hai."
2. **Mechanism** — "Engine us scope ko zinda rakhta hai kyunki inner function usse reference kar raha hai (`[[Environment]]`)."
3. **Use** — private state / factory / callback context / memoize — ek concrete example.
4. **`var` bug** — "`var i` ek shared binding; sab closures `3` dekhte hain. `let` fix — per-iteration binding. Purana fix — IIFE."
5. **Leak** — "Long-lived closure bada object capture kare to leak; cleanup zaroori."

Red flag: "Closure matlab function ke andar function" — sirf nesting bolna, outer-variable capture aur lifetime miss karna.

</InterviewAngle>

## Common Mistakes

<Mistake>

**Closure ko "function ke andar function" tak limit samajhna.** Nesting closure ka sirf ek hissa hai. Asli baat: inner function outer ke variables capture karta hai aur unhe outer ke return ke baad bhi zinda rakhta hai. Bina outer-variable use ke sirf nesting closure ka point miss karti hai.

</Mistake>

<Mistake>

**`var` loop ke andar closure banana.** `for (var i...) arr.push(() => i)` — sab `i` ki final value dete hain. Loop variable ko `let` karo — har iteration ka apna binding — ya IIFE se per-iteration scope banao.

</Mistake>

<Mistake>

**Stale closure — purani value capture karke fresh expect karna.** React `useEffect(() => setInterval(() => setCount(count + 1), 1000), [])` hamesha `count = 0` dekhta hai kyunki callback pehle render pe close hua. Functional update `setCount(c => c + 1)` ya sahi deps use karo.

</Mistake>

<Mistake>

**Long-lived listener mein bada object capture karna.** `addEventListener` ka callback agar ek bade array/DOM tree ko close over kare aur listener kabhi remove na ho, wo memory kabhi free nahi hoti. Sirf zaroori chhoti value capture karo aur cleanup pe listener hataao.

</Mistake>

<Mistake>

**Private state ke liye closure banakar phir accidentally leak karna.** `function make() { let secret = 1; return { get: () => secret, raw: () => secret, _s: secret }; }` — `_s` ne value bahar expose kar di. Closure ka poora fayda tab jab andar ki cheez sirf controlled methods se mile.

</Mistake>

## Quick Revision

<QuickRevision>

- **Scope** = is line pe kaunse variables dikhte hain: global / function / block (`let`/`const`).
- **Lexical scope** = access "kahan likha hai" se, "kahan call hua" se nahi.
- **Scope chain** = current -> outer (jahan likha) -> ... -> global -> `ReferenceError`.
- **Closure** = function + uska outer scope; outer return hone ke baad bhi outer vars accessible.
- **Mechanism** = engine wo scope zinda rakhta hai jab tak inner function usse reference kar raha (`[[Environment]]`).
- **Uses** — private state, factory functions, callback context, currying, memoization.
- **`var` loop bug** — ek shared binding, sab closures final value dekhte hain; `let` ya IIFE se fix.
- **Leak** — long-lived closure + bada captured object = no GC; cleanup / capture-less karo.

</QuickRevision>

## Practice

<Callout type="tip">

**Chhota:** `for (let i = 0; i < 3; i++) setTimeout(() => console.log(i)); ` vs same with `var`. Dono ka output likho aur ek line mein `let` ne kya kiya.

**Medium:** Ek `createLogger(prefix)` factory likho jo ek function return kare `(msg) => console.log("[" + prefix + "] " + msg)`. `const api = createLogger("API")` banao. Explain karo `prefix` `createLogger` ke return hone ke baad bhi kaise zinda hai.

**Bada:** Ek `memoize(fn)` likho jo results ko ek closure-held `Map` mein cache kare (key = JSON.stringify(args)). Ek slow `fib(n)` pe try karo. Phir batao: is `Map` ko kaun zinda rakhe hue hai, aur agar `memoize`d function ko long-lived global bana do to memory ke saath kya risk hai.

</Callout>
