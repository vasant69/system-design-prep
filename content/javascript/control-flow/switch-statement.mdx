<SimpleDefinition>

`switch` compares **one value** against a list of `case` labels using **strict (`===`)** equality and runs the matching case's statements. Execution **falls through** to the next case unless you write `break` (or `return`) — fall-through can be used deliberately to group cases but is a common accidental bug. When you are just **mapping one value to another**, an object or `Map` lookup is often clearer; a long `if`-`else` chain is better when conditions are **ranges** or involve **multiple variables**.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Jab tumhe **ek hi variable** ko kai possible exact values ke against check karna ho — `status` `"pending"` hai ya `"shipped"` ya `"delivered"` — to `if (x === "a") ... else if (x === "b") ...` repetitive lagta hai. `switch` isi pattern ka dedicated syntax hai. Par iske do sharp edges hain (fall-through aur block scope) aur ek behtar alternative (lookup table) jo interview mein aksar poochha jaata hai.

### Ye kya hai — switch / case / break / default

```javascript
switch (fruit) {
  case "apple":
    price = 40;
    break;
  case "banana":
    price = 20;
    break;
  default:
    price = 0;
}
```

- `switch (fruit)` — ye value ek baar evaluate hoti hai.
- `case "apple":` — `fruit === "apple"` ho to yahan se chalna shuru.
- `break` — switch se bahar niklo. **Isko bhoolna sabse common bug hai.**
- `default` — koi case match na ho to yahan. Kahin bhi likh sakte ho par convention last mein.

### Ye kyun exist karta hai

Ek value, kai discrete branches — ye itna common pattern hai ki ise apna syntax mila. `switch` `if`-`else if` se thoda flatter dikhta hai jab har branch ek exact `===` match ho. C/Java se aayi hai, isliye fall-through jaisa purana behaviour bhi saath aaya.

### Internally kaise kaam karta hai — `===` match + fall-through

1. `switch (x)` ki `x` ek baar evaluate hoti hai.
2. Engine har `case` value ke saath `x === caseValue` check karta hai, upar se neeche.
3. Pehla match milte hi wahan se code chalna **shuru** hota hai — aur **rukta nahi** jab tak `break`, `return`, `throw`, ya switch ka end na aaye. Match ke baad ke `case` labels **ignore** hote hain, unka code phir bhi chalta hai. Isko **fall-through** kehte hain.

```javascript
switch (n) {
  case 1:
    console.log("one");
  case 2:
    console.log("two");
  case 3:
    console.log("three");
    break;
  default:
    console.log("other");
}
// n = 1 -> "one", "two", "three"  (break tak sab chala!)
// n = 2 -> "two", "three"
// n = 4 -> "other"
```

Matching **strict** hai — `switch (x) { case "1": }` `x = 1` (number) ke liye match **nahi** karega.

### Deliberate fall-through — cases group karna

Jab do-teen values ka same handling ho, `break` jaan-boojh ke chhodo:

```javascript
switch (day) {
  case "Sat":
  case "Sun":
    return "weekend";
  case "Mon":
  case "Tue":
  case "Wed":
  case "Thu":
  case "Fri":
    return "weekday";
}
```

`"Sat"` match hua -> koi statement nahi -> `"Sun"` mein gir gaya -> `return "weekend"`. Ye idiomatic hai. Confusion tab hoti hai jab ek case mein **code** ho aur `break` miss ho — reader nahi bata sakta "jaan-boojh ke" hai ya bug. Isliye deliberate fall-through pe `// falls through` comment likhne ka convention hai (ESLint `no-fallthrough` isi comment se santusht hota hai).

### Simple real-life analogy

`switch` = ek train jo ek station (matching case) pe rukti hi nahi — waha se chalti rehti hai agli sab stations pe (`break` = emergency stop / destination). `default` = "koi station match nahi hua to last stop pe utaar do".

### Code — line by line

```javascript
function getStatusLabel(status) {
  switch (status) {
    case "pending":
    case "processing":
      return "In progress";
    case "shipped":
      return "On the way";
    case "delivered":
      return "Complete";
    default:
      return "Unknown";
  }
}
```

- `case "pending":` ke neeche kuch nahi -> `"processing"` mein fall-through -> dono `"In progress"`.
- `return` use kiya `break` ke bajaye — `return` function se hi bahar nikaal deta hai, to `break` ki zaroorat nahi aur galti se fall-through ka risk khatam.
- `default: return "Unknown"` — har unknown status safe.

### Block scope in cases — `let` / `const` ke liye `{ }` chahiye

Saare `case` ek hi block share karte hain. Ek case mein `let`/`const` declare kiya to wo doosre cases ke liye bhi "exist" karta hai (TDZ mein) — `SyntaxError: Identifier 'x' has already been declared` ya lexical errors aate hain.

```javascript
switch (type) {
  case "a": {
    const result = compute();   // apna { } block
    return result;
  }
  case "b": {
    const result = other();     // ab ye alag scope hai — OK
    return result;
  }
}
```

Har aisi case body ko `{ }` mein wrap karo jisme `let`/`const` ho.

### Day-to-day use

- Redux/`useReducer` reducers — `switch (action.type)` classic pattern.
- State machines — `switch (currentState)`.
- Command dispatch — CLI arg, event kind.
- HTTP status buckets, enum-like string handling.

### DECISION: switch vs if-else chain vs lookup table

| Scenario | Best choice | Kyun |
|---|---|---|
| Ek variable, 3+ **exact** value matches, har branch mein logic/statements | `switch` | Flat, intent clear, reducer-style |
| Ek variable ko doosri value pe **map** karna (value -> label, key -> handler) | **lookup object / Map** | Data hai, control flow nahi — ek line, test/extend aasan |
| Conditions **ranges** hain (`score > 90`), ya **multiple variables** involved | `if` / `else if` | `switch` sirf `===` karta hai, ranges express nahi kar sakta |
| 2 cases | plain `if` / ternary | `switch` overkill |
| Handlers jo runtime pe register/override hote hain | `Map` | keys dynamic ho sakti hain, `switch` static hai |

**Lookup table example** — jab har case sirf "return a value" ya "call a function" ho:

```javascript
// switch se
function labelFor(kind) {
  switch (kind) {
    case "info": return "Information";
    case "warn": return "Warning";
    case "error": return "Error";
    default: return "Notice";
  }
}

// lookup se — data-driven
const LABELS = { info: "Information", warn: "Warning", error: "Error" };
const labelFor = (kind) => LABELS[kind] ?? "Notice";

// handlers ke liye
const handlers = { start: startFn, stop: stopFn, reset: resetFn };
function dispatch(cmd, ...args) {
  const fn = handlers[cmd] || fallbackFn;
  return fn(...args);
}
```

Lookup better hoti hai jab: mapping pure data hai, cases badalte rehte hain, ya keys config/plugin se aati hain. `switch` better jab: har branch mein multi-step logic hai, ya `default` ke alawa complex control flow (early returns, throws) hai.

### `break` vs `return`

Function ke andar `switch` ho to har case mein `return` likho — `break` ki zaroorat khatam, aur accidental fall-through impossible. `switch` sirf side-effects ke liye (kuch set karna, kuch call karna) ho tabhi `break` chahiye.

### Kab switch use karna chahiye

- Ek discrete value, 3+ exact-match branches, har branch mein real logic.
- `useReducer` / Redux reducer — community standard, readable.
- Deliberate case grouping needed (weekday/weekend).

### Kab switch use nahi karna chahiye

- Sirf value-to-value mapping — lookup object cleaner.
- Range conditions ya multiple variables — `if`/`else if`.
- 2 branches — `if`/ternary.
- Fall-through logic itni complex ho ki comment ke bina samajh na aaye.

### Pros and cons

**`switch`**

- **Pros:** ek variable ke exact matches ke liye flat aur readable; case grouping possible; reducer pattern ka idiom.
- **Cons:** fall-through default hai (bug-prone); sirf `===` (no ranges); `let`/`const` ke liye `{ }` chahiye; lookup table se zyada boilerplate jab mapping pure data ho.

### Alternatives

- **Lookup object / `Map`** — value-to-value ya key-to-handler mapping; dynamic keys.
- **`if` / `else if`** — ranges, multiple variables, complex boolean conditions.
- **Polymorphism / strategy pattern** — jab branches badi classes/modules ban jaayein.
- **Pattern matching libs** (`ts-pattern`) — TypeScript mein exhaustive, type-safe matching.

### Interview mein "switch vs object lookup?"

> "`switch` tab use karta hoon jab ek variable ke 3+ exact-match cases hon aur har branch mein real logic ho — jaise ek reducer. Par agar main sirf ek value ko doosri value ya ek handler function pe map kar raha hoon, to object/`Map` lookup zyada saaf hai: wo control flow nahi, data hai, ek line mein likh sakta hoon, test karna aur naye cases add karna trivial hai, aur keys runtime pe aa sakti hain. `if`/`else if` tab jab conditions ranges hon ya ek se zyada variable involve ho — `switch` sirf `===` karta hai. Aur function ke andar main `break` ki jagah `return` use karta hoon taaki accidental fall-through ho hi na sake."

</Hinglish>

<Callout type="trap">

`switch` **strict `===`** use karta hai. `case "1":` string, `switch (userInput)` jahan `userInput` number `1` hai — match nahi karega. Types pehle align karo (`Number(x)` / `String(x)`).

</Callout>

## Real World Example

<RealWorld company="Redux / React useReducer">

Redux reducers aur React ke `useReducer` mein `switch (action.type)` de-facto standard hai: har `case "INCREMENT":` naya state return karta hai, `default: return state` unknown actions ke liye. Yahan `switch` isliye jeetta hai — har branch mein real state-transition logic hota hai, aur `return` fall-through ko impossible bana deta hai. Redux Toolkit ke `createSlice` ne isse abstract kar diya, par under the hood wahi dispatch-on-type pattern hai.

</RealWorld>

<RealWorld company="Node.js CLI tools / Express">

CLI tools mein `switch (command)` common tha, par bade tools (webpack, ESLint) command-to-handler **lookup objects** use karte hain: `const commands = { build, watch, init }; (commands[argv._[0]] || help)()`. Isse har command apni file mein reh sakti hai, plugins naye commands register kar sakte hain, aur ek missing command handle karna ek `|| help` hai — 30-line `switch` maintain karne se behtar.

</RealWorld>

## Numbers That Matter

<Numbers>

- `switch` cases **strict `===`** se compare hote hain — koi type coercion nahi (unlike `==`).
- Fall-through **default behaviour** hai — har `case` mein explicitly `break`/`return` chahiye warna agla case bhi chalega.
- `default` clause **optional** hai aur switch mein **kahin bhi** ho sakti hai (last mein rakhna sirf convention).
- ESLint `no-fallthrough` rule ek `// falls through` comment ya empty case ko allow karta hai; code-wali case bina break ke error deta hai.
- Ek `switch` ke saare cases **ek lexical scope** share karte hain — per-case `let`/`const` ke liye `{ }` mandatory.
- Modern style guides (Airbnb) reducer ke bahar `switch` ko discourage karti hain jab lookup object kaam kar sakta ho.

</Numbers>

## Interview Angle

<InterviewAngle>

Do cheezein guaranteed: (1) fall-through predict karna — `case 1:` bina `break` ke, (2) "switch vs object lookup kab?"

Model answer shape:

1. **Mechanism** — "ek value, `===` match, matching case se chalna shuru, `break`/`return` tak rukta nahi (fall-through)."
2. **Deliberate grouping** — "`break` jaan-boojh ke chhodkar multiple cases group kar sakte ho."
3. **Scope gotcha** — "per-case `let`/`const` ke liye `{ }` block chahiye."
4. **Decision** — "value-to-value mapping = lookup object; ranges/multi-var = `if/else if`; discrete exact matches with logic = `switch`."
5. **Practice** — "function ke andar `break` ki jagah `return`."

Red flag: yeh sochna ki `switch` `==` (loose) use karta hai, ya `case x > 5:` jaisa range likhna (invalid).

</InterviewAngle>

## Common Mistakes

<Mistake>

**`break` bhoolna.** Ek `case` mein code likha par `break`/`return` nahi — agla case bhi chal jaata hai. Function ke andar hamesha `return`; side-effect switch mein har case ke end pe `break`.

</Mistake>

<Mistake>

**Ye maanna ki `switch` loose equality karta hai.** `case "1":` `switch (1)` ke number `1` ko match nahi karega — `===` hai. String/number align karo pehle.

</Mistake>

<Mistake>

**Per-case `let`/`const` ko `{ }` mein na wrap karna.** Saare cases ek scope share karte hain — do cases mein `const x` `SyntaxError` deta hai. Har aisi case body ko `{ }` block do.

</Mistake>

<Mistake>

**Ranges ke liye `switch` use karne ki koshish.** `case n > 90:` invalid — ye `(n > 90) === n` compare karega jo hamesha `false`. Ranges ke liye `if`/`else if`.

</Mistake>

<Mistake>

**Pure value mapping ke liye 20-line `switch`.** `switch (kind) { case "a": return "A"; ... }` — ye ek `const MAP = { a: "A", ... }; return MAP[kind] ?? fallback` hai. Data ko data ki tarah likho.

</Mistake>

## Quick Revision

<QuickRevision>

- `switch (x)` — `x` ek baar evaluate, har `case` se `x === caseValue` (**strict**).
- Match ke baad code **rukta nahi** — `break` / `return` / `throw` / end tak chalta hai = **fall-through**.
- Deliberate fall-through: empty cases stack karke group (`case "Sat": case "Sun": return "weekend"`).
- Function ke andar: `break` ki jagah **`return`** — accidental fall-through impossible.
- Per-case `let`/`const` -> us case body ko `{ }` block mein wrap karo (saare cases ek scope share karte hain).
- `default` optional, kahin bhi rakh sakte ho, convention last.
- **Lookup object / Map** better jab: value-to-value / key-to-handler mapping, dynamic keys, cases badalte rehte hain.
- **`if` / `else if`** better jab: range conditions (`x > 90`), multiple variables, complex booleans.
- `switch` `===` karta hai — `case "1"` number `1` ko match nahi karega.
- Reducer (`switch (action.type)`) = `switch` ka strongest legitimate use case.

</QuickRevision>

## Practice

<Callout type="tip">

**Chhota:** Predict output: `switch (2) { case 1: console.log("a"); case 2: console.log("b"); case 3: console.log("c"); break; case 4: console.log("d"); }` — kya print hoga aur kyun?

**Medium:** Ek `httpCategory(code)` `switch` se likho jo `200`-`299` ko... nahi ruko — ye ranges hain, `switch` galat tool hai. `Math.floor(code / 100)` pe `switch` karo: `2 -> "success"`, `3 -> "redirect"`, `4 -> "client error"`, `5 -> "server error"`, `default -> "unknown"`. Phir batao tumne `code` pe direct `switch` kyun nahi kiya.

**Bada:** Ek chhota event system: `switch (event.type)` se `"click"`, `"hover"`, `"focus"`, `"blur"` handle karo, har case mein 2-3 lines ka logic. Ab isko ek `handlers` object mein refactor karo (`{ click: fn, hover: fn, ... }`) aur `(handlers[event.type] || noop)(event)` se dispatch karo. Do-teen line mein likho ki kis situation mein `switch` version behtar tha aur kis mein object version.

</Callout>
