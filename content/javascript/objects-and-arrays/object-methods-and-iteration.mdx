<SimpleDefinition>

`Object.keys`, `Object.values`, and `Object.entries` turn an object's **own enumerable string-keyed** properties into arrays, which you loop over with `for...of`. `for...in` also loops keys but **walks the prototype chain**, which is why the `Object.*` helpers are safer. `Object.assign` and **object spread** (`{ ...a, ...b }`) merge or copy objects, but only **one level deep** — nested objects stay shared. `structuredClone` makes a true **deep copy**; `JSON.parse(JSON.stringify(x))` is a limited older alternative.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Object bana lena aasaan hai — asli kaam hai uske upar loop karna, use copy karna, do objects merge karna. Yahi 3 cheezein daily code mein baar-baar aati hain, aur har ek mein ek chhupa hua trap hai: prototype chain, aur shallow copy.

### Ye kya hai — keys/values/entries

Object khud iterable nahi hai (`for...of obj` error deta hai). Use loop karne ke liye pehle uski properties ko **array** mein badlo:

```javascript
const user = { name: "Vasant", age: 30, city: "Pune" };

Object.keys(user);    // ["name", "age", "city"]
Object.values(user);  // ["Vasant", 30, "Pune"]
Object.entries(user); // [["name","Vasant"], ["age",30], ["city","Pune"]]
```

Teeno sirf **own enumerable string keys** dete hain — prototype ki properties, non-enumerable properties, aur symbol keys chhod dete hain.

### Ye kyun exist karta hai

Purane din mein sirf `for...in` tha, jo prototype chain bhi walk karta tha — har loop mein defensive `if (obj.hasOwnProperty(k))` likhna padta tha. ES5 ne `Object.keys` diya (own-only, predictable), ES2017 ne `Object.values` / `Object.entries` diye taaki `Object.keys(o).map(k => o[k])` jaisa boilerplate na likhna pade. Ab standard pattern hai `for...of` + `Object.entries`.

### Internally kaise kaam karta hai

Har object ke paas ek internal `[[OwnPropertyKeys]]` list hoti hai. `Object.keys` us list se sirf **string** keys leta hai jinka `enumerable` flag `true` hai, un order mein: pehle integer-jaisi keys ascending, phir baaki string keys insertion order mein. `for...in` iske upar prototype chain bhi chadhta hai — `obj` ke keys, phir `Object.getPrototypeOf(obj)` ke enumerable keys, aur aage tak. Isi liye kisi ne agar `Array.prototype` ya `Object.prototype` pe koi enumerable property add ki (purani libraries karti thin), to tumhara `for...in` usko bhi pick kar leta.

### Simple real-life analogy

`Object.keys` = ek register jismein sirf **is kamre ke apne** saamaan ki list hai. `for...in` = wahi list, par usme upar wale floors (parent, grandparent) ka bhi saamaan mix ho jata hai jab tak tum har entry pe "ye is kamre ka hai kya?" (`hasOwnProperty`) na poochho.

### Code — line by line

```javascript
const price = { apple: 50, banana: 20, cherry: 200 };

for (const [item, cost] of Object.entries(price)) {
  console.log(item + ": " + cost);
}

const total = Object.values(price).reduce((sum, c) => sum + c, 0);

const expensive = Object.keys(price).filter((k) => price[k] > 30);
```

- `Object.entries(price)` — `[["apple",50], ["banana",20], ["cherry",200]]` array banaya.
- `for (const [item, cost] of ...)` — har pair ko destructure karke `item` aur `cost` variables mein rakha; `for...of` isliye kyunki ab hamare paas ek array hai.
- `Object.values(price).reduce(...)` — sirf values ka array le ke unhe add kiya.
- `Object.keys(price).filter(...)` — keys pe filter, andar `price[k]` se value dekhi.

### for...in vs Object.keys — kaunsa kab

| | `for...in` | `for...of Object.keys(obj)` |
|---|---|---|
| Kya iterate karta | own + inherited enumerable string keys | sirf own enumerable string keys |
| Prototype pollution risk | haan | nahi |
| `break` / `continue` | haan | haan |
| Arrays pe use | **avoid** (index string milte, order guarantee kamzor) | theek, par `for...of arr` ya `.forEach` behtar |
| Recommendation | sirf jab inherited keys genuinely chahiye | **default choice** |

### Merge aur copy — Object.assign / spread

```javascript
const defaults = { theme: "light", fontSize: 14 };
const userPrefs = { fontSize: 16 };

const merged1 = Object.assign({}, defaults, userPrefs);
const merged2 = { ...defaults, ...userPrefs };
// dono: { theme: "light", fontSize: 16 }
```

- `Object.assign(target, ...sources)` — sources ko left-to-right `target` mein copy karta hai, **target ko mutate** karta hai aur return bhi karta hai. Isi liye pehla arg `{}` — warna `defaults` mutate ho jata.
- `{ ...defaults, ...userPrefs }` — naya object, baad wale spread ki keys pehle wali ko override karti hain. Ye zyada common aur readable hai.

### THE trap — shallow copy

```javascript
const original = { name: "V", address: { city: "Pune" } };
const copy = { ...original };

copy.name = "Raj";            // original.name still "V"  -- theek
copy.address.city = "Mumbai"; // original.address.city ALSO "Mumbai"  -- LEAK
```

Spread aur `Object.assign` **shallow** hain: top-level primitive values copy hoti hain, par nested object/array ki sirf **reference** copy hoti hai. `copy.address` aur `original.address` **wahi ek object** point karte hain. Isi liye state management mein "maine to copy banaya tha, phir bhi original badal gaya" wala bug aata hai.

### Deep copy — structuredClone

```javascript
const original = { name: "V", address: { city: "Pune" }, tags: ["a", "b"] };
const deep = structuredClone(original);

deep.address.city = "Mumbai"; // original.address.city still "Pune"  -- alag object
```

`structuredClone` (browsers + Node 17+) recursively sab kuch copy karta hai — nested objects, arrays, `Date`, `Map`, `Set`, typed arrays, even circular references. **Functions**, DOM nodes, aur class prototype identity copy nahi hote (function pe `DataCloneError`).

### Purana hack — JSON.parse(JSON.stringify(x))

```javascript
const deep = JSON.parse(JSON.stringify(original));
```

Chalta hai plain data ke liye, par bahut kuch todta hai:

- `undefined`, functions, symbols → key hi gayab ho jati hai.
- `Date` → ISO **string** ban jati hai (wapas `Date` nahi milta).
- `NaN`, `Infinity` → `null`.
- `Map`, `Set` → `{}` (empty object).
- `BigInt` → **throw**.
- Circular reference → **throw**.

Aaj `structuredClone` available hai to wahi use karo; JSON hack sirf tab jab tum 100% jante ho data plain JSON-safe hai (ya purana environment ho).

### Kab kya use karna chahiye

- Loop karna → `for...of Object.entries(obj)` (ya `keys`/`values` — jo chahiye).
- Merge / override with defaults → `{ ...defaults, ...overrides }`.
- Ek object ki flat copy → `{ ...obj }`.
- Nested data ki safe copy → `structuredClone(obj)`.
- Inherited properties genuinely chahiye → `for...in` (+ `hasOwnProperty` guard agar sirf own chahiye).

### Kab kya use nahi karna chahiye

- Plain object ko iterate karne ke liye `for...in` mat use karo — prototype leak. `Object.keys` / `entries`.
- Nested object ki copy ke liye `{ ...obj }` mat samjho deep hai — nested references shared reh jate hain.
- `Date`/`Map`/`BigInt`/circular data pe `JSON.parse(JSON.stringify())` mat use karo — silent data loss ya throw.
- `Object.assign(a, b)` jab `a` ko mutate nahi karna — pehla arg `{}` bhoolna mat.

### Pros and cons

**`Object.keys/values/entries` + `for...of`**

- Own-only, predictable order, `break`/`continue` chalte hain.
- `entries` destructuring ke saath sabse readable.
- Cons: har call ek naya array banata hai (bade hot loops mein micro-cost).

**`for...in`**

- Inherited enumerable keys bhi milti hain (kabhi-kabhi chahiye).
- Cons: prototype pollution, arrays pe order/index-type surprises, har iteration pe guard chahiye.

### Alternatives

- **`Object.getOwnPropertyNames(obj)`** — non-enumerable keys bhi chahiye to.
- **`Reflect.ownKeys(obj)`** — string + symbol keys dono.
- **`Object.fromEntries(pairs)`** — `entries` ka ulta; array of pairs se object banao (map/filter ke baad object wapas banane mein).
- **Lodash `cloneDeep`** — `structuredClone` se pehle deep-copy ka standard; functions handle karta hai, par ek dependency.

### Interview mein "for...in kyun avoid karte ho?"

> "`for...in` prototype chain walk karta hai, to agar kisi ne `Object.prototype` ya kisi parent pe enumerable property add ki ho, wo bhi loop mein aa jati hai — isliye har baar `hasOwnProperty` guard chahiye. `Object.keys` / `entries` shuru se hi own-only, enumerable-only, predictable order dete hain, aur `for...of` ke saath `break` bhi kaam karta hai. Arrays pe `for...in` aur bhi kharab — wo string indices deta hai aur order guarantee kamzor hai."

</Hinglish>

<Callout type="tip">

`{ ...obj }` aur `structuredClone(obj)` ka farak yaad rakhne ka tareeka: spread ek **level** khodta hai, `structuredClone` **poora ped** khodta hai. State/Redux/React reducers mein jitne levels tum badal rahe ho, utne levels naye banao — ya `structuredClone` se poora clone.

</Callout>

## Real World Example

<RealWorld company="Redux / React state">

Redux ka core rule: state ko mutate mat karo, naya object return karo. Log `{ ...state, count: state.count + 1 }` likhte hain — ye theek hai kyunki sirf top-level badla. Par jab nested update hota hai — `state.user.profile.name` — to `{ ...state, user: { ...state.user, profile: { ...state.user.profile, name } } }` likhna padta hai. Jo team ye bhool ke `{ ...state }` karke `state.user.profile.name = x` kar deti hai, uska component re-render hi nahi hota (reference wahi rehti hai) — classic shallow-copy bug. Isi dard ki wajah se Redux Toolkit `immer` use karta hai.

</RealWorld>

<RealWorld company="Node.js APIs">

Config merge Node backends mein har jagah: `const config = { ...defaultConfig, ...envConfig, ...cliFlags }` — right-most source jeetta hai. `Object.entries(process.env)` se env vars pe loop karke prefix-filter karna (`DB_` se shuru hone wale) bhi common. Aur jab ek API response ko log karne se pehle `password` field hatana ho, log `const safe = structuredClone(user); delete safe.password;` karte hain taaki original request object touch na ho.

</RealWorld>

## Numbers That Matter

<Numbers>

- `Object.keys` **ES5 (2009)**; `Object.values` / `Object.entries` **ES2017**; `Object.fromEntries` **ES2019**.
- `structuredClone` global function **2022** mein standardize hua (Node 17+, saare modern browsers).
- Key order: integer-jaisi keys pehle **ascending numeric**, phir string keys **insertion order** — 2 groups.
- `Object.assign` aur spread dono **1 level** deep copy karte hain.
- `JSON.parse(JSON.stringify())` kam se kam **6** cheezein galat karta hai: `undefined`/function drop, `Date`→string, `NaN`/`Infinity`→`null`, `Map`/`Set`→`{}`, `BigInt`→throw, circular→throw.
- `for...in` prototype chain ke **saare** levels ki enumerable string keys deta hai.

</Numbers>

## Interview Angle

<InterviewAngle>

Do cheezein test hoti hain: (1) object pe loop karne ka idiomatic tareeka, (2) shallow vs deep copy ka farak — aur ye ki tumne isse bug khaya hai ya nahi.

Model answer shape:

1. **Iteration** — "`for...of Object.entries(obj)` with destructuring; `Object.keys`/`values` jab sirf ek chahiye."
2. **for...in caveat** — "Prototype chain walk karta hai, isliye own objects pe avoid."
3. **Merge** — "`{ ...a, ...b }` — right-most jeetta hai; `Object.assign` mutating hai, pehla arg `{}`."
4. **Shallow trap** — "Spread/`assign` nested references share karte hain — `copy.nested.x = 1` original ko bhi badalta hai."
5. **Deep copy** — "`structuredClone` — handles nested, Date, Map, circular; functions nahi. Purana hack `JSON.parse(JSON.stringify())` — limited."

Red flag: "spread se deep copy ho jati hai" — nahi, sirf ek level.

</InterviewAngle>

## Common Mistakes

<Mistake>

**`for...in` se plain object iterate karna bina guard ke.** Agar kisi dependency ne prototype pollute kiya (ya tumne khud `Object.prototype` extend kiya), extra keys loop mein ghus jati hain. `Object.keys(obj)` / `Object.entries(obj)` shuru se own-only hain — inhe default banao.

</Mistake>

<Mistake>

**`{ ...obj }` ko deep copy samajhna.** Top-level primitives copy hote hain, par `obj.nested` ki sirf reference. `copy.nested.value = 1` original ko bhi badal deta hai. Nested safe copy chahiye to `structuredClone(obj)` ya har level manually spread karo.

</Mistake>

<Mistake>

**`Object.assign(target, source)` mein `target` ko `{}` na dena.** `Object.assign(defaults, overrides)` `defaults` ko mutate kar deta hai — agla jo `defaults` use karega use badla hua milega. Copy chahiye to `Object.assign({}, defaults, overrides)`.

</Mistake>

<Mistake>

**`JSON.parse(JSON.stringify(obj))` ko universal deep-clone maanna.** `Date` string ban jati hai, `undefined`/function keys gayab, `Map`/`Set` khali `{}`, `NaN`→`null`, `BigInt` aur circular refs throw karte hain. Modern code mein `structuredClone`.

</Mistake>

<Mistake>

**`Object.values` / `entries` ka order guaranteed number-sorted maan lena.** Sirf integer-jaisi keys pehle numeric order mein aati hain; baaki string keys insertion order mein. Agar `{ 2: "b", 1: "a", x: "c" }` hai to order `1, 2, x` hai — insertion order nahi.

</Mistake>

## Quick Revision

<QuickRevision>

- `Object.keys / values / entries` → own enumerable string keys ka array; `for...of` se loop.
- `for (const [k, v] of Object.entries(obj))` — idiomatic object loop.
- `for...in` prototype chain walk karta hai → plain objects pe avoid; sirf jab inherited keys chahiye.
- `{ ...a, ...b }` — merge, right-most key jeetti hai; naya object.
- `Object.assign(target, ...src)` — `target` mutate karta hai; copy ke liye `Object.assign({}, ...)`.
- Spread aur `Object.assign` **shallow** — nested object/array references shared reh jate hain.
- `structuredClone(obj)` — true deep copy; Date/Map/Set/circular OK; functions nahi (throw).
- `JSON.parse(JSON.stringify(obj))` — purana hack; Date→string, undefined/function drop, Map/Set→{}, BigInt/circular throw.
- `Object.fromEntries(pairs)` — entries ka ulta, array-of-pairs se object.
- Key order: integer keys ascending pehle, phir string keys insertion order.

</QuickRevision>

## Practice

<Callout type="tip">

**Chhota:** `const a = { x: 1, nested: { y: 2 } }; const b = { ...a }; b.nested.y = 99; console.log(a.nested.y);` — kya print hoga aur kyun?

**Medium:** Ek function `invert(obj)` likho jo keys aur values swap kar de — `invert({ a: 1, b: 2 })` → `{ "1": "a", "2": "b" }`. `Object.entries` + `map` + `Object.fromEntries` use karo.

**Bada:** Ek `mergeConfig(defaults, overrides)` likho jo **deep** merge kare (nested objects recursively merge hon, arrays overrides se replace hon). Ek test case likho jahan shallow `{ ...defaults, ...overrides }` galat jawab deta hai aur tumhara version sahi.

</Callout>
