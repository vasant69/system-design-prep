<SimpleDefinition>

`forEach`, `map`, `filter`, `find`, `findIndex`, `some`, `every`, `includes`, and `indexOf` are the standard array iteration methods. `map` returns a **new array of the same length** with each element transformed — use it for its return value; `forEach` returns `undefined` and exists only for **side effects**. `filter` returns an **array of all matches** (possibly empty); `find` returns the **first match or `undefined`** and stops early. Chaining `map` and `filter` reads well but makes **multiple passes** over the data.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Ye methods JavaScript ka daily bread hain. Interview mein sabse common galti: `map` ko `forEach` ki jagah use karna (ya ulta), aur `filter` ko `find` ki jagah. Dono jodon ka farak clear hona chahiye — kab kaunsa, aur kyun.

### Ye kya hai — ek quick map

| Method | Kya deta hai | Kab rukta hai |
|---|---|---|
| `forEach(fn)` | `undefined` | poora array, hamesha |
| `map(fn)` | naya array (same length) | poora array, hamesha |
| `filter(fn)` | naya array (matching elements) | poora array, hamesha |
| `find(fn)` | pehla matching **element** ya `undefined` | pehla match milte hi |
| `findIndex(fn)` | pehle match ka **index** ya `-1` | pehla match milte hi |
| `some(fn)` | `true` agar koi ek match, warna `false` | pehla `true` milte hi |
| `every(fn)` | `true` agar sab match, warna `false` | pehla `false` milte hi |
| `includes(x)` | `true`/`false` — value mojood hai? | match milte hi |
| `indexOf(x)` | index ya `-1` | match milte hi |

### Ye kyun exist karta hai

`for` loop se sab ho sakta hai, par intent chhup jata hai. `results.filter(r => r.active)` ek nazar mein bata deta hai "subset chahiye"; `for` loop padhne ke liye body poori scan karni padti hai. Ye methods **declarative** hain — kya chahiye wo bolta hai, kaise nahi.

### Internally kaise kaam karta hai

Har method array pe iterate karta hai aur har element pe tumhara callback `(element, index, array)` ke saath call karta hai. Farak sirf itna hai ki result kaise banta hai:

- `map` ek naya array pehle se allocate karta hai (same length) aur har slot mein callback ka return daalta hai.
- `filter` naya array banata hai aur sirf woh elements push karta hai jinpe callback truthy return kare.
- `find`/`some` short-circuit karte hain — pehla match/`true` milte hi loop `break` kar dete hain, baaki elements touch nahi hote.
- `forEach` return value collect hi nahi karta — callback ka return discard.

Holes (empty slots) ko `map`/`filter`/`forEach` **skip** karte hain, `find`/`includes` unhe `undefined` treat karte hain.

### Simple real-life analogy

- `map` = ek assembly line — har item andar jata hai, transform hoke bahar aata hai, **utne hi** items nikalte hain.
- `filter` = ek chhalni (sieve) — kuch items pass hote hain, baaki reh jate hain, count kam ho sakta hai.
- `forEach` = ek inspector jo har item dekhta hai aur kahin note likhta hai (side effect), par line se kuch nikalta nahi.
- `find` = "pehla laal box dhoondo aur ruk jao" — mil gaya to aage nahi dekhte.

### map vs forEach — the decision

```javascript
const prices = [100, 200, 300];

// map: return value CHAHIYE
const withGst = prices.map((p) => p * 1.18); // [118, 236, 354]

// forEach: SIDE EFFECT ke liye
prices.forEach((p) => console.log("Price:", p)); // undefined return, sirf logging
```

| Sawaal | `map` | `forEach` |
|---|---|---|
| Return | naya transformed array | `undefined` |
| Use kab | tumhe transformed array chahiye | sirf side effect (log, DOM update, push to external) |
| Chain ho sakta | haan (`.map().filter()`) | nahi (undefined return) |
| Callback pure hona chahiye? | haan (sirf transform, side effect nahi) | side effect hi iska kaam hai |

**Rule:** agar tum returned array use nahi kar rahe, to `map` mat likho — `forEach` ya `for...of` use karo. `map` jiska result phenk diya jaye wo reader ko confuse karta hai aur linter (`no-unused-expressions` / `array-callback-return`) flag karta hai.

```javascript
// GALAT — map ka result use nahi ho raha
items.map((item) => { renderRow(item); });

// SAHI
items.forEach((item) => renderRow(item));
// ya
for (const item of items) renderRow(item);
```

### filter vs find — the decision

```javascript
const users = [
  { id: 1, role: "admin" },
  { id: 2, role: "user" },
  { id: 3, role: "admin" },
];

const admins = users.filter((u) => u.role === "admin"); // [{id:1...}, {id:3...}]
const firstAdmin = users.find((u) => u.role === "admin"); // {id:1, role:"admin"}
const noManager = users.find((u) => u.role === "manager"); // undefined
```

| Sawaal | `filter` | `find` |
|---|---|---|
| Return | **hamesha array** (0, 1, ya zyada matches) | pehla matching **element**, ya `undefined` |
| Kitne matches | saare | sirf pehla |
| Rukta hai jaldi | nahi — poora array | haan — pehla match milte hi |
| Empty result | `[]` | `undefined` |
| Use kab | subset / list chahiye, ya count (`.filter(...).length`) | ek specific item chahiye (id se lookup) |

**Common bug:** `find` ka result use karne se pehle undefined check karo. `users.find(u => u.id === 99).name` crash karta hai agar koi user nahi mila (`Cannot read properties of undefined`). `users.find(...)?.name` ya pehle `if (user)`.

**Ulta bug:** ek hi item chahiye par `filter` use karke `[0]` lena — `users.filter(u => u.id === 5)[0]`. Ye poora array scan karta hai aur ek throwaway array banata hai. `find` short-circuit karta hai aur seedha element deta hai.

### some vs every vs includes

```javascript
[1, 2, 3].some((n) => n > 2);    // true  -- kam se kam ek
[1, 2, 3].every((n) => n > 0);   // true  -- sab
[1, 2, 3].includes(2);           // true  -- exact value (===, NaN bhi handle)
[1, 2, 3].indexOf(2);            // 1     -- index, ya -1
```

- `some` = "koi bhi?" — OR jaisa, pehla `true` pe ruk jata hai.
- `every` = "sabhi?" — AND jaisa, pehla `false` pe ruk jata hai. (Note: khali array pe `every` `true` deta hai — vacuous truth.)
- `includes` vs `indexOf`: `includes` `NaN` ko dhoondh leta hai (`[NaN].includes(NaN)` `true`), `indexOf` nahi (`[NaN].indexOf(NaN)` `-1`). Sirf "hai ya nahi" chahiye to `includes` saaf hai; index chahiye to `indexOf`/`findIndex`.

### Chaining aur "two passes" cost

```javascript
const result = orders
  .filter((o) => o.status === "paid")
  .map((o) => o.amount)
  .reduce((sum, a) => sum + a, 0);
```

Readable hai, par `filter` poora array ek baar ghoomta hai (naya array banata), phir `map` us naye array ko dubara (ek aur naya array), phir `reduce`. Chhote/medium arrays pe ye bilkul theek — clarity jeeti. **Bade arrays (lakhon elements) ya hot paths pe** ye 2-3 passes + 2 intermediate arrays cost karta hai; wahan ek single `reduce` ya `for...of` behtar:

```javascript
let total = 0;
for (const o of orders) {
  if (o.status === "paid") total += o.amount;
}
```

### for...of — jab break / await chahiye

```javascript
for (const item of items) {
  if (item.broken) break;          // map/forEach mein break nahi hota
  await save(item);                // forEach async ko await nahi karta
}
```

`forEach` ke callback mein `await` likhne se `forEach` **wait nahi karta** — wo saare callbacks fire karke aage badh jata hai. Sequential async ke liye `for...of` + `await`. `break`/`continue`/`return` (outer function se) bhi sirf `for...of` / classic `for` mein kaam karte hain.

### Kab kya use karna chahiye

- Har element ko transform, naya array chahiye → `map`.
- Sirf side effect (log, DOM, external push), koi return nahi → `forEach` (ya `for...of`).
- Subset / list / count → `filter` (`.filter(...).length` count ke liye).
- Ek specific item (id se) → `find` / `findIndex`.
- "Koi match hai?" boolean → `some`; "sab match?" → `every`.
- "Ye value hai?" → `includes`.
- `break` / early exit / sequential `await` → `for...of`.

### Kab kya use nahi karna chahiye

- `map` jiska result phenk do — reader + linter confuse. `forEach`/`for...of`.
- `filter(...)[0]` ek item ke liye — poora scan + throwaway array. `find`.
- `forEach` async loop ke saath jab sequential chahiye — `await` ignore hota hai. `for...of`.
- Deeply chained `map`/`filter` million-element hot path pe — passes + memory. Single `reduce`/`for`.
- `find` ka result bina `?.` ya null-check ke use karna — undefined pe crash.

### Pros and cons

**Iteration methods (`map`/`filter`/`find`/...)**

- Declarative, intent saaf, chainable.
- Callback-scoped variables — kam leak.
- Cons: `break` nahi (except via `some`/`find` trick), async await nahi, har method ek pass + (map/filter) ek naya array.

**`for...of` / classic `for`**

- `break`/`continue`/`await` natural, single pass, zero extra array.
- Cons: zyada boilerplate, intent implicit, index off-by-one risk (classic `for`).

### Interview mein "map ya forEach?"

> "`map` tab jab mujhe har element ka transformed version ek naye array mein chahiye — aur callback pure hona chahiye, sirf transform. `forEach` tab jab mujhe sirf side effect karna hai — logging, DOM update, kisi external cheez mein push — aur return value ki zaroorat nahi. Agar main `map` ka return use nahi kar raha to wo galat choice hai; wahan `forEach` ya `for...of`. Aur agar loop mein `break` ya sequential `await` chahiye to dono chhod ke `for...of`."

</Hinglish>

<Callout type="tip">

`find` early-exit karta hai, `filter` nahi. Ek 10-lakh element array mein pehla match index 3 pe hai — `find` 4 elements dekhta hai, `filter(...)[0]` 10 lakh. Lookup-by-id ke liye hamesha `find`.

</Callout>

## Real World Example

<RealWorld company="React">

React lists `map` se render hoti hain: `todos.map((t) => <TodoItem key={t.id} todo={t} />)` — yahan return value (elements ka array) hi JSX mein jata hai, to `map` sahi. Ek item ko id se dhoondhna — `const active = todos.find((t) => t.id === activeId)` — phir `active?.title` (undefined-safe kyunki item delete ho chuka ho sakta hai). Filtering UI — `todos.filter((t) => !t.done)` incomplete list ke liye. `forEach` React render mein kam dikhta hai kyunki render pure hona chahiye; `forEach` side-effect ke liye hai jo effects/handlers mein hota hai.

</RealWorld>

<RealWorld company="Node.js / Express">

API handler mein validation: `const missing = requiredFields.filter((f) => !(f in body))` — agar `missing.length` non-zero to 400 return. Permission check: `roles.some((r) => r === "admin")`. Batch processing jahan har item ke liye DB write sequential chahiye — `for (const row of rows) { await db.insert(row); }`, kyunki `rows.forEach(async ...)` saare inserts ek saath fire kar deta hai aur handler `await` nahi karta — connection pool blow ho sakta hai ya order tut sakta hai.

</RealWorld>

## Numbers That Matter

<Numbers>

- `map`/`filter`/`forEach`/`some`/`every`/`indexOf` **ES5 (2009)**; `find`/`findIndex` **ES6 (2015)**; `includes` **ES2016**; `findLast`/`findLastIndex` **ES2023**.
- `map` output length = input length, **hamesha**. `filter` output length = 0 se input length.
- `find`/`some` best case **O(1)** (pehla element match), worst **O(n)**; `filter`/`map`/`forEach` hamesha **O(n)**.
- `[].every(fn)` khali array pe **`true`** (vacuous); `[].some(fn)` **`false`**.
- `includes` `NaN` find karta hai; `indexOf` nahi (`-1`).
- 3-method chain (`filter().map().reduce()`) = **3 passes** + **2 intermediate arrays**.
- `forEach` async callback ko **await nahi** karta — sequential ke liye `for...of`.

</Numbers>

## Interview Angle

<InterviewAngle>

Do decision questions guaranteed hain: **map vs forEach** aur **filter vs find**. Interviewer dekhta hai ki tum "return value chahiye ya nahi" aur "ek match ya saare" ke terms mein soch pate ho.

Model answer shape:

1. **map vs forEach** — "map naya array deta hai, use jab transform chahiye; forEach undefined, use sirf side effect. Return use nahi kar rahe to map galat."
2. **filter vs find** — "filter hamesha array (0+ matches, poora scan); find pehla element ya undefined (short-circuit). Id lookup = find."
3. **find undefined trap** — "find ka result `?.` ya null-check ke saath."
4. **some/every** — "some = koi ek; every = sab; dono short-circuit."
5. **for...of kab** — "break ya sequential await chahiye to."
6. **Chaining cost** — "map+filter chain readable par multiple passes; hot path pe single reduce/for."

Red flag: "`filter` bhi pehla match milte hi ruk jata hai" — nahi, poora array.

</InterviewAngle>

## Common Mistakes

<Mistake>

**`map` ko `forEach` ki jagah use karna (result phenk dena).** `items.map((x) => { doThing(x); })` — naya array banta hai jo koi use nahi karta, aur `array-callback-return` linter warn karta hai. Side effect ke liye `forEach` ya `for...of`.

</Mistake>

<Mistake>

**Ek item ke liye `filter(...)[0]` likhna.** Poora array scan hota hai aur ek throwaway array banta hai, jabki `find` pehla match milte hi ruk jata hai aur seedha element deta hai. Id/unique lookup = `find`.

</Mistake>

<Mistake>

**`find` ka result bina check ke use karna.** `list.find((x) => x.id === id).name` — agar koi match nahi to `find` `undefined` deta hai aur `.name` `TypeError` deta hai. `list.find(...)?.name` ya pehle `if`.

</Mistake>

<Mistake>

**`forEach` ke saath `async`/`await` se sequential expect karna.** `arr.forEach(async (x) => { await save(x); })` — `forEach` promises ko ignore karta hai, saare `save` ek saath chalte hain, aur baad ka code inke complete hone se pehle chal jata hai. `for (const x of arr) { await save(x); }`.

</Mistake>

<Mistake>

**`every` ko khali array pe `false` maan lena.** `[].every(fn)` `true` deta hai (vacuous truth — "koi element fail nahi hua"). Agar "non-empty AND sab pass" chahiye to `arr.length > 0 && arr.every(fn)`.

</Mistake>

## Quick Revision

<QuickRevision>

- `map` → naya array, **same length**, har element transformed; use for return value.
- `forEach` → `undefined`; sirf side effects; chain nahi hota.
- **Return use nahi kar rahe → `map` mat likho**, `forEach`/`for...of`.
- `filter` → **hamesha array** (0+ matches), poora scan.
- `find` → pehla **element** ya `undefined`, short-circuit; `findIndex` → index ya `-1`.
- Id/unique lookup → `find`, na ki `filter(...)[0]`.
- `find` result → `?.` ya null-check ke saath use karo.
- `some` → koi ek match (OR); `every` → sab match (AND, khali array pe `true`); dono short-circuit.
- `includes` → value hai? (`NaN`-safe); `indexOf` → index ya `-1` (`NaN` miss).
- `break` / sequential `await` → `for...of` (methods mein nahi).
- Chained `map().filter()` = multiple passes + intermediate arrays; hot path pe `reduce`/`for`.

</QuickRevision>

## Practice

<Callout type="tip">

**Chhota:** `const r = [1, 2, 3].forEach((n) => n * 2); console.log(r);` — `r` kya hai aur kyun? `forEach` ki jagah kya likhte agar doubled array chahiye tha?

**Medium:** Ek `users` array (`{ id, name, active }`) do. Likho: (a) sirf active users ke names ka array, (b) `id === 3` wala user ka name (safe, undefined pe crash nahi), (c) kya koi inactive user hai (boolean).

**Bada:** `orders` array (`{ status, amount }`, 5 lakh elements maano) ka total `"paid"` amount nikalo. Pehle `filter().map().reduce()` chain se likho, phir single `for...of` se. Do line mein likho ki bade array pe dusra version kyun behtar hai.

</Callout>
