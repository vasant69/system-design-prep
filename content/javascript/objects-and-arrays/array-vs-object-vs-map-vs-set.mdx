<SimpleDefinition>

JavaScript's four core collections solve different problems. An **Array** is an ordered, index-addressed sequence that allows duplicates. A plain **Object** is a record with a known set of string/symbol keys, or a simple string-keyed lookup. A **Map** is a keyed collection that accepts **any** key type, keeps insertion order, exposes `.size`, and is built for frequent add/delete. A **Set** stores **unique** values and answers "is this in here?" fast. Choosing right is mostly about *what you look things up by*, whether *order and size* matter, and *how often you write*.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Yeh section ka sabse important decision topic hai. Interview mein bahut common: "`const employees = []` — array kyun, object ya Map kyun nahi?" Sahi jawaab ke liye chaaron structures ka **kaam** clear hona chahiye, "syntax" nahi.

### Ek line mein har structure

- **Array** — ek **sequence**. Order matters, duplicates OK, tum ise **loop** karte ho aur position (`arr[0]`, "pehla", "aakhri") se sochte ho.
- **Object** — ek **record**. Fixed/chhota known set of string keys (ek config, ek DTO, ek API response shape). Ya ek simple string-keyed lookup jab keys valid identifiers hon aur order/size/frequent-delete important na ho.
- **Map** — ek **dictionary** jo har cheez ko key bana sake (object bhi), insertion order guarantee, `.size`, safe+cheap add/delete, prototype-key collision nahi.
- **Set** — ek **bag of unique values**. Fast `has()`, dedupe (`[...new Set(arr)]`).

### Ye kyun — object "as a map" ke footguns

Log historically plain object ko dictionary ki tarah use karte the. Problems:

```javascript
const seen = {};
seen["toString"];        // function! -- inherited from Object.prototype
seen["__proto__"] = 1;   // silently ignored / prototype tamper (engine-dependent)
seen[1] = "a";
seen["1"];               // "a" -- number key "1" string ban gaya
Object.keys(seen).length;// size ke liye poora keys array banana padta hai
```

- **Inherited keys** — `obj["toString"]`, `obj["constructor"]` prototype se aate hain, to `if (obj[key])` false positive de sakta hai. `Object.hasOwn(obj, key)` ya `Object.create(null)` chahiye.
- **`__proto__`** — special key, normal data ki tarah behave nahi karti.
- **Key coercion** — object keys hamesha string (ya symbol). `obj[1]` aur `obj["1"]` same. `obj[someObject]` → `obj["[object Object]"]` (sab objects ek hi key!).
- **No `.size`** — `Object.keys(obj).length` (O(n), naya array).
- **Order** — modern engines mein integer-jaisi keys pehle ascending, phir string keys insertion order. Yaani `{ "2": ..., "1": ... }` iterate karne pe `1` pehle aata hai. Predictable but surprising.

Map yeh saari problems solve karta hai — isi liye woh exist karta hai.

### Internally kaise kaam karta hai

- **Array** — contiguous indexed storage (engines "packed" arrays optimise karte hain). Index access O(1). `push`/`pop` O(1); `shift`/`unshift`/`splice` O(n) (sab elements shift).
- **Object** — hidden classes / property maps. Known-shape objects (hamesha same keys) engine bahut fast banata hai. Dynamic keys ("dictionary mode") slow path pe chala jaata hai.
- **Map** — actual hash table, kisi bhi key type ke liye. Add/get/delete/has average O(1). Insertion order ek linked list se maintain.
- **Set** — Map jaisa hash table, sirf keys (values hi keys hain). `has` average O(1) — array ke `includes` (O(n)) se bahut tez bade data pe.

Equality: Map/Set keys **SameValueZero** se compare hote hain — `NaN` khud ke barabar (ek hi `NaN` key), `+0`/`-0` same, baaki `===` jaisa. Objects **reference** se — do alag `{}` do alag keys.

### Simple real-life analogy

- **Array** = train ke dabbe — line mein, number se, ek hi jaisa dabba do baar ho sakta hai.
- **Object** = ek form jisme fixed fields hain (naam, umar, sheher).
- **Map** = ek register jisme entries add hoti rehti hain, koi bhi cheez "naam" (key) ho sakti hai, aur register bata deta hai kitni entries hain.
- **Set** = ek guest list jisme har naam ek hi baar — dobara likhne se kuch nahi hota.

### Decision table

| Scenario | Pick | Why |
|---|---|---|
| Employees ki list jise loop karna hai, order matters | **Array** | Sequence hai, position se sochte ho, stable id se lookup nahi |
| Ek user object API se — `name`, `email`, `role` | **Object** | Fixed known shape, ek record |
| App config / options | **Object** | Chhota fixed set of string keys |
| `userId -> userRecord` lookup, users add/remove hote rehte | **Map** | Bahut writes, unknown keys, `.size` chahiye |
| Key ek object hai (DOM node -> metadata) | **Map** | Object keys sirf Map mein possible |
| "Yeh id already process ho chuka?" | **Set** | Fast `has`, uniqueness |
| Array se duplicates hataana | **Set** | `[...new Set(arr)]` |
| Kisi cheez ki frequency count (`word -> count`) | **Map** (ya `Object.create(null)`) | Unknown string keys, no prototype clash |
| Data jo `JSON.stringify` hoke network pe jaana hai | **Array / Object** | Map/Set JSON mein survive nahi karte |
| Fixed order + numeric index + ordered iteration | **Array** | Yahi array ka kaam hai |

### Code — chaaron ka basic use

```javascript
// Array
const employees = ["Asha", "Ravi", "Meera"];
employees.push("Kabir");
for (const name of employees) { /* ordered */ }

// Object (record / simple lookup)
const config = { retries: 3, timeout: 5000 };
config.timeout;                     // 5000

// Map
const usersById = new Map();
usersById.set(101, { name: "Asha" });
usersById.get(101);                 // { name: "Asha" }
usersById.has(101);                 // true
usersById.size;                     // 1
usersById.delete(101);
for (const [id, user] of usersById) { /* insertion order */ }

// Set
const processedIds = new Set();
processedIds.add("txn_1");
processedIds.has("txn_1");          // true
const unique = [...new Set([1, 1, 2, 3, 3])]; // [1, 2, 3]
```

### Iteration syntax (har structure alag)

```javascript
for (const x of array) {}                       // values
for (const key in object) {}                    // keys (+ inherited enumerable! careful)
for (const key of Object.keys(object)) {}       // safer
for (const [k, v] of Object.entries(object)) {} // pairs
for (const [k, v] of map) {}                    // pairs, insertion order
for (const v of set) {}                         // values, insertion order
map.forEach((v, k) => {});                      // note: (value, key)
```

### JSON-serialisability

`JSON.stringify` sirf Array aur plain Object ko samajhta hai. `Map` aur `Set` `{}` ban jaate hain (empty!) — data chup-chaap gayab. Network/localStorage pe bhejne se pehle Map ko `Object.fromEntries(map)` ya `[...map]` mein convert karo, Set ko `[...set]` mein. Wapas parse karke `new Map(...)` / `new Set(...)`.

### Performance note

- Membership: `set.has(x)` average **O(1)**; `array.includes(x)` **O(n)**. 10k+ items ki repeated lookup pe Set clearly jeet-ta.
- `map.get(k)` vs `obj[k]`: dono fast; par bahut dynamic keys (constantly add/delete, non-identifier strings) pe Map consistently fast, object "dictionary mode" mein deoptimise ho sakta hai.
- Bade insert/delete workloads: Map object se behtar (aur clearer intent).
- Chhote fixed-shape records: plain object sabse fast — engine hidden class optimise karta hai.

### Kab kya — clean rules

**Array chuno jab:** ordered sequence hai, index/position matters, duplicates allowed, tum ise iterate karte ho, stable unique id se random lookup nahi karte.

**Object chuno jab:** ek record with known/small string keys (config, DTO, function args bundle), ya ek simple lookup jaha keys valid identifiers hain aur tumhe `.size`/order/frequent-delete/non-string keys nahi chahiye, ya data ko `JSON.stringify` karna hai.

**Map chuno jab:** keys non-string (objects, numbers where you care), keys unknown/user-supplied (prototype clash se bachne ke liye), bahut add/delete, `.size` chahiye, ya "yeh ek dictionary hai" intent clearly dikhana hai.

**Set chuno jab:** uniqueness enforce karni hai, ya fast repeated membership test chahiye, ya dedupe.

### Kab NAHI

- Array ko id-lookup ke liye mat use karo (`employees.find(e => e.id === x)` har baar O(n)) — agar yeh baar-baar hota hai to Map bana lo (`employeesById`).
- Object ko user-supplied ya non-string keys ke liye mat use karo — prototype pollution / coercion bugs.
- Map/Set ko wahan mat use karo jaha data ko JSON serialize karna hai bina conversion ke.
- Set ko "ordered unique list jise index chahiye" ke liye mat use karo — Set mein index access nahi (`set[0]` `undefined`).

### Interview mein: "`const employees = []` — array kyun, object/Map kyun nahi?"

> "`employees` ek **ordered sequence** hai — mujhe insertion/display order chahiye aur main ise iterate karta hoon (list render, filter, map). Main kisi employee ko ek stable unique key se random-access nahi karta — main poori list pe kaam karta hoon. Isliye array. Object isliye nahi kyunki object ka kaam hai ek **record** ya string-keyed lookup — yaha mujhe na named fields chahiye, na key-based lookup, aur object numeric order aur `.length` ke liye awkward hai. Map isliye nahi kyunki Map tab chahiye jab main `id -> employee` dictionary maintain karta, bahut add/delete karta, aur `.size` chahiye — yaha aisa nahi. Agar baad mein mujhe `employeeById.get(id)` ki zaroorat pade to main ek Map **saath mein** bana lunga, array ki jagah nahi."

</Hinglish>

<Callout type="tip">

Rule of thumb: **loop karte ho aur order matters → Array. Known fixed fields → Object. Kuch bhi key ho sakta hai / bahut writes / `.size` chahiye → Map. Sirf uniqueness / fast `has` → Set.**

</Callout>

## Real World Example

<RealWorld company="React rendering lists">

React mein UI lists hamesha arrays hain — `todos.map(t => <Row key={t.id} />)` — kyunki render order deterministic chahiye aur JSX children ordered hote hain. Lekin "kaunse rows expanded hain" jaise state ke liye teams `Set` use karti hain (`expandedIds.has(row.id)`), aur "id se row nikaalna" ke liye ek `Map` derive karti hain (`useMemo(() => new Map(rows.map(r => [r.id, r])), [rows])`) taaki har lookup O(n) na ho. Ek hi feature mein teeno — array for order, Map for lookup, Set for membership.

</RealWorld>

<RealWorld company="Node.js — caching & dedupe">

In-memory caches Map se banti hain: `const cache = new Map()` — arbitrary keys, `.size` se eviction decide, `cache.delete(key)` cheap. Request dedup ("yeh id pehle process hui?") ke liye `Set`. Config objects plain objects rehte hain kyunki woh known-shape hote hain aur `JSON.stringify` hoke log/response mein jaate hain. `WeakMap` ka special case: kisi object (jaise ek request object) ke saath metadata attach karna bina memory leak ke — key GC ho to entry apne aap chali jaati hai.

</RealWorld>

## Numbers That Matter

<Numbers>

- `Map` aur `Set` **ES6 (2015)** mein aaye; `Object.fromEntries` (Map→object) **ES2019**.
- `set.has` / `map.get` average **O(1)**; `array.includes` / `array.indexOf` **O(n)**.
- `JSON.stringify(new Map([["a",1]]))` → `"{}"` — Map/Set serialize **nahi** hote.
- Object keys hamesha **string ya symbol** — `obj[1]` === `obj["1"]`; `obj[{}]` === `obj["[object Object]"]`.
- Map/Set key equality **SameValueZero** — ek hi `NaN` key possible (`map.set(NaN, 1); map.get(NaN)` works).
- `array.shift()` / `unshift()` / `splice()` = **O(n)**; `push()` / `pop()` = **O(1)**.
- `Object.create(null)` = prototype-less object, dictionary use ke liye safe (koi inherited `toString` etc.).

</Numbers>

## Interview Angle

<InterviewAngle>

Poocha jaata hai: (1) "Array vs Object kab" ya "`const x = []` — array kyun". (2) "Object ko map ki tarah use karne mein kya problem" — inherited keys, `__proto__`, string coercion, no `.size`. (3) "Duplicates kaise hataoge" — `Set`. (4) "10000 items mein baar-baar check karna hai koi value hai — kya use karoge" — `Set` (O(1) vs O(n)).

Achhe jawaab ka shape:

1. **Access pattern** — "Kya main position/order se access karta hoon (Array) ya key se (Object/Map)?"
2. **Keys** — "String identifiers aur fixed shape → Object; kuch bhi / dynamic / non-string → Map."
3. **Order + size + writes** — "Insertion order guarantee, `.size`, cheap delete chahiye → Map."
4. **Uniqueness** — "Unique values / fast membership → Set."
5. **Serialisation** — "JSON chahiye → Array/Object; Map/Set convert karne padte hain."

Red flag: "Map aur object basically same hain" — nahi, key types, order, size, prototype safety, aur JSON behaviour alag hain.

</InterviewAngle>

## Common Mistakes

<Mistake>

**Object ko dynamic/user-supplied keys wale dictionary ki tarah use karna.** `const counts = {}; counts[userInput]++` — agar `userInput` `"__proto__"` ya `"constructor"` ho to weird behaviour. `new Map()` ya `Object.create(null)` use karo.

</Mistake>

<Mistake>

**Repeated membership check array pe.** `if (bigArray.includes(id))` ek loop ke andar = O(n*m). Pehle `const idSet = new Set(bigArray)` banao, phir `idSet.has(id)` — O(1) per check.

</Mistake>

<Mistake>

**Map/Set ko `JSON.stringify` karke network/localStorage pe bhejna.** Result `"{}"` — saara data gayab, silently. Map → `Object.fromEntries(map)` ya `[...map]`; Set → `[...set]`; receiving end pe wapas `new Map`/`new Set`.

</Mistake>

<Mistake>

**Object ko key banana plain object ke andar.** `obj[user] = 1` — `user` `"[object Object]"` string ban jaata hai, to har object same key pe likhta hai. Object-as-key chahiye to `Map` (ya `WeakMap`).

</Mistake>

<Mistake>

**Set ko indexed list ki tarah treat karna.** `mySet[0]`, `mySet.length` — dono `undefined`. Set mein position access nahi. Index chahiye to `[...mySet]` se array banao (order preserved), ya array + manual dedupe.

</Mistake>

## Quick Revision

<QuickRevision>

- **Array** — ordered sequence, index access, duplicates OK, tum ise loop karte ho.
- **Object** — record with known string keys (config/DTO), ya simple identifier-keyed lookup; JSON-friendly.
- **Map** — any key type (objects!), insertion order, `.size`, cheap add/delete, no prototype clash.
- **Set** — unique values, O(1) `has`, dedupe via `[...new Set(arr)]`.
- Object keys hamesha string/symbol; `obj[1] === obj["1"]`; `obj[{}] === obj["[object Object]"]`.
- Object "as map" footguns: inherited keys (`toString`), `__proto__`, no `.size`, key coercion.
- `set.has` / `map.get` = **O(1)**; `array.includes` = **O(n)**.
- **Map/Set `JSON.stringify` mein `{}` ban jaate hain** — convert before serialising.
- Iteration: `for..of` array/Map/Set values/pairs; object ke liye `Object.keys/entries`.
- "`const employees = []`" → sequence, order matters, no id-lookup → Array; lookup chahiye to Map **saath** rakho.

</QuickRevision>

## Practice

<Callout type="tip">

**Chhota:** `const s = new Set([1, 2, 2, 3]); console.log(s.size, [...s]);` — output kya hai aur `s[0]` kya dega?

**Medium:** Ek function `dedupeById(records)` likho jo records array se woh objects rakhe jinke `id` unique hain (pehla wala jeet-e). `Set` ya `Map` — jo bhi fit kare — use karo aur batao kyun choose kiya.

**Bada:** Ek chhota "user store" banao: employees ek **array** mein (display order), ek `Map` `id -> employee` (fast lookup), aur ek `Set` `activeIds` (membership). `addEmployee`, `deactivate(id)`, aur `getActiveEmployeesInOrder()` implement karo. Phir ise `JSON.stringify` karne ke liye ek `serialize()` likho jo Map/Set ko sahi se convert kare, aur `deserialize(json)` jo wapas bana de.

</Callout>
