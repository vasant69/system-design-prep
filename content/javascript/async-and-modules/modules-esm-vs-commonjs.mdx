<SimpleDefinition>

A **module** is a file whose code has its own scope and which explicitly declares what it **exposes** (`export`) and what it **depends on** (`import`). JavaScript has two module systems. **ES Modules (ESM)** are the language standard — `import` / `export` statements that are **static, hoisted, and analysable**, which enables tree-shaking. **CommonJS (CJS)** is Node's older system — `require()` and `module.exports`, which are **synchronous and dynamic**. New code should use ESM; existing CommonJS Node codebases should stay on CJS unless a deliberate migration is planned.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Ek zamane mein saara JS ek hi global scope mein `<script>` tags se load hota tha — har variable clash kar sakta tha, dependency order manually manage karna padta tha. Modules ne isko fix kiya. Aaj do systems coexist karte hain — ESM (standard) aur CommonJS (Node legacy) — aur interview mein "farak kya hai, kaunsa kab" bahut common hai.

### Ye kya hai — module ka matlab

Ek **module** = ek file jo:

- apna **private scope** rakhti hai (top-level `const x` global nahi banta),
- explicitly `export` karti hai jo doosre use kar sakein,
- explicitly `import` karti hai jo use chahiye.

Isse teen fayde: **encapsulation** (internal cheezein chhupi rehti hain), **explicit dependencies** (file ke top pe dikh jaata hai kya-kya chahiye), **no global pollution**.

### ES Modules — the standard

```javascript
// math.js
export const PI = 3.14159;
export function area(r) { return PI * r * r; }
export default function circumference(r) { return 2 * PI * r; }

// app.js
import circumference, { PI, area } from "./math.js";
import * as math from "./math.js";
const load = () => import("./heavy.js"); // dynamic -> returns a Promise
```

- `export const` / `export function` — **named exports**, kitne bhi.
- `export default` — ek per module, "the main thing".
- `import { x } from` — named import (naam match karna zaroori).
- `import def from` — default import (naam kuch bhi rakh sakte ho).
- `import * as ns` — sab named exports ek namespace object mein.
- `import("./m.js")` — **dynamic import**, ek Promise return karta hai, lazy loading / code splitting ke liye.

### CommonJS — Node legacy

```javascript
// math.js
const PI = 3.14159;
function area(r) { return PI * r * r; }
module.exports = { PI, area };

// app.js
const { PI, area } = require("./math");
const math = require("./math");
```

- `require("./math")` — file ko sync load karke `module.exports` return karta hai.
- `module.exports = ...` — jo bhi assign karo wahi export hota hai.
- `__dirname`, `__filename` directly available (ESM mein nahi — `import.meta.url` use karo).

### Internally kaise kaam karta hai — sabse bada farak

**ESM: static + do-phase.** Engine pehle **parse** karta hai aur bina code chalaye saare `import`/`export` statements ka graph banata hai (ye statements top pe hoist hote hain, tumhare likhne ki jagah se independent). Phir modules ko link karta hai, phir execute. Kyunki dependencies compile-time pe pata hain, bundler **tree-shaking** kar sakta hai — jo exports kahi use nahi hue unhe bundle se hata do.

**CJS: dynamic + synchronous.** `require()` ek normal function call hai jo **jab wo line chalti hai** tab file ko load aur execute karta hai. Tum `if` ke andar, loop mein, ya computed path se `require` kar sakte ho — poori tarah runtime decision. Isi flexibility ki keemat: static analysis mushkil, tree-shaking reliable nahi.

### Live bindings vs value copy

```javascript
// counter.js
export let count = 0;
export function inc() { count++; }
```

```javascript
// esm consumer
import { count, inc } from "./counter.js";
console.log(count); // 0
inc();
console.log(count); // 1  <-- importer ko updated value dikhti hai
```

ESM imports **live bindings** hain — tum exporting module ke variable ki current value dekhte ho (read-only view). CJS mein `require` ke waqt jo value thi uski ek **copy** milti hai — baad ka update nahi dikhta (jab tak tum poora object destructure na karo).

### Node mein ESM kaise on karein

- `package.json` mein `"type": "module"` — ab `.js` files ESM.
- Ya file ka extension `.mjs` — hamesha ESM. `.cjs` — hamesha CJS.
- ESM mein relative imports ka **full extension zaroori** — `import x from "./util.js"`, `"./util"` nahi.

### Browser

```html
<script type="module" src="app.js"></script>
```

- **Deferred by default** — HTML parse hone ke baad chalta hai.
- **CORS-enforced** — cross-origin module ko proper headers chahiye.
- **One-time evaluation** — same URL do baar import karo, module ek hi baar chalta hai.
- Bare specifiers (`import x from "lodash"`) directly nahi chalte — chahiye import map ya bundler.

### Interop pain point

CJS ko ESM se import karo: `import pkg from "cjs-lib"` — `pkg` wo `module.exports` object hai. Named imports (`import { thing } from "cjs-lib"`) kabhi-kabhi kaam karte hain (Node static-analyse kar leta hai) kabhi nahi. ESM ko CJS se `require` nahi kar sakte — `await import()` use karna padta hai. Ye "dual package hazard" hai jo library authors ko dukh deta hai.

### Kab ESM use karna chahiye

- Har **naya** project (frontend ya Node).
- Jab tree-shaking / bundle size matter karta hai (browser apps).
- Jab code browser aur Node dono mein chalega (isomorphic).
- Jab top-level `await` chahiye (sirf ESM mein).

### Kab ESM use nahi karna chahiye

- Ek bada **existing CJS Node codebase** — poori migration risky hai, aur mixed graph mein interop bugs aate hain. Deliberately plan karo, ya CJS pe raho.
- Jab koi critical dependency sirf CJS deta hai aur uska ESM interop tuta hua hai.
- Bahut purana Node (12 se neeche) ya tooling jo ESM samajhta hi nahi.

### Pros and cons

**ESM**

- Language standard — browser aur Node dono mein native.
- Static structure -> tree-shaking, better tooling, circular deps zyada predictable.
- Hamesha strict mode; apna module scope.
- Async loading + dynamic `import()` + top-level `await`.

**CJS**

- Synchronous aur simple mental model — `require` bas ek function.
- Fully dynamic — conditional / computed requires.
- `__dirname` built-in; huge existing npm ecosystem.
- No build step needed in Node.

### Alternatives / related

- **Bundlers (Vite, esbuild, webpack, Rollup)** — dono formats ko ek output mein merge karte hain, browser ke liye.
- **TypeScript `import`/`export`** — ESM syntax, compile pe target module system pe emit hota hai (`module` tsconfig option).
- **UMD** — ek purana wrapper jo CJS + AMD + global teeno mein kaam karta tha (library builds mein abhi dikhta hai).

### Interview mein "ESM aur CommonJS mein farak?"

> "CommonJS Node ka original system hai — `require()` ek synchronous function call hai jo runtime pe file load karta hai, aur `module.exports` se export hota hai. Kyunki wo dynamic hai (`if` ke andar require kar sakte ho), static analysis mushkil hai aur tree-shaking reliable nahi. ESM language standard hai — `import`/`export` statements static hain, file ke top pe hoist hote hain, aur engine code chalaye bina dependency graph bana leta hai; isliye bundlers dead code hata sakte hain. ESM imports live bindings hain (exporter ki current value dikhti hai), CJS ek value copy deta hai. Node mein ESM `\"type\": \"module\"` ya `.mjs` se on hota hai. Naya code main hamesha ESM mein likhta hoon; ek established CJS codebase ko bina strong reason ke migrate nahi karta kyunki interop bugs real hain."

</Hinglish>

<Callout type="tip">

ESM mein `import` statements hoist hote hain — wo file mein kahi bhi likhe hon, dependencies sabse pehle load aur evaluate hoti hain. Isliye ek `import` ko conditionally "skip" nahi kar sakte; conditional loading ke liye dynamic `import()` chahiye.

</Callout>

## Real World Example

<RealWorld company="Vite / modern frontend build">

Vite dev server browser ke native ESM pe chalta hai — har source file ek alag `import` request hoti hai, koi bundle step nahi, isliye startup instant hai. Production build ke liye Rollup ESM ke static structure ka fayda uthakar tree-shaking karta hai: agar tum `import { debounce } from "lodash-es"` karte ho, sirf `debounce` aur uski dependencies bundle mein aati hain, poori library nahi. Yahi wajah hai ki libraries ab `lodash-es` jaise ESM builds ship karti hain — CJS `lodash` tree-shake nahi hota aur poora ~70KB le aata hai.

</RealWorld>

<RealWorld company="Node.js backend migration">

Bahut si Node teams ek "dual" phase se guzri hain: naye files `.mjs` / `"type": "module"`, purane `.cjs`. Common dard: ek popular CJS-only dependency ko ESM se import karne pe `import { X } from "pkg"` fail hota hai kyunki Node named exports detect nahi kar paata — fix hai `import pkg from "pkg"; const { X } = pkg;`. Doosra: ESM mein `__dirname` nahi hota, isliye `path.join(__dirname, ...)` wale sab lines ko `fileURLToPath(import.meta.url)` se rewrite karna padta hai. Isiliye guide kehta hai: migration deliberate karo, file-by-file, ek plan ke saath.

</RealWorld>

## Numbers That Matter

<Numbers>

- ESM syntax **ES2015 (ES6)** mein language mein aaya; Node mein stable (bina flag) **Node 14 (2020)** se.
- Dynamic `import()` aur `import.meta` — **ES2020**.
- Top-level `await` (sirf ESM) — **ES2022**.
- CommonJS Node mein **2009** se hai — ES modules se ~6 saal purana.
- ESM module hamesha strict mode mein chalta hai — `"use strict"` likhne ki zaroorat nahi.
- `<script type="module">` default **deferred** hai; normal `<script>` blocking hai jab tak `defer`/`async` na ho.

</Numbers>

## Interview Angle

<InterviewAngle>

Poocha jaata hai: "ESM aur CJS mein farak?", "tree-shaking kyun ESM ke saath hi kaam karta hai?", "Node mein ESM kaise enable karte ho?", "live bindings kya hain?", ya interop ke bare mein ek scenario.

Achhe jawaab ka shape:

1. **Syntax** — "ESM: `import`/`export`. CJS: `require`/`module.exports`."
2. **Static vs dynamic** — "ESM statements static + hoisted -> compile-time graph -> tree-shaking. CJS `require` runtime function call -> dynamic -> static analysis mushkil."
3. **Sync vs async** — "CJS sync; ESM async load, plus dynamic `import()` aur top-level `await`."
4. **Bindings** — "ESM live read-only bindings; CJS value copy at require time."
5. **Enable + decision** — "`\"type\": \"module\"` ya `.mjs`; naya code -> ESM, bada CJS codebase -> stay unless deliberate migration."

Red flag: "`import` aur `require` bas alag syntax hain, behaviour same hai" — static/dynamic aur sync/async farak bade hain.

</InterviewAngle>

## Common Mistakes

<Mistake>

**ESM mein relative import ka extension chhodna.** `import x from "./util"` Node ESM mein `ERR_MODULE_NOT_FOUND` deta hai — full `"./util.js"` chahiye. Bundlers ise resolve kar dete hain, isliye ye bug tab dikhta hai jab code bina bundler ke Node mein chalta hai.

</Mistake>

<Mistake>

**`import` ko conditionally skip karne ki koshish.** `if (flag) import x from "./a.js"` — `SyntaxError`. `import` statements top-level aur unconditional hote hain (hoisted). Conditional / lazy loading ke liye `const x = await import("./a.js")` use karo.

</Mistake>

<Mistake>

**ESM mein `__dirname` / `__filename` use karna.** Ye CJS-only hain. ESM mein `import { fileURLToPath } from "url"` aur `const __dirname = path.dirname(fileURLToPath(import.meta.url))` chahiye.

</Mistake>

<Mistake>

**CJS library se named import maan lena.** `import { readFileSync } from "some-cjs-pkg"` kabhi kaam karta hai kabhi `SyntaxError` — Node ki CJS-named-export detection best-effort hai. Safe pattern: `import pkg from "some-cjs-pkg"; const { readFileSync } = pkg;`.

</Mistake>

<Mistake>

**`package.json` mein `"type": "module"` daal ke sochna sab `.js` abhi bhi CJS chalega.** Wo flag flip karte hi har `.js` file ESM ban jaati hai — `require`, `module.exports`, `__dirname` sab break. Purani CJS files ko `.cjs` rename karo ya poora convert karo.

</Mistake>

## Quick Revision

<QuickRevision>

- Module = apna scope + explicit `export` + explicit `import`. Fayde: encapsulation, explicit deps, no global pollution.
- **ESM**: `import`/`export`, static + hoisted + analysable -> **tree-shaking**; hamesha strict mode; **live bindings**; async load + dynamic `import()` + top-level `await`.
- **CJS**: `require()`/`module.exports`, synchronous, dynamic (conditional require OK), **value copy**, `__dirname` available.
- Node mein ESM on: `"type": "module"` in `package.json`, ya `.mjs` extension. Relative imports ka full extension zaroori.
- Browser: `<script type="module">` — deferred, CORS-enforced, one-time eval; bare specifiers ke liye import map / bundler.
- Interop: CJS ko ESM se `import def from "pkg"` (default); named imports flaky. ESM ko CJS se sirf `await import()`.
- Decision: **naya code -> ESM**; bada existing CJS codebase -> stay unless deliberate migration.

</QuickRevision>

## Practice

<Callout type="tip">

**Chhota:** `counter.js` mein `export let count = 0; export function inc(){ count++; }`. Ek ESM file mein import karke `console.log(count)`, phir `inc()`, phir dobara `console.log(count)`. Output kya? Ab explain karo ki CJS mein `module.exports = { count, inc }` ke saath yeh kyun alag behave karta.

**Medium:** Ek chhota Node script likho jo ek local module ko conditionally load kare — sirf jab `process.env.DEBUG` set ho. Pehle `import` statement se try karo (fail hoga — kyun?), phir dynamic `import()` + `await` se sahi karo.

**Bada:** Ek `math.mjs` banao named + default exports ke saath. Use teen tareeke se import karo (`import def, { named }`, `import * as ns`, dynamic `await import`). Phir ek `math.cjs` version banao aur likho ki ESM file se ise import karte waqt kya-kya adjust karna pada (default vs named, extension, `__dirname`).

</Callout>
