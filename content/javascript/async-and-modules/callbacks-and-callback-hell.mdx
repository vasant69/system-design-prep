<SimpleDefinition>

A **callback** is a function you pass to other code so that code can call it **later** — most often when an asynchronous operation (a timer, a network request, a file read) finishes. Node's classic style is the **error-first callback**: `(err, data) => {}` — first argument is an error or `null`, second is the result. Chaining many callbacks for sequential steps creates **callback hell** (the "pyramid of doom"): deeply nested, hard to read, error handling repeated at every level, and `try/catch` doesn't reach across the async boundary. Callbacks also mean **inversion of control** — you hand your logic to someone else and trust them to run it once, correctly. Promises and `async/await` exist to fix this.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Async ka sabse pehla tool callback hai — aur sabse purana. Promises aur `async/await` samajhne se pehle ye samajhna zaroori hai ki callback kya deta hai aur kaha toot-ta hai, kyunki wahi problems Promises solve karte hain.

### Ye kya hai — function ko argument ki tarah pass karna

JavaScript mein functions **first-class** hain — inhe variable mein rakh sakte ho, argument bana sakte ho, return kar sakte ho. **Callback** = ek function jo tum kisi doosre function/API ko pass karte ho, is umeed se ki wo use "baad mein" call karega.

```javascript
// synchronous callback — abhi turant call hota hai
[1, 2, 3].forEach(function (n) {
  console.log(n);
});

// asynchronous callback — kaam poora hone pe call hota hai
setTimeout(function () {
  console.log("2 second baad");
}, 2000);

button.addEventListener("click", function () {
  console.log("jab bhi click ho");
});
```

- `forEach` wala callback **synchronous** hai — `forEach` line par hi teeno baar chal jata hai.
- `setTimeout` / `addEventListener` wale **asynchronous** hain — abhi register hote hain, actual call baad ke event loop tick mein.

Interview mein "callback kya hai" poochhen to: "Ek function jo doosre code ko pass kiya jata hai taaki wo use later invoke kare — synchronous (jaise `map`) ya asynchronous (jaise `fs.readFile`)."

### Ye kyun exist karta hai

Async operation ka result us line pe ready nahi hota. To engine ko batana kaise ki "jab result aaye to ye chalana"? Sabse simple mechanism: ek function de do. Language ko koi nayi feature nahi chahiye — functions to already first-class hain. Isiliye 1995 se lekar ES6 tak, async ka **poora** JavaScript world callbacks pe chalta tha: `setTimeout`, DOM events, `XMLHttpRequest.onreadystatechange`, Node ki saari `fs` APIs, database drivers.

### Node ka error-first convention

Callbacks mein error report karne ka koi built-in tarika nahi — `throw` async callback se bahar nahi nikalta. Node ne ek **convention** banaya: callback ka pehla argument hamesha error hota hai (ya `null` agar sab theek).

```javascript
const fs = require("fs");

fs.readFile("config.json", "utf8", function (err, data) {
  if (err) {
    console.error("padhne mein dikkat:", err.message);
    return; // zaroori — warna neeche undefined data use hoga
  }
  const config = JSON.parse(data);
  console.log(config);
});
```

- `function (err, data)` — pehla `err`, doosra result. Ye order har Node-style API mein same.
- `if (err) { ...; return; }` — har callback ke shuru mein. `return` bhoolna common bug hai — error log bhi hota hai aur code aage bhi badh jata hai.
- Success path `if` ke baad — nesting is liye badhti jati hai jab steps sequential hon.

### Internally kaise kaam karta hai — inversion of control

Jab tum `getData(myCallback)` likhte ho, tum `myCallback` ka control `getData` ko de dete ho. Ab tum **trust** kar rahe ho ki `getData`:

- `myCallback` ko **exactly ek baar** call karega (0 baar = tumhara code hang; 2 baar = double charge, double render).
- Error case mein bhi call karega (kabhi kabhi library sirf success pe call karti hai — tumhara error handler kabhi chalta hi nahi).
- Sahi arguments dega, sahi order mein.
- Synchronously call nahi karega jab tum async expect kar rahe ho (ya vice versa — "release Zalgo").

Ise **inversion of control** kehte hain — normally tum apna code call karte ho; yaha koi aur tumhara code call karta hai, uski sh/rton pe. Third-party library ke saath ye real risk hai. Promises isse fix karte hain: Promise **guarantee** karta hai ki wo ek hi baar settle hoga, aur `.then`/`.catch` tumhare paas control wapas laate hain.

### Simple real-life analogy

Callback = doston ko ghar ki chaabi de kar bolna "jab parcel aaye to andar rakh dena." Ab tum trust kar rahe ho: wo parcel sahi jagah rakhega, ek hi baar rakhega, aur agar parcel na aaye to tumhe batayega. Ek dost = theek. Lekin agar "parcel aaye to A ko bolo, A phir B ko chaabi de, B parcel khole to C ko bulaye" — har step alag dost, har ek pe trust, aur kuch galat ho to kise poochho? Yahi callback hell hai.

### Code — callback hell, line by line

```javascript
getUser(userId, function (err, user) {
  if (err) return handleError(err);
  getOrders(user.id, function (err, orders) {
    if (err) return handleError(err);
    getOrderDetails(orders[0].id, function (err, details) {
      if (err) return handleError(err);
      getShipping(details.shipmentId, function (err, shipping) {
        if (err) return handleError(err);
        console.log(shipping.status); // 4 level andar
      });
    });
  });
});
```

- Har step **pichle step ke result** pe depend karta hai — isliye nest karna padta hai, side-by-side nahi likh sakte.
- `if (err) return handleError(err)` **4 baar** — same line repeat, DRY nahi.
- Indentation daayen badhti jati hai — "pyramid of doom". 7-8 steps pe screen se bahar chali jati hai.
- Beech mein koi step add/remove karna = saare andar wale blocks ka indentation shift.
- `try/catch` yaha lagana bekaar — `getOrders` ka async error `try` block ke bahar, uss tick mein stack alag hota hai.

### Day-to-day use — callbacks abhi bhi kaha theek hain

- **Event listeners** — `addEventListener("click", handler)`. Ye callback hi hai aur bilkul idiomatic — event baar baar fire hota hai, Promise (jo ek baar settle hota hai) yaha fit nahi.
- **Array methods** — `map`, `filter`, `reduce`, `forEach` — synchronous callbacks, perfect.
- **`setTimeout` / `setInterval`** — chhote one-off delays ke liye theek.
- **Node streams** — `.on("data", ...)`, `.on("end", ...)`.

Matlab callback "bura" nahi hai — **nested async sequential callbacks** bure hain.

### Kab callback use karna theek hai

- Synchronous higher-order functions (`map`/`filter`/`sort` comparator).
- Recurring events (DOM events, streams, `setInterval`) — jaha ek hi baar "settle" hone wala model fit nahi.
- Ek single, flat async call jaha aage chaining nahi hai.

### Kab callback use nahi karna chahiye

- Do ya zyada **sequential** async steps — Promise chain ya `async/await`.
- Jab tumhe error handling ek jagah chahiye — Promise `.catch` ek chain ka poora error pakadta hai.
- Jab result ko `Promise.all` jaise combinators mein daalna ho.
- Third-party API ke saath jaha "ek hi baar call hoga" ki guarantee chahiye.

### Partial fixes (Promises se pehle log kya karte the)

- **Named functions** — anonymous inline ki jagah har step ka naam de kar top-level pe rakho: `getUser(id, onUser)`, `function onUser(err, user) {...}`. Nesting kam, par error handling abhi bhi har function mein.
- **Modularise** — har step apni file/function mein.
- **`async.js` library** — `async.waterfall`, `async.series` — callback flow ko manage karti thi. Kaam karti thi par ek aur dependency.
- Ye sab band-aid the. Asli fix Promises the.

### Pros and cons

**Callbacks**

- **Pros**: koi language feature nahi chahiye — functions first-class hain; simple mental model ek single call ke liye; events/streams ke liye natural fit; zero overhead.
- **Cons**: sequential steps pe pyramid of doom; error handling har level pe repeat; `try/catch` async boundary paar nahi karta; inversion of control — library pe trust; combine karna (parallel + wait) manually mushkil.

**Promises (agla topic)**

- **Pros**: flat chaining; ek `.catch` poore chain ke liye; guaranteed single settle; `Promise.all`/`race` jaise combinators; `async/await` ke saath sync jaisa dikhta hai.
- **Cons**: thoda naya syntax seekhna; abhi bhi `.then` mein `return` bhoolna common bug.

### Alternatives

- **Promises** — ek future value ka object; chaining + central error handling. (Agla topic.)
- **`async/await`** — Promises ke upar syntax jo async code ko synchronous jaisa likhne deta hai. `try/catch` wapas kaam karta hai.
- **`util.promisify` (Node)** — purani error-first callback API ko Promise-returning banata hai: `const readFile = util.promisify(fs.readFile)`.
- **Event emitters / streams** — recurring cheezon ke liye (jaha callback hi theek tha).

### Interview mein "Callback hell kya hai aur kaise avoid karte ho?"

> "Callback hell tab hota hai jab kai sequential async steps ho aur har step agle ke callback ke andar nest ho — code daayen ki taraf pyramid ban jata hai, har level pe `if (err) return` repeat hota hai, aur `try/catch` async errors nahi pakadta. Main isse Promises se avoid karta hoon — har async step ek Promise return kare aur main `.then` se **flat chain** banau, ek `.catch` poore chain ka error handle kare. Usse bhi saaf `async/await` hai: `const user = await getUser(id)` — code top-to-bottom padhta hai aur `try/catch` phir se kaam karta hai. Node ki purani callback APIs ko `util.promisify` se wrap kar leta hoon."

</Hinglish>

## Real World Example

<RealWorld company="Node.js standard library">

Node ki poori original `fs`, `http`, `dns`, `crypto` API error-first callbacks pe bani thi — `fs.readFile(path, (err, data) => {...})`. Ye itna standard tha ki `util.promisify` core mein add kiya gaya taaki koi bhi `(err, result)` callback API ek line mein Promise-returning ban jaye. Aaj `fs/promises` module wahi APIs natively Promise-based deta hai, par purana callback form abhi bhi backward compatibility ke liye maujood hai.

</RealWorld>

<RealWorld company="jQuery / legacy front-end AJAX">

Promises se pehle browser AJAX aisa dikhta tha: `$.get(url1, function (a) { $.get(url2, function (b) { $.get(url3, ...) }) })`. Do-teen dependent calls mein hi code pyramid ban jata tha aur har callback apna `error:` handler alag rakhta tha. jQuery ne baad mein `$.Deferred` (Promise jaisa) add kiya, aur native `fetch` ne AJAX ko poori tarah Promise-based bana diya — yahi wo shift hai jisne callback hell ko mainstream front-end se hataya.

</RealWorld>

## Numbers That Matter

<Numbers>

- Callbacks JavaScript mein **1995 se** hain (`setTimeout`, event handlers) — Promises se `20` saal purane.
- Error-first callback ka shape fix hai: `(err, result)` — `err` **pehla** parameter, hamesha.
- Callback hell "3 levels" pe hi noticeable ho jata hai; `5+` sequential steps pe code practically unreadable.
- `Promise` ES6 (**2015**) mein standard bane; `async/await` **ES2017** mein.
- `util.promisify` Node **8.0 (2017)** mein aaya — ek line mein callback API ko Promise API banata hai.

</Numbers>

## Interview Angle

<InterviewAngle>

Ye aksar "async evolution" story ke roop mein poocha jata hai: callbacks -> Promises -> async/await, aur "har step ne kya problem solve kiya".

Achhe jawaab ka shape:

1. **Callback kya hai** — "Function jo later call hone ke liye pass kiya jata hai; sync (`map`) ya async (`fs.readFile`)."
2. **Error-first** — "Node convention: `(err, data)`, `err` pehle, har callback mein `if (err) return`."
3. **Callback hell** — "Sequential dependent steps nest hote hain -> pyramid, repeated error handling, `try/catch` kaam nahi karta."
4. **Inversion of control** — "Tum apna code library ko de rahe ho; trust ki wo ek baar, sahi se call kare."
5. **Fix** — "Promises flat chain + ek `.catch`; async/await sync jaisa readable + `try/catch` wapas."

Red flag: "callbacks purani hain, ab use hi nahi hote" — galat, DOM events aur array methods callbacks hi hain aur bilkul sahi jagah hain.

</InterviewAngle>

## Common Mistakes

<Mistake>

**`if (err)` ke baad `return` bhoolna.** `if (err) callback(err);` (bina `return`) — error handle hone ke baad bhi function aage badhta hai aur success code `undefined`/`null` data pe chal jata hai, jisse crash kisi unrelated line pe aata hai. Hamesha `if (err) return callback(err);`.

</Mistake>

<Mistake>

**Async callback ke around `try/catch` lagana.** `try { getData(cb) } catch (e) {}` — `getData` ka **async** error is `catch` mein kabhi nahi aayega, kyunki jab error hota hai tab tak `try` block ka execution poora ho chuka hota hai. Error callback ke `err` parameter mein aata hai, exception ki tarah nahi.

</Mistake>

<Mistake>

**Sequential ko parallel samajhna (ya ulta).** Nested callbacks har step ko **agle ka wait** karwate hain. Agar 3 independent API calls hain, unhe nest karna 3x slow hai — unhe saath fire karke count-based join karo (ya Promise.all).

</Mistake>

<Mistake>

**Callback ke do baar call hone ka case na sochna.** Kuch libraries error + success dono par callback call kar deti hain, ya retry pe dubara. Agar callback DB write ya payment karta hai, double-call = double effect. Ek `called` flag ya Promise (jo guaranteed single-settle hai) use karo.

</Mistake>

<Mistake>

**Callback se value `return` karke use karne ki koshish.** `const data = getData(cb)` mein `getData` `undefined` (ya Promise) deta hai — actual data `cb` ke andar aata hai. Async result ko us line pe `return` nahi kiya ja sakta.

</Mistake>

## Quick Revision

<QuickRevision>

- **Callback** = function jo doosre code ko pass hota hai later-call ke liye; sync (`map`) ya async (`fs.readFile`).
- **Error-first** = Node convention `(err, data)`; `err` pehla; har callback mein `if (err) return`.
- **Callback hell** = sequential dependent async steps nest hote hain -> pyramid of doom.
- Symptoms: daayen badhti indentation, har level pe repeated error handling, `try/catch` async error nahi pakadta.
- **Inversion of control** = tum apna code library ko de rahe ho; trust ki ek baar + sahi se call ho.
- Callbacks abhi bhi sahi: DOM events, array methods, streams, chhote `setTimeout`.
- Partial fixes (purane): named functions, `async.js` — band-aid the.
- Asli fix: **Promises** (flat chain + ek `.catch` + guaranteed single settle), phir **async/await**.
- Node callback API ko Promise banao: `util.promisify(fn)`.

</QuickRevision>

## Practice

<Callout type="tip">

**Chhota:** Ye do-line likho aur predict karo: `try { setTimeout(() => { throw new Error("boom"); }, 0); } catch (e) { console.log("pakda", e.message); }` — kya `catch` chalega? Kyun ya kyun nahi?

**Medium:** Ek fake `getUser(id, cb)`, `getPosts(userId, cb)`, `getComments(postId, cb)` banao (har ek `setTimeout` se `(null, data)` return kare). Inhe nested callbacks se chain karke user ke pehle post ke comments log karo. Phir ginо: `if (err) return` kitni baar likhna pada, aur indentation kitne level gaya.

**Bada:** Upar wali teeno callback functions ko `util.promisify`-style manually wrap karo (har ek ko ek `Promise`-returning version do). Ab wahi flow `.then` chain se likho — ek `.catch` ke saath. Do-teen line mein likho ki kya-kya behtar hua (line count, error handling, readability).

</Callout>
