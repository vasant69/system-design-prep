<SimpleDefinition>

`===` (strict equality) compares **type and value with no coercion** — different types means an immediate `false`. `==` (loose equality) **coerces** the operands to a common type first, which produces a long list of surprising results. `Object.is` behaves like `===` except it treats `NaN` as equal to itself and `-0` as **not** equal to `+0`. The practical rule: **always `===`**; the one accepted `==` is `x == null` (matches `null` and `undefined`).

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Ye ek **decision topic** hai — question hamesha yahi hai "`==` kab, `===` kab?" — aur iska ek short, confident jawaab har interview mein expected hai. Spoiler: answer "`===` hamesha, `==` sirf `null` check ke liye" hai. Baaki topic wo *kyun* hai.

### Ye kya hai — teen equality operators

| Operator | Naam | Coercion? | `NaN` self-equal? | `-0 === +0`? |
|---|---|---|---|---|
| `===` | strict equality | Nahi | Nahi (`NaN === NaN` false) | Haan (equal) |
| `==` | loose equality | Haan | Nahi | Haan |
| `Object.is` | SameValue | Nahi | **Haan** (`Object.is(NaN, NaN)` true) | **Nahi** (`-0` !== `+0`) |

### `===` — no surprises

`a === b`:

1. Agar `a` aur `b` ke **types alag** hain -> `false`. Bas, khatam.
2. Same type -> value compare. Primitives: actual value. Objects: same reference?

```javascript
1 === 1;            // true
1 === "1";          // false  -- number vs string, koi coercion nahi
null === undefined; // false  -- alag types
NaN === NaN;        // false  -- IEEE-754
{} === {};          // false  -- alag references
```

Ye predictable hai. Reader ko `===` dekh ke pata hai "koi hidden conversion nahi ho raha".

### `==` — coerce, phir compare

`a == b` pehle dono ko ek common type mein laata hai (roughly: number ki taraf), phir compare. Rules complex hain — yahi problem hai. Kuch known results:

```javascript
0 == "";           // true   -- "" -> 0
0 == "0";          // true   -- "0" -> 0
"" == "0";         // false  -- dono string, no coercion, "" !== "0"
false == "0";      // true   -- false -> 0, "0" -> 0
false == "";       // true   -- dono -> 0
null == undefined; // true   -- special-cased
null == 0;         // false  -- null sirf undefined ke barabar
undefined == 0;    // false  -- same
NaN == NaN;        // false
[] == false;       // true   -- [] -> "" -> 0, false -> 0
[] == ![];         // true   -- ![] -> false -> 0; [] -> 0; 0 == 0
"1" == 1;          // true
[1] == 1;          // true   -- [1] -> "1" -> 1
```

`"" == "0"` `false` par `0 == ""` aur `0 == "0"` dono `true` — matlab `==` **transitive nahi** hai. Ye akela reason kaafi hai ise avoid karne ka.

### Internally kaise kaam karta hai — `==` ka rough algorithm

`a == b` (same type nahi):

- Ek `null` aur doosra `undefined` -> `true`.
- Ek `number`, doosra `string` -> string ko `ToNumber`, phir compare.
- Ek `boolean` -> boolean ko `ToNumber` (`true`->1, `false`->0), phir dobara compare.
- Ek `object`, doosra primitive -> object ko `ToPrimitive`, phir dobara compare.
- `null`/`undefined` kisi aur cheez ke saath (except each other) -> `false`.

`===` mein ye poora ladder nahi hai — type mismatch pe seedha `false`.

### `Object.is` — `===` ka fixed version do edge-cases pe

```javascript
Object.is(NaN, NaN);   // true   <- === deta false
Object.is(-0, 0);      // false  <- === deta true
Object.is(1, 1);       // true   <- baaki sab === jaisa
Object.is({}, {});     // false  <- reference, === jaisa
```

React internally `Object.is` use karта hai state/props comparison ke liye. Tumhe rozana iski zaroorat nahi — `NaN` check ke liye `Number.isNaN` clearer hai, `-0` rarely matter karta hai.

### Simple real-life analogy

- `===` = passport check jo naam **aur** nationality dono match karta hai. Alag country? Reject, aage baat hi nahi.
- `==` = ek guard jo "arre naam mil raha hai, aa jao" bol deta hai — kabhi `"0"` waale ko `false` waale ke saath andar bhej deta hai kyunki dono "kind of zero" lagte hain.

### Comparison table — kab kya

| Scenario | `==` | `===` | Kya use karein |
|---|---|---|---|
| Normal value compare (number, string, boolean) | coerces, risky | exact | **`===`** |
| `null` **aur** `undefined` dono check karne hain | `x == null` works | verbose (`x === null \|\| x === undefined`) | **`x == null`** (only OK `==`) |
| `NaN` check | `NaN == NaN` false | `NaN === NaN` false | **`Number.isNaN(x)`** |
| `-0` vs `+0` distinguish | can't | can't (`-0 === 0` true) | **`Object.is(x, -0)`** |
| Object/array content equality | reference only | reference only | manual / `JSON.stringify` / Lodash `isEqual` |
| `if (typeof x === "string")` | — | exact | **`===`** (always for typeof) |

### Day-to-day use

- Har `if`, filter, guard, switch-like check -> `===`.
- Optional value present hai? -> `x == null` (absent) ya `x != null` (present).
- Enum/string constant match -> `status === "active"`.
- Number parse ke baad valid? -> `!Number.isNaN(n)`.

### Kab `==` use karna chahiye

Practically ek hi jagah: **`x == null`** — jab tumhe `null` aur `undefined` dono ek saath check karne hon aur baaki kuch nahi. Ye idiom itna common aur safe hai ki ESLint ka `eqeqeq` rule bhi ise `{ null: "ignore" }` se allow karta hai.

### Kab `==` use nahi karna chahiye

Baaki har jagah. Specifically:

- User input / form values compare karte waqt (`value == 0` galat matches deta hai).
- Numbers aur strings mix ho sakte hon (`id == "42"`).
- Boolean flags (`flag == true` — bilkul mat likho, seedha `if (flag)`).
- Kisi ko bhi impress karne ke liye "main `==` samajhta hoon" — samajhna aur use karna alag hai.

### Pros and cons

**`===` (strict)**

- **Pros** — predictable, no hidden coercion, transitive, linter default, review-friendly, self-documenting.
- **Cons** — `null`/`undefined` dono check karne ke liye do comparisons (ya `== null` exception).

**`==` (loose)**

- **Pros** — `x == null` concise; kuch quick-script cases mein kam typing.
- **Cons** — non-transitive (`0 == ""`, `0 == "0"`, but `"" != "0"`), `[] == ![]` absurdities, silent bugs, har new dev ko surprise.

### Alternatives

- **`Object.is(a, b)`** — jab `NaN`/`-0` semantics chahiye (React internals, low-level libs).
- **`Number.isNaN(x)`** — `NaN` check ke liye clearest.
- **Lodash `isEqual` / `dequal`** — deep structural equality objects/arrays ke liye.
- **`JSON.stringify(a) === JSON.stringify(b)`** — quick structural check (key order-sensitive, `undefined`/functions drop).
- **ESLint `eqeqeq` rule** — `==`/`!=` ko error banata hai, `null` exception ke saath.

### Interview mein "`==` vs `===`?"

> "`===` type aur value dono strictly compare karta hai, koi coercion nahi — agar types alag hain to seedha `false`. `==` pehle operands ko coerce karta hai, jisse `0 == \"\"`, `false == \"0\"`, `[] == ![]` jaise counter-intuitive results aate hain, aur ye transitive bhi nahi hai. Mera rule: **hamesha `===`**. `==` main sirf ek jagah use karta hoon — `x == null` — kyunki wo cleanly `null` aur `undefined` dono ko match karta hai aur kisi aur value ko nahi. Codebases mein ESLint ka `eqeqeq` rule isi ko enforce karta hai. `NaN` ke liye `Number.isNaN`, aur `-0`/`NaN` ki exact semantics chahiye to `Object.is`."

</Hinglish>

## Real World Example

<RealWorld company="ESLint / Airbnb style guide">

Airbnb, Google, aur practically har team ka ESLint config `eqeqeq` rule on rakhta hai, jo `==` aur `!=` ko lint error banata hai. Config aksar `["error", "always", { "null": "ignore" }]` hota hai — matlab `x == null` allowed hai par baaki har `==` CI pe fail karta hai. Iska seedha matlab: modern code review mein ek bhi non-null `==` ek blocking comment hai, aur naye devs ki ye sabse pehli PR nit hoti hai.

</RealWorld>

<RealWorld company="React (Object.is under the hood)">

React `useState` ke bailout check aur `React.memo` / `useMemo` ke dependency comparison mein `Object.is` use karta hai (`===` nahi). Iska practical asar: agar tumhara state `NaN` hai aur tum dobara `NaN` set karte ho, React re-render **skip** karta hai (`Object.is(NaN, NaN)` true) — jabki plain `===` hote to wo hamesha "changed" lagta. Aur `-0` vs `+0` ko React alag maanta hai. Rozmarra code mein ye rarely bite karta hai par interview mein "React kaunsa equality use karta hai?" ek real question hai.

</RealWorld>

## Numbers That Matter

<Numbers>

- `===` type mismatch pe **immediately** `false` — koi coercion ladder nahi.
- `==` ke coercion rules spec mein **~10 steps** ka algorithm hain — yahi complexity avoid karne ki wajah hai.
- `==` **transitive nahi**: `0 == ""` true, `0 == "0"` true, par `"" == "0"` **false**.
- `null == undefined` -> `true`; `null == 0` -> `false`; `null` sirf `undefined` (aur khud) ke barabar.
- `Object.is` `===` se sirf **2** cases mein alag: `NaN` (equal) aur `-0`/`+0` (not equal).
- ESLint `eqeqeq` — practically universal; `{ null: "ignore" }` common exception.
- `Object.is` **ES2015** mein aaya; `===`/`==` original language se hain.

</Numbers>

## Interview Angle

<InterviewAngle>

Ye lagbhag guaranteed hai. Formats: "`==` vs `===` farak?", "`0 == "0"` kyun true par `"" == "0"` false?", "`==` kab use karoge?", "`Object.is` kya hai?".

Model answer ka shape:

1. **One-liner** — "`===` no coercion, type+value; `==` coerces first."
2. **Concrete surprise** — "`0 == ""` true, `[] == ![]` true, aur `==` transitive nahi."
3. **The rule** — "Hamesha `===`. `==` sirf `x == null` ke liye."
4. **Tooling** — "ESLint `eqeqeq` isi ko enforce karta hai."
5. **Edge** — "`NaN` -> `Number.isNaN`; `NaN`/`-0` exact semantics -> `Object.is`."

Red flag: "`==` value compare karta hai, `===` type bhi" — technically-ish but misses coercion; ya `==` ko defend karna "agar aapko rules pata hon to theek hai".

</InterviewAngle>

## Common Mistakes

<Mistake>

**`flag == true` / `flag == false` likhna.** Ye `==` ka worst use hai — `1 == true` true par `2 == true` false, `"1" == true` true par `"yes" == true` false. Boolean flag ke liye seedha `if (flag)` / `if (!flag)`, ya value strict compare `flag === true`.

</Mistake>

<Mistake>

**`value == 0` se "zero ya empty" check karna.** `0 == ""` aur `0 == "0"` aur `0 == false` sab `true` — to `value == 0` bahut kuch match kar leta hai jo tum nahi chahte. `value === 0` use karo.

</Mistake>

<Mistake>

**`x === null` likhna jab `undefined` bhi possible ho.** Agar property missing ho sakti hai (undefined) aur explicitly null bhi set ho sakti hai, to `x === null` undefined case miss kar deta hai. `x == null` dono ko pakadta hai.

</Mistake>

<Mistake>

**`NaN` ko `x === NaN` ya `x == NaN` se check karna.** Dono hamesha `false` — `NaN` kisi ke (khud ke bhi) barabar nahi. `Number.isNaN(x)` use karo.

</Mistake>

<Mistake>

**`obj1 === obj2` se do objects/arrays ka content compare karna.** `===` (aur `==`) sirf reference dekhta hai. `{a:1} === {a:1}` `false`. Content ke liye deep-equal helper, `JSON.stringify` (order-sensitive), ya Lodash `isEqual`.

</Mistake>

## Quick Revision

<QuickRevision>

- `===` — no coercion; type alag -> `false`; primitives value, objects reference.
- `==` — coerces to common type first; long list of surprises.
- `==` **non-transitive**: `0 == ""` true, `0 == "0"` true, `"" == "0"` **false**.
- `null == undefined` true; `null == 0` false; `[] == ![]` true.
- **Rule: always `===`.** The one OK `==` is `x == null` (matches null + undefined only).
- `x != null` = "value present" (excludes null/undefined, allows 0/""/false).
- `NaN` check -> `Number.isNaN(x)`, never `x === NaN`.
- `Object.is` = `===` except `Object.is(NaN, NaN)` true and `Object.is(-0, 0)` false.
- React uses `Object.is` for state/props bailout.
- ESLint `eqeqeq` enforces this; `{ null: "ignore" }` allows the idiom.
- Content equality of objects/arrays: deep-equal helper / Lodash `isEqual` / `JSON.stringify`.

</QuickRevision>

## Practice

<Callout type="tip">

**Chhota:** Bina chalaye, `true`/`false` aur ek-line reason: `0 == ""`, `0 == "0"`, `"" == "0"`, `null == undefined`, `null == 0`, `NaN == NaN`, `[] == false`, `"1" === 1`.

**Medium:** Ek function `isBlank(x)` likho jo `true` de jab `x` `null`, `undefined`, ya empty/whitespace-only string ho — aur `false` for `0`, `false`, `[]`, `"a"`. `== null` aur `===` dono ka sahi use dikhao. Batao `x == 0` waale approach mein kya galat hota.

**Bada:** Ek `strictDeepEqual(a, b)` likho jo primitives ke liye `Object.is` use kare (taaki `NaN` equal ho aur `-0 !== 0`), aur objects/arrays ko recursively compare kare. Phir 3 test cases likho jaha `strictDeepEqual` `JSON.stringify`-based compare se alag result deta hai (hint: `NaN`, key order, `undefined` values).

</Callout>
