<SimpleDefinition>

The mental model behind every endpoint we will build: an API is a contract between a client and a server exchanged over HTTP; each HTTP message has a method, path, headers, body, and status code; REST models the server's data as resources addressed by noun URLs and manipulated with a small fixed set of verbs; and JSON is the text format the request and response bodies are serialized to and from.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Code likhne se pehle ek clear tasveer chahiye ki jab koi hamari `EmployeeManagement.Api` se baat karta hai to actually hota kya hai. Ye topic sirf theory nahi — har controller action jo hum likhenge woh isi model ka ek chhota implementation hoga.

### What is it — API kya hai

API = **Application Programming Interface**. Sidhi baat: ek program ka doosre program se baat karne ka **darwaza aur uske rules**. UI human ke liye hota hai (buttons, forms); API doosre software ke liye hota hai (mobile app, Angular frontend, ek doosri service).

Web API me do kirdaar hain:
- **Client** — request bhejta hai (browser, Postman, Angular app, mobile app).
- **Server** — hamari ASP.NET Core app — request sunta hai, kaam karta hai, response bhejta hai.

Beech me ek **contract** hai: "agar tum `GET /api/employees/7` bhejoge, main ek employee ka JSON aur status `200` doonga; agar woh id nahi mili to `404`." Ye contract hi API hai. Client ko andar ka code nahi pata — sirf contract pata hai.

### Why do we need it — iske bina kya tootta hai

Agar client-server contract clear na ho, to har team apna-apna guess karti hai. Frontend `PUT` bhejta hai jaha backend `PATCH` expect karta hai; backend `200` bhejta hai jaha frontend `201` par redirect karta hai; error pe `200` ke andar `{"error": "..."}` aa jaata hai to client retry logic likh hi nahi sakta. HTTP + REST ek **common vocabulary** deta hai jise duniya bhar ke tools (browsers, proxies, caches, load balancers) samajhte hain — tumhe apna protocol invent nahi karna padta.

### How does it work — ek HTTP message ki anatomy

Har HTTP **request** me chaar cheezein hoti hain:

```text
POST /api/employees HTTP/1.1          <- method + path + version (request line)
Host: localhost:5028                   <- headers (key: value)
Content-Type: application/json
Authorization: Bearer eyJhbGc...
                                       <- ek khaali line
{ "fullName": "Aarti Rao",             <- body (optional)
  "email": "aarti@bank.example" }
```

- **Method (verb)** — kya karna hai: `GET` (padho), `POST` (banao), `PUT`/`PATCH` (badlo), `DELETE` (hatao).
- **Path** — kis cheez pe: `/api/employees`, `/api/employees/7`.
- **Headers** — request ke baare me metadata: body ka format (`Content-Type`), client kya format chahta hai (`Accept`), auth token (`Authorization`).
- **Body** — actual data (sirf `POST`/`PUT`/`PATCH` me), aksar JSON.

Har HTTP **response** me teen cheezein:

```text
HTTP/1.1 201 Created                   <- status line (code + reason)
Content-Type: application/json
Location: /api/employees/7             <- headers
                                       <- khaali line
{ "id": 7, "fullName": "Aarti Rao" }   <- body
```

- **Status code** — 3-digit number jo batata hai kya hua (neeche detail).
- **Headers** — response metadata.
- **Body** — result data (JSON), ya error details.

### The verbs aur unka intent

| Verb | Intent | Body? | Safe? | Idempotent? |
| --- | --- | --- | --- | --- |
| GET | Resource padho, kuch badlo mat | Nahi | Haan | Haan |
| POST | Naya resource banao (collection me) | Haan | Nahi | Nahi |
| PUT | Poora resource replace/create karo at a known URL | Haan | Nahi | Haan |
| PATCH | Resource ka kuch hissa badlo | Haan | Nahi | Aksar nahi |
| DELETE | Resource hatao | Nahi | Nahi | Haan |

- **Safe** = server ka state nahi badalta (sirf `GET`). Browser aur crawlers safely `GET` kar sakte hain.
- **Idempotent** = same request 1 baar ya 10 baar bhejo, end result same. `GET`, `PUT`, `DELETE` idempotent. `POST` nahi — 3 baar `POST /api/employees` = 3 employees.

Concrete: employee ka email badalna — agar sirf email bhej rahe ho to `PATCH /api/employees/7`; agar poora employee object bhej ke replace kar rahe ho to `PUT /api/employees/7`.

### Status code families

- **2xx — success.** `200 OK` (mila/ho gaya, body ke saath), `201 Created` (naya bana, `Location` header ke saath), `204 No Content` (ho gaya, bhejne ko kuch nahi — jaise `DELETE`).
- **4xx — client ki galti.** `400 Bad Request` (input invalid/malformed), `401 Unauthorized` (token nahi ya galat — actually "unauthenticated"), `403 Forbidden` (logged in ho par permission nahi), `404 Not Found` (resource nahi mila), `409 Conflict` (state clash — jaise duplicate email, ya concurrent update).
- **5xx — server ki galti.** `500 Internal Server Error` (unhandled exception — client kuch nahi kar sakta except retry).

Rule: agar client theek request bheje to 4xx nahi aana chahiye; agar 5xx aaya to **hamari** bug hai.

### What REST means

REST ek **architectural style** hai (protocol nahi). Iske core ideas jo hum follow karenge:

1. **Resources** — server ki har cheez ek "resource" hai jise ek URL identify karta hai. Hamare paas `employees` resource hai.
2. **Nouns in URLs, verbs in HTTP** — URL me `/api/employees` (noun), `/api/getEmployees` nahi. Kaam HTTP method batata hai.
3. **Collection aur item** — `/api/employees` = poori list; `/api/employees/7` = ek item (id `7`).
4. **Statelessness** — har request apne aap me complete honi chahiye. Server do requests ke beech client ki "memory" nahi rakhta; auth token har request me aata hai. Isse koi bhi server instance koi bhi request handle kar sakta hai (scaling aasan).
5. **Uniform interface** — sab resources same tarike se behave karte hain (`GET` list, `POST` create, ...). Naya resource seekhne me effort kam.

Hamari saari routes isi shape me hongi: `GET /api/employees`, `GET /api/employees/{id}`, `POST /api/employees`, `PUT /api/employees/{id}`, `DELETE /api/employees/{id}`.

### JSON as the wire format

HTTP body sirf text (bytes) le jaata hai. C# ka `Employee` object network par nahi ja sakta — use pehle text me badalna padta hai. Woh text format JSON hai:

```json
{
  "id": 7,
  "fullName": "Aarti Rao",
  "email": "aarti@bank.example",
  "salary": 900000,
  "isActive": true
}
```

- **Serialization** — C# object se JSON text banana (response bhejte waqt).
- **Deserialization** — JSON text se C# object banana (request aane par).

ASP.NET Core ye dono kaam **automatic** karta hai `System.Text.Json` se. Default me C# `PascalCase` properties JSON me `camelCase` ban jaati hain (`FullName` to `fullName`). Tum controller me `Ok(employee)` likhte ho — framework baaki karta hai.

### Where is it used in day-to-day development

- **API design meeting** — naya feature aane par team pehle URL aur verbs aur status codes decide karti hai, code baad me.
- **Debugging** — browser DevTools ya Postman me request/response dekh ke "kya bheja, kya mila, kaunsa status" — 90% bugs yahin dikh jaate hain.
- **Frontend integration** — Angular/React dev tumse contract poochta hai: "create pe 201 dega ya 200? error pe body kya?"
- **Postman/Swagger** — har endpoint manually hit karke verify karna daily kaam hai.

### Pros and cons of the REST + HTTP + JSON stack

Faayde: universal (har language, har tool samajhta hai), human-readable (JSON aankh se padh sakte ho), cache-friendly (`GET` cacheable), stateless (scale aasan). Nuksaan: JSON verbose hai (bytes zyada), over/under-fetching (`GET /employees/7` me shayad tumhe sirf naam chahiye tha par pura object aaya), aur "REST" ki koi strict definition na hone se har team thoda alag karti hai. High-performance internal service-to-service calls ke liye gRPC ya message queue behtar ho sakte hain — lekin public/partner-facing aur BFSI web APIs ke liye REST+JSON default hai.

### When to use / when NOT to use plain REST+JSON

Use jab: public ya partner API, browser/mobile client, CRUD-shaped data (hamara case). **Mat** use jab: real-time push chahiye (WebSockets/SignalR), bahut high-throughput internal RPC (gRPC), ya complex client-driven queries jaha client exact fields chunna chahe (GraphQL). Hamara Employee API classic CRUD hai, isliye REST+JSON perfect fit.

### Ek concrete failure scenario

Maan lo tumne "delete employee" ko `GET /api/employees/7/delete` bana diya. Do cheezein tootengi: (1) `GET` safe hona chahiye, isliye koi browser prefetch, link crawler, ya antivirus jo URL open karta hai woh chup-chaap employees delete kar dega. (2) Koi bhi caching proxy `GET` response cache kar sakta hai. Sahi tareeka: `DELETE /api/employees/7`, jo na safe hai na cacheable, aur intent bilkul saaf hai.

</Hinglish>

<Callout type="warning">

`401` ka naam "Unauthorized" hai par uska matlab **"unauthenticated"** hai — tumne pehchaan nahi karwayi (token missing/invalid). `403 Forbidden` = pehchaan ho gayi lekin is kaam ki permission nahi. Interview me ye ulta bolne se marks jaate hain.

</Callout>

## Real World Example

<RealWorld company="A digital-lending startup">

Ek lending startup ke loan-application API me create endpoint success par `200` deta tha aur response body me poora application object. Mobile team ne assume kar liya ki `200` ka matlab "already exists" ho sakta hai aur retry logic me duplicate applications ban gaye. Fix: create par strictly `201 Created` + `Location: /api/applications/{id}` header, aur idempotency key header support. Iske baad "verb + status code contract" har PR review ka mandatory check ban gaya.

</RealWorld>

<RealWorld company="A BFSI systems integrator (TCS / Infosys style)">

Ek core-banking integration me ek service partner ke API ko `PUT` ki jagah `POST` se "update" kar rahi thi. Network flaky hone par client retries hote the, aur `POST` idempotent na hone se same transaction do baar post ho gaya — reconciliation team ko manually reverse karna pada. Lesson: update ke liye idempotent verb (`PUT`) aur idempotency keys — ye HTTP semantics ka seedha business impact hai.

</RealWorld>

## Numbers That Matter

<Numbers>

- 4 parts har HTTP request me: method, path, headers, body
- 3 parts har HTTP response me: status code, headers, body
- 5 verbs jo hum use karenge: GET, POST, PUT, PATCH, DELETE
- 3 status families: 2xx success, 4xx client-error, 5xx server-error
- 9 status codes hamare course me: 200, 201, 204, 400, 401, 403, 404, 409, 500
- Idempotent verbs: GET, PUT, DELETE (safe sirf GET); POST idempotent nahi
- Default JSON casing: C# `PascalCase` to wire `camelCase` (System.Text.Json)
- 2 route shapes per resource: `/api/employees` (collection), `/api/employees/{id}` (item)

</Numbers>

## Interview Angle

<InterviewAngle>

Ye topic freshers ke liye "very-high" frequency hai — "what is REST", "difference between PUT and PATCH", "201 vs 200", "401 vs 403", "is POST idempotent" almost har .NET/Java web interview me aata hai. Strong 20-second answer for PUT vs PATCH: "`PUT` poora resource replace karta hai given URL par aur idempotent hai — same body 10 baar bhejo, same result. `PATCH` partial update hai, sirf bheje gaye fields badalte hain, aur generally idempotent nahi maana jaata. Practically, agar client sirf ek employee ka email badalna chahta hai to `PATCH /api/employees/7`; agar poora employee object bhej ke overwrite kar raha hai to `PUT`." Aise hi 401-vs-403: "401 = tum kaun ho pata nahi (authentication missing/failed); 403 = pata hai tum kaun ho, par ye kaam allowed nahi (authorization)."

</InterviewAngle>

## Common Mistakes

<Mistake>

Verbs URL me daalna — `/api/getEmployees`, `/api/createEmployee`, `/api/employees/7/delete`. REST me URL noun hota hai; kaam HTTP method batata hai. `GET /api/employees`, `POST /api/employees`, `DELETE /api/employees/7`.

</Mistake>

<Mistake>

Error par `200 OK` bhejna aur body me `{ "success": false, "error": "..." }` rakhna. Client, proxies, monitoring sab status code dekhte hain — invalid input par `400`, missing resource par `404` bhejo, `200` nahi.

</Mistake>

<Mistake>

`401` aur `403` ko ulta samajhna. `401` = authentication nahi hui (token missing/invalid). `403` = authenticated ho par permission nahi.

</Mistake>

<Mistake>

`POST` ko idempotent maan lena aur retry logic me safeguard na rakhna. Network retry par duplicate resources ban jaate hain. Create ke liye idempotency key ya `PUT` at a known id use karo.

</Mistake>

<Mistake>

Create endpoint se `200` dena bina `Location` header ke. Convention `201 Created` + `Location: /api/employees/{newId}` hai — client ko naye resource ka URL turant mil jaata hai.

</Mistake>

## Quick Revision

<QuickRevision>

- API = client aur server ke beech ek contract, HTTP par exchange hota hai; client ko sirf contract pata hota hai, andar ka code nahi
- HTTP request = method + path + headers + body; HTTP response = status code + headers + body
- Verbs: GET (padho, safe, idempotent), POST (banao, not idempotent), PUT (replace, idempotent), PATCH (partial, usually not idempotent), DELETE (hatao, idempotent)
- Status families: 2xx ok (200, 201, 204), 4xx client galti (400, 401, 403, 404, 409), 5xx server galti (500)
- 401 = unauthenticated (kaun ho pata nahi); 403 = authenticated par permission nahi
- REST = resources ko noun URLs se address karo, kaam HTTP verb se; `/api/employees` (collection) aur `/api/employees/{id}` (item); stateless (har request self-contained, token har baar)
- JSON = wire format; serialization = object to JSON, deserialization = JSON to object; ASP.NET Core `System.Text.Json` se automatic, PascalCase to camelCase
- Idempotent = 1 baar ya N baar bhejo, result same (GET, PUT, DELETE); safe = state nahi badalta (sirf GET)

</QuickRevision>
