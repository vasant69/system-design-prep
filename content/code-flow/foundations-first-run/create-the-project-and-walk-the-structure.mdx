<SimpleDefinition>

The one-time setup step for our entire course project: using the `dotnet` CLI to scaffold an ASP.NET Core Web API, then walking every file and folder the template creates — the `.csproj`, `Program.cs`, `appsettings.json`, `Properties/launchSettings.json`, and the sample controller — so nothing in the project is a black box before we start changing it.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Is poore course me hum **ek hi project** banayenge — ek BFSI-style **Employee Management Web API** — aur har naya concept isi project me add karenge. Isliye ye pehla practical step sabse important hai: project ban kaise raha hai, aur template jo files deta hai unme kya-kya hai. Agar ye skeleton clear ho gaya, to aage sab kuch "isme kahan add karoon" ka sawaal ban jaata hai, "ye kya hai" ka nahi.

### What is it — hum kar kya rahe hain

.NET ke saath ek command-line tool aata hai: **`dotnet` CLI**. Ye tool naya project bana sakta hai, build kar sakta hai, run kar sakta hai, packages add kar sakta hai. Visual Studio ya Rider bhi yahi kaam GUI se karte hain — andar wahi CLI chalti hai. Hum CLI use karenge kyunki har line dikhti hai, kuch chhupa hua nahi hota.

Ek "project" `.NET` me ek **`.csproj` file** hoti hai plus uske aas-paas ka code. `.csproj` batati hai: kaunsa .NET version, kaunse NuGet packages chahiye, aur kaunsi files compile karni hain. Ek "solution" (`.sln`) sirf ek container hota hai jo ek ya zyada projects ko ek saath group karta hai — Visual Studio ke liye convenience.

### Why do we need it — ye step skip kyun nahi kar sakte

Bahut se beginners `dotnet new` chala kar seedha code likhna shuru kar dete hain, aur `Program.cs` ki har line ko "magic" maan lete hain. Phir jab kuch break hota hai — port already in use, Swagger nahi khul raha, environment galat hai — to unhe pata hi nahi hota dekhein kahan. Har file ka ek specific kaam hai; ek baar wo pata ho, debugging 10x aasan ho jaati hai.

### How does it work — step by step

**Step 1 — SDK check.** Terminal me:

```bash
dotnet --version
```

Agar `8.0.x` jaisa kuch dikhe, SDK installed hai. Nahi to `dotnet.microsoft.com` se .NET 8 SDK install karo.

**Step 2 — solution aur project banao.** Hum ek folder me sab rakhenge:

```bash
mkdir EmployeeManagement
cd EmployeeManagement
dotnet new sln -n EmployeeManagement
dotnet new webapi -n EmployeeManagement.Api --use-controllers
dotnet sln add EmployeeManagement.Api/EmployeeManagement.Api.csproj
```

Line by line:

- `dotnet new sln -n EmployeeManagement` — ek khaali solution file `EmployeeManagement.sln` banata hai. `-n` matlab name.
- `dotnet new webapi -n EmployeeManagement.Api --use-controllers` — ye asli kaam hai. `webapi` ek **template** ka naam hai. `-n EmployeeManagement.Api` project ka naam aur folder ka naam set karta hai. `--use-controllers` bahut important hai: .NET 8 me `dotnet new webapi` **by default Minimal APIs** deta hai (sab kuch `Program.cs` me), lekin hum **controller-based** API padhna chahte hain kyunki jobs me wahi zyada milta hai — is flag se template `Controllers/` folder wala version deta hai.
- `dotnet sln add ...` — naye project ko solution me register karta hai.

**Step 3 — run karo.**

```bash
cd EmployeeManagement.Api
dotnet run
```

Terminal me kuch aisa dikhega: `Now listening on: http://localhost:5xxx`. Browser me `http://localhost:5xxx/swagger` kholo — ek interactive API page khulega jisme ek sample `WeatherForecast` endpoint hoga. Iska matlab project chal gaya.

### Show it in our project — har file kya hai

`dotnet new webapi --use-controllers` ye structure deta hai:

```text
EmployeeManagement.Api/
├── Controllers/
│   └── WeatherForecastController.cs
├── Properties/
│   └── launchSettings.json
├── appsettings.json
├── appsettings.Development.json
├── EmployeeManagement.Api.csproj
├── Program.cs
└── WeatherForecast.cs
```

#### `EmployeeManagement.Api.csproj`

```xml
<Project Sdk="Microsoft.NET.Sdk.Web">

  <PropertyGroup>
    <TargetFramework>net8.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
  </PropertyGroup>

  <ItemGroup>
    <PackageReference Include="Swashbuckle.AspNetCore" Version="6.6.2" />
  </ItemGroup>

</Project>
```

- `Sdk="Microsoft.NET.Sdk.Web"` — batata hai ye ek **web** project hai, isliye `dotnet` ise extra web build steps (jaise `wwwroot` handling, `launchSettings`) deta hai.
- `<TargetFramework>net8.0</TargetFramework>` — kaunsa .NET version. Isi ek line se tum .NET 8 se .NET 9 pe upgrade karte ho.
- `<Nullable>enable</Nullable>` — nullable reference types on. Iska matlab: compiler tumhe warn karega agar tum `null` ho sakne wali cheez ko bina check kiye use karo. Beginners ko ye annoying lagta hai, lekin production bugs isse bahut kam hote hain.
- `<ImplicitUsings>enable</ImplicitUsings>` — common `using` statements (jaise `System`, `System.Linq`, `Microsoft.AspNetCore.Builder`) automatically har file me available. Isliye chhoti files me tum `using` lines nahi dekhte.
- `<PackageReference Include="Swashbuckle.AspNetCore" ... />` — ek **NuGet package** dependency. Swashbuckle hi Swagger UI generate karta hai. Version pinned hai taaki har machine pe same build mile.

#### `Program.cs`

```csharp
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddControllers();
builder.Services.AddEndpointsApiExplorer();
builder.Services.AddSwaggerGen();

var app = builder.Build();

if (app.Environment.IsDevelopment())
{
    app.UseSwagger();
    app.UseSwaggerUI();
}

app.UseHttpsRedirection();
app.UseAuthorization();
app.MapControllers();

app.Run();
```

Ye file itni important hai ki iski har line ka apna alag topic hai (agla topic). Abhi sirf **do-hisso** wala mental model yaad rakho:

1. **`builder` section (`app.Build()` se pehle)** — yahan tum services **register** karte ho DI container me. `AddControllers()`, `AddSwaggerGen()` — ye sab "app ko chalane ke liye kya-kya chahiye" bata rahe hain.
2. **`app` section (`app.Build()` ke baad)** — yahan tum **middleware pipeline** banate ho — request aane par kya-kya steps chalenge, kis order me. `UseHttpsRedirection`, `UseAuthorization`, `MapControllers` — ye har incoming request pe upar se neeche chalte hain.

`app.Run()` — server start karta hai aur block ho jaata hai (process yahan "ruka" rehta hai requests sunte hue) jab tak tum `Ctrl+C` na dabao.

#### `appsettings.json` aur `appsettings.Development.json`

```json
{
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "Microsoft.AspNetCore": "Warning"
    }
  },
  "AllowedHosts": "*"
}
```

- `appsettings.json` — base configuration. Yahan hum baad me `ConnectionStrings`, JWT settings, wagairah rakhenge.
- `appsettings.Development.json` — sirf tab load hota hai jab environment `Development` ho. Ye base file ke **upar merge** hota hai — jo keys yahan hain wo override kar deti hain, baaki base se aati hain. Isi tarah tum local aur production ke liye alag settings rakhte ho bina code badle.

#### `Properties/launchSettings.json`

```json
{
  "profiles": {
    "http": {
      "commandName": "Project",
      "launchBrowser": true,
      "launchUrl": "swagger",
      "applicationUrl": "http://localhost:5028",
      "environmentVariables": {
        "ASPNETCORE_ENVIRONMENT": "Development"
      }
    }
  }
}
```

- Ye file **sirf local development** ke liye hai — production me ye deploy hi nahi hoti.
- `applicationUrl` — konsa port. "Port already in use" error aaye to yahan number badal do.
- `launchUrl: "swagger"` — `dotnet run` ke baad browser seedha `/swagger` pe khulega.
- `ASPNETCORE_ENVIRONMENT: "Development"` — **yahi decide karta hai** ki `IsDevelopment()` true hoga aur `appsettings.Development.json` load hoga.

#### `Controllers/WeatherForecastController.cs` aur `WeatherForecast.cs`

Ye sirf **sample code** hai — template ne diya taaki tumhe ek working endpoint dikhe. Hum agle module me apna pehla real controller likhne se pehle **in dono files ko delete kar denge**. Inhe rakhna zaroori nahi.

### Where is it used in day-to-day development

- Naya microservice ya naya project shuru karte waqt — har baar yahi `dotnet new` step.
- Onboarding ke pehle din — naye team member ko yahi structure samjhaya jaata hai.
- CI/CD pipeline `dotnet build` aur `dotnet test` chalati hai — wahi CLI jo tum abhi use kar rahe ho.
- `.csproj` din me kai baar khulti hai — har baar jab naya NuGet package add karna ho.

</Hinglish>

<Callout type="tip">

`.NET 8` me `dotnet new webapi` bina flag ke **Minimal API** deta hai (koi `Controllers/` folder nahi). Is course ke liye hamesha `--use-controllers` lagao. Agar galti se bina flag ke bana liya, project delete karke dobara banao — Minimal se controllers me convert karna beginner ke liye zyada confusing hai.

</Callout>

## Real World Example

<RealWorld company="A BFSI systems integrator (TCS / Infosys style)">

Bade Indian IT services projects me har naya API service ek **internal starter template** se banta hai jo `dotnet new` ke output ko customize karta hai — pre-added logging, standard folder structure (`Controllers`, `Services`, `Repositories`, `Models`, `DTOs`), aur company ki NuGet feed. Naya developer `dotnet new company-webapi -n Xyz.Api` chalata hai aur usse wahi skeleton milta hai jo hum yahan haath se bana rahe hain. Isliye template ke andar kya hai ye samajhna zaroori hai — warna customized template bhi black box lagta hai.

</RealWorld>

<RealWorld company="A digital-lending startup">

Ek lending startup ke KYC service me `launchSettings.json` ka `ASPNETCORE_ENVIRONMENT` galti se `Production` chhod diya gaya tha ek developer ki machine pe. Result: local pe Swagger nahi khul raha tha (kyunki `if (app.Environment.IsDevelopment())` false tha) aur woh developer aadha din "Swagger toota hai" debug karta raha. Fix ek line thi. Yahi wajah hai ki hum har file ko upfront samajhte hain.

</RealWorld>

- 3 config sources default me merge hote hain: `appsettings.json`, `appsettings.{Environment}.json`, environment variables (baad wala jeetta hai)

## Common Mistakes

<Mistake>

`dotnet new webapi` bina `--use-controllers` chala kar Minimal API project bana lena, phir tutorials me `Controllers/` folder dhoondhna jo hai hi nahi. .NET 8 ka default change ho gaya hai — flag zaroori hai.

</Mistake>

<Mistake>

`launchSettings.json` ko production config samajhna aur usme secrets (connection strings, API keys) daal dena. Ye file deploy hi nahi hoti aur aksar git me commit ho jaati hai — secrets kabhi yahan nahi.

</Mistake>

<Mistake>

`Program.cs` me middleware ka order badal dena bina samjhe — jaise `app.UseAuthorization()` ko `app.MapControllers()` ke baad rakhna. Pipeline order matter karta hai; galat order pe auth silently skip ho sakta hai.

</Mistake>

<Mistake>

Sample `WeatherForecastController.cs` ko project me chhod dena aur uske upar apna code likhna. Ye clutter banata hai aur naye log confuse hote hain ki `WeatherForecast` project ka hissa hai. Module 2 se pehle delete karo.

</Mistake>

<Mistake>

`appsettings.Development.json` ko poori nayi config samajhna. Ye base `appsettings.json` ke **upar merge** hota hai — sirf woh keys likho jo override karni hain, poori file dobara mat likho.

</Mistake>

## Quick Revision

<QuickRevision>

- `dotnet new sln` + `dotnet new webapi -n EmployeeManagement.Api --use-controllers` + `dotnet sln add` — the one-time scaffold; `--use-controllers` is required on .NET 8 (default is Minimal API)
- `.csproj` = SDK + `<TargetFramework>` + NuGet `PackageReference`s; change the framework in one line to upgrade
- `Program.cs` has two halves split by `app.Build()`: `builder.Services.Add...` (register services in DI) then `app.Use.../app.Map...` (middleware pipeline, runs top-to-bottom per request)
- `app.Run()` starts the server and blocks until Ctrl+C
- `appsettings.json` is the base; `appsettings.Development.json` merges on top and only loads when `ASPNETCORE_ENVIRONMENT=Development`
- `Properties/launchSettings.json` is local-dev only, never deployed — it sets the port, the launch URL (`swagger`), and the environment name; never put secrets here
- The `WeatherForecast` controller + model are sample code — delete both before module 2
- `if (app.Environment.IsDevelopment())` is why Swagger shows locally but not in production by default

</QuickRevision>
