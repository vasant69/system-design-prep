<SimpleDefinition>

Passwords are never stored as plaintext or in any reversible form; the server stores only a slow, salted, one-way hash produced by a purpose-built password hashing function such as PBKDF2 (via ASP.NET Core Identity's `PasswordHasher`) or BCrypt. On registration the API hashes the chosen password and saves only the digest on the `User` row; on login it recomputes and compares in constant time, then issues a JWT, and it transparently upgrades old digests when the work factor increases.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Pichhle teen topics me humne identity verify karna (JWT) aur permission check karna (roles/policies) seekha. Lekin ek sawaal chhoot gaya: wo username aur password **aata kahan se hai** aur server unhe **store kaise karta hai**. Is topic me hum `EmployeeManagement.Api` me ek `User` store banayenge aur password ko sahi tareeke se — matlab kabhi wapas na padha ja sake aisa — save karenge.

### What is it — password hashing ka plain matlab

Password hashing ka matlab hai password ko ek **one-way function** se guzaar kar ek fixed-length string (digest) banana, aur sirf wahi digest database me rakhna. One-way ka matlab: digest se wapas original password nikaalna practically impossible hai. Login pe server user ka diya password dobara usi function se guzaarta hai aur naye digest ko stored digest se compare karta hai — match hua to password sahi tha.

Do cheezein isse "normal hash" (jaise `SHA-256`) se alag banati hain:

- **Salt** — har user ke liye ek random value jo password ke saath mila kar hash hoti hai. Isse do users jinka password same hai unke digest alag aate hain, aur pre-computed "rainbow table" bekaar ho jaati hai.
- **Work factor (iterations / cost)** — function ko jaan-boojh kar **dheema** banaya jaata hai, laakhon internal iterations. Ek legit login pe 50-200 millisecond lagna theek hai; ek attacker jo crore passwords try kar raha hai uske liye ye deewar ban jaati hai.

### Why do we need it — bina iske kya tootega

Agar tum plaintext password store karo aur database leak ho (backup chori, SQL injection, ek disgruntled DBA), to har user ka password turant expose. Log same password kai jagah use karte hain — tumhara leak unke bank aur email tak pahunch jaata hai. BFSI me ye direct regulatory violation hai.

Agar tum **reversible encryption** use karo (`AES` ke saath ek key), to problem sirf shift hoti hai: ab ek key sab kuch khol deti hai, aur wo key aksar usi server pe milti hai jo compromise hua. Hashing me koi "master key" hai hi nahi jise chura kar sab kuch pada ja sake.

Agar tum plain `SHA-256` use karo (salt ke bina, single pass): wo **bahut fast** hai — ek modern GPU crore SHA-256 hashes per second nikaalta hai. 8-character password minuto me crack ho jaata hai. Fast hash password ke liye galat tool hai; hume jaan-boojh kar slow chahiye.

Concrete failure scenario: ek team ne "hash to kar rahe hain" keh kar `SHA-256(password)` bina salt store kiya. Leak hua, attacker ne ek public rainbow table se 60% passwords 10 minute me reverse kar liye, kyunki bina salt ke same password = same hash aur wo hashes internet pe already mapped the.

### How does it work — mechanism step by step

1. **Register pe:** server ek CSPRNG se random salt banata hai (ya library khud banati hai), password + salt ko chosen algorithm (PBKDF2 / BCrypt / Argon2) se hazaaron-laakhon iterations chalata hai, aur ek **self-describing string** banata hai jisme algorithm id, iteration count, salt, aur final hash — sab ek saath encode hote hain. Yahi ek string `PasswordHash` column me jaati hai. Alag `Salt` column ki zaroorat nahi — salt digest ke andar hai.
2. **Login pe:** server us stored string ko parse karta hai (algorithm, iterations, salt nikaalta hai), user ka diya password usi salt aur iterations ke saath hash karta hai, aur do byte arrays ko **constant-time** compare karta hai (jaldi return nahi karta pehle mismatch pe — warna response time se attacker guess kar sakta hai).
3. **Upgrade (rehash):** agar stored digest purane, kamzor iteration count pe bana tha, to successful login pe server naye (zyada) work factor se dobara hash karke `PasswordHash` update kar deta hai. User ko kuch pata nahi chalta. Isi tarah security parameters time ke saath badhte hain bina "sabko password reset karo" mail bheje.

```csharp
    public int Id { get; set; }
    public string Username { get; set; } = string.Empty;
```

```csharp
public DbSet<User> Users => Set<User>();

protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<User>(entity =>
    {
```

Ye ek `Users` table banata hai `Id`, `Username` (unique), `PasswordHash`, `Role`, `AccessFailedCount`, `LockoutEndUtc` columns ke saath. **Plaintext password ke liye koi column nahi hai — aur na kabhi hoga.**

### Show it in our project — Part 2: hashing wiring aur register endpoint

Sabse simple production-ready approach: ASP.NET Core ka built-in `PasswordHasher<T>` (`Microsoft.AspNetCore.Identity` namespace, koi alag package nahi chahiye .NET 8 me — `Microsoft.Extensions.Identity.Core`). Ye andar **PBKDF2-HMAC-SHA256** use karta hai, current default 100,000+ iterations, salt digest me embedded.

`Program.cs`:

```csharp
builder.Services.AddScoped<IPasswordHasher<User>, PasswordHasher<User>>();
```

`AuthController` me register — sirf `Admin` naye users bana sakta hai (BFSI me self-signup nahi hota; HR/IT accounts provision karta hai):

```csharp
[Authorize(Roles = "Admin")]
[HttpPost("register")]
public async Task<ActionResult<UserDto>> Register(RegisterRequest request)
{
    var exists = await _db.Users
        .AnyAsync(u => u.Username == request.Username);
    if (exists)
        return Conflict(new { message = "Username already taken" });

    var user = new User
    {
        Username = request.Username,
        Role = request.Role
    };

    user.PasswordHash = _hasher.HashPassword(user, request.Password);

    _db.Users.Add(user);
    await _db.SaveChangesAsync();

    return CreatedAtAction(nameof(GetById), new { id = user.Id },
        new UserDto(user.Id, user.Username, user.Role));
}

public record RegisterRequest(string Username, string Password, string Role);
public record UserDto(int Id, string Username, string Role);
```

### Show it in our project — Part 3: login verify + issue JWT

`jwt-end-to-end` wale topic ka `Login` ab hardcoded user ke bajaye asli store use karega:

```csharp
[AllowAnonymous]
[HttpPost("login")]
public async Task<ActionResult<LoginResponse>> Login(LoginRequest request)
{
    var user = await _db.Users
        .SingleOrDefaultAsync(u => u.Username == request.Username);

    if (user is null)
    {
        // dummy hash verify — timing ko user-exists case jaisa rakhne ke liye
        _hasher.VerifyHashedPassword(new User(), DummyHash, request.Password);
        return Unauthorized(new { message = "Invalid username or password" });
    }

    if (user.LockoutEndUtc is { } until && until > DateTimeOffset.UtcNow)
        return StatusCode(StatusCodes.Status423Locked,
            new { message = "Account temporarily locked. Try later." });

    var result = _hasher.VerifyHashedPassword(
        user, user.PasswordHash, request.Password);

    if (result == PasswordVerificationResult.Failed)
    {
        user.AccessFailedCount++;
        if (user.AccessFailedCount >= 5)
            user.LockoutEndUtc = DateTimeOffset.UtcNow.AddMinutes(15);
        await _db.SaveChangesAsync();
        return Unauthorized(new { message = "Invalid username or password" });
    }

    if (result == PasswordVerificationResult.SuccessRehashNeeded)
        user.PasswordHash = _hasher.HashPassword(user, request.Password);

    user.AccessFailedCount = 0;
    user.LockoutEndUtc = null;
    await _db.SaveChangesAsync();

    var token = _tokenService.CreateToken(user);   // topic 2 ka ITokenService
    return Ok(new LoginResponse(token.AccessToken, token.ExpiresAtUtc));
}
```

### Code explained line by line

- `AddScoped<IPasswordHasher<User>, PasswordHasher<User>>()` — DI me hasher register. Interface pe depend karo taaki test me fake inject ho sake aur baad me BCrypt pe switch karna ek line ka kaam ho.
- `_hasher.HashPassword(user, request.Password)` — `user` argument sirf signature ka hissa hai (generic `TUser`); built-in implementation use nahi karta. Return: ek base64 string jisme format-marker + iteration count + salt + subkey. Yahi `PasswordHash` me store hota hai.
- `HasIndex(u => u.Username).IsUnique()` — DB level pe do same usernames rok deta hai; race condition me bhi `SaveChangesAsync` exception dega, sirf application check ke bharose mat raho.
- `VerifyHashedPassword(user, storedHash, providedPassword)` — return enum: `Failed`, `Success`, ya `SuccessRehashNeeded`. Andar constant-time comparison hota hai — tumhe khud `==` nahi likhna.
- **Dummy-hash verify** jab user nahi mila — taaki "user exists but wrong password" aur "user does not exist" dono me response time lagbhag same rahe. Warna attacker timing se valid usernames enumerate kar leta hai.
- `PasswordVerificationResult.SuccessRehashNeeded` — password sahi tha par digest purane parameters pe bana tha; hum turant naye default se rehash karke update karte hain.
- `AccessFailedCount` / `LockoutEndUtc` — simple account lockout: 5 galat attempts pe 15 minute lock. Brute-force ko dheema karta hai. Ek behtar layer (per-IP rate limit) agle topic me.
- Generic `"Invalid username or password"` — kabhi mat batao ki username galat tha ya password. Dono cases ek hi message, ek hi status.
- `CreateToken(user)` — verify pass hone ke baad hi JWT banta hai. Yahi is topic ko `jwt-end-to-end` se jodta hai: hashing "kaun ho" prove karti hai, JWT us proof ko portable banata hai.

### Simplest to production — teen levels

1. **`PasswordHasher<User>` (jo humne kiya)** — built-in, PBKDF2, salt + rehash support. 95% apps ke liye kaafi. Koi extra dependency nahi.
2. **`BCrypt.Net-Next` package** — `BCrypt.HashPassword(password, workFactor: 12)` aur `BCrypt.Verify(password, hash)`. Memory-hard nahi hai par battle-tested, cost factor tune karna aasan. Tab chuno jab team ise already jaanti ho ya cross-platform interop chahiye.
3. **Argon2** (`Konscious.Security.Cryptography.Argon2`) — 2015 Password Hashing Competition winner, memory-hard (GPU/ASIC attacks pe best). Sabse strong, par tuning (memory, parallelism, iterations) soch-samajh ke karni padti hai.

Aur ek poora framework: **ASP.NET Core Identity** — `UserManager`, `SignInManager`, lockout, email confirmation, 2FA, external logins, password reset tokens — sab ready. Agar tumhe ye saara chahiye to Identity add karo; agar sirf ek `Users` table + JWT chahiye (hamara case) to manual store lighter aur samajhne me saaf hai.

### Where is it used in day-to-day development

- Har `AuthController` / `AccountController` ka `register`, `login`, `change-password`, `reset-password` — sab isi hasher ke around bante hain.
- Data migration scripts: legacy system se users import karte waqt purane hashes ko as-is nahi daal sakte agar algorithm alag hai — aksar "next login pe rehash" strategy lagti hai.
- Seed data: dev environment me ek default `admin` user seed karte waqt password ko seed code me `HashPassword` se hash karke daalo, plaintext kabhi nahi.
- Security review / pentest findings: "passwords stored with fast hash" ek common high-severity finding hai — fix wahi jo yahan padha.

### When to use / when NOT to use

- **Hashing use karo** har jagah jahan tum password store kar rahe ho. Iska koi exception nahi.
- **Password store hi mat banao** agar tum ise avoid kar sakte ho — OAuth/OIDC (Google, Entra ID, Keycloak) use karke password ka jhanjhat hi mat lo. Tab tumhare paas hash bhi nahi hota, sirf ek external `sub` claim.
- **Reversible encryption** sirf tab jab tumhe original value **wapas chahiye** (jaise ek third-party API ka password jo tumhe unhe bhejna hai) — wo "password verification" nahi hai, wo "secret storage" hai, alag problem, vault use karo.

## Real World Example

<RealWorld company="A digital-lending startup">

Ek lending app ne launch ke time `SHA-256(password + "staticpepper")` use kiya — salt nahi, sirf ek hardcoded string sabke liye. 8 mahine baad ek staging DB dump galti se public S3 bucket me chala gaya. Attacker ne ek 12 GB wordlist ke against poori table 40 minute me crack kar li kyunki har row ek hi transformation pe thi. Remediation: `PasswordHasher<User>` pe migrate, sabhi active users ko next-login pe forced rehash, aur inactive users ko forced reset. Ek `salt` ki kami ne ek weekend ka incident bana diya.

</RealWorld>

<RealWorld company="A BFSI systems integrator (TCS / Infosys style)">

Ek core-HR module me login latency spike ka ticket aaya — p95 800ms. Root cause: ek architect ne PBKDF2 iterations 2,000,000 set kar diye the "extra safe" ke chakkar me, aur load test me har login ne ek CPU core 300ms tak khaa liya. 5 concurrent logins pe server choke. Fix: iterations ko OWASP-recommended range (PBKDF2-SHA256 ke liye ~600,000) pe laaya, aur ek per-IP rate limiter add kiya taaki brute-force defence iteration count ke bharose na ho. Lesson: work factor security aur availability ke beech ka trade-off hai, "jitna zyada utna achha" nahi.

</RealWorld>

## Numbers That Matter

<Numbers>

- Plaintext / reversible password columns: **0** — kabhi nahi
- Built-in `PasswordHasher<User>` = **PBKDF2-HMAC-SHA256**, .NET 8 default **100,000+** iterations (format marker `0x01`)
- OWASP 2024 guidance: PBKDF2-HMAC-SHA256 ~**600,000** iterations, BCrypt cost **10-12**, Argon2id **19 MiB** memory
- Legit login hash cost budget: **50-250 ms** — usse kam matlab weak, usse zyada matlab DoS surface
- Account lockout: **5** failed attempts, **15 min** lock (is topic me use kiya)
- `VerifyHashedPassword` returns: **Failed**, **Success**, **SuccessRehashNeeded**
- Fast unsalted SHA-256 crack rate: **crore+ hashes/second** ek single modern GPU pe

</Numbers>

## Common Mistakes

<Mistake>

Password ko `SHA-256` / `MD5` se hash karke "secure" maan lena. Ye fast hashes hain, GPU pe crore/second — bina salt aur bina work factor ke, ek leaked table minuto me crack ho jaati hai. Purpose-built PBKDF2 / BCrypt / Argon2 hi chahiye.

</Mistake>

<Mistake>

Ek hi static salt ("pepper") sab users ke liye use karna, ya salt bilkul na lagana. Per-user random salt chahiye — warna do users jinke passwords same hain unke digest same aayenge aur precomputed rainbow tables kaam kar jaati hain.

</Mistake>

<Mistake>

Login pe alag-alag error dena — "user not found" vs "wrong password". Isse attacker valid usernames enumerate kar leta hai. Dono cases me ek hi generic message, ek hi status code, aur user-not-found case me ek dummy verify chalao taaki response time bhi na farak kare.

</Mistake>

<Mistake>

Password ko database me encrypt (reversible) karke rakhna aur socha "decrypt kar sakte hain to secure hai". Encryption me ek key sab kuch kholti hai aur wo key aksar usi compromised server pe hoti hai. Password verification ke liye hashing chahiye, encryption nahi.

</Mistake>

<Mistake>

Hash comparison khud `storedHash == computedHash` se karna. Ye early-exit karta hai pehle mismatched byte pe, jisse timing side-channel banta hai. Fixed/constant-time comparison use karo — `PasswordHasher` aur BCrypt libraries ye andar se karte hain, unpe bharosa karo.

</Mistake>

<Mistake>

Brute-force defence sirf iteration count pe chhod dena. Iterations attacker ko dheema karte hain par ek determined attacker phir bhi try karta rahega. Account lockout ya per-IP / per-user rate limiting alag se chahiye.

</Mistake>

## Quick Revision

<QuickRevision>

- Passwords **never** stored plaintext or reversible — only a slow, per-user salted, one-way hash (PBKDF2 / BCrypt / Argon2).
- Salt kills rainbow tables and "same password = same hash"; work factor (iterations/cost) makes brute-force expensive — budget 50-250 ms per login.
- .NET built-in: `IPasswordHasher<User>` / `PasswordHasher<User>` = PBKDF2-HMAC-SHA256, salt embedded in the digest string, no separate `Salt` column.
- Register: `HashPassword(user, password)` then save the string. Login: `VerifyHashedPassword(user, storedHash, password)` returns `Failed` / `Success` / `SuccessRehashNeeded`.
- On `SuccessRehashNeeded`, re-hash with current parameters and update the row — transparent security upgrades, no mass reset.
- Login hygiene: generic `"Invalid username or password"`, a dummy verify when the user is missing (timing), account lockout after N fails, per-IP rate limit next topic.
- `Users` table: `Id`, `Username` (unique index), `PasswordHash`, `Role`, plus `AccessFailedCount` / `LockoutEndUtc` for lockout. Verify passes then `ITokenService.CreateToken` issues the JWT.
- Never `SHA-256`/`MD5`, never a shared static salt, never `==` for hash compare, never reversible encryption for verification.
- Need the full package (2FA, email confirm, password reset, external logins)? Use **ASP.NET Core Identity**. Need just a user table + JWT? Manual store is lighter and clearer.

</QuickRevision>

## Practice

<Callout type="tip">

**Chhota (small):** `User` entity (`Id`, `Username`, `PasswordHash`, `Role`) banao, `DbContext` me `DbSet` + unique index add karo, `AddUsers` migration banao aur `database update` karo. `Program.cs` me `IPasswordHasher<User>` register karo. Ek seed `admin` user daalo jiska password code me `HashPassword` se hash hokar jaaye — plaintext kahin nahi.

**Medium:** `authorize-roles-policies-claims` topic se jodo — `POST /api/auth/register` banao jo `[Authorize(Roles = "Admin")]` ho, duplicate username pe 409 de, aur naye user ka `PasswordHash` set kare. Phir `POST /api/auth/login` ko hardcoded user se hata kar is store pe le jao: `VerifyHashedPassword` chalao, `Failed` pe generic 401, `Success` pe topic 2 ka `ITokenService` se JWT. Swagger se: Admin token se register, phir naye creds se login karke token lo.

**Bada (large):** Poora account-safety layer add karo — `AccessFailedCount` + `LockoutEndUtc` se lockout (5 fails, 15 min), user-not-found case me dummy verify, `SuccessRehashNeeded` pe rehash-and-save, aur ek `POST /api/auth/change-password` endpoint jo current password verify karke naya hash set kare aur `AccessFailedCount` reset kare. Ek password policy validator (min 12 chars, common-password list block) FluentValidation se lagao. xUnit tests: wrong password 5 baar -> 6th call 423 Locked; correct password lockout window ke baad -> 200 + token; rehash-needed digest -> login ke baad DB me hash badla hua.

</Callout>
