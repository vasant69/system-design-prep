<SimpleDefinition>

The `Employee` class is the plain C# object (POCO) that defines the shape of one employee record in our API: its properties, their types, and their nullability, with no behaviour attached. It lives in the `Models` folder and is the single typed contract that every layer of the app agrees on.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Module 1 me humne `EmployeesController` ke andar ek `static List<Employee>` seed list rakhi thi, lekin `Employee` class ko jaldi me likha tha. Ab is module ka pura CRUD isi class ke upar khada hoga, isliye pehle ise **theek se design** karte hain — har field, uska type, aur nullable hai ya nahi, soch-samajh ke.

### What is it — Employee model kya hai

`Employee` ek **POCO** hai — Plain Old CLR Object. Matlab ek normal C# class jisme sirf **properties** hain, koi database code nahi, koi HTTP code nahi, koi business rule nahi. Ye sirf batati hai "ek employee record dikhta kaisa hai": uska Id kya hai, naam kya hai, salary kya hai, wagairah. Isko hum apne project me **domain model** ya **entity** bolenge.

### Why do we need it — iske bina kya tootega

Model ke bina do hi raaste bachte hain: `Dictionary<string, object>` me data ghumao, ya anonymous objects use karo. Dono me compiler tumhari koi madad nahi karta. `employee["Salry"]` likh do (typo) — compile ho jaayega, runtime pe `null` milega, aur tum aadha din dhoondhoge. Ek typed class ke saath `employee.Salry` **compile hi nahi hoga** — galti turant pakdi jaati hai. Iske alawa Swagger, model binding, aur JSON serialization sab ko ek concrete type chahiye taaki wo schema bana sakein.

### How does it work — mechanism

C# runtime har `Employee` object ke liye memory me ek block banata hai jisme har property ki value hoti hai. Jab request aati hai, ASP.NET Core ka **model binder** incoming JSON ko property-naam se match karke ek `new Employee { ... }` bhar deta hai. Jab response bhejte hain, `System.Text.Json` ulta kaam karta hai — object ko wapas JSON me. Beech me hum us object ko list me add/find/remove karte hain. Class me koi logic na hone se ye har layer me safely ghum sakta hai.

### Show it in our project — `Models/Employee.cs`

```csharp
namespace EmployeeManagement.Api.Models;

public class Employee
{
    // --- Identity ---
    public int Id { get; set; }

    // --- Profile ---
    public string FullName { get; set; } = string.Empty;
    public string Email { get; set; } = string.Empty;
    public string? MiddleName { get; set; }

    // --- Employment ---
    public int DepartmentId { get; set; }
    public string DepartmentName { get; set; } = string.Empty; // temp until module 4
    public DateOnly DateOfJoining { get; set; }
    public decimal Salary { get; set; }
    public string PanNumber { get; set; } = string.Empty; // format AAAAA9999A

    // --- Status ---
    public bool IsActive { get; set; }
}
```

### Code explained line by line

- `namespace EmployeeManagement.Api.Models;` — file-scoped namespace. Har model isi namespace me rahega, taaki `using EmployeeManagement.Api.Models;` ek hi line me sab mil jaaye.
- `public class Employee` — **class**, `record` nahi. Reason neeche "Pros and cons" me — entity ke liye class, DTO ke liye record.
- `public int Id { get; set; }` — primary identity. `int` isliye kyunki in-memory list me hum `max + 1` se naya id denge; module 4 me database ise auto-generate karega. `int` ki default value `0` hai — ek "abhi save nahi hua" employee ka Id `0` hota hai.
- `public string FullName { get; set; } = string.Empty;` — `Nullable` reference types on hain (`.csproj` me `<Nullable>enable</Nullable>`), isliye ek non-nullable `string` ko initialise karna padta hai warna compiler warning deta hai. `= string.Empty` ka matlab "ye field hamesha honi chahiye, default khaali string".
- `public string? MiddleName { get; set; }` — yahan `?` hai. Middle name **genuinely optional** hai — bahut logon ka hota hi nahi. `string?` batata hai "yahan `null` valid hai", aur code me use karne se pehle check karna padega.
- `public int DepartmentId { get; set; }` — foreign key ka number. Abhi koi `Department` table nahi hai, bas number store kar rahe hain.
- `public string DepartmentName { get; set; }` — **temporary**. Module 4 me jab `Department` entity aayegi, ye string hat jaayegi aur `Department` navigation property aayegi. Abhi read-friendly rakhne ke liye naam bhi store kar rahe hain.
- `public DateOnly DateOfJoining { get; set; }` — joining ki sirf **taareekh** matter karti hai, time nahi. `.NET 6+` me `DateOnly` exactly yeh represent karta hai — koi `00:00:00` ka jhamela nahi. `.NET 8` ka `System.Text.Json` ise seedha `"2021-06-14"` JSON string me serialize karta hai.
- `public decimal Salary { get; set; }` — **`decimal`, kabhi `double`/`float` nahi.** `m` suffix (`1_450_000m`) compiler ko batata hai ye decimal literal hai. Underscore sirf readability ke liye hai, compiler ignore karta hai.
- `public string PanNumber { get; set; }` — PAN ka format `AAAAA9999A` hai (5 letters, 4 digits, 1 letter). Ise **string** me rakho, number me nahi — leading letters number me fit hi nahi honge, aur `0` se shuru hone waale codes toot jaayenge. Format validation module 5 (FluentValidation) me aayegi; abhi bas type sahi rakh rahe hain.
- `public bool IsActive { get; set; }` — employee currently active hai ya exit ho gaya. `bool` ki default `false` hai, isliye create karte waqt hum explicitly `IsActive = true` set karenge.

### `decimal` vs `double` — money ka rule

`double` aur `float` **binary floating point** hain. Ye `0.1` ko exactly represent nahi kar sakte — bilkul waise jaise hum `1/3` ko decimal me exactly nahi likh sakte. Chhoti-chhoti rounding errors har operation me jama hoti hain. Lakhs of salary rows, interest calculations, TDS deductions — inme se ek bhi jagah `double` use kiya to totals audit se match nahi karenge, aur BFSI me wo ek reportable incident hai.

`decimal` **base-10** hai, 128-bit, aur paise tak exact rehta hai. Rule seedha hai: **paisa, percentage, interest rate, tax — sab `decimal`.** Sirf scientific/measurement data (temperature, coordinates) ke liye `double`.

### When to use / when NOT to use a shared model

Abhi is chhote project me ek hi `Employee` class sab jagah use karna theek hai. Lekin jaise hi API bahar clients ke saamne expose hoti hai, **isi class ko request/response me use karna band** kar denge — wo agla topic (Models vs DTOs) hai. Rule of thumb: **entity model andar-andar (storage, business logic) ke liye; DTO bahar (HTTP contract) ke liye.** Chhote internal tools me ek model kaafi hai; koi bhi public ya multi-team API me nahi.

### Failure scenario

Maan lo tumne `Salary` ko `double` bana diya. Ek report banata hai jo 5000 employees ki salary jodta hai. Expected total `71,23,45,000.00`, actual `71,23,44,999.98`. Finance team reconciliation me atak jaati hai, aur bug reproduce karna mushkil hai kyunki wo data pe depend karta hai. Ek `double` se `decimal` ka change poore report pipeline ko dobara test karne ke liye majboor karta hai. Isliye din 1 se sahi type.

### Where is it used in day-to-day development

- Naya feature = pehle model/field decide karna: type, nullable, default.
- Code review me sabse zyada comments model pe aate hain — "ye `string` kyun, enum kyun nahi", "ye nullable kyun".
- Database migration models se generate hoti hai (module 4) — galat type ab, to galat column baad me.
- Frontend team model dekh ke apne TypeScript interfaces banati hai.

### Pros and cons — class vs record for an entity

- **Class (jo humne chuna):** mutable properties (`set`), reference equality, EF Core ise track kar sakta hai, inheritance/navigation properties aasan. Entity ke liye yahi standard hai.
- **Record:** immutable-by-default (`init`), value equality, `with` expression se copy. Ye **DTOs** ke liye perfect hai — ek request DTO ban kar aata hai aur badalta nahi. Isliye is module ke DTO topic me hum `record` use karenge.

</Hinglish>

<Callout type="warning">

Model class me **koi method mat likho** — na `CalculateTenure()`, na `Validate()`, na `ToJson()`. Model sirf data ka shape hai. Derived values service layer ya DTO me banao. Logic model me daalte hi wo har layer me ghusega aur testing mushkil ho jaayegi.

</Callout>

## Real World Example

<RealWorld company="A digital-lending startup">

Ek lending startup ke payroll module me original developer ne `InterestRate` aur `EmiAmount` ko `double` rakha tha "kyunki chhota number hai". 8 mahine baad, ek customer ne complaint ki ki uska EMI `4,999.99` dikhta hai kabhi aur `5,000.01` kabhi. Root cause: `double` rounding. Fix ke liye teen entity fields, do DTOs, ek calculation service aur saari existing rows migrate karni padi — ek din ka kaam jo model design ke waqt 0 minute ka hota.

</RealWorld>

<RealWorld company="A BFSI systems integrator (TCS / Infosys style)">

Bade bank projects me har entity field ka ek "data dictionary" hota hai — field name, type, nullable, PII hai ya nahi, retention period. `Employee.PanNumber` waha "string, not null, PII, mask in logs" mark hota hai. Model class us dictionary ka code version hai, isliye field types aur nullability review me utni hi seriously dekhi jaati hai jitna business logic.

</RealWorld>

## Numbers That Matter

<Numbers>

- `decimal` = 128 bits, ~28-29 significant digits, base-10 exact — money ke liye yahi
- `double` = 64 bits, base-2 — `0.1 + 0.2` `!=` `0.3` hota hai, kabhi money me mat use karo
- `int` default = `0`, `bool` default = `false`, reference type default = `null`
- PAN format = 10 characters: 5 letters + 4 digits + 1 letter (`AAAAA9999A`)
- `DateOnly` `.NET 6` me aaya; `.NET 8` `System.Text.Json` ise bina extra config serialize karta hai
- 1 model class, 4 layers isko share karti hain — isliye ek galat type ka blast radius bada hai

</Numbers>

## Interview Angle

<InterviewAngle>

Sabse common sawaal: "You have a Salary or Amount field — what type do you use and why?" Strong 20-second jawaab: "`decimal`. `double` aur `float` binary floating point hain, `0.1` jaise values ko exactly store nahi kar sakte, aur rounding errors financial totals me jama hote hain jo audits me pakde jaate hain. `decimal` base-10 hai, 128-bit, paise tak exact — money, tax, interest sab `decimal`, `double` sirf scientific data ke liye." Follow-up aksar: "PAN ya phone number kis type me?" — answer: "string, kyunki wo identifiers hain arithmetic nahi, aur leading zeros / letters number me toot jaayenge." Interviewer dekh raha hai ki tum type ko **data ke meaning** se choose karte ho, size se nahi.

</InterviewAngle>

## Common Mistakes

<Mistake>

`Salary`, `Amount`, `InterestRate` ko `double` ya `float` banana "kyunki chhota number hai". Money hamesha `decimal`. Ye BFSI code review me instant rejection hai.

</Mistake>

<Mistake>

PAN, Aadhaar, phone number, account number ko `int`/`long` me store karna. Ye identifiers hain, numbers nahi — inpe kabhi jodna-ghatana nahi hota, aur leading zeros ya letters toot jaate hain. Hamesha `string`.

</Mistake>

<Mistake>

Model class me `CalculateTenure()`, `GetFormattedSalary()`, ya `Validate()` jaise methods daalna. Model sirf data ka shape hai — logic service layer ya DTO me. Logic model me aate hi separation of concerns toot jaata hai.

</Mistake>

<Mistake>

`<Nullable>enable</Nullable>` ke saath har `string` ko blindly `string?` bana dena taaki warnings chali jaayein. `?` ka matlab hai "yahan `null` genuinely valid hai". `FullName` kabhi `null` nahi honi chahiye — usse `= string.Empty` do ya (module 5 me) `required` lagao, `?` mat lagao.

</Mistake>

<Mistake>

`DateOfJoining` ko `DateTime` banana aur phir har jagah `.Date` call karke time part hatana. Agar time matter hi nahi karta to `DateOnly` use karo — intent clear rehta hai aur timezone bugs nahi aate.

</Mistake>

## Quick Revision

<QuickRevision>

- `Employee` ek POCO hai — sirf properties, koi logic nahi — `Models/Employee.cs` me, `EmployeeManagement.Api.Models` namespace
- Entity ke liye **class** (mutable, EF-trackable); DTO ke liye **record** (immutable, value equality) — agla DTO topic dekhna
- **`Salary` = `decimal`**, kabhi `double`/`float` nahi — binary floating point rounding errors money totals ko audit se mismatch kara deti hai; literal suffix `m`
- PAN, Aadhaar, phone, account number = **`string`** (identifiers, arithmetic nahi; leading zeros/letters safe)
- `DateOfJoining` = **`DateOnly`** (`.NET 6+`) — time part hai hi nahi, timezone bug nahi
- `<Nullable>enable</Nullable>` ke saath: non-nullable `string` ko `= string.Empty`; `?` sirf tab jab `null` genuinely valid ho (`MiddleName`)
- `int` default `0`, `bool` default `false` — isliye create pe `IsActive = true` explicitly set karna padta hai
- `DepartmentName` string abhi temporary hai — module 4 me `Department` navigation property aayegi

</QuickRevision>
