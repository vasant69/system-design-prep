<SimpleDefinition>

ASP.NET Core's configuration system layers key-value settings from many providers in a fixed precedence order (`appsettings.json`, then `appsettings.{Environment}.json`, then user secrets in development, then environment variables, then command-line arguments) into one `IConfiguration`. The Options pattern binds a section of that configuration to a strongly-typed class you inject as `IOptions<T>`, `IOptionsSnapshot<T>`, or `IOptionsMonitor<T>`, and secrets are kept out of source control using the Secret Manager locally and a secrets vault in production.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Ab tak humne `appsettings.json` me sirf ek `ConnectionStrings` daala hai aur `DbContext` topic me `builder.Configuration.GetConnectionString("Default")` se use kiya hai. Is topic me hum configuration ko theek se samajhenge: settings kahan-kahan se aati hain, kaun jeetta hai jab do jagah same key ho, aur code me use karne ka **saaf tarika** kya hai — kyunki `_config["Jwt:Key"]` har jagah likhna production code me ganda aur bug-prone hai.

### What is it — configuration kya hai

Configuration matlab wo values jo **code me hardcode nahi** karni chahiye kyunki wo environment ke hisaab se badalti hain: database connection string, JWT signing key, PAN verification API ka base URL, file storage folder ka path, token expiry minutes. ASP.NET Core in sab ko ek jagah la deta hai — `IConfiguration` — chahe wo JSON file me ho, environment variable me ho, ya command line se aayi ho.

`IConfiguration` ek **flat key-value dictionary** hai. Nested JSON ko wo colon (`:`) se flatten karta hai. Ye JSON:

```json
{
  "Jwt": {
    "Issuer": "EmployeeManagement.Api",
    "ExpiryMinutes": 60
  }
}
```

...`IConfiguration` me do keys ban jaati hai: `Jwt:Issuer` aur `Jwt:ExpiryMinutes`.

### Why do we need it — bina iske kya tootega

Maan lo tumne connection string aur JWT key seedha `Program.cs` me string literal me likh di. Ab:

- Local SQL Server ka naam aur production ka naam alag hai — har deploy pe code badalna padega.
- JWT signing key **git me commit ho jaayegi** — koi bhi repo dekhne wala tokens forge kar sakta hai. BFSI me ye ek reportable security incident hai.
- QA environment ke liye alag PAN API URL chahiye — phir se code change, phir se build, phir se review.

Configuration system in teeno problems ko solve karta hai: values bahar rakho, environment ke hisaab se override karo, secrets ko source control se bahar rakho.

### How does it work — provider precedence (order matters)

`WebApplication.CreateBuilder(args)` ek default set of providers register karta hai, **is order me** (baad wala pehle wale ko override karta hai):

1. `appsettings.json`
2. `appsettings.{Environment}.json` — jaise `appsettings.Development.json` ya `appsettings.Production.json`
3. **User Secrets** — sirf jab environment `Development` ho
4. **Environment variables**
5. **Command-line arguments**

"Override" ka matlab: agar same key (`Jwt:ExpiryMinutes`) do jagah hai, to jo provider **baad me** add hua uski value jeetti hai. To command line se diya `--Jwt:ExpiryMinutes=5` `appsettings.json` ke `60` ko haraa dega.

Environment kaunsa hai ye `ASPNETCORE_ENVIRONMENT` variable decide karta hai (`launchSettings.json` me local pe `Development` set hota hai). Isi se `app.Environment.IsDevelopment()` true/false hota hai aur isi se sahi `appsettings.{Environment}.json` load hoti hai.

Nested override poori file replace nahi karta — sirf **matching keys** merge hote hain. `appsettings.Development.json` me sirf wo keys likho jo base se alag hain.

### Show it in our project — strongly-typed Options

Hum `EmployeeManagement.Api` me teen config groups add karenge: JWT (module 6 me use hoga), file storage (module 7 KYC upload), aur PAN verification (module 7 external API).

`appsettings.json`:

```json
{
  "ConnectionStrings": {
    "Default": "Server=.;Database=EmployeeManagement;Trusted_Connection=True;TrustServerCertificate=True"
  },
  "Jwt": {
    "Issuer": "EmployeeManagement.Api",
    "Audience": "EmployeeManagement.Client",
    "ExpiryMinutes": 60
  },
  "FileStorage": {
    "RootPath": "App_Data/documents",
    "MaxFileSizeMb": 5,
    "AllowedExtensions": [ ".pdf", ".jpg", ".png" ]
  },
  "PanVerification": {
    "BaseUrl": "https://sandbox.pan-verify.example.com",
    "TimeoutSeconds": 10
  }
}
```

Notice: `Jwt:Key` (the actual signing secret) **yahan nahi hai** — wo user secrets / environment variable se aayega.

Ab har group ke liye ek plain class, `Options/` folder me:

```csharp
namespace EmployeeManagement.Api.Options;

public class JwtOptions
{
    public const string SectionName = "Jwt";

    public string Issuer { get; set; } = string.Empty;
    public string Audience { get; set; } = string.Empty;
    public string Key { get; set; } = string.Empty;
    public int ExpiryMinutes { get; set; } = 60;
}
```

```csharp
namespace EmployeeManagement.Api.Options;

public class FileStorageOptions
{
    public const string SectionName = "FileStorage";

    public string RootPath { get; set; } = "App_Data/documents";
    public int MaxFileSizeMb { get; set; } = 5;
    public string[] AllowedExtensions { get; set; } = Array.Empty<string>();
}
```

`Program.cs` me bind karo:

```csharp
builder.Services
    .Configure<JwtOptions>(builder.Configuration.GetSection(JwtOptions.SectionName));

builder.Services
    .AddOptions<FileStorageOptions>()
    .Bind(builder.Configuration.GetSection(FileStorageOptions.SectionName))
    .ValidateDataAnnotations()
    .ValidateOnStart();
```

Ab kisi bhi service me inject karo:

```csharp
public class TokenService
{
    private readonly JwtOptions _jwt;

    public TokenService(IOptions<JwtOptions> jwtOptions)
    {
        _jwt = jwtOptions.Value;
    }

    public string Issuer => _jwt.Issuer;
}
```

### Code explained line by line

- `public const string SectionName = "Jwt";` — section ka naam class ke saath rakhne se `Program.cs` me magic string repeat nahi hota, aur rename karna ek jagah ka kaam ban jaata hai.
- Har property `{ get; set; }` — Options binder **reflection** se properties set karta hai, isliye public settable hone chahiye. Default values isliye di hain taaki config missing ho to app crash na kare.
- `builder.Configuration.GetSection("Jwt")` — poori config me se sirf `Jwt` sub-tree nikaalta hai. `GetSection` kabhi `null` nahi return karta — missing section bhi ek empty section object deta hai.
- `builder.Services.Configure<JwtOptions>(section)` — DI container me register karta hai: "jab koi `IOptions<JwtOptions>` maange, is section ko `JwtOptions` me bind karke do." Bind matlab property naam se JSON key match karo.
- `AddOptions<FileStorageOptions>().Bind(...)` — `Configure(...)` ka fluent version, jisme aage `.Validate...` chain kar sakte ho.
- `.ValidateDataAnnotations()` — agar `FileStorageOptions` pe `[Required]`, `[Range]` jaisi annotations hain to unhe enforce karo.
- `.ValidateOnStart()` — validation **app start pe** chalao, na ki pehli baar inject hone pe. Galat config → app boot pe hi fail, na ki 3 din baad pehli request pe. BFSI deploy me ye behaviour chahiye — fail fast.
- `IOptions<JwtOptions> jwtOptions` constructor parameter — DI ise resolve karta hai. `.Value` property actual `JwtOptions` object deta hai.

### The three flavors — IOptions vs IOptionsSnapshot vs IOptionsMonitor

Ye interview me poocha jaata hai. Teeno bind same section ko karte hain, farq **lifetime aur reload** me hai:

| Interface | Lifetime | Reload on file change? | Use when |
| --- | --- | --- | --- |
| `IOptions<T>` | Singleton | Nahi — app life ke liye ek baar bind | Value kabhi nahi badlega (issuer, audience) |
| `IOptionsSnapshot<T>` | Scoped | Haan — har request pe fresh bind | Scoped/transient service, aur value runtime pe badal sakti hai |
| `IOptionsMonitor<T>` | Singleton | Haan — plus `OnChange` callback | Singleton service ko latest value chahiye, ya change pe react karna hai |

`IOptionsSnapshot<T>` ko **singleton me inject mat karo** — wo scoped hai, singleton captive dependency ban jaayega (yahi captive-dependency trap jo layering module me aaya tha). Singleton ke liye `IOptionsMonitor<T>` use karo:

```csharp
public class PanVerificationClient
{
    private readonly IOptionsMonitor<PanVerificationOptions> _options;

    public PanVerificationClient(IOptionsMonitor<PanVerificationOptions> options)
    {
        _options = options;
    }

    private string BaseUrl => _options.CurrentValue.BaseUrl; // har call pe latest
}
```

### Secrets — kabhi git me nahi

Local development me signing key ke liye **Secret Manager**:

```bash
cd EmployeeManagement.Api
dotnet user-secrets init
dotnet user-secrets set "Jwt:Key" "dev-only-super-long-random-signing-key-change-me"
```

`dotnet user-secrets init` `.csproj` me ek `<UserSecretsId>` GUID daalta hai. Actual values tumhare **user profile folder** me JSON file me jaati hain (repo ke bahar) — `~/.microsoft/usersecrets/<id>/secrets.json` (Windows: `%APPDATA%\Microsoft\UserSecrets\<id>\secrets.json`). Ye provider **sirf `Development` environment** me load hota hai.

Production me user secrets kaam nahi karega. Wahan options:

- **Environment variables** — key `Jwt__Key` (double underscore `__` = config ka `:`). Container / App Service me set hoti hai.
- **Azure Key Vault** — `builder.Configuration.AddAzureKeyVault(...)`, secrets vault se aati hain, RBAC se protected.
- **AWS Secrets Manager** / **AWS Systems Manager Parameter Store** — same idea AWS side.

Rule: `appsettings.json` me sirf **non-sensitive** values. Koi bhi cheez jo leak hone pe nuksaan kare — key, password, connection string with credentials — provider chain ke secret-safe hisse me.

### Where is it used in day-to-day development

- Har naye external dependency ke saath: naya `XyzOptions` class + section + `Configure<>` + `.ValidateOnStart()`.
- Feature flags: `Features:EnableNewPayroll` config me, `IOptionsSnapshot` se padho taaki restart ke bina toggle ho.
- Environment-specific: dev me sandbox PAN URL, prod me real — same code, alag `appsettings.{Environment}.json`.
- Debugging "prod pe alag behave kar raha hai": 90% time koi environment variable base file ko override kar raha hota hai — precedence yaad rakho.

### Pros and cons

Strongly-typed Options ke fayde: compile-time safety (typo `Jwt:Isuer` pe property `null` milta hai, exception nahi — phir bhi raw string se behtar), IntelliSense, validation, testability (test me `Options.Create(new JwtOptions{...})` pass kar do). Nuksaan: thoda boilerplate (class + registration), aur bina `.ValidateOnStart()` ke missing config silently default value de deta hai.

Raw `IConfiguration["Jwt:Key"]` ka faayda: zero setup. Nuksaan: har call site pe magic string, koi validation nahi, test karna mushkil. Use raw access **sirf `Program.cs` ke andar bootstrap ke liye** (jaise connection string padhna), aage har jagah Options.

</Hinglish>

<Callout type="trap">

`_config["Jwt:ExpiryMinutes"]` hamesha `string` return karta hai — direct `int` me compare mat karo. Options binding automatically `"60"` ko `int 60` me convert karti hai; raw access me tumhe khud `int.Parse` karna padta hai, aur missing key pe wo `null` deta hai, `NullReferenceException` nahi — silent bug.

</Callout>

<Tradeoff
  pros={["Strongly-typed: IntelliSense, compile-time property names, no magic strings at call sites", "Validation with ValidateDataAnnotations + ValidateOnStart catches bad config at boot", "Trivially testable: inject Options.Create(new T{...}) in unit tests", "IOptionsSnapshot / IOptionsMonitor give per-request or live reload for free"]}
  cons={["Boilerplate: a class plus a registration line per config group", "Without ValidateOnStart, missing keys silently fall back to defaults", "Binding is reflection-based and case-insensitive, so a typo'd JSON key just stays default with no error"]}

## Real World Example

<RealWorld company="A digital-lending startup">

Ek lending startup ne JWT signing key `appsettings.json` me commit kar di thi, aur repo internal GitHub pe tha. Ek intern ne repo clone kiya, key dekhi, aur mazak me apne liye ek "admin" token forge kar liya jo loan approval endpoints hit kar sakta tha. Koi actual fraud nahi hua, lekin security review me ye "critical" finding bana: sabhi environments ki keys rotate karni padi, aur ek policy aayi — `appsettings.json` me koi bhi cheez jo `Key`, `Secret`, `Password`, `Token` me end hoti hai, CI check fail karega. Local dev ab `dotnet user-secrets`, prod AWS Secrets Manager se.

</RealWorld>

<RealWorld company="A BFSI systems integrator (TCS / Infosys style)">

Ek banking client ke onboarding API me QA team complain kar rahi thi ki "config change karne ke baad bhi purani value aa rahi hai." Root cause: service `IOptions<T>` use kar raha tha (singleton, ek baar bind), jabki QA `appsettings.json` ko live edit karke expect kar raha tha ki reload ho jaaye. Fix: jis ek feature-flag section ko runtime pe toggle karna tha uske liye `IOptionsSnapshot<T>` pe switch kiya. Baaki stable config `IOptions<T>` pe hi rahi — sab kuch snapshot karna performance overhead hai bina reason ke.

</RealWorld>

## Numbers That Matter

<Numbers>

- 5 default config providers, in precedence order: `appsettings.json` → `appsettings.{Environment}.json` → User Secrets (Development only) → environment variables → command-line args
- `:` is the config key separator; environment variables use `__` (double underscore) instead
- 3 Options interfaces: `IOptions<T>` (singleton, no reload), `IOptionsSnapshot<T>` (scoped, per-request reload), `IOptionsMonitor<T>` (singleton, `OnChange` + `CurrentValue`)
- User secrets live outside the repo at `%APPDATA%\Microsoft\UserSecrets\<id>\secrets.json` on Windows
- `.ValidateOnStart()` moves config validation from first-injection to app-boot — fail fast
- `ASPNETCORE_ENVIRONMENT` has 3 well-known values: `Development`, `Staging`, `Production` (default is `Production` if unset)
- Reload-on-change is on by default for `appsettings*.json` (`reloadOnChange: true`)

</Numbers>

## Common Mistakes

<Mistake>

`IOptionsSnapshot<T>` ko ek singleton service me inject karna. `IOptionsSnapshot` scoped hai — singleton use pe ye captive dependency ban jaata hai aur DI validation error deta hai (ya galat, stale value). Singleton ke liye `IOptionsMonitor<T>` use karo aur `.CurrentValue` padho.

</Mistake>

<Mistake>

Signing keys, passwords ya credentials-wali connection strings `appsettings.json` me daalna aur commit kar dena. Ye git history me hamesha ke liye reh jaata hai. Local pe `dotnet user-secrets`, prod pe env vars / vault.

</Mistake>

<Mistake>

`Configure<T>` karna lekin `.ValidateOnStart()` chhod dena. Config me typo ho ya key missing ho to app chup-chaap default value use kar leta hai, aur bug 3 din baad production me kisi random request pe dikhta hai.

</Mistake>

<Mistake>

`appsettings.Development.json` me poori `appsettings.json` copy karke sirf ek value badalna. Ye files **merge** hoti hain key-by-key — sirf woh keys likho jo override karni hain, warna do jagah maintain karni padengi.

</Mistake>

<Mistake>

Environment variable me `Jwt:Key` likhna (single colon). Kuch shells colon allow nahi karti; ASP.NET Core ka convention `Jwt__Key` (double underscore) hai, jo internally `:` me convert hota hai.

</Mistake>

## Quick Revision

<QuickRevision>

- `IConfiguration` = one flat key-value store; nested JSON flattens with `:` (`Jwt:Issuer`)
- Provider precedence (later wins): `appsettings.json` → `appsettings.{Environment}.json` → User Secrets (dev) → env vars → command line
- `ASPNETCORE_ENVIRONMENT` picks the environment file and drives `IsDevelopment()`
- Options pattern: a POCO class + `builder.Services.Configure<T>(builder.Configuration.GetSection("X"))`
- `IOptions<T>` = singleton, no reload; `IOptionsSnapshot<T>` = scoped, per-request reload; `IOptionsMonitor<T>` = singleton, `CurrentValue` + `OnChange`
- Never inject `IOptionsSnapshot<T>` into a singleton — captive dependency; use `IOptionsMonitor<T>`
- `.ValidateDataAnnotations().ValidateOnStart()` = validate config at boot, fail fast
- Secrets: `dotnet user-secrets` locally (repo-external, dev-only), env vars / Azure Key Vault / AWS Secrets Manager in prod; nothing sensitive in `appsettings.json`
- Env var naming: `Section__Key` (double underscore) maps to `Section:Key`

</QuickRevision>

## Practice

<Callout type="tip">

**Chhota (small):** `JwtOptions` class banao with `SectionName`, add the `Jwt` section (Issuer, Audience, ExpiryMinutes) to `appsettings.json`, register it with `builder.Services.Configure<JwtOptions>(...)`, and set `Jwt:Key` via `dotnet user-secrets`. Inject `IOptions<JwtOptions>` into a throwaway `ConfigCheckController` GET action that returns `Issuer` and whether `Key` is non-empty.

**Medium:** Add `FileStorageOptions` (RootPath, MaxFileSizeMb, AllowedExtensions) with `[Required]` and `[Range(1, 20)]` DataAnnotations. Wire `.AddOptions<FileStorageOptions>().Bind(...).ValidateDataAnnotations().ValidateOnStart()`. Deliberately break the config (set `MaxFileSizeMb` to 0) and confirm the app fails on startup with a clear message, then fix it. Combine with the previous validation topic: also return a 500 through the global exception handler if options resolution fails at request time.

**Bada (large):** Introduce three environments. Create `appsettings.Development.json` and `appsettings.Staging.json` overriding only `PanVerification:BaseUrl` and `Jwt:ExpiryMinutes`. Add a `PanVerificationClient` singleton that reads `IOptionsMonitor<PanVerificationOptions>.CurrentValue`. Write a short doc in the repo showing, for each of the 5 providers, one concrete value that comes from it in your project, and prove precedence by overriding `Jwt:ExpiryMinutes` from the command line and logging the effective value at startup.

</Callout>
