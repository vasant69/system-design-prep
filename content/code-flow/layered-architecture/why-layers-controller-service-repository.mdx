<SimpleDefinition>

Layering is splitting an application into stacked responsibilities where each layer has exactly one job: the Controller handles HTTP, the Service holds business rules and orchestration, and the Repository handles data access. Requests flow downward through the layers and results flow back up, so each layer can be changed, tested, and reused without disturbing the others.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Module 2 ke end me hamara `EmployeesController` ek "sab kuch khud karne wala" controller ban chuka hai. Ek hi file me: HTTP routing, `static List<Employee>` par LINQ queries, DTO mapping, aur business rules (duplicate email reject karna, PAN format check karna). Chalta hai — lekin ye ab ek problem hai, feature nahi. Is module me hum ise teen saaf layers me todenge: `Controller -> Service -> Repository`. Ye topic un teen layers ka **kyun** hai; agle topics **kaise**.

### What is it — layering kya hai

Layering ka matlab hai code ko **responsibility ke hisaab se** horizontal slabs me baant dena, jahan har slab ke neeche wale slab par depend karta hai, upar wale ko nahi jaanta. Hamare Web API me teen layers:

- **Controller (HTTP layer)** — sirf HTTP ki baat. Route match karna, request body ko object me bind karna, sahi status code (`200`, `201`, `404`, `409`) lautana. Controller ko ye nahi pata data list me hai ya SQL me.
- **Service (business layer)** — application ke rules aur orchestration. "Duplicate email allowed nahi", "active employee delete nahi kar sakte", "PAN `AAAAA9999A` pattern follow kare". Service ko HTTP ka `H` bhi nahi pata — na `Request`, na `Response`, na status codes.
- **Repository (data-access layer)** — sirf data laana aur rakhna. Add, get by id, get all, update, remove. Koi rule nahi, koi HTTP nahi — pure CRUD.

Request neeche jaati hai (`Controller` se `Service` se `Repository`), result upar aata hai. Har layer sirf **apne se neeche** wale ko call karti hai.

### Why do we need it — fat controller ka cost

Ek "fat controller" (jaisa module 2 me bana) teen taraike se mehenga hai:

1. **Untestable.** `EmployeeService.Create()` ki duplicate-email rule test karni ho, to fat controller me tumhe poora HTTP stack, model binding, aur routing spin karna padta hai. Alag Service class ho to bas `new EmployeeService(fakeRepo)` aur method call — 3 line ka unit test.
2. **Un-reusable.** Kal ek nightly background job aaya jo CSV se employees import karta hai. Usko wahi rules chahiye — duplicate email, PAN check. Agar rules controller ke andar hain, job unhe call hi nahi kar sakti (job ke paas `HttpContext` nahi hota). Result: rules copy-paste, aur do jagah do alag versions ban jaate hain.
3. **Logic duplication.** Ek hi PAN-validation regex ab `Create` aur `Update` dono actions me likha hai. Teesri jagah aayegi to teen. Ek din regex galat nikla — teeno jagah fix karna yaad rahega? Nahi.

Failure scenario, concrete: import job ne PAN check skip kar diya (kyunki wo controller me tha), 4000 galat PAN wali rows database me ghus gayi, aur compliance audit me BFSI client ko penalty lagi. Root cause: rule galat layer me tha.

### How does it work — step by step

1. Request aati hai: `POST /api/employees` ek JSON body ke saath.
2. **Controller** body ko `CreateEmployeeDto` me bind karta hai, `_service.Create(dto)` call karta hai. Bas.
3. **Service** rules chalata hai: `_repo.EmailExists(dto.Email)` false hona chahiye; PAN regex match hona chahiye. Phir `Employee` entity banata hai aur `_repo.Add(employee)` call karta hai. Return karta hai ek `EmployeeDto`.
4. **Repository** entity ko store (abhi `static List`, module 4 me SQL) me daal deta hai aur Id assign karta hai.
5. Result upar lautta hai. **Controller** use `201 Created` me wrap karke client ko de deta hai.

Har arrow ek **method call** hai, network hop nahi — sab ek hi process me. Layering physical separation nahi, **logical** separation hai.

### Show it in our project — "Controller to Database" phir Repository insert

Sabse pehla natural design sirf do layers hai: **`Controller -> Service -> Database`**. Service seedha data store se baat kare. Yeh chhote apps ke liye bilkul theek hai.

Hum ismein **Repository** isliye ghusaate hain kyunki:

- Module 4 me data store `static List` se badal ke **EF Core + SQL Server** banega. Agar Service ke andar list par LINQ likha hai, to poora Service module 4 me rewrite hoga.
- Repository ek **interface** ke peeche data access chhupa deta hai. Aaj `InMemoryEmployeeRepository`, kal `EfEmployeeRepository` — Service ko farak nahi padta.

```text
EmployeeManagement.Api/
├── Controllers/
│   └── EmployeesController.cs      // HTTP only
├── Services/
│   ├── IEmployeeService.cs         // business contract
│   └── EmployeeService.cs          // rules + orchestration
├── Repositories/
│   ├── IEmployeeRepository.cs      // data contract
│   └── InMemoryEmployeeRepository.cs   // wraps the list (module 4: swap for EF)
├── Models/
│   └── Employee.cs
├── Dtos/
│   ├── EmployeeDto.cs
│   ├── CreateEmployeeDto.cs
│   └── UpdateEmployeeDto.cs
└── Program.cs                      // wires the layers with DI
```

### Code explained line by line — "one job each" ka test

Ek line dekh ke batao wo kis layer ki hai:

```csharp
return CreatedAtAction(nameof(GetById), new { id = created.Id }, created);
```

- `CreatedAtAction`, status `201`, `Location` header — ye **HTTP** hai. Yeh line sirf **Controller** me ho sakti hai. Service me `CreatedAtAction` likhna galat hai.

```csharp
if (_repo.EmailExists(dto.Email))
    throw new DomainRuleException("Employee with this email already exists.");
```

- Ye ek **business rule** hai — "duplicate email nahi". Repository ko nahi pata ye rule; Controller ko nahi pata ye rule. Ye **Service** me hi hai.

```csharp
_employees.Add(employee);
```

- Pure **data store** operation, koi decision nahi. Ye **Repository** me hai.

Rule of thumb: agar line me `Ok(...)` / `NotFound()` / `[HttpGet]` hai — Controller. Agar `if` / rule / "kya allowed hai" hai — Service. Agar `Add` / `Find` / `Where` / `SaveChanges` hai — Repository.

### Where is it used in day-to-day development

- **Har naya feature** isi shape me aata hai: interface me method add karo, Service me rule likho, Controller me endpoint add karo.
- **Code review** me sabse common comment: "ye validation controller me kyun hai, service me le jao".
- **Bug fixing** — jab pata ho rule kahan rehta hai, to "duplicate email allow ho raha hai" bug seedha `EmployeeService.Create` me jaake dekha jaata hai, poore controller me nahi.
- **Onboarding** — naya dev "employees kaise save hote hain" poochhe to jawab ek layer diagram hota hai.

### Pros and cons — honest trade-offs

Layering muft nahi hai. Ek `GET /employees/{id}` ke liye ab teen files touch hoti hain: interface, service, controller. Chhote CRUD ke liye ye "boilerplate" mehsoos hota hai. Lekin project jaise-jaise badhta hai (rules, background jobs, doosre callers), ye teen files hi tumhe bachati hain.

### When to use / when NOT to use

- **Use** jab: app 6 mahine se zyada chalegi, ek se zyada developer hai, business rules hain (validation, workflows), ya data source future me badal sakta hai.
- **Skip (ya sirf 2 layers)** jab: throwaway script, ek weekend ka prototype, ya ek admin tool jisme 3 endpoints hain aur koi rule nahi — bas `Controller -> DbContext` bhi chalega. Over-layering ek chhote app ko navigate karna mushkil bana deti hai (ek line badalne ke liye 3 file khUlti hain).

Hamara EmployeeManagement.Api pehli category me hai, isliye poori layering justified hai.

## Real World Example

<RealWorld company="A digital-lending startup">

Ek lending startup ne shuruaat me sab kuch controllers me rakha — loan eligibility rules, KYC checks, sab `LoanController` me. 8 mahine baad jab ek "bulk pre-approval" batch job banana pada, to poora eligibility logic dobara likha gaya, aur do versions ban gaye. Ek release me API version update hua, batch version nahi — kuch customers ko galat pre-approval mile. Post-mortem ke baad rule bana: koi bhi decision logic controller me nahi, sirf `*Service` classes me — taaki API aur batch dono ek hi source call karein.

</RealWorld>

<RealWorld company="A BFSI systems integrator (TCS / Infosys style)">

Bade services projects me code review checklist me literally ek line hoti hai: "Controllers thin hain? Koi `if` business rule controller me to nahi?". Reason simple hai — in projects me ek hi domain logic ko REST API, ek SOAP facade, aur ek scheduled job teeno expose karte hain. Agar logic Service layer me hai to teeno usse call karte hain; controller me hai to teen jagah maintain karna padta hai.

</RealWorld>

## Numbers That Matter

<Numbers>

- 3 layers: Controller (HTTP), Service (rules), Repository (data) — is module ka core
- 2 layers (`Controller -> Service`) tab bhi valid jab data source kabhi nahi badlega
- 1 rule, 1 jagah — PAN regex, duplicate-email check sirf Service me, kabhi controller me nahi
- 3 files ek naye feature slice ke liye touch hoti hain: interface + service + controller
- Controller me allowed HTTP concerns: status codes, headers, model binding, routing — bas
- 0 references to `HttpContext` / `Request` / `Response` Service aur Repository me hone chahiye

</Numbers>

## Interview Angle

<InterviewAngle>

Ye ek round-defining topic hai — "explain layered architecture" ya "why not put logic in the controller" har .NET interview me aata hai. Strong 20-second jawab: "Controller sirf HTTP translate karta hai — request in, status code out. Business rules Service me rehte hain taaki wo testable ho aur ek se zyada caller (API, background job) unhe reuse kar sakein. Repository data access ko interface ke peeche chhupata hai taaki storage badle to Service na badle. Fat controller ka asli cost testing aur logic duplication hai, na ki 'ganda dikhta hai'." Agar tum "single responsibility per layer" aur "reuse by a background job" bol dete ho, interviewer samajh jaata hai tumne production me ye pain feel kiya hai.

</InterviewAngle>

## Common Mistakes

<Mistake>

Validation aur business rules controller me chhod dena "kyunki chhota sa `if` hai". Har `if` ek business rule hai — wo Service me jaata hai. Controller me sirf `[ApiController]` ka automatic model-binding validation (`ModelState`) acceptable hai, custom rules nahi.

</Mistake>

<Mistake>

Service me `IActionResult` ya `NotFound()` return karna. Service ko HTTP nahi pata hona chahiye — wo `null` ya entity ya exception lautaye, aur Controller decide kare wo `404` hai ya `409`. Service me `Microsoft.AspNetCore.Mvc` ka `using` hi ek smell hai.

</Mistake>

<Mistake>

Repository me business rules ghusa dena — jaise `Add()` ke andar duplicate-email check. Repository "kya store karna chahiye" decide nahi karta, sirf "store kar do". Rule Service me, plain CRUD Repository me.

</Mistake>

<Mistake>

Har layer ko blindly banana jabki wo kuch add nahi karti — Service me sirf `return _repo.GetAll()` likhna aur bas. Kabhi-kabhi ye theek hai (consistency ke liye), lekin agar poori Service aisi hi hai to shaayad app ko abhi Service layer chahiye hi nahi.

</Mistake>

<Mistake>

Ye maan lena ki layering ka matlab alag projects/DLLs hai. Abhi sab ek hi project me alag folders me hai — ye bhi layering hai. Alag assemblies (Clean Architecture) ek alag, baad ka decision hai (module "Quality & Architecture").

</Mistake>

## Quick Revision

<QuickRevision>

- Layering = code ko responsibility ke hisaab se baantna; har layer ka ek kaam, har layer sirf apne neeche wale ko call karti hai
- **Controller** = HTTP only (routes, model binding, status codes). Koi business rule nahi
- **Service** = business rules + orchestration (duplicate email, PAN format, "active employee delete nahi"). Koi HTTP nahi, koi `IActionResult` nahi
- **Repository** = pure data access (Add/GetById/GetAll/Update/Remove). Koi rule nahi
- Fat controller ka cost: untestable, un-reusable (background job reuse nahi kar sakti), logic duplication (`Create` + `Update` dono me same regex)
- Starting design `Controller -> Service -> Database`; Repository isliye insert karte hain taaki module 4 me list-to-SQL swap Service ko na chhoote
- Skip layering: throwaway script, weekend prototype, 3-endpoint admin tool with no rules
- Rule of thumb: `Ok()/NotFound()/[HttpGet]` -> Controller; `if`/rule -> Service; `Add`/`Where`/`SaveChanges` -> Repository

</QuickRevision>

**Chhota (small):** Module 2 wale `EmployeesController` ki har line ke aage ek comment likho: `// HTTP`, `// RULE`, ya `// DATA`. Count karo kitni `// RULE` aur `// DATA` lines controller me hain — yahi lines agle topics me bahar nikalengi.

**Medium:** `EmployeeManagement.Api` me ek naya folder `Services/` banao aur usme khaali `IEmployeeService.cs` interface likho jisme paanch method signatures hain: `GetAll`, `GetById`, `Create`, `Update`, `Delete`. Abhi implement mat karo — sirf contract. Saath me ek 5-line note likho ki har method me kaunsa rule aayega.

**Bada (large):** Ek chhota console app (`EmployeeImportJob`) banao jo ek CSV file padh ke employees "import" karega. Isme `EmployeesController` ka code copy-paste karo (rules included). Ab dekho: agar PAN regex galat nikle, to kitni jagah fix karni padegi? Ye exercise document karo — yahi is poore module ki motivation hai. (Baad ke topics me tum is job ko refactor karke same `IEmployeeService` call karwaoge.)

</Callout>
