<SimpleDefinition>

Extracting a service layer means moving business rules, orchestration, and DTO mapping out of the controller into a dedicated class behind an interface, so the controller is left with only HTTP concerns. The controller receives the service through constructor injection and simply translates the service's results into HTTP responses.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Module 2 ke end me hamara `EmployeesController` sab kuch khud kar raha hai: `static List<Employee>` par LINQ, DTO mapping, aur rules (duplicate email reject, PAN format check). Pichhle do topics me humne decide kiya `Controller -> Service -> Repository` aur samjha ki inhe interface ke peeche kyun rakhte hain. Ab actual refactor: sabse pehla step hai **Service layer nikalna**. Repository agla topic hai — is topic me Service abhi seedha list ke saath baat karega, taaki ek waqt me ek hi cheez badle.

### What is it — Service layer kya hai

Service layer ek plain C# class hai (`EmployeeService`) jo ek interface (`IEmployeeService`) implement karti hai aur application ke **use-cases** rakhti hai: "employee create karo", "employee update karo", "employee delete karo". Isme teen cheezein rehti hain jo abhi controller me hain:

1. **Business rules** — duplicate email nahi, PAN `AAAAA9999A` pattern, active employee delete nahi.
2. **Orchestration** — "pehle check karo, phir entity banao, phir store karo, phir DTO wapas do" — steps ka sequence.
3. **DTO mapping** — `Employee` entity ko `EmployeeDto` me, `CreateEmployeeDto` ko `Employee` me.

Service ko HTTP ka `H` bhi nahi pata — na `IActionResult`, na status codes, na `Request`/`Response`.

### Why do we need it — controller me sab rakhne se kya tootega

Fat controller ka cost pichhle topic me detail me tha; yahan sirf yaad dilao: rule test karne ke liye poora HTTP stack chahiye, background job rules reuse nahi kar sakti, aur `Create` + `Update` me same PAN regex do jagah copy hota hai. Concrete failure: ek nightly CSV-import job PAN check skip kar deta hai (kyunki wo check controller me tha), aur hazaaron galat PAN wali rows database me chali jaati hain — BFSI audit me penalty.

Service nikaalne ke baad wahi rule ek jagah — `EmployeeService` — se aata hai, aur API + job dono use call karte hain.

### How does it work — step by step

1. `IEmployeeService` interface likho — 5 method signatures, koi body nahi.
2. `EmployeeService` class likho jo `: IEmployeeService` ho. Abhi ye `static List<Employee>` ko field ki tarah rakhegi (agla topic me ye list Repository ke peeche jaayegi).
3. Controller ke `[HttpGet]`/`[HttpPost]` actions ke andar ka **rules + mapping + LINQ** code ko `EmployeeService` ke methods me move karo.
4. Controller ke constructor me `IEmployeeService` maango.
5. `Program.cs` me `builder.Services.AddScoped<IEmployeeService, EmployeeService>();` register karo — warna DI resolve nahi karega.

### Show it in our project

**`Services/IEmployeeService.cs`** — contract:

```csharp
namespace EmployeeManagement.Api.Services;

public interface IEmployeeService
{
    IReadOnlyList<EmployeeDto> GetAll();
    EmployeeDto? GetById(int id);
    EmployeeDto Create(CreateEmployeeDto dto);
    EmployeeDto? Update(int id, UpdateEmployeeDto dto);
    bool Delete(int id);
}
```

**`Services/EmployeeService.cs`** — implementation (rules + mapping + list):

```csharp
using System.Text.RegularExpressions;
using EmployeeManagement.Api.Dtos;
using EmployeeManagement.Api.Models;

namespace EmployeeManagement.Api.Services;

public class EmployeeService : IEmployeeService
{
    private static readonly List<Employee> _employees = new();
    private static int _nextId = 1;

    private static readonly Regex PanRegex =
        new("^[A-Z]{5}[0-9]{4}[A-Z]$", RegexOptions.Compiled);

    public IReadOnlyList<EmployeeDto> GetAll() =>
        _employees.Select(ToDto).ToList();

    public EmployeeDto? GetById(int id)
    {
        var employee = _employees.FirstOrDefault(e => e.Id == id);
        return employee is null ? null : ToDto(employee);
    }

    public EmployeeDto Create(CreateEmployeeDto dto)
    {
        if (_employees.Any(e => e.Email.Equals(dto.Email, StringComparison.OrdinalIgnoreCase)))
            throw new DomainRuleException("Employee with this email already exists.");

        if (!PanRegex.IsMatch(dto.PanNumber))
            throw new DomainRuleException("PAN number format is invalid. Expected AAAAA9999A.");

        var employee = new Employee
        {
            Id = _nextId++,
            FullName = dto.FullName,
            Email = dto.Email,
            DepartmentId = dto.DepartmentId,
            DateOfJoining = dto.DateOfJoining,
            Salary = dto.Salary,
            PanNumber = dto.PanNumber,
            IsActive = true
        };

        _employees.Add(employee);
        return ToDto(employee);
    }

    public EmployeeDto? Update(int id, UpdateEmployeeDto dto)
    {
        var employee = _employees.FirstOrDefault(e => e.Id == id);
        if (employee is null) return null;

        employee.FullName = dto.FullName;
        employee.DepartmentId = dto.DepartmentId;
        employee.Salary = dto.Salary;
        return ToDto(employee);
    }

    public bool Delete(int id)
    {
        var employee = _employees.FirstOrDefault(e => e.Id == id);
        if (employee is null) return false;

        if (employee.IsActive)
            throw new DomainRuleException("Cannot delete an active employee. Deactivate first.");

        _employees.Remove(employee);
        return true;
    }

    private static EmployeeDto ToDto(Employee e) => new()
    {
        Id = e.Id,
        FullName = e.FullName,
        Email = e.Email,
        DepartmentId = e.DepartmentId,
        DateOfJoining = e.DateOfJoining,
        Salary = e.Salary,
        PanNumber = e.PanNumber,
        IsActive = e.IsActive
    };
}

public class DomainRuleException : Exception
{
    public DomainRuleException(string message) : base(message) { }
}
```

**Before — the fat controller (module 2):**

```csharp
[ApiController]
[Route("api/[controller]")]
public class EmployeesController : ControllerBase
{
    private static readonly List<Employee> _employees = new();
    private static int _nextId = 1;

    [HttpPost]

    {
        if (_employees.Any(e => e.Email == dto.Email))

            return BadRequest("PAN number format is invalid.");

        var employee = new Employee { Id = _nextId++, FullName = dto.FullName, /* ...8 more lines... */ };
        _employees.Add(employee);

        return CreatedAtAction(nameof(GetById), new { id = employee.Id }, result);
```

**After — the thin controller:**

```csharp
[ApiController]
[Route("api/[controller]")]
public class EmployeesController : ControllerBase
{
    private readonly IEmployeeService _service;

    public EmployeesController(IEmployeeService service)
    {
        _service = service;
    }

    [HttpGet]
    public ActionResult<IReadOnlyList<EmployeeDto>> GetAll() =>
        Ok(_service.GetAll());

    [HttpGet("{id:int}")]
    public ActionResult<EmployeeDto> GetById(int id)
    {
        var dto = _service.GetById(id);
        return dto is null ? NotFound() : Ok(dto);
    }

    [HttpPost]
    public ActionResult<EmployeeDto> Create(CreateEmployeeDto dto)
    {
        var created = _service.Create(dto);
        return CreatedAtAction(nameof(GetById), new { id = created.Id }, created);
    }

    [HttpPut("{id:int}")]
    public ActionResult<EmployeeDto> Update(int id, UpdateEmployeeDto dto)
    {
        var updated = _service.Update(id, dto);
        return updated is null ? NotFound() : Ok(updated);
    }

    [HttpDelete("{id:int}")]
    public IActionResult Delete(int id) =>
        _service.Delete(id) ? NoContent() : NotFound();
}
```

Controller ab sirf ye karta hai: `_service` call karo, aur return value ko HTTP me translate karo (`null` -> `404`, `bool false` -> `404`, success -> `200`/`201`/`204`). Ek bhi `if` business rule nahi.

`DomainRuleException` ko `409`/`400` me convert karna ek exception-handling middleware ka kaam hai (alag topic) — abhi ke liye ek chhota `try/catch` controller me bhi chal jaata, lekin cleaner hai ek global handler. Point ye hai: **decision Service me, HTTP translation Controller me**.

### Code explained line by line — constructor injection

```csharp
private readonly IEmployeeService _service;
```

- Field ka type **interface** hai. `_service` ke andar `EmployeeService` ho ya `CachedEmployeeService` — controller ko farak nahi. `readonly` — constructor ke baad reassign nahi ho sakti, yaani accidentally `_service = something` kahin aur nahi likh sakte.

```csharp
public EmployeesController(IEmployeeService service)
{
    _service = service;
}
```

- Constructor ek `IEmployeeService` **parameter** leta hai. Controller khud `new EmployeeService()` nahi karta — wo apni dependency **bahar se maangta hai**. Ise **constructor injection** kehte hain.
- Ye instance kaun deta hai? ASP.NET Core ka **DI container**. Jab request aati hai aur `EmployeesController` banana hota hai, container constructor ke parameters dekhta hai, `IEmployeeService` ke liye apni registration dhoondta hai (`AddScoped<IEmployeeService, EmployeeService>()`), ek `EmployeeService` banata hai, aur controller ko pass kar deta hai.
- Isliye `Program.cs` me registration zaroori hai. Bina uske: runtime exception "Unable to resolve service for type 'IEmployeeService' while attempting to activate 'EmployeesController'".

```csharp
public EmployeesController(IEmployeeService service) => _service = service;
```

- Yahi cheez expression-bodied form me — do-line body ka short form. `.NET` codebases me dono style common hain.

### Register in Program.cs

```csharp
builder.Services.AddControllers();
builder.Services.AddEndpointsApiExplorer();
builder.Services.AddSwaggerGen();

builder.Services.AddScoped<IEmployeeService, EmployeeService>();   // <-- naya

var app = builder.Build();
```

- `AddScoped<IEmployeeService, EmployeeService>()` — "jise `IEmployeeService` chahiye, ek `EmployeeService` bana ke do, aur ek HTTP request ke andar wahi ek instance reuse karo". Scoped lifetime ke details DI topic me — abhi itna: Services aur Repositories ke liye `AddScoped` default choice hai.

### Where is it used in day-to-day development

- **Har naya feature**: interface me method add karo, `EmployeeService` me rule + orchestration likho, controller me ek patli action jode.
- **Code review** ka sabse common comment: "ye `if` validation controller me kyun hai? Service me le jao."
- **Bug fixing**: "duplicate email allow ho raha hai" — seedha `EmployeeService.Create` kholo, poora controller scan nahi karna padta.
- **Legacy cleanup**: purane fat controllers ko refactor karne ka pehla step hamesha yahi — "service nikaalo, controller ko patla karo".

### Pros and cons — honest trade-offs

Ab ek chhote `GET /employees/{id}` ke liye do files (interface + service) plus controller — teen jagah. Chhote CRUD me ye "boilerplate" mehsoos hota hai. Cost ye bhi hai ki agar Service sirf `return _repo.GetAll()` type pass-through methods rakhti hai to wo ek dead middleman ban jaati hai (anemic service). Fayda: rules ek jagah, testable bina HTTP ke, aur ek se zyada caller (API + job) reuse karte hain.

### When to use / when NOT to use

- **Extract a service** jab: rules hain (validation, workflows), ek se zyada caller ho sakta hai, ya app 6 mahine se zyada chalegi. Hamara EmployeeManagement.Api yahi hai.
- **Skip it** jab: 3-endpoint throwaway admin tool, koi business rule nahi, sirf pass-through CRUD — `Controller -> DbContext` bhi acceptable hai. Service tab add karo jab usko genuinely kaam ho.

</Hinglish>

<Callout type="warning">

Refactor ke waqt ek hi cheez badlo. Is topic me Service nikli, lekin storage abhi bhi `EmployeeService` ke andar `static List` hai. Repository agla topic hai. Agar Service + Repository dono ek saath nikaloge aur build tootega, to pata nahi lagega kaunse move ne toda.

</Callout>

## Real World Example

<RealWorld company="A digital-lending startup">

Ek lending platform ka `LoanController` 600 lines ka tha — eligibility rules, KYC checks, EMI calculation sab andar. Jab "bulk pre-approval" batch job banana pada, team ne pehle `ILoanEligibilityService` nikaala aur controller ke andar ka har rule usme move kiya. Controller 600 se 90 lines ka ho gaya. Batch job ne wahi `ILoanEligibilityService` inject kiya — zero rule duplication. Ye refactor ek sprint me hua kyunki move mechanical tha: rule uthao, service me daalo, controller me service call karo.

</RealWorld>

<RealWorld company="A BFSI systems integrator (TCS / Infosys style)">

Ek insurance client ke project me code-review gate literally check karta tha: "koi controller action 25 line se lambi to nahi?". Lambi action ka matlab tha usme rules ghus gaye hain. Reviewer author ko wapas bhejta tha ek `*Service` class banane ke liye. Reason: usi domain logic ko REST API aur ek nightly reconciliation job dono call karte the — Service me hota to ek source, controller me hota to do.

</RealWorld>

## Numbers That Matter

<Numbers>

- 5 methods `IEmployeeService` me: `GetAll`, `GetById`, `Create`, `Update`, `Delete`
- 3 business rules Service me move hue: duplicate email, PAN regex `^[A-Z]{5}[0-9]{4}[A-Z]$`, "active employee delete nahi"
- 1 line DI registration: `AddScoped<IEmployeeService, EmployeeService>()`
- After refactor controller actions ~2-4 lines each — sirf call plus HTTP translation
- 0 `if` business rules controller me; 0 `IActionResult` / status codes Service me
- Controller ka pehla `using Microsoft.AspNetCore.Mvc;` theek — Service me wahi `using` ek smell

</Numbers>

## Interview Angle

<InterviewAngle>

"How would you refactor a fat controller?" ya "what goes in the service layer?" guaranteed questions hain. Strong jawab: "Controller me sirf HTTP rehna chahiye — model binding, status codes, routing. Business rules, orchestration, aur DTO mapping ek `IEmployeeService` implementation me jaate hain. Controller constructor injection se `IEmployeeService` leta hai aur uske results ko HTTP me translate karta hai — `null` to `404`, entity to `200`, created to `201`. Service ko `Microsoft.AspNetCore.Mvc` ka pata nahi hona chahiye. Refactor step-by-step karo — pehle service, phir repository — taaki ek waqt me ek hi cheez badle." Agar tum "constructor injection needs a matching `AddScoped` registration in `Program.cs`" bol dete ho, interviewer samajh jaata hai tumne ye khud kiya hai.

</InterviewAngle>

## Common Mistakes

<Mistake>

Service me `IActionResult` ya `NotFound()` return karna. Service ko HTTP nahi pata hona chahiye — wo `null`, entity, `bool`, ya exception lautaye. Controller decide kare wo `404` hai ya `409`. `using Microsoft.AspNetCore.Mvc;` Service file me dikhe to samajh jao boundary tooti hai.

</Mistake>

<Mistake>

Constructor me concrete type maangna (`EmployeesController(EmployeeService service)`) jabki DI me `IEmployeeService` register kiya. Runtime error: "Unable to resolve service for type 'EmployeeService'". Constructor me wahi type maango jo `Program.cs` me register hua.

</Mistake>

<Mistake>

`Program.cs` me `AddScoped` line bhoolna. Sab compile ho jaata hai, phir pehli request pe "Unable to resolve service for type 'IEmployeeService' while attempting to activate 'EmployeesController'". Interface banane ke saath uski registration bhi karo.

</Mistake>

<Mistake>

DTO mapping ko aadha controller me aadha service me chhod dena. Mapping poori tarah Service me — `ToDto` ek private method. Controller ko `Employee` entity dikhni hi nahi chahiye, sirf `EmployeeDto`.

</Mistake>

<Mistake>

Service ke methods ko `async` bina kisi wajah ke banana ("sab async hona chahiye na"). Abhi storage ek in-memory `List` hai — koi I/O nahi, isliye sync methods theek hain. `async` module 4 me aayega jab EF Core ke `await SaveChangesAsync()` aayega. Fake async (`Task.FromResult`) sirf shor hai.

</Mistake>

## Quick Revision

<QuickRevision>

- Service layer = ek class behind an interface jo business rules + orchestration + DTO mapping rakhti hai; Controller me sirf HTTP bacha
- Move out of controller: duplicate-email check, PAN regex, "active employee delete nahi", `Select(ToDto)` mapping, `static List` access
- Controller constructor `IEmployeeService` maangta hai (constructor injection); wo khud `new` nahi karta
- `Program.cs`: `builder.Services.AddScoped<IEmployeeService, EmployeeService>();` — bina iske runtime "Unable to resolve service" error
- After: har controller action 2-4 lines — service call plus HTTP translation (`null` -> `404`, success -> `200`/`201`/`204`)
- Service `IActionResult` / status codes return nahi karti; `using Microsoft.AspNetCore.Mvc;` Service me ek smell hai
- Ek waqt me ek move — pehle Service (storage abhi `static List` Service ke andar), Repository agla topic
- Abhi sync methods theek — koi real I/O nahi; `async` module 4 me EF Core ke saath aayega

</QuickRevision>

## Practice

<Callout type="tip">

**Chhota (small):** `Services/IEmployeeService.cs` aur `Services/EmployeeService.cs` banao. Sirf `GetAll()` aur `GetById(int id)` implement karo (list access + `ToDto`). `Program.cs` me `AddScoped<IEmployeeService, EmployeeService>()` register karo aur controller ke `GetAll`/`GetById` actions ko `_service` par point karwao. Build aur Swagger se test karo.

**Medium:** Baaki teen methods (`Create`, `Update`, `Delete`) bhi move karo, teeno business rules ke saath (`DomainRuleException` use karo). Controller ke actions ko 2-4 line pe le aao. Ek `try/catch` ya chhota exception filter add karo jo `DomainRuleException` ko `409 Conflict` me convert kare. Purane fat-controller code ko delete karo.

**Bada (large):** Ek xUnit test project (`EmployeeManagement.Api.Tests`) banao. Ek `FakeEmployeeStore` (ya abhi ke liye seedha `EmployeeService` reset karke) ke against 6 tests likho: `Create` duplicate email pe `DomainRuleException`, `Create` galat PAN pe `DomainRuleException`, `Create` valid input pe DTO with `Id`, `Delete` active employee pe exception, `Delete` inactive pe `true`, `GetById` unknown id pe `null`. Sab tests bina `WebApplicationFactory`, bina HTTP — sirf `new EmployeeService()` aur method calls.

</Callout>
