<SimpleDefinition>

Back-of-the-envelope estimation is the practice of using rough, defensible numbers to size a system — traffic, storage, bandwidth, and server count — during a design interview, prioritizing reasonable approximation over precision. The goal is not the exact right answer but a number that is order-of-magnitude correct, arrived at through explicit, stated assumptions.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Yeh section har system design interview mein aata hai, aur yehi woh jagah hai jahan bahut smart candidates bhi ghabra jaate hain — kyunki unhe lagta hai calculator chahiye, ya exact numbers yaad hone chahiye. Reality iske ulta hai: interviewer **precision nahi**, tumhara **estimation process** dekh raha hai. Kya tum sahi cheezon ko estimate kar rahe ho, kya tum reasonable assumptions bol rahe ho, aur kya tumhara final number kisi doosre order of magnitude mein nahi hai (jaise agar sahi answer 1000 servers hai aur tum 10 bol do, woh red flag hai — lekin 800 vs 1200 mein farak interview mein kisi ko nahi padta).

### Kyun zaroori hai yeh skill

Bina estimation ke, "design Swiggy" jaisa problem completely abstract reh jaata hai — tum bol sakte ho "hume ek database chahiye" lekin nahi bata sakte ki single database machine kaafi hai ya sharding chahiye, ek server kaafi hai ya load balancer ke peeche 50 chahiye, ek cache instance kaafi hai ya distributed cache cluster chahiye. Estimation hi woh bridge hai jo abstract design ko concrete engineering decisions se connect karta hai.

### Standard reference numbers — yaad rakhne layak

Kuch numbers itni baar use hote hain ki unhe memorize karna interview mein time bachata hai:

- **Seconds in a day** — actual value 86,400 hai, lekin math easy karne ke liye interview mein **100,000** round kar lo. Isse error sirf ~15-16% aata hai — jo estimation ke context mein completely acceptable hai, aur division bahut simpler ho jaati hai.
- **1 million ~ 10^6**, **1 billion ~ 10^9** — India context mein "10 lakh = 1 million" aur "100 crore = 1 billion" yaad rakhna helpful hai, kyunki interview mein DAU jaisi numbers aksar crore/lakh mein sochne se easier lagti hain phir convert kar lo.
- **Byte conversions** — 1 KB ~ 10^3 bytes, 1 MB ~ 10^6 bytes, 1 GB ~ 10^9 bytes, 1 TB ~ 10^12 bytes, 1 PB ~ 10^15 bytes. Interview mein exact 1024 vs 1000 ka farak kabhi matter nahi karta — order of magnitude sahi hona chahiye.
- **Typical read:write ratio** — bahut consumer apps (social media, e-commerce browsing, food delivery search) mein reads writes se **10:1 se 100:1** tak zyada hote hain, kyunki log browse zyada karte hain, transact kam. Yeh ratio system ko design karte waqt caching strategy directly decide karta hai — read-heavy system mein caching ka ROI bahut zyada hota hai.
- **Peak-to-average traffic multiplier** — average QPS ka **2x se 5x** typically peak time pe expect karo (dinner rush, sale events, breaking news). Kabhi kabhi flash-sale jaise events mein yeh 10x-50x bhi ho sakta hai — is baat ko explicitly bolna chahiye ki peak multiplier ek assumption hai, exact science nahi.

### Interview technique: "round aggressively, state assumptions out loud"

Do cheezein yahan critical hain:

1. **Round aggressively** — agar calculation mein 86,400 aata hai, use 100,000 kar do. Agar DAU "23.7 million" jaisa koi weird number diya gaya hai, use 25 million round kar do. Exact arithmetic ka koi marks nahi milta, aur galat multiplication se time waste hota hai jo interviewer ka patience test karta hai.
2. **Assumptions zor se bolo** — kabhi bhi silently ek number mat pick karo. Bolo "Main assume kar raha hoon ki 10% active users daily order karte hain — yeh ek reasonable retention/engagement number hai food delivery apps ke liye." Agar interviewer disagree karta hai, woh number correct kar dega, aur tumhara process hi correct rahega. Silent assumption se agar galat foundation pe pura design ban jaaye, to poora answer shaky lagta hai.

Yeh combination — rough numbers + loud assumptions — hi asli signal hai jo interviewer dhundta hai: **structured quantitative thinking**, calculator-level precision nahi.

### Worked example: Swiggy-scale food delivery app (India)

Chalo poora estimation step by step karte hain, jaisa interview mein bolna chahiye.

**Step 1 — Assumptions (explicitly stated)**

```text
- DAU (Daily Active Users) = 20 million (2 crore) — reasonable for a large
  Indian food delivery app at scale
- 10% of DAU place at least one order per day => 2 million orders/day
- Each active user (whether ordering or just browsing) generates ~20 API
  requests per session on average (search, menu views, cart, coupon checks,
  order tracking pings)
- Peak traffic multiplier = 3x average (dinner-time 7-10 PM concentrates load)
- Read:Write ratio ~ 20:1 (browsing/search reads dominate over actual writes)
- Each order record is ~2 KB (items, address, payment reference, metadata)
- Average API response payload ~5 KB (JSON for menu/cart/order data)
```

**Step 2 — Total requests per day**

```text
Total requests/day = DAU x requests per user per day
                    = 20,000,000 x 20
                    = 400,000,000 requests/day  (400 million)
```

**Step 3 — Average QPS**

```text
Seconds in a day ~ 100,000 (rounded from 86,400 for easy math)

Average QPS = Total requests/day / seconds in a day
            = 400,000,000 / 100,000
            = 4,000 requests/second (average)
```

**Step 4 — Peak QPS**

```text
Peak QPS = Average QPS x peak multiplier
         = 4,000 x 3
         = 12,000 requests/second (peak, e.g. during dinner rush)
```

**Step 5 — Order-specific QPS (writes)**

```text
Orders/day = 2,000,000
Average order QPS = 2,000,000 / 100,000 = 20 orders/second (average)
Peak order QPS (dinner rush concentrates even harder, ~5x here)
             = 20 x 5 = 100 orders/second (peak)
```

**Step 6 — Storage per day and per year**

```text
Daily order storage = orders/day x size per order
                     = 2,000,000 x 2 KB
                     = 4,000,000 KB = 4,000 MB = ~4 GB/day

Yearly order storage = 4 GB/day x 365
                      = ~1,460 GB
                      = ~1.5 TB/year (order records only, not images/logs)
```

**Step 7 — Bandwidth**

```text
Peak bandwidth (response traffic only)
   = Peak QPS x avg response size
   = 12,000 requests/sec x 5 KB
   = 60,000 KB/s = 60 MB/s
   ~ 480 Mbps at peak (excluding CDN-served images, which are separate)
```

**Final numbers to present to the interviewer**: ~4,000 QPS average, ~12,000 QPS peak, ~1.5 TB/year storage growth just for order records, ~480 Mbps peak bandwidth for API responses. From here the natural next step is: "Ek single database aur ek app server clearly is scale ko handle nahi karega — humein load balancer ke peeche multiple app server instances chahiye, aur database ko bhi read replicas ya sharding ki zaroorat padegi jab yeh 1-2 order of magnitude aur badhega."

This is exactly the kind of number-driven transition that leads naturally into horizontal scaling, caching, and sharding discussions in later design steps.

</Hinglish>

<Callout type="tip">

Jab bhi numbers estimate karo, apne answer ko round karke bolo aur explicitly kaho "yeh ek order-of-magnitude estimate hai." Yeh line akele hi interviewer ko signal deti hai ki tumhe pata hai estimation ka goal precision nahi, directional correctness hai.

</Callout>

## Real World Example

<RealWorld company="Uber">

Uber engineers publicly bata chuke hain ki unke internal capacity planning mein bhi yehi approach use hota hai — rides/day se shuru karke, per-ride kitne location-update events generate hote hain (GPS pings every few seconds during a trip), phir usse total events/second aur storage/day derive kiya jaata hai. Real production capacity planning bhi conceptually back-of-envelope estimation ka hi ek zyada rigorous version hai, bas assumptions ko real historical data se validate kiya jaata hai.

</RealWorld>

<RealWorld company="Swiggy">

Swiggy jaisi Indian companies ke liye peak multiplier sirf "dinner rush" tak limited nahi hai — cricket match ke breaks, IPL final, ya festival days (jaise New Year's Eve) mein traffic normal peak se bhi 2-3x zyada spike kar sakta hai. Isliye interview mein agar tum Indian-context system design kar rahe ho, "peak multiplier" ko ek single fixed number ki jagah "baseline peak x event-day multiplier" jaisa do-level estimate bolna zyada impressive lagta hai.

</RealWorld>

## Numbers That Matter

<Numbers>

- Seconds in a day — 86,400 actual, round to 100,000 for quick math
- 1 million ~ 10^6 (~10 lakh); 1 billion ~ 10^9 (~100 crore)
- 1 KB ~ 10^3 bytes, 1 MB ~ 10^6, 1 GB ~ 10^9, 1 TB ~ 10^12, 1 PB ~ 10^15
- Typical read:write ratio for consumer apps — 10:1 to 100:1 (reads dominate)
- Peak-to-average traffic multiplier — 2x to 5x normally, 10x-50x during flash sales/events
- A single modern app server instance can typically handle roughly 1,000-5,000 simple requests/second before needing horizontal scaling (highly workload dependent — state this caveat out loud)
- Swiggy-scale worked example above: ~4,000 QPS average, ~12,000 QPS peak, ~1.5 TB/year order storage, ~480 Mbps peak bandwidth

</Numbers>

## Interview Angle

<InterviewAngle>

This step almost always comes right after requirements gathering, before high-level design. Interviewer wants to see a clean, narrated chain: **DAU to total requests to QPS to peak QPS to storage to bandwidth**, each step built on the previous one with an explicitly stated assumption. A weak candidate either skips this entirely and jumps to drawing boxes, or gets stuck doing precise arithmetic in their head and loses the thread.

Model approach: write the assumptions down first (even just saying them out loud in order), then chain the math one line at a time, rounding at every step. End with a concrete sentence connecting the numbers to a design decision — e.g., "12,000 peak QPS means one server definitely isn't enough, so we need a load balancer and horizontal scaling from the start," which sets up the rest of the interview.

</InterviewAngle>

## Common Mistakes

<Mistake>

Doing precise arithmetic with ugly numbers (86,400, or a DAU like 23.7 million) instead of rounding aggressively — this wastes interview time and increases the chance of an arithmetic mistake under pressure.

</Mistake>

<Mistake>

Picking assumptions silently instead of stating them out loud. If the interviewer disagrees with an unstated assumption, the entire downstream calculation looks wrong even if the math itself was correct.

</Mistake>

<Mistake>

Estimating traffic (QPS) but forgetting storage and bandwidth entirely — a complete estimation covers all three: compute (QPS/servers), storage (data growth), and network (bandwidth).

</Mistake>

<Mistake>

Treating the peak multiplier as a fixed universal constant (always "2x") instead of reasoning about the specific system — a chat app's peak pattern (evening hours) looks very different from a food delivery app's (mealtime spikes) or a sale-event e-commerce app's (10x-50x for a few hours).

</Mistake>

<Mistake>

Getting anxious about the "correct" final number. Two candidates estimating 4,000 QPS vs 6,000 QPS for the same system are both fine — the interviewer cares about the reasoning chain and the assumptions, not matching a hidden exact answer.

</Mistake>

## Quick Revision

<QuickRevision>

- Goal is order-of-magnitude correctness, not precision — round aggressively, state assumptions out loud
- Seconds/day ~ 100,000 (rounded from 86,400) — the single most useful rounding trick
- 1M ~ 10^6, 1B ~ 10^9; KB/MB/GB/TB/PB scale by 10^3 each step
- Standard chain: DAU -> total requests/day -> average QPS -> peak QPS (x2-5x multiplier) -> storage/day -> storage/year -> bandwidth
- Typical read:write ratio for consumer apps is 10:1 to 100:1 — reads dominate
- Swiggy-scale worked example: 20M DAU -> 4,000 avg QPS -> 12,000 peak QPS -> ~1.5 TB/year storage -> ~480 Mbps peak bandwidth
- Always end the estimate with a design implication ("so we need horizontal scaling from day one"), not just a bare number
- Two reasonable candidates can land on different numbers and both be correct — the reasoning chain is what's graded

</QuickRevision>
