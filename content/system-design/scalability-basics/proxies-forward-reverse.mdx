<SimpleDefinition>

A forward proxy sits in front of a group of clients and acts on their behalf when talking to the internet — the destination server sees the proxy, not the real client. A reverse proxy sits in front of a group of servers and acts on their behalf when talking to clients — the client sees the proxy, not the real backend server. They solve distinct problems even though both are intermediaries.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Forward proxy aur reverse proxy dono "beech mein baithe hain" — lekin **kiske liye kaam kar rahe hain** wahi fundamental difference hai. Yaad rakhne ka sabse simple tareeka: forward proxy **client ki taraf se** internet se baat karta hai; reverse proxy **server ki taraf se** clients se baat karta hai. Direction ulti hai, isliye naam "forward" aur "reverse" hai.

### Forward proxy — client ke liye represent karta hai

Forward proxy client aur internet ke beech baithta hai. Client apni request proxy ko bhejta hai, proxy uss request ko actual destination server tak forward karta hai apni taraf se — destination server ko sirf proxy ka IP dikhta hai, real client ka nahi. Use cases:

- **Corporate network egress control/filtering** — Company apne saare employees ka outbound traffic ek forward proxy ke through route karti hai, taaki kaunsi websites access ho sakti hain control kar sake, aur traffic ko monitor/log kar sake.
- **Anonymity** — Client apni identity (IP address) chhupa sakta hai destination server se, kyunki server ko sirf proxy dikhta hai.
- **Geo-restriction bypass** — Agar koi content sirf ek specific country mein available hai, ek forward proxy us country mein located hoke user ko access dila sakta hai (destination server proxy ki location dekhta hai, user ki nahi).
- **Caching for a group of clients** — Ek forward proxy multiple clients ke liye common requested content cache kar sakta hai — jaise ek office ke saare employees agar same external resource baar-baar access karte hain, proxy ek baar fetch karke sabko serve kar sakta hai.

### Reverse proxy — server ke liye represent karta hai

Reverse proxy servers aur clients ke beech baithta hai, lekin **server ki taraf se** kaam karta hai. Client ko sirf reverse proxy ka address pata hota hai — asli backend servers uske peeche chhupe hote hain. Use cases:

- **Load balancing** — Requests ko multiple backend servers ke beech distribute karna. (Yahan ek important clarification: **load balancer essentially ek specialized reverse proxy hi hai** — load balancing reverse proxy ka ek specific, bahut common use case hai, koi alag fundamentally different cheez nahi.)
- **SSL termination** — HTTPS encryption/decryption ka heavy computational kaam reverse proxy pe handle hota hai, backend servers plain HTTP pe internally baat karte hain — isse backend servers ka CPU load kam hota hai aur certificate management centralized ho jaata hai ek jagah.
- **Request routing** — URL path, header, ya kisi aur criteria ke basis pe request ko sahi backend service tak route karna (jaise microservices architecture mein `/api/orders` ko orders-service tak, `/api/users` ko users-service tak).
- **Hiding internal topology** — Client ko yeh pata hi nahi chalta ki backend mein kitne servers hain, unka internal IP structure kya hai, ya woh kaise organized hain — security aur flexibility dono ke liye achha hai, internal architecture change karna client-facing contract ko affect nahi karta.
- **Basic DDoS absorption** — Reverse proxy pehla layer hoke kuch malicious/excessive traffic patterns ko absorb ya rate-limit kar sakta hai, isse pehle ki woh actual backend servers tak pahunche.
- **Compression** — Response ko gzip/brotli jaisa compress karna ek central jagah, taaki har backend server ko yeh kaam individually na karna pade.

</Hinglish>

<Callout type="tip">

Ek load balancer ko "yeh reverse proxy se alag cheez hai" mat socho — load balancer basically ek reverse proxy hai jiska primary focus **traffic distribution** hai. Reverse proxy ek broader category hai (SSL termination, routing, compression sab isme aa sakte hain); load balancing usi category ka ek specific, bahut common specialization hai. Interview mein yeh distinction bolna ek achha signal hai.

</Callout>

## Real World Example

<RealWorld company="Cloudflare">

Cloudflare production mein dono roles play karta hai: ek reverse proxy ke roop mein (websites ke aage baithkar DDoS protection, caching, SSL termination deta hai), aur alag se Cloudflare WARP jaisa product ek forward proxy/VPN-jaisa service hai jo end users ke devices ka outbound traffic secure aur route karta hai.

</RealWorld>

<RealWorld company="Amazon">

AWS environments mein NAT Gateway ek forward-proxy-jaisa role play karta hai — private subnet ke andar EC2 instances ka outbound internet traffic ek common gateway ke through jaata hai, taaki instances ka private IP internet ko directly expose na ho.

</RealWorld>

<RealWorld company="Flipkart">

Flipkart jaisi large-scale systems mein nginx ya similar reverse proxy layer client-facing traffic ko receive karta hai aur internal microservices (catalog, cart, order, payment) tak route karta hai — client ko kabhi pata nahi chalta ki uske request ke peeche kitne alag services actually kaam kar rahe hain.

</RealWorld>

## Numbers That Matter

<Numbers>

- nginx as a reverse proxy — commonly handles tens of thousands of concurrent connections per instance
- SSL/TLS termination at reverse proxy removes that CPU cost from every backend instance individually
- Forward proxy caching for a shared client group can cut redundant external bandwidth usage significantly for common resources
- Reverse proxy added latency — typically sub-millisecond to a few milliseconds for routing/header work

</Numbers>

## Interview Angle

<InterviewAngle>

Common quick-check question: **"What's the difference between a forward proxy and a reverse proxy, and is a load balancer one of them?"** This is often a fast warm-up sub-question inside a larger design discussion. The expected shape: forward proxy acts on behalf of clients (hides the client from the destination), reverse proxy acts on behalf of servers (hides the server from the client) — and yes, a load balancer is a specialized reverse proxy. Getting the direction backwards (saying a reverse proxy hides the client) is the single most common way candidates fumble this, so state clearly which side each proxy represents.

</InterviewAngle>

## Common Mistakes

<Mistake>

Forward aur reverse proxy ki directions ulta bol dena — jaise yeh keh dena ki reverse proxy client ki identity chhupaata hai server se, jabki asal mein woh server ki identity chhupaata hai client se.

</Mistake>

<Mistake>

Load balancer ko reverse proxy se bilkul alag, unrelated concept samajhna — jabki load balancer reverse proxy ka hi ek specialized use case hai.

</Mistake>

<Mistake>

Yeh sochna ki proxy sirf security/anonymity ke liye hota hai — reverse proxy ke SSL termination, routing, compression jaise operational use cases ko miss kar dena.

</Mistake>

<Mistake>

Forward proxy aur VPN ko exactly same cheez samajh lena — dono traffic ko intermediate karte hain lekin VPN typically poora network-level traffic encrypt karta hai end-to-end, jabki forward proxy usually application-level (jaise HTTP) traffic ke liye hota hai aur encryption guarantee nahi karta by default.

</Mistake>

## Quick Revision

<QuickRevision>

- Forward proxy = represents the client toward the internet; reverse proxy = represents the server toward the client
- Forward proxy use cases: corporate egress filtering, anonymity, geo-restriction bypass, caching for a client group
- Reverse proxy use cases: load balancing, SSL termination, request routing, hiding internal topology, basic DDoS absorption, compression
- A load balancer is essentially a specialized reverse proxy focused on traffic distribution
- nginx is the canonical reverse proxy example in production systems
- Direction is the key thing to get right in an interview - don't flip which side each proxy hides
- Forward proxy is not the same as a VPN - VPN typically encrypts at the network level end-to-end, forward proxy usually operates at the application level

</QuickRevision>
