## The Scenario

It's Priya's first day. Rahul sends her the repo URL and says: "clone it, then push a small fix to the README so we know your setup works." Priya clones the repo, opens the README in her editor, types a line, and saves.

Then she runs `git status` — and it says her change isn't staged, isn't committed, isn't anywhere near "done." She saved the file. Why doesn't Git think it's saved?

## The Mental Picture

Git moves your work through three areas, one at a time:

- **Working Directory = your desk.** Whatever file you're editing right now sits here. Saving the file just means the desk has your latest draft on it — Git hasn't been told anything yet.
- **Staging Area = the packing box.** You explicitly place things into it with `git add`. This is you deciding "this specific change goes into the next parcel."
- **Commit = a sealed parcel with a label.** `git commit` seals the box and gives it a message. Once sealed, it's permanent history — it can't quietly change again.

`git clone` is the warehouse (the remote) shipping you a full copy of the desk *and* every sealed parcel ever made, so you can start working immediately. `git init` skips the warehouse entirely — you're just building a brand new, empty desk with no history at all.

## Diagram

Before Priya edits anything, right after `git clone`:

```
 Working Directory         Staging Area         Local Repo (commits)
 ------------------        ------------         ---------------------
 README.md (clean)         (empty)               C1 "Initial commit"
```

After she edits and saves README.md — nothing has moved yet:

```
 Working Directory         Staging Area         Local Repo (commits)
 ------------------        ------------         ---------------------
 README.md (MODIFIED)      (empty)               C1 "Initial commit"
```

After `git add README.md` — the change is boxed up, but not shipped:

```
 Working Directory         Staging Area              Local Repo (commits)
 ------------------        ------------------        ---------------------
 README.md (clean)         README.md (staged)        C1 "Initial commit"
```

After `git commit -m "..."` — the box is sealed into history:

```
 Working Directory         Staging Area         Local Repo (commits)
 ------------------        ------------         ---------------------
 README.md (clean)         (empty)               C1---C2 "Update README"
```

## Commands

```bash
git clone <repo-url>                              # warehouse ships you the desk + every sealed parcel (full history)
cd <repo-folder>                                  # sit down at your new desk

# --- only if starting a brand new project, no warehouse involved ---
git init                                          # build an empty desk, zero history

git status                                        # ask: what's on my desk right now, and what's boxed?
git add README.md                                 # move this specific change from the desk into the box
git commit -m "Update README with setup notes"    # seal the box, label it — now it's permanent history
```

## What Actually Happened

- `git clone` copied the entire warehouse (remote history) down and unpacked the latest snapshot straight onto your desk (working directory) — you got the full parcel history for free.
- Editing and saving README.md only changed the desk. The staging area and the commit history had no idea it happened.
- `git add` moved exactly that change into the packing box — you decide what goes into the next parcel, nothing is boxed automatically.
- `git commit` sealed the box into a labeled, permanent snapshot in your local repo. It's now history that won't silently change.

## Gotcha

<Mistake>

New devs assume "I saved the file" means "Git has it." It doesn't. Saving only updates the working directory (the desk). Until `git add`, the change isn't even in the box; until `git commit`, it's not permanent. If `git status` shows a file under "Changes not staged for commit," that's Git telling you: it's still just sitting on the desk.

</Mistake>

## Interview Angle

<InterviewAngle>

**"Walk me through what happens, area by area, when you edit a file and then run `git add` and `git commit`."**

Editing a file only changes the working directory — Git tracks that it's modified but hasn't captured its content anywhere yet. `git add` copies that content into the staging area, which is a preview of the next commit. `git commit` takes exactly what's staged and seals it into an immutable, labeled snapshot in the repo's history. Three separate, explicit steps — nothing moves to the next area until you tell it to.

</InterviewAngle>
