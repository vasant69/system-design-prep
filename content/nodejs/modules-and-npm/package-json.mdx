<SimpleDefinition>

`package.json` is the **manifest** file at the root of every Node project. It records the project's **identity** (`name`, `version`), **how it loads** (`type`, `main`, `exports`, `bin`), **what commands it runs** (`scripts`), **what it depends on** (`dependencies`, `devDependencies`, `peerDependencies`, `optionalDependencies`), and **constraints and publishing rules** (`engines`, `files`, `private`). npm, Node itself, and nearly every tool in the ecosystem reads this one file.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

`package.json` har Node project ki **ID card + instruction sheet** hai. npm ise padh ke dependencies install karta hai, Node ise padh ke decide karta hai ki entry file kaunsi hai aur modules CommonJS hain ya ESM, aur bundlers/test-runners/linters sab isi se apna config aur commands uthate hain. Ek Node developer ko har field ka matlab pata hona chahiye — interview mein "ye field kya karti hai" seedha poocha jata hai.

### Ye kya hai — package.json

Ek plain **JSON** file, project root mein. Comments allowed nahi (JSON hai, JSON5 nahi). `npm init` ise banata hai. Minimum valid `package.json` `{}` bhi ho sakta hai, lekin publish karne ke liye kam se kam `name` aur `version` chahiye.

### Ye kyun exist karta hai

Iske bina: dependencies ka koi record nahi, "is project ko chalane ke liye kya command hai" ka koi documented jawaab nahi, aur npm ko nahi pata ki tumne kya install kiya. `package.json` in sab ka **single source of truth** hai jo git mein commit hota hai.

### Field by field

```json
{
  "name": "billing-service",
  "version": "2.4.1",
  "description": "Invoice generation and payment reconciliation API",
  "type": "module",
  "main": "./dist/index.js",
  "exports": {
    ".": "./dist/index.js",
    "./utils": "./dist/utils.js"
  },
  "bin": {
    "billing-cli": "./bin/cli.js"
  },
  "scripts": {
    "dev": "nodemon src/index.js",
    "build": "tsc",
    "test": "jest",
    "lint": "eslint ."
  },
  "dependencies": {
    "express": "^4.18.2",
    "pg": "^8.11.3"
  },
  "devDependencies": {
    "typescript": "^5.3.3",
    "jest": "^29.7.0"
  },
  "peerDependencies": {
    "react": ">=18"
  },
  "optionalDependencies": {
    "fsevents": "^2.3.3"
  },
  "engines": {
    "node": ">=18.17.0"
  },
  "files": ["dist", "bin", "README.md"],
  "private": true
}
```

- **`name`** — package ka naam. Lowercase, URL-safe. Publish karna hai toh registry mein unique hona chahiye (ya scoped: `@myorg/billing-service`). **Required** to publish.
- **`version`** — SemVer string (`MAJOR.MINOR.PATCH`). `npm version patch/minor/major` ise bump karta hai aur git tag banata hai. **Required** to publish.
- **`description`** — ek line, `npm search` results aur registry page pe dikhta hai. Optional.
- **`type`** — `"commonjs"` (default agar absent) ya `"module"`. `"module"` matlab `.js` files ko **ESM** treat karo (`import`/`export`), CommonJS nahi. Ye ek switch hai jo poore package ke `.js` files ko affect karta hai.
- **`main`** — legacy entry point. Jab koi `require("billing-service")` kare toh kaunsi file load ho. Optional (default `index.js`).
- **`exports`** — modern entry-point map. `main` ko override karta hai jahan supported ho. Ye **encapsulation** deta hai: jo path yahan listed nahi, use consumer `require`/`import` **nahi** kar sakta — `require("billing-service/src/internal/db.js")` block ho jayega. Conditional exports (`import` vs `require`, `node` vs `browser`) bhi yahin define hote hain. Optional but recommended for libraries.
- **`bin`** — is package ke command-line executables. `"billing-cli": "./bin/cli.js"` matlab global install ya `npx` pe `billing-cli` command banega jo us file ko chalata hai (file ke top pe `#!/usr/bin/env node` shebang chahiye). Optional.
- **`scripts`** — named shell commands. `npm run build` `scripts.build` chalata hai. `test`, `start` jaise kuch names special hain (`npm test`, `npm start` bina `run` ke chalte hain). `pre<name>` / `post<name>` scripts automatically wrap hote hain. Optional but har real project mein hota hai.
- **`dependencies`** — packages jo **runtime pe production mein** chahiye — `express`, `pg`. `npm install <pkg>` default yahin add karta hai.
- **`devDependencies`** — sirf **develop / build / test** ke liye — `typescript`, `jest`, `eslint`, `nodemon`. `npm install -D <pkg>`. Production install (`npm ci --omit=dev`) inhe skip karta hai.
- **`peerDependencies`** — "main ye khud install nahi karunga, lekin mujhe host app se chahiye, aur is version range mein." Plugins use karte hain — jaise ek Express middleware `express` ko peer declare karta hai taaki app aur middleware **same** Express copy share karein, do alag nahi.
- **`optionalDependencies`** — install fail ho jaye toh bhi npm error nahi karta, chup-chaap skip. Platform-specific cheezon ke liye — `fsevents` sirf macOS pe build hota hai; Linux pe skip ho jata hai bina build tode.
- **`engines`** — required Node / npm version. `"node": ">=18.17.0"`. Default sirf **warning** hai; `.npmrc` mein `engine-strict=true` se **hard fail** ban jata hai.
- **`files`** — publish karte waqt **kaunsi files tarball mein jayein**. Yahan `["dist", "bin"]` matlab `src`, tests, configs publish nahi honge. `.npmignore` iska ulta (blacklist) hai. Application (non-published) projects mein ignore.
- **`private`** — `true` set karo toh `npm publish` **refuse** kar dega. Har application repo (jo library nahi hai) mein ye zaroor daalo taaki galti se internal code registry pe na chala jaye.

### Simple real-life analogy

`package.json` ek **product ka box** hai. Bahar likha hai naam aur model number (`name`, `version`), kis desh mein banaa (`engines`), kaunse cables andar hain (`files`). Andar ek manual hai jismein "power on karne ke steps" (`scripts`), "ye alag se kharidna padega" (`peerDependencies`), aur "ye optional accessory hai" (`optionalDependencies`) likha hai.

### Code — line by line (npm init)

```bash
npm init -y
```

Ye ek file banata hai:

```json
{
  "name": "my-folder-name",
  "version": "1.0.0",
  "description": "",
  "main": "index.js",
  "scripts": {
    "test": "echo \"Error: no test specified\" && exit 1"
  },
  "keywords": [],
  "author": "",
  "license": "ISC"
}
```

- `name` — current folder ka naam le leta hai.
- `version` — `1.0.0` se shuru.
- `main` — `index.js` default.
- `scripts.test` — placeholder jo fail karta hai jab tak tum real test command na daalo.
- `license` — `ISC` default; company projects mein aksar `"UNLICENSED"` + `"private": true`.

`-y` ke bina `npm init` ek interactive wizard chalata hai jo ye sab ek-ek karke poochhta hai.

### Day-to-day use

- `npm run` — saare available scripts list karo.
- `npm pkg get dependencies` — CLI se ek field padho.
- `npm pkg set scripts.lint="eslint ."` — CLI se field likho (JSON hand-edit karne se safe).
- `npm version patch` — `version` bump + git tag.
- `npm install` — `dependencies` + `devDependencies` dono laata hai (local dev).

### Kab kaunsa dependency bucket

- Code `import`/`require` karega **aur** production mein chalega → `dependencies`.
- Sirf build/test/lint/dev-server → `devDependencies`.
- Tum ek plugin/library ho jo host ki copy chahte ho → `peerDependencies`.
- Platform-specific, fail ho toh chalega → `optionalDependencies`.

### Kab `exports` use nahi karna

- Chhoti internal app jahan koi tumhare package ko import nahi karega — sirf `main` kaafi hai, `exports` ka encapsulation overhead bekaar.
- Jab tumhe deliberately consumers ko deep-import allow karna ho (rare) — `exports` unhe block kar dega.

### Pros and cons (manifest-driven approach)

**Pros**

- Ek file mein poori project identity, deps, aur commands — git-tracked, reviewable.
- Har tool same file padhta hai — consistency.
- `scripts` se onboarding trivial: `npm install && npm run dev`.

**Cons**

- JSON hai — comments nahi, trailing commas nahi, easy to break with a typo.
- `dependencies` vs `devDependencies` galat bucket mein daalna common aur prod ko affect karta hai.
- `exports` field ka behaviour version aur tool ke hisaab se subtle — misconfigure karo toh "module not found" jo debug karna mushkil.

### Alternatives

- **`deno.json` / `jsr`** — Deno ka apna manifest; URL imports, no `node_modules`.
- **`Cargo.toml`, `pyproject.toml`, `go.mod`** — dusri languages ke equivalents; concept same (manifest + lockfile).
- **`pnpm-workspace.yaml` / `turbo.json` / `nx.json`** — monorepo tooling jo `package.json` ke **upar** baithti hai, replace nahi karti.

### Interview mein "package.json ki ye field kya karti hai?"

> "`type: module` poore package ke `.js` files ko ESM banata hai. `main` legacy single entry point hai; `exports` modern map hai jo entry points define karta hai aur baaki sab paths ko private bana deta hai — deep imports block ho jate hain. `bin` package ke CLI executables register karta hai. `engines` required Node version declare karta hai, default warning, `engine-strict` se hard fail. `private: true` accidental `npm publish` rok deta hai — har app repo mein rakhta hoon. `files` control karta hai ki publish tarball mein kya jaye — usually sirf `dist`."

</Hinglish>

<Callout type="tip">

`package.json` ko hand-edit karne ke bajaye `npm pkg set` / `npm pkg get` / `npm pkg delete` use karo — ye JSON ko valid rakhta hai aur formatting consistent rehti hai. Ek missing comma poore `npm install` ko `EJSONPARSE` se tod deta hai.

</Callout>

## Real World Example

<RealWorld company="React ecosystem (peerDependencies)">

`react-router`, `@mui/material`, `react-redux` — ye sab apni `package.json` mein `react` ko `dependencies` mein nahi, `peerDependencies` mein daalte hain (`"react": ">=18"`). Reason: agar har library apni React copy install kare toh app mein React ke 3-4 alag copies aa jayein, aur React hooks / context toot jaate hain kyunki wo "same module instance" pe depend karte hain. Peer declare karne se ye libraries app ki ek hi React copy use karti hain, aur agar version incompatible ho toh npm install pe warning milti hai.

</RealWorld>

<RealWorld company="nodemon / TypeScript in company APIs">

Ek typical BFSI backend repo mein `dependencies` chhoti hoti hai — `express`, `pg`, `jsonwebtoken`, `zod` — sirf wo jo chalte hue server ko chahiye. `devDependencies` badi hoti hai — `typescript`, `ts-node`, `jest`, `supertest`, `eslint`, `prettier`, `nodemon`. Production Docker image `npm ci --omit=dev` chalati hai, jisse image se ~150MB+ dev tooling nikal jata hai aur attack surface chhota ho jata hai. Agar galti se `typescript` `dependencies` mein aa jaye toh prod image bloat ho jata hai bina koi runtime fayde ke.

</RealWorld>

## Numbers That Matter

<Numbers>

- `npm init -y` bani hui default file mein **7-8 fields** hote hain; ek production repo ki file mein aksar **20-30**.
- `version` `1.0.0` se shuru hota hai `npm init` mein; SemVer ke teen number `MAJOR.MINOR.PATCH`.
- `type` sirf **do** valid values leta hai: `"commonjs"` (default) aur `"module"`.
- `engines` by default sirf warning deta hai; `engine-strict=true` `.npmrc` mein daalne pe install **fail** karta hai.
- `npm ci --omit=dev` ek typical TS backend image se **100-200MB** dev dependencies hata deta hai.
- `files` array ke alawa 4 files **hamesha** publish hoti hain chahe kuch bhi likho: `package.json`, `README`, `LICENSE`, aur entry point.

</Numbers>

## Interview Angle

<InterviewAngle>

Ye pure knowledge-check round mein aata hai. Interviewer ek field bol ke poochhta hai "ye kya karti hai" — `type`, `main` vs `exports`, `peerDependencies`, `engines`, `private`. Ya reverse: "typescript ko kaunse bucket mein daaloge aur kyun."

Achhe jawaab ka shape:

1. **Identity** — `name` + `version` (publish ke liye required), SemVer.
2. **Loading** — `type` (CJS/ESM switch), `main` (legacy entry), `exports` (modern map + encapsulation), `bin` (CLI executables).
3. **Commands** — `scripts`, special names (`test`/`start`), `pre`/`post` hooks.
4. **Deps** — `dependencies` (runtime prod), `devDependencies` (build/test), `peerDependencies` (host provides), `optionalDependencies` (fail-safe).
5. **Rules** — `engines` (Node version), `files` (publish whitelist), `private` (block publish).

Red flag: `dependencies` aur `devDependencies` ka farak na bata pana, ya `peerDependencies` ko "same as dependencies" bolna.

</InterviewAngle>

## Common Mistakes

<Mistake>

**Build tool ko `dependencies` mein daalna.** `npm install typescript` (bina `-D`) `typescript` ko `dependencies` mein daal deta hai. Production image ise install karega — ~50MB extra, zero runtime benefit, aur ek badi dependency jo compile hone ke baad chahiye hi nahi. Build tools hamesha `-D` ke saath.

</Mistake>

<Mistake>

**Runtime dependency ko galti se `devDependencies` mein chhod dena.** `dotenv` ya `pg` ko `-D` se install kar diya. Local dev mein sab chalta hai kyunki wahan dev deps installed hain. Production `npm ci --omit=dev` chalti hai, `pg` install hi nahi hota, server `Cannot find module 'pg'` se crash. Agar production code use karta hai → `dependencies`.

</Mistake>

<Mistake>

**`private: true` bhoolna application repos mein.** Bina iske, koi teammate ya CI galti se `npm publish` chala de toh internal source code (DB credentials patterns, business logic) public npm registry pe chala jata hai. Har non-library repo ki `package.json` mein `"private": true` first line hone chahiye.

</Mistake>

<Mistake>

**`main` aur `exports` dono set karna aur sochna `main` hi kaam karega.** Jab `exports` present hai, modern Node aur bundlers `exports` ko **prioritize** karte hain; agar `.` entry `exports` mein galat path pe point karti hai toh `main` sahi hone ke bawajood import fail hota hai. Ek library publish karne se pehle `exports` map ko `npm pack` + actual import se test karo.

</Mistake>

<Mistake>

**JSON syntax break karna hand-edit se.** Trailing comma, single quotes, ya comment daal dena `package.json` mein — `npm install` turant `EJSONPARSE` error deta hai aur koi command nahi chalti. `npm pkg set`/`get` use karo, ya editor ka JSON linter on rakho.

</Mistake>

## Quick Revision

<QuickRevision>

- `package.json` = project ka **manifest**: identity + loading + commands + deps + rules. Plain JSON, no comments.
- **Required to publish**: `name`, `version` (SemVer `MAJOR.MINOR.PATCH`).
- `type`: `"commonjs"` (default) ya `"module"` — poore package ke `.js` ko CJS ya ESM banata hai.
- `main` = legacy single entry; `exports` = modern entry map **+ encapsulation** (unlisted paths deep-import se block).
- `bin` = package ke CLI executables (shebang chahiye). `scripts` = named commands; `test`/`start` special, `pre`/`post` auto-wrap.
- `dependencies` = runtime prod; `devDependencies` = build/test only (`-D`); `peerDependencies` = host provides (plugins); `optionalDependencies` = skip on install failure.
- `engines` = required Node/npm version — default warning, `engine-strict` se hard fail.
- `files` = publish whitelist (usually `["dist"]`); `private: true` = block `npm publish` — har app repo mein daalo.
- `npm init -y` = default file bina prompts; `npm pkg set/get/delete` = safe programmatic edit.
- Prod image: `npm ci --omit=dev` → devDependencies skip → chhota image, chhoti attack surface.

</QuickRevision>

## Practice

<Callout type="tip">

**Chhota:** `npm init -y` chalao. Phir `npm pkg set scripts.hello="node -e \"console.log(42)\""` aur `npm run hello` chala ke dekho. Phir `npm pkg get type` aur `npm pkg set type=module` karke dekho file mein kya badla.

**Medium:** Ek chhota project banao jismein `express` (`dependencies`) aur `nodemon` (`devDependencies`) ho. `npm ci --omit=dev` chala ke `node_modules` mein check karo `nodemon` hai ki nahi. Phir `nodemon` ko `dependencies` mein move karke phir se try karo aur farak note karo.

**Bada:** Ek do-file library banao (`index.js` + `internal.js`), `package.json` mein `"exports": { ".": "./index.js" }` set karo, phir `npm pack` se tarball banao. Tarball extract karke dekho `internal.js` kyun andar hai (ya nahi, `files` set karne pe). Phir ek dusre folder se us tarball ko `npm install ./billing-lib-1.0.0.tgz` karke `require("billing-lib/internal.js")` try karo aur dekho `exports` use kaise block karta hai.

</Callout>
