<SimpleDefinition>

**npm** is two things at once: a **command-line tool** that ships bundled with Node, and the **public registry** it downloads from at `registry.npmjs.org`. When you run `npm install <pkg>`, npm resolves a version, downloads that version's tarball, extracts it into `node_modules`, runs any lifecycle scripts the package declares, and updates `package.json` plus the lockfile. Packages install either **locally** (into the current project) or **globally** (`-g`, for command-line tools). **npx** runs a package's binary without permanently installing it.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Node install karte hi `npm` bhi aa jata hai — alag se kuch nahi karna padta. Har Node project mein tum `npm install` chalao ge, `package.json` dekho ge, aur `node_modules` folder ke saath deal karo ge. Isliye npm ka mental model saaf hona chahiye: **npm ek CLI hai, aur ek registry hai** — dono ko "npm" bolte hain, isliye confusion hoti hai.

### Ye kya hai — npm

- **npm CLI** — wo `npm` command jo terminal mein chalti hai (`npm install`, `npm run`, `npm publish`). Ye Node ke saath bundled aati hai.
- **npm registry** — ek bada public server (`registry.npmjs.org`) jisme lakhs open-source packages ke tarballs aur metadata rakhe hain. CLI isi server se baat karti hai.

Jab koi bolta hai "npm par ye package hai", uska matlab registry. Jab koi bolta hai "npm install chala do", uska matlab CLI.

### Ye kyun exist karta hai

Pehle log JavaScript libraries ko manually download karke apne project mein copy karte the — versioning ka koi tareeka nahi, update karna dard, transitive dependencies (dependency ki dependency) khud manage karni padti thi. npm ne ye teen problem solve ki:

- **ek central jagah** se packages milein
- har package ka **version** ho, aur tum range specify kar sako
- ek package ki dependencies **automatically** resolve aur install ho jayein

### Internally kaise kaam karta hai

`npm install express` chalane par step-by-step:

1. **Resolve** — npm registry se `express` ka metadata maangta hai (saare published versions ki list). Tumhare `package.json` ki range (jaise `^4.18.0`) ke against best matching version choose karta hai.
2. **Download** — us version ka `.tgz` tarball download karta hai. Ek local **cache** (`~/.npm/_cacache`) mein bhi rakhta hai taaki agli baar network hit na ho.
3. **Integrity check** — tarball ka SHA-512 hash verify karta hai lockfile / registry metadata ke against — taaki koi tampered tarball na aaye.
4. **Extract** — tarball ko `node_modules/express/` mein khol deta hai. Express ki apni dependencies (jaise `body-parser` nahi, but `qs`, `send`, etc.) bhi resolve hoti hain aur `node_modules` mein aati hain.
5. **Lifecycle scripts** — agar package `preinstall` / `install` / `postinstall` scripts declare karta hai (jaise native addon compile karna), wo chalti hain.
6. **Write** — `package.json` ke `dependencies` mein `express` add hota hai, aur `package-lock.json` poore resolved tree ke saath update hota hai.

### Simple real-life analogy

Registry ek **library (kitab-ghar)** hai — har kitab ke kai editions (versions). npm CLI wo **librarian** hai jise tum parchi dete ho ("mujhe express, koi bhi 4.x edition"). Librarian sahi edition dhoondta hai, uski jo referenced kitabein hain wo bhi nikaalta hai, sab tumhare **local shelf** (`node_modules`) pe rakh deta hai, aur register (`package-lock.json`) mein likh deta hai ki exactly kaunsi copy di.

### Code — line by line

```bash
# ek naya project shuru karo
npm init -y

# runtime dependency — production mein chahiye
npm install express

# dev-only dependency — sirf develop/test ke liye
npm install --save-dev nodemon

# global install — machine-wide CLI ban jata hai
npm install -g pm2

# install kuch nahi, sirf ek package ki binary ek baar chalao
npx create-react-app my-app

# lockfile se exactly waise hi install karo (CI ke liye)
npm ci
```

- `npm init -y` — bina sawaal poochhe ek default `package.json` bana deta hai (`-y` = "yes to all").
- `npm install express` — express ko resolve/download/extract karta hai, `dependencies` mein likhta hai.
- `npm install --save-dev nodemon` — `-D` bhi likh sakte ho; `devDependencies` mein jata hai.
- `npm install -g pm2` — project ke `node_modules` mein nahi, ek **global** location mein install hota hai; `pm2` command PATH mein aa jati hai.
- `npx create-react-app my-app` — `create-react-app` ko temporarily fetch karke uski binary chalata hai; permanent install nahi.
- `npm ci` — `package.json` nahi, seedha `package-lock.json` dekh ke exact tree install karta hai; pehle `node_modules` delete karta hai.

### Day-to-day use

- `npm install` (bina naam ke) — `package.json` ki saari dependencies laata hai; naya repo clone karne ke baad pehla command.
- `npm run <script>` — `package.json` ke `scripts` block se ek command chalata hai (`npm run dev`, `npm run build`).
- `npm run` (bina naam) — available scripts list karta hai.
- `npm ls` — installed dependency tree dikhata hai.
- `npm outdated` — kaunse packages ke naye versions available hain.
- `npm uninstall <pkg>` — hata deta hai aur `package.json` update karta hai.

### Kab local install karna chahiye (default)

- Har wo package jo tumhare **application code** `require`/`import` karega — `express`, `pg`, `lodash`.
- Har build/test tool jo project-specific version chahiye — `jest`, `typescript`, `eslint`. Team ke sab log same version paayein isliye ye `devDependencies` mein local hone chahiye, global nahi.

### Kab global (`-g`) install theek hai

- Sirf **standalone CLI tools** jo kisi ek project se bandhe nahi — `pm2`, `vercel`, `npm` khud, kabhi-kabhi `typescript` for quick scratch use.
- Even then, better hai `npx` use karna ya project mein local rakhna, kyunki global version machine-wide hota hai — do projects ko alag versions chahiye toh clash ho jata hai.

### Kab use nahi karna chahiye

- **Global install** ko project dependency ki tarah rely mat karo — CI machine ya naye teammate ke paas wo global package nahi hoga, build toot jayega. Jo cheez `package.json` mein nahi likhi, wo "exist hi nahi karti" doosron ke liye.
- `sudo npm install -g` — permission errors ko `sudo` se dabana galat hai; wo cache aur global folder ka ownership bigaad deta hai. Node version manager (`nvm`, `fnm`) use karo.

### Pros and cons

**Pros**

- Bahut bada ecosystem — jo bhi chahiye lagbhag mil jata hai.
- Node ke saath bundled — zero setup.
- Lockfile + integrity hashes se reproducible aur tamper-resistant installs.
- `scripts` se project ka har task ek jagah documented.

**Cons**

- `node_modules` bahut bada aur deep ho jata hai — "heaviest object in the universe" wala meme isi liye hai.
- Transitive dependencies ki wajah se supply-chain risk — ek chhoti dependency compromise ho toh tum bhi affected.
- Lifecycle scripts (`postinstall`) arbitrary code chalate hain install ke time.
- npm ka default install pnpm se slower aur disk-heavy hai.

### Alternatives

- **pnpm** — ek global **content-addressable store** rakhta hai aur `node_modules` mein hard-links banata hai; isliye 10 projects ek hi `lodash` version share karein toh disk pe ek hi copy. Fast, strict (phantom dependencies nahi milti).
- **Yarn** — Facebook ne banaya jab npm slow tha; Yarn 1 classic ya Yarn Berry (PnP mode, no `node_modules`). Ab npm kaafi catch up kar chuka hai.
- **Bun** — naya all-in-one runtime + package manager; `bun install` bahut fast, npm registry se hi compatible.
- Sab **same registry** (`registry.npmjs.org`) se hi packages laate hain — sirf resolution algorithm, disk layout, aur speed alag hai.

### node_modules structure — ek paragraph

Purane npm (v2) mein har dependency ki dependency **nested** hoti thi — `node_modules/a/node_modules/b/node_modules/c` — jisse Windows par path bahut lambe ho jate the aur same package ki 10 copies. npm v3+ ne **flat-ish** layout diya: jitna ho sake dependencies ko top-level `node_modules` mein **hoist** (uthana) kar do aur **dedupe** kar do, sirf jab do packages ko **conflicting versions** chahiye tabhi nesting. Isliye aaj `node_modules` ke top level pe wo packages bhi dikhte hain jo tumne khud install nahi kiye — wo transitive deps hain jo hoist ho gaye.

### Interview mein "Why not just install everything globally?"

> "Global installs project ke `package.json` mein record nahi hote, isliye wo reproducible nahi — CI ya naya developer ke paas wo package nahi hoga aur build silently toot jayega ya galat version chalega. Local install se har project apni exact versions pin karta hai lockfile ke through, aur `npm ci` se wahi tree har jagah banta hai. Global sirf machine-wide standalone CLIs ke liye rakhta hoon jaise `pm2`, aur one-off tools ke liye `npx` use karta hoon taaki kuch permanently install hi na ho."

</Hinglish>

<Callout type="tip">

`npm install <pkg>` aur `npm i <pkg>` same hai. `--save` ab default hai — alag se likhne ki zaroorat nahi; sirf `--save-dev` / `-D` explicitly likhna padta hai dev dependency ke liye.

</Callout>

## Real World Example

<RealWorld company="Vercel / Netlify build pipelines">

CI/CD platforms jaise Vercel har deploy pe ek fresh machine par tumhara repo clone karti hain aur `npm ci` chalati hain — `npm install` nahi. `npm ci` lockfile ko source of truth maanta hai: agar `package.json` aur `package-lock.json` match na karein toh fail ho jata hai, aur pehle `node_modules` ko poora delete karta hai. Isse har deploy exactly wahi dependency tree paata hai jo developer ke laptop pe tha. Yahi wajah hai ki lockfile ko git mein commit karna mandatory hai — CI usi pe depend karta hai.

</RealWorld>

<RealWorld company="create-react-app / create-next-app via npx">

Naya React ya Next.js project banane ke liye log `npx create-next-app` chalate hain. `npx` `create-next-app` package ko registry se fetch karta hai, uski binary ko ek baar chalata hai project scaffold karne ke liye, aur phir kuch permanent nahi chhodta. Agar tum `npm install -g create-next-app` karte toh ek purana version machine pe atak jata aur har naye project mein stale scaffolding milti — `npx` hamesha latest (ya specified) version laata hai.

</RealWorld>

## Numbers That Matter

<Numbers>

- npm registry par **3.5 million+** packages published hain — duniya ka sabse bada software registry.
- npm CLI Node ke saath bundled aati hai; Node 20 ke saath **npm 10** aata hai.
- npm ka local cache `~/.npm/_cacache` mein hota hai; `npm cache verify` se check, `npm cache clean --force` se clear.
- Integrity hash **SHA-512** hai (`sha512-...` prefix lockfile mein) — pehle SHA-1 tha, security ke liye upgrade hua.
- pnpm typically **half se bhi kam disk** leta hai multi-project setups mein, kyunki packages hard-linked ek global store se aate hain.
- `npm ci` `npm install` se **~2x tez** hota hai bade projects mein kyunki wo resolution skip karke seedha lockfile follow karta hai.

</Numbers>

## Interview Angle

<InterviewAngle>

Ye topic screening / first round mein aata hai, aksar aise: "`npm install` karne par exactly kya hota hai?" ya "local vs global install mein kya farak hai?" Interviewer dekhta hai ki tum daily kaam ke tools ko sirf muscle-memory se chalate ho ya samajhte bhi ho.

Achhe jawaab ka shape:

1. **Do cheezein** — "npm ek CLI hai aur ek registry, dono ko npm bolte hain."
2. **install ke steps** — "version resolve, tarball download + cache, integrity hash verify, `node_modules` mein extract, lifecycle scripts, `package.json` + lockfile update."
3. **local vs global** — "local default; jo code import karega wo local. Global sirf standalone CLIs. Global project ke lockfile mein record nahi hota isliye reproducible nahi."
4. **npx** — "binary ek baar chalao bina install kiye — scaffolding tools ke liye."
5. **install vs ci** — "`npm install` lock update kar sakta hai; `npm ci` lock ko exactly follow karta hai, CI ke liye."

Red flag: "`npm install` bas internet se code copy karta hai" — resolution, caching, integrity verification, aur lockfile ka role na bata pana.

</InterviewAngle>

## Common Mistakes

<Mistake>

**Global install pe production code ko depend karna.** `npm install -g typescript` karke `package.json` mein na likhna. Tumhare laptop pe chalega, CI pe `tsc: command not found` aayega. Rule: jo cheez `package.json` (`dependencies` ya `devDependencies`) mein nahi hai, wo dusron ke liye exist hi nahi karti.

</Mistake>

<Mistake>

**`node_modules` ko git mein commit kar dena.** Wo hazaaron files, platform-specific compiled binaries, aur megabytes ka bloat hai. `.gitignore` mein `node_modules/` daalo. Reproducibility `package-lock.json` deta hai, `node_modules` nahi — lockfile commit karo, folder nahi.

</Mistake>

<Mistake>

**Permission error aane par `sudo npm install` chala dena.** `sudo` global folder aur cache ka ownership `root` kar deta hai, jisse aage aur errors aati hain. Asli fix: Node ko `nvm` / `fnm` se user ke home directory mein install karo taaki `sudo` ki zaroorat hi na pade.

</Mistake>

<Mistake>

**`npm install` aur `npm ci` ko interchangeable samajhna.** CI pipeline mein `npm install` use karna lockfile ko chupke se modify kar sakta hai (agar range naye version ko allow kare), jisse "works on my machine" bugs aate hain. CI mein hamesha `npm ci` — wo lockfile se deviate hone par fail karta hai.

</Mistake>

<Mistake>

**Har chhoti utility ke liye package install karna.** `left-pad` type ki one-liner dependencies supply-chain surface badhati hain — har transitive dep ek trust decision hai. Pehle check karo ki 3-line ka code khud likha ja sakta hai kya, ya wo cheez already Node core / lodash mein hai kya.

</Mistake>

## Quick Revision

<QuickRevision>

- npm = **CLI** (jo command chalti hai) + **registry** (`registry.npmjs.org`, 3.5M+ packages). Dono ka naam npm.
- `npm install <pkg>` = resolve version, download + cache tarball, verify SHA-512, extract into `node_modules`, run lifecycle scripts, update `package.json` + `package-lock.json`.
- **Local** install (default) = project ke `node_modules` mein; jo code import kare wo local rakho.
- **Global** (`-g`) = machine-wide; sirf standalone CLIs (`pm2`, `vercel`). Lockfile mein record nahi hota → reproducible nahi.
- **npx** = package ki binary ek baar chalao bina permanent install ke — scaffolding tools ke liye ideal.
- `npm install` lock update kar sakta hai; **`npm ci`** lock ko exactly follow karta hai (CI ke liye), pehle `node_modules` delete karta hai.
- **pnpm** = hard-linked global store → bada disk saving; **Yarn**, **Bun** bhi alternatives, sab same registry use karte hain.
- `node_modules` **flat-ish** hai — npm v3+ dependencies ko top-level pe hoist + dedupe karta hai; conflict pe hi nesting.
- `node_modules/` **kabhi commit mat karo**; `package-lock.json` **hamesha commit karo**.
- `sudo npm install` mat chalao — Node ko `nvm`/`fnm` se install karo.

</QuickRevision>

## Practice

<Callout type="tip">

**Chhota:** Ek fresh folder mein `npm init -y` chalao, phir `npm install lodash`. `package.json` aur `package-lock.json` kholo — dekho `lodash` ki entry kahan aayi aur lock mein integrity hash kaisa dikhta hai. Phir `npm uninstall lodash` karke dekho dono files se kya hata.

**Medium:** `node_modules` delete karo, phir ek baar `npm install` aur ek baar (delete karke phir) `npm ci` chala ke time karo (`time npm ci`). Farak note karo. Phir `package-lock.json` mein ek version manually badal do aur `npm ci` chala ke dekho wo kaise fail karta hai.

**Bada:** Ek chhoti CLI script likho (`hello.js` jo `console.log("hi")` kare), `package.json` mein `"bin": { "myhello": "hello.js" }` add karo, phir `npm link` chala ke `myhello` ko globally available banao. Samjhao ki `npm link` `npm install -g` se kaise alag hai (symlink vs copy).

</Callout>
