<SimpleDefinition>

Modern Angular templates use block control flow: `@if` / `@else if` / `@else` for conditionals, `@for (item of items; track item.id)` with an `@empty` block for lists, and `@switch` / `@case` / `@default` for multi-branch rendering. It is built into the compiler — no imports — and replaces the older `*ngIf` and `*ngFor` structural directives.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Templates me hume conditions ("agar loading hai to spinner") aur loops ("har employee ke liye ek row") chahiye. Naya Angular (v17+) ye `@`-blocks se deta hai — pehle ye `*ngIf` / `*ngFor` directives se hota tha.

### What is it

**`@if`:**

```html
@if (loading()) {
  <app-spinner />
} @else if (error()) {
  <p class="error">{{ error() }}</p>
} @else {
  <app-employee-table [rows]="employees()" />
}
```

**`@for`:**

```html
<ul>
  @for (emp of employees(); track emp.id) {
    <li>{{ emp.firstName }} {{ emp.lastName }}</li>
  } @empty {
    <li>Koi employee nahi mila.</li>
  }
}
</ul>
```

**`@switch`:**

```html
@switch (employee.status) {
  @case ('active')   { <span class="badge green">Active</span> }
  @case ('on-leave') { <span class="badge amber">On Leave</span> }
  @default           { <span class="badge grey">Inactive</span> }
}
```

### Why do we need it — kyun naya syntax

Purana `*ngIf` / `*ngFor`:

- `CommonModule` (ya `NgIf`, `NgFor`) import karna padta tha — bhool jao to error.
- `*ngIf="x; else tmpl"` + `<ng-template #tmpl>` — else likhna verbose.
- `*ngFor` me `trackBy` **optional** tha — log skip karte the -> performance bugs.
- `*ngIf` + `*ngFor` ek hi element pe nahi lag sakte the.

Naya control flow:

- **Zero imports** — compiler feature.
- `@else` / `@empty` inline — readable.
- `track` **mandatory** in `@for` — performance by default.
- Thoda faster runtime (compiler optimized).

### How does it work

Compile time pe Angular in blocks ko efficient instructions me badal deta hai. `@if` DOM ko add/remove karta hai (hide nahi — element hata deta hai). `@for` `track` expression se items ki identity nikaalta hai aur list badalne pe DOM nodes reuse karta hai.

### `track` — sabse important detail

```html
@for (emp of employees(); track emp.id) { ... }
```

- `track emp.id` — Angular jaanta hai kaunsa DOM node kaunse item ka hai. List reorder/filter pe wo nodes **move** karta hai, dobin-scratch nahi banata.
- Bina identity ke: `track $index` — sirf tab jab items ka koi stable id nahi (aur list append-only ho).
- Galat `track` (jaise `track emp` jab har render naya object) = har baar poora re-render, `<input>` focus loss.

### Show it in our project

`EmployeeList` template:

```html
@if (loading()) {
  <app-skeleton-table />
} @else {
  <table>
    <tbody>
      @for (emp of pageItems(); track emp.id) {
        <app-employee-row [employee]="emp"
          (edit)="onEdit($event)" (delete)="onDelete($event)" />
      } @empty {
        <tr><td colspan="5">No employees match your filters.</td></tr>
      }
    </tbody>
  </table>
}
```

Har cell ke status badge ke liye `@switch`.

### Where is it used in day-to-day development

Har list screen (`@for` + `@empty`), har loading/error/empty state (`@if` chain), status/type-based rendering (`@switch`). Ye teen blocks practically har feature template me hote hain.

### Pros and cons

**Pros**

- No imports, less boilerplate, inline `@else`/`@empty`.
- `track` mandatory — performance galtiyan kam.
- Slightly faster than legacy directives.

**Cons**

- Purane tutorials/StackOverflow `*ngIf`/`*ngFor` me — mental translation.
- Legacy libraries jo `<ng-template>` context expect karti hain unke saath thoda friction.
- `@if` element ko DOM se hata deta hai — agar aap sirf CSS-hide chahte the to `[hidden]` / `[class]` use karo.

</Hinglish>

<Callout type="trap">

`@if (user)` element ko **DOM se remove** karta hai jab false — child components destroy ho jaate hain (state, scroll, focus gaya). Agar aap chahte ho element rahe par dikhe na, to `[hidden]="!user"` ya CSS use karo.

</Callout>

Ek dev ne pattern seekha, saari list screens same shape me ban jaati hain.

## Numbers That Matter

<Numbers>

- `@for` me `track` **syntactically required** — chhodne par compile error (legacy `*ngFor` me `trackBy` optional tha).
- Angular team ke benchmarks me new control flow legacy directives se roughly **up to 90% faster** kuch list-heavy cases me.
- `@if` supports `@else if` chains of any length + one `@else`.
- Ek automated migration hai: `ng generate @angular/core:control-flow` — poore codebase ke `*ngIf`/`*ngFor`/`*ngSwitch` ko blocks me convert karta hai.

</Numbers>

## Interview Angle

<InterviewAngle>

Bahut common (v17+ ke baad): "naya control flow kya hai?", "`@for` me `track` kyun mandatory?", "`@if` vs `[hidden]`?", "`*ngFor` se `@for` migrate kaise?".

Strong answer:

1. `@if`/`@else if`/`@else`, `@for` + `track` + `@empty`, `@switch`/`@case`/`@default` — compiler built-in, no imports.
2. `track` = item identity -> DOM node reuse on list change -> performance + preserved focus/scroll.
3. `@if` element ko DOM se add/remove karta hai (destroy/recreate), `[hidden]`/CSS sirf visually chhupata hai.
4. Migration: `ng g @angular/core:control-flow` schematic.

Red flag: "`@for` bina `track` ke chalega" — nahi, compile error; aur legacy me skip karna classic perf bug tha.

</InterviewAngle>

## Common Mistakes

<Mistake>

**`track $index` use karna jab list reorder/filter hoti hai.** `$index` position hai identity nahi — filter kar do to Angular galat rows reuse karega, `<input>` values / expanded states cross ho jaayenge. Stable `id` par track karo.

</Mistake>

<Mistake>

**`@if` se element hataana jab sirf visually hide karna tha.** `@if` child components destroy karta hai — unsaved form state, scroll position, focus sab gaya. Toggle-heavy panels ke liye `[hidden]` ya CSS.

</Mistake>

<Mistake>

**Purane `*ngIf="a && b as x"` patterns ko literally `@if` me copy karna.** `@if (data(); as d) { ... }` naya `as` syntax hai — `d` block ke andar available. Purana `; else` template ab `@else` block hai.

</Mistake>

<Mistake>

**`@for` ke andar bhaari expression `track` me.** `track computeKey(emp)` jo har item pe kaam karta hai — sasta rakho, ideally `emp.id`.

</Mistake>

<Mistake>

**`@empty` ko `@if (list.length === 0)` se replace karna.** `@for`'s `@empty` cleaner hai aur automatically list empty hone par render hota hai — extra condition maintain nahi karni.

</Mistake>

## Quick Revision

<QuickRevision>

- `@if (c) { } @else if (c2) { } @else { }` — compiler built-in, no imports.
- `@for (x of list; track x.id) { } @empty { }` — `track` is mandatory.
- `@switch (v) { @case ('a') { } @default { } }`.
- `track` gives item identity -> DOM node reuse on reorder/filter -> perf + preserved focus/scroll.
- Use `track x.id` (stable); `track $index` only for append-only lists with no id.
- `@if` adds/removes DOM (destroys children). To only hide visually, use `[hidden]` or CSS.
- Replaces `*ngIf`/`*ngFor`/`*ngSwitch`; migrate with `ng g @angular/core:control-flow`.
- New `@if (expr; as x) { }` binds the value inside the block.

</QuickRevision>

## Practice

<Callout type="tip">

**Chhota:** `EmployeeList` me ek `loading` signal banao. Template me `@if (loading()) { <p>Loading...</p> } @else { <ul>@for (e of employees(); track e.id) { <li>{{ e.firstName }}</li>} @empty { <li>Empty</li>}</ul> }`. `loading` toggle karke aur `employees` khaali karke teenon states dekho.

**Medium:** Employee status ke liye `@switch` add karo: `active` -> green badge, `on-leave` -> amber, warna grey. Ek dropdown se status badalke live badge change dekho.

**Bada:** Ek list banao 5 items ki, har `<li>` ke andar ek `<input>`. `@for` me pehle `track $index` use karo. Input me kuch type karo, phir ek button se list ko `reverse()` karo — dekho input values galat rows me chali gayin. Ab `track item.id` karo aur wahi test — ab values sahi rows ke saath move karti hain. Kya hua aur kyun, 4 line me likho.

</Callout>
