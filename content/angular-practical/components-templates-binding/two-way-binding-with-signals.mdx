<SimpleDefinition>

Two-way binding synchronises a value in both directions — class to view and view to class — with the `[(x)]="value"` "banana in a box" syntax. It is exactly a `[x]` property binding plus an `(xChange)` event binding. On native inputs it is provided by `ngModel` (from `FormsModule`); for your own components you expose a two-way input with the `model()` signal function.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Ab tak: interpolation/property = class -> view, event = view -> class. Two-way = **dono ek saath**, ek hi syntax me.

### What is it

```html
<input [(ngModel)]="name" />
```

`[(ngModel)]="name"` do cheezein karta hai:

1. `name` ki value input me daalta hai (`[ngModel]="name"`).
2. User type karein to `name` update karta hai (`(ngModelChange)="name = $event"`).

"Banana in a box": `[()]` — brackets (property) ke andar parentheses (event). Ye sirf syntactic sugar hai:

```html
<!-- ye -->
<input [(ngModel)]="name" />
<!-- exactly ye hai -->
<input [ngModel]="name" (ngModelChange)="name = $event" />
```

### Why do we need it — kyun

Chhote forms me har field ke liye alag `[value]` + `(input)` likhna repetitive hai. `[(ngModel)]` ek line me sync deta hai. Aur "component ka ek value parent ke saath sync rahe" pattern (jaise ek `<app-search-box>` jiska text parent ke saath sync ho) two-way se natural lagta hai.

### How does it work — the naming rule

Angular `[(foo)]` ko `[foo]` + `(fooChange)` me expand karta hai. Isliye kisi bhi input `x` ko two-way banane ke liye ek `xChange` output chahiye — **ya** aap `model()` use karo jo dono khud bana deta hai.

### `ngModel` — native inputs ke liye

```ts
import { FormsModule } from "@angular/forms";

@Component({
  imports: [FormsModule],
  template: `<input [(ngModel)]="email" name="email" /> <p>{{ email }}</p>`,
})
export class QuickForm {
  email = "";
}
```

- `FormsModule` import zaroori.
- `name` attribute chahiye jab input ek `<form>` ke andar ho.

### `model()` — apne components ke liye

```ts
import { Component, model } from "@angular/core";

@Component({
  selector: "app-search-box",
  template: `<input [value]="text()" (input)="text.set($any($event.target).value)" />`,
})
export class SearchBox {
  text = model<string>("");   // ek two-way signal input
}
```

Parent:

```html
<app-search-box [(text)]="query" />
<p>Searching for: {{ query }}</p>
```

`model()` ek writable signal hai jo automatically ek `textChange` output bhi expose karta hai — isliye parent `[(text)]` use kar sakta hai. Child ke andar `this.text()` read, `this.text.set(...)` write.

### Show it in our project

EMS me hum **reactive forms** use karenge bade forms (Add/Edit Employee) ke liye — wahaan `ngModel` nahi. Par two-way chhoti jagah useful:

- Ek `<app-search-box [(text)]="search">` toolbar me.
- Ek "items per page" `<select [(ngModel)]="pageSize">`.
- Ek toggle `<input type="checkbox" [(ngModel)]="showInactiveOnly">`.

### Where is it used in day-to-day development

Quick filters, toggles, search boxes, chhote settings forms. Reusable input-like components (`app-star-rating`, `app-tag-picker`) jinka value parent ke saath sync ho — `model()`. Bade forms me reactive forms preferred, two-way nahi.

### Pros and cons

**Pros**

- Ek line me bidirectional sync — kam boilerplate.
- `model()` reusable "input-like" components banana clean karta hai.
- Padhne me intent clear: "ye value dono taraf sync hai".

**Cons**

- Bade forms me `ngModel` per-field validation/state track karna messy — reactive forms behtar.
- `[(x)]` "magic" lag sakta hai jab tak `[x]` + `(xChange)` expansion na pata ho.
- Two-way overuse se data flow trace karna mushkil — kaun value badal raha hai clear nahi rehta.

</Hinglish>

<Callout type="tip">

Rule: chhoti local UI state (filter, toggle, search) -> two-way theek. Ek business form jisme validation, submit, dirty-tracking chahiye -> reactive forms, two-way nahi.

</Callout>

## Real World Example

<RealWorld company="List toolbars and filter bars">

EMS ki employee list ke toolbar me typically: ek search `<app-search-box [(text)]="filters.search">`, ek `<select [(ngModel)]="filters.departmentId">`, ek `<input type="checkbox" [(ngModel)]="filters.activeOnly">`. Teenon two-way, kyunki ye chhoti transient UI state hai jo turant ek query trigger karti hai. Actual employee **form** (naam, email, salary, validation) reactive forms se banta hai — wahan har field ka apna control, error state, aur validators chahiye.

</RealWorld>

## Numbers That Matter

<Numbers>

- `[(x)]` hamesha exactly **do** bindings me expand hota hai: `[x]` + `(xChange)`.
- `ngModel` ke liye **`FormsModule`** import zaroori — bina uske "Can't bind to 'ngModel'" error.
- `model()` Angular **v17.2+** ka feature hai; usse pehle two-way ke liye manual `@Input() x` + `@Output() xChange` likhna padta tha.
- Ek `<form>` ke andar har `ngModel` input ko ek unique **`name`** chahiye, warna form control register nahi hota.

</Numbers>

## Interview Angle

<InterviewAngle>

Common: "two-way binding kaise kaam karta hai?", "`[(ngModel)]` internally kya hai?", "apne component me two-way kaise banaoge?", "`ngModel` vs reactive forms?".

Strong answer:

1. `[(x)]` = `[x]` + `(xChange)` — pure syntactic sugar, "banana in a box".
2. Native inputs: `[(ngModel)]`, needs `FormsModule`.
3. Custom: `model()` signal — writable signal + auto `xChange` output.
4. Bade forms: reactive forms, two-way nahi — per-control validation/state.

Red flag: "`[(ngModel)]` ek special magic binding hai" — nahi, ye do standard bindings ka shorthand hai, aur naming convention `xChange` hai.

</InterviewAngle>

## Common Mistakes

<Mistake>

**`[(ngModel)]` use karna bina `FormsModule` import kiye.** Error: "Can't bind to 'ngModel' since it isn't a known property of 'input'". Component ke `imports` me `FormsModule` add karo.

</Mistake>

<Mistake>

**`<form>` ke andar `ngModel` input pe `name` attribute na dena.** Control register nahi hota, form value me field missing. Har `ngModel` ko `name="..."` do (ya `[ngModelOptions]="{standalone: true}"`).

</Mistake>

<Mistake>

**Custom component me `[(value)]` chahiye par `valueChange` output banana bhool jaana.** Ya to `@Input value` + `@Output valueChange` dono likho, ya `model()` use karo jo dono deta hai.

</Mistake>

<Mistake>

**Bade employee form ko `[(ngModel)]` se banana.** 12 fields, cross-field validation, async email check — `ngModel` me ye sab painful. Reactive forms use karo.

</Mistake>

<Mistake>

**Two-way overuse.** Har child value ko `[(x)]` karna data flow ko do-tarfa aur trace-karna-mushkil bana deta hai. Aksar `[x]` input + explicit `(action)` output cleaner hota hai (unidirectional).

</Mistake>

## Quick Revision

<QuickRevision>

- `[(x)]="v"` = `[x]="v"` + `(xChange)="v = $event"` — "banana in a box", pure shorthand.
- Native inputs: `[(ngModel)]`, requires `FormsModule` in `imports`.
- Inside a `<form>`, every `ngModel` needs a unique `name`.
- Custom components: `x = model<T>(initial)` — a writable signal + auto `xChange` output; read `x()`, write `x.set()`.
- `model()` is Angular v17.2+; before that use `@Input() x` + `@Output() xChange`.
- Use two-way for small transient UI state (filters, toggles, search); use reactive forms for real business forms.
- Overusing two-way makes data flow hard to trace — prefer `[input]` + `(output)` where a clear action exists.

</QuickRevision>

## Practice

<Callout type="tip">

**Chhota:** Ek component me `FormsModule` import karo aur `<input [(ngModel)]="name" />` + `<p>{{ name }}</p>` rakho. Type karke dekho `<p>` live update hota hai. Phir `[(ngModel)]` ko `[ngModel]` + `(ngModelChange)` me manually expand karke confirm karo same behaviour.

**Medium:** Ek `SearchBox` component banao jisme `text = model<string>("")`. Parent me `<app-search-box [(text)]="query" />` aur `{{ query }}` dikhao. Child ke andar ek "clear" button add karo jo `this.text.set("")` karta hai — confirm parent bhi clear ho jaata hai.

**Bada:** Ek toolbar banao 3 two-way controls ke saath: search (`model()` component), department `<select [(ngModel)]>`, aur "active only" `<input type="checkbox" [(ngModel)]>`. Teenon values ek `filters` object me rakho. Ek `{{ filters | json }}` dikhao. Phir socho aur likho: agar ye ek 12-field employee form hota, two-way approach kahan-kahan dukh deti — 4 concrete points.

</Callout>
