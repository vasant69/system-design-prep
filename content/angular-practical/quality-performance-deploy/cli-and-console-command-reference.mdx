<SimpleDefinition>

A practical cheat-sheet of the console commands you type day to day on an Angular project: the **Angular CLI** (`ng new`, `ng serve`, `ng generate`, `ng build`, `ng test`, `ng update`), **npm / npx** (`install`, `ci`, `run`, `audit`, `outdated`), and everyday **git** commands. Each has a one-line Hinglish note on *kya karta hai* and *kab use karo*.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Ye reference hai — yaad karne ki zaroorat nahi, samajhne aur laut kar dekhne ke liye.

### Angular CLI — `ng`

| Command | Kya karta hai (Hinglish) |
|---|---|
| `ng version` / `ng v` | Installed Angular CLI, Node, aur package versions dikhata hai. Bug report / debug me pehla command. |
| `ng new ems-frontend --routing --style=scss --ssr=false` | Naya Angular project banata hai. `--routing` = routes file, `--style=scss`, `--ssr=false` = client-only. |
| `ng serve` / `ng s` | Dev server chalata hai `http://localhost:4200` par, live-reload ke saath. In-memory build, optimize NAHI karta. |
| `ng serve --open` / `-o` | Wahi, plus browser khud khol deta hai. |
| `ng serve --port 4300` | Alag port par serve karo (4200 busy ho to). |
| `ng serve --configuration production` | Production settings ke saath serve (rarely; debugging prod-only issues). |
| `ng build` | Production static bundle banata hai `dist/<app>/browser/` me — minified, tree-shaken, hashed. **Yahi deploy hota hai.** |
| `ng build --configuration development` | Dev-config build (source maps on, no minify) — debugging ke liye. |
| `ng build --base-href /ems/` | App ko sub-path par deploy kar rahe ho to base href set karo. |
| `ng build --watch` | File change par rebuild karta rehta hai (CI/preview setups me). |
| `ng test` / `ng t` | Unit tests chalata hai (Karma/Jasmine) watch mode me. |
| `ng test --watch=false --browsers=ChromeHeadless` | CI mode — ek baar chalao, headless browser, exit code. |
| `ng test --code-coverage` | Coverage report (`coverage/` folder) generate karta hai. |
| `ng e2e` | End-to-end tests chalata hai (agar configured — Playwright/Cypress). |
| `ng lint` | Lint chalata hai (ESLint, agar `@angular-eslint` setup hai). |
| `ng generate component features/employees/employee-list` | Component banata hai (TS + HTML + styles + spec) sahi folder/naming me. Short: `ng g c ...`. |
| `ng g c ... --skip-tests` | Bina `.spec.ts` ke component. |
| `ng g c ... --inline-template --inline-style` | Chhote component ke liye sab ek file me. |
| `ng g s core/services/employee` | Service banata hai (`ng g service`). |
| `ng g guard core/guards/auth --functional` | Functional route guard (`CanActivateFn`) banata hai. |
| `ng g interceptor core/interceptors/auth` | HTTP interceptor (`HttpInterceptorFn`) banata hai. |
| `ng g pipe shared/pipes/time-ago` | Custom pipe banata hai. |
| `ng g directive shared/directives/has-permission` | Custom directive banata hai. |
| `ng g @angular/material:navigation` | Material schematic (agar Material added hai) — ready-made layout. |
| `ng add @angular/material` | Ek library install + configure karta hai (theming, animations set up). `npm install` se zyada — wiring bhi karta hai. |
| `ng add @angular/ssr` | Server-side rendering + hydration add karta hai. |
| `ng update` | Batata hai kaunse Angular packages outdated hain. |
| `ng update @angular/core @angular/cli` | Angular ko next major version par upgrade + automated code migrations chalata hai. Ek version at a time. |
| `ng config` | `angular.json` values ko command se read/set karta hai. |
| `ng cache clean` / `ng cache info` | Angular build cache clear / info. |
| `ng generate @angular/core:control-flow` | Poore codebase ke `*ngIf`/`*ngFor` ko `@if`/`@for` blocks me migrate karta hai. |
| `ng generate @angular/core:standalone` | NgModule-based code ko standalone me migrate karta hai (multi-step). |

**Rule:** project ke andar `npx ng ...` use karo — wo project-local CLI (jo `package.json` me pinned hai) chalata hai, global version mismatch se bacha jata hai.

### npm & npx

| Command | Kya karta hai (Hinglish) |
|---|---|
| `npm install` / `npm i` | `package.json` ke saare dependencies install karta hai `node_modules/` me. `package-lock.json` update ho sakti hai. |
| `npm ci` | Lockfile se **exactly** install karta hai, `node_modules/` pehle delete karke. CI me hamesha `ci`, `install` nahi — reproducible. |
| `npm i lodash-es` | Ek runtime dependency add karta hai (`dependencies`). |
| `npm i -D eslint` / `--save-dev` | Ek dev-only dependency add karta hai (`devDependencies`). |
| `npm i -g @angular/cli` | Angular CLI ko globally install karta hai (`ng` command system-wide). |
| `npm uninstall <pkg>` / `npm rm <pkg>` | Dependency hata deta hai. |
| `npm run <script>` | `package.json` ke `scripts` me define kiya command chalata hai (`npm run build` = `ng build`). |
| `npm start` | `scripts.start` (usually `ng serve`) ka shortcut. |
| `npm test` | `scripts.test` (usually `ng test`) ka shortcut. |
| `npm outdated` | Kaunse packages ka naya version available hai, table me. |
| `npm audit` | Known security vulnerabilities dikha hai dependency tree me. |
| `npm audit fix` | Safe automatic fixes apply karta hai (patch/minor bumps). |
| `npm audit --audit-level=high` | CI gate — high/critical vuln ho to non-zero exit. |
| `npm ls <pkg>` | Ek package kis version me, kis dependency ke through aaya — tree dikha hai. |
| `npm dedupe` | Duplicate nested dependencies flatten karta hai. |
| `npm cache clean --force` | npm cache clear (corrupt install debug me). |
| `npx <pkg>` | Ek package ko bina globally install kiye chalata hai (`npx serve dist/...`). |
| `npx ng <cmd>` | Project-local Angular CLI chalata hai — recommended over global `ng`. |
| `npm view <pkg> versions` | Ek package ke saare published versions. |
| `npm pkg set scripts.lint="ng lint"` | `package.json` ko command se edit karta hai. |

### git — rozmarra ke commands

| Command | Kya karta hai (Hinglish) |
|---|---|
| `git status` | Kaunsi files changed/staged/untracked hain. Commit se pehle hamesha dekho. |
| `git add <file>` / `git add -A` | Files ko staging area me daalo (commit ke liye ready). `-A` = sab. |
| `git add -p` | Interactively, hunk-by-hunk stage karo (ek file ke kuch changes only). |
| `git commit -m "message"` | Staged changes ka ek snapshot banao message ke saath. |
| `git commit -am "message"` | Tracked (already-known) files ko stage + commit ek saath (untracked skip). |
| `git log --oneline -10` | Last 10 commits ek-ek line me. |
| `git diff` | Unstaged changes dikhao. `git diff --staged` = staged changes. |
| `git branch feature/employee-form` | Nayi branch banao (switch nahi karta). |
| `git switch -c feature/x` / `git checkout -b feature/x` | Nayi branch banao **aur** us par switch karo. |
| `git switch main` / `git checkout main` | `main` branch par jao. |
| `git merge feature/x` | `feature/x` ko current branch me merge karo. |
| `git rebase main` | Current branch ke commits ko `main` ke upar dobara lagao (linear history). |
| `git pull` | Remote se latest fetch + merge (ya rebase, config ke hisaab se). |
| `git fetch` | Remote se updates laao par merge mat karo (dekhne ke liye). |
| `git push` | Local commits ko remote par bhejo. |
| `git push -u origin feature/x` | Nayi branch ko pehli baar push + upstream set karo. |
| `git stash` | Abhi ke uncommitted changes ko side me rakho (working tree clean). |
| `git stash pop` | Side me rakhe changes wapas laao. |
| `git restore <file>` | Ek file ke unstaged changes discard karo (working copy revert). |
| `git restore --staged <file>` | File ko unstage karo (changes rahenge). |
| `git reset --soft HEAD~1` | Last commit undo karo par changes staged rakho. |
| `git reset --hard HEAD~1` | Last commit **aur** uske changes dono delete karo. Careful — data loss. |
| `git revert <hash>` | Ek purane commit ke changes ko ek naye commit se undo karo (history safe). |
| `git cherry-pick <hash>` | Ek specific commit ko current branch par apply karo. |
| `git clean -fd` | Untracked files/folders delete karo (build junk). Careful. |
| `git remote -v` | Configured remotes (origin URL etc.). |
| `git config user.name "..."` | Git identity set karo (commit author). |
| `.gitignore` | Isme listed files git track nahi karta (`node_modules/`, `dist/`, `.env`). |

### The typical daily loop

```bash
git switch -c feature/employee-form   # nayi branch
npx ng g c features/employees/employee-form
npx ng serve                          # kaam karo, browser auto-reload
npm test -- --watch=false             # tests
git add -A && git commit -m "Add employee form"
git push -u origin feature/employee-form
# PR raise karo, review, merge
git switch main && git pull            # main update
```

### Show it in our project

Poora EMS is exact loop se bana: har feature ek branch, `ng g` se files, `ng serve` par dev, `ng test` + `ng lint` + `ng build` CI me, `git` se version control, aur `npm ci` + deploy pipeline me.

### Where is it used in day-to-day development

Har din. `ng serve` background me, `ng g` naye files ke liye, `git status`/`add`/`commit`/`push` har change par, `npm ci` naya machine setup / CI me, `ng build` release se pehle.

### Pros and cons

**Pros**

- CLI se consistent, scriptable, reproducible workflow — koi manual boilerplate nahi.
- `npm ci` + lockfile = har jagah same build.
- Git commands ek baar seekh lo to har project me same.

**Cons**

- Bahut commands/flags — beginners ko overwhelming; is reference ki zaroorat hi isliye hai.
- `git reset --hard` / `git clean -fd` / `git push --force` galat use se data loss.
- Global vs local CLI version mismatch confusing errors deta hai (`npx ng` se bacho).

</Hinglish>

<Callout type="tip">

Do commands jo **irreversible-ish** hain, sochke chalao: `git reset --hard` (commits + changes delete), `git clean -fd` (untracked files delete), `git push --force` (remote history overwrite — team branch par kabhi nahi). Baaki sab git operations recoverable hote hain (`git reflog` se).

</Callout>

## Numbers That Matter

<Numbers>

- `ng serve` port default: **4200**. `ng build` output: `dist/<app>/browser/`.
- `npm ci` deletes `node_modules/` and installs **exactly** from the lockfile — use it in CI, not `npm install`.
- `ng g c <path/name>` creates ~**4** files (`.ts`, `.html`, styles, `.spec.ts`).
- `ng update` upgrades **one major version at a time** with automated migrations.
- Irreversible-ish: `git reset --hard`, `git clean -fd`, `git push --force` — everything else is recoverable via `git reflog`.
- Prefer `npx ng ...` inside a project to avoid global-vs-local CLI version mismatch.

</Numbers>

## Interview Angle

<InterviewAngle>

Common (screening / practical rounds): "naya project kaise start karoge?", "`ng serve` vs `ng build`?", "`ng g` kya deta hai?", "`npm install` vs `npm ci`?", "feature branch ka git flow?", "`git merge` vs `git rebase`?".

Strong answer:

1. `ng new` → scaffold; `ng serve` = dev server (in-memory, no optimize); `ng build` = optimized `dist/` for deploy.
2. `ng g c/s/guard/interceptor/pipe/directive` = correct files + naming + spec.
3. `npm ci` = lockfile-exact clean install (CI); `npm install` = resolve + maybe update the lock.
4. Git flow: branch → `ng g` + code → lint/test/build → `add`/`commit`/`push` → PR → merge → pull `main`.
5. `merge` keeps history as-is (a merge commit); `rebase` replays commits for a linear history (don't rebase shared branches).

Red flag: "`git push --force` on a shared branch" or "`npm install` in CI".

</InterviewAngle>

## Common Mistakes

<Mistake>

**`npm install` in CI instead of `npm ci`.** Non-reproducible; a transitive version can drift. `npm ci` is lockfile-exact.

</Mistake>

<Mistake>

**Deploying `ng serve` output.** It writes nothing to disk. Deploy `ng build`'s `dist/<app>/browser/`.

</Mistake>

<Mistake>

**Global `ng` version ≠ project version.** Confusing errors. Use `npx ng ...` inside the project.

</Mistake>

<Mistake>

**`git commit -am` and expecting new files in.** `-a` only stages **tracked** files; new files need `git add` first.

</Mistake>

<Mistake>

**`git reset --hard` / `git clean -fd` without thinking.** Deletes commits/changes/untracked files. Check `git status` first; `git stash` if unsure.

</Mistake>

<Mistake>

**`git push --force` on `main` or a shared branch.** Overwrites everyone's history. Use `--force-with-lease` only on your own branch, and rarely.

</Mistake>

## Quick Revision

<QuickRevision>

- **`ng`**: `new` (scaffold), `serve` (dev server, 4200, no optimize), `build` (optimized `dist/<app>/browser/`), `test` (`--watch=false --browsers=ChromeHeadless` for CI), `lint`, `g c|s|guard|interceptor|pipe|directive` (files + spec), `add <lib>` (install + configure), `update @angular/core @angular/cli` (one major at a time).
- Use `npx ng ...` inside a project to dodge global-vs-local CLI mismatch.
- **npm**: `install` (resolve + maybe update lock), `ci` (lockfile-exact clean install — CI), `run <script>`, `audit` / `audit --audit-level=high`, `outdated`, `ls <pkg>`, `-D` for dev deps, `-g` for global.
- **git daily**: `status` → `add -A` / `add -p` → `commit -m` → `push -u origin <branch>`; `switch -c` for a new branch; `merge` (merge commit) vs `rebase` (linear, not on shared branches); `stash` / `stash pop`; `restore` (discard) / `restore --staged` (unstage); `revert <hash>` (safe undo).
- Irreversible-ish, think first: `git reset --hard`, `git clean -fd`, `git push --force`. Everything else is recoverable via `git reflog`.
- Never deploy `ng serve` output; never `npm install` in CI; never `git push --force` a shared branch.

</QuickRevision>

## Practice

<Callout type="tip">

**Chhota:** In a scratch project, run `ng version`, `ng g c demo`, `ng g s demo`, `ng g pipe demo` and note the files each creates. Then `npm run` (with no args) to list the available scripts.

**Medium:** Do one full loop: `git switch -c feature/demo`, generate a component, `ng serve` and change something, `ng build` (read `dist/`), `git add -A && git commit -m "..."`, `git push -u origin feature/demo`. Then `git switch main`, `git stash` an experiment, `git stash pop` it back.

**Bada:** Deliberately break things and recover: make a bad commit and undo it with `git reset --soft HEAD~1` (keep changes), then `git reset --hard HEAD~1` (lose them) and recover the lost commit via `git reflog` + `git cherry-pick`. Run `npm ci` on a fresh clone and time it vs `npm install`. Run `npm audit` and `npm outdated` and read the output. 8-line note on which commands are safe vs destructive.

</Callout>
