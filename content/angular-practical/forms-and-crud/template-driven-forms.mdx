<SimpleDefinition>

Template-driven forms build the form model *in the template* using `ngModel` and form directives; Angular infers a `FormGroup`/`FormControl` tree behind the scenes. They need `FormsModule`. They are quick and readable for small forms (login, a search filter), but become hard to manage for large forms with cross-field or async validation — that is where reactive forms take over.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Angular me forms ke do "flavours" hain: template-driven aur reactive. Ye topic pehla — jahan form ki structure HTML me likhi jaati hai.

### The login form

```ts
@Component({
  selector: "app-login-page",
  imports: [FormsModule],
  template: `
    <form #f="ngForm" (ngSubmit)="onSubmit(f)">
      <input name="email" [(ngModel)]="model.email" required email #email="ngModel" />
      @if (email.invalid && email.touched) {
        <small>Valid email required.</small>
      }

      <input name="password" type="password" [(ngModel)]="model.password" required minlength="6" />

      <button type="submit" [disabled]="f.invalid || submitting()">Log in</button>
    </form>
  `,
})
export class LoginPage {
  model = { email: "", password: "" };
  submitting = signal(false);

  onSubmit(f: NgForm) {
    if (f.invalid) return;
    // f.value === { email, password }
  }
}
```

Line by line:

- `imports: [FormsModule]` — required for `ngModel`, `ngForm`, `ngSubmit`.
- `#f="ngForm"` — a template ref to the `NgForm` directive Angular auto-attaches to `<form>`. `f.value`, `f.valid`, `f.controls`.
- `(ngSubmit)` — fires on submit and prevents the native page reload.
- `name="email"` + `[(ngModel)]` — registers a control named `email` in `f`. **`name` is mandatory** inside a `<form>`.
- `required`, `email`, `minlength="6"` — built-in validator directives (plain HTML-like attributes).
- `#email="ngModel"` — a ref to that control's `NgModel` — `email.invalid`, `email.touched`, `email.errors`.
- `[disabled]="f.invalid"` — disable submit until valid.

### Control state flags

Every control (and the form) exposes: `valid`/`invalid`, `pristine`/`dirty` (has the value changed?), `touched`/`untouched` (has it been blurred?), `pending` (async validator running). Show errors on `invalid && touched` so you don't yell at the user before they've typed.

### `ngModelGroup` for sub-objects

```html
<div ngModelGroup="address">
  <input name="city" ngModel />
  <input name="pin" ngModel />
</div>
<!-- f.value === { ..., address: { city, pin } } -->
```

### When template-driven is fine

- Login, a single search field, a small settings toggle group.
- ~1–6 fields, simple built-in validation, no cross-field rules.
- You want minimal TS.

### When it hurts

- 10+ fields, conditional fields, cross-field validation ("confirm password", "end date after start date"), async validation (email uniqueness), dynamic add/remove rows (`FormArray`).
- Programmatic control (disable a field based on another, reset parts, patch values from an API).
- Unit-testing the form logic — it's tangled with the template.

### Show it in our project

The EMS **login** form is template-driven (`FormsModule`, `ngForm`, two fields). Everything bigger — Add/Edit Employee, filters with async checks, Leave Request — uses **reactive** forms (next topics).

### Where is it used in day-to-day development

Login screens, quick filters, small config panels, prototypes. Many teams use reactive forms everywhere for consistency and reserve template-driven for genuinely tiny forms.

### Pros and cons

**Pros**

- Fast to write, little TS, familiar HTML-attribute validation.
- Two-way binding keeps the model in sync automatically.
- Great for small, static forms.

**Cons**

- Form model is implicit (inferred from the template) — hard to see the shape at a glance.
- Cross-field and async validation are awkward.
- `name` attributes are mandatory and easy to forget.
- Validation runs synchronously in the template; complex logic leaks into HTML.
- Harder to unit-test in isolation.

</Hinglish>

<Callout type="tip">

Rule of thumb: **login / 1–3 fields / no cross-field rules -> template-driven is fine.** Anything with real validation logic, dynamic fields, or that you want to test -> reactive forms.

</Callout>

## Real World Example

<RealWorld company="EMS login">

The EMS login page is the one template-driven form in the app: `<form #f="ngForm">`, an `email` control with `required email`, a `password` control with `required minlength`, and a submit button disabled while `f.invalid`. It is ~15 lines of template and needs almost no TypeScript. Every other form — where fields depend on each other, where the server does uniqueness checks, where data is loaded and patched in — is a reactive form, because that model scales and template-driven doesn't.

</RealWorld>

## Numbers That Matter

<Numbers>

- Template-driven forms require `FormsModule` in the component's `imports`.
- Every control inside a `<form>` needs a unique `name` attribute to register.
- Control state flags: `valid/invalid`, `pristine/dirty`, `touched/untouched`, `pending`.
- Show errors on `invalid && touched` (or `&& dirty`) — not immediately on load.
- Practical ceiling: roughly **6 fields** and only built-in, single-field validation before reactive forms pay off.

</Numbers>

## Interview Angle

<InterviewAngle>

Common: "template-driven vs reactive forms?", "`ngForm` kya hai?", "`name` attribute kyun zaroori?", "form state flags?".

Strong answer:

1. Template-driven: model built in the template via `ngModel` + directives; Angular infers the `FormGroup`. Needs `FormsModule`.
2. `#f="ngForm"` gives the auto-attached `NgForm` (`f.value`, `f.valid`). `(ngSubmit)` prevents reload.
3. Each control needs a `name`; `#x="ngModel"` exposes its state (`invalid`, `touched`, `errors`).
4. Good for small/static forms; reactive for cross-field, async, dynamic, or testable forms.
5. Show errors on `invalid && touched`.

Red flag: "sab forms template-driven se banata hoon" — cross-field/async/dynamic forms become a mess.

</InterviewAngle>

## Common Mistakes

<Mistake>

**`FormsModule` import karna bhool jaana.** "Can't bind to 'ngModel'". Add it to the component's `imports`.

</Mistake>

<Mistake>

**`<form>` ke andar `ngModel` input par `name` na dena.** The control doesn't register; `f.value` misses the field (and a console warning).

</Mistake>

<Mistake>

**Errors immediately on load dikhana.** Gate them with `invalid && touched` (or `dirty`) so a fresh form isn't covered in red.

</Mistake>

<Mistake>

**Cross-field validation ko template-driven me force karna.** "Confirm password" via a form-level directive is awkward. Use reactive forms with a group validator.

</Mistake>

<Mistake>

**Native `(submit)` bina prevent.** Use `(ngSubmit)` — it prevents the page reload and gives you the form.

</Mistake>

## Quick Revision

<QuickRevision>

- Template-driven: the form model is built in the template with `ngModel` + validator directives; Angular infers the `FormGroup`. Needs `FormsModule`.
- `#f="ngForm"` -> the auto-attached `NgForm` (`f.value`, `f.valid`, `f.controls`). Use `(ngSubmit)` (prevents reload).
- Every control inside `<form>` needs a `name`; `#x="ngModel"` exposes `invalid`, `touched`, `dirty`, `errors`, `pending`.
- Show errors on `invalid && touched` (or `dirty`).
- `ngModelGroup="address"` nests a sub-object in `f.value`.
- Use for small, static forms (login, quick filters). Reactive forms for cross-field/async/dynamic/testable forms.

</QuickRevision>

## Practice

<Callout type="tip">

**Chhota:** Login form banao `FormsModule` ke saath: `email` (`required email`), `password` (`required minlength="6"`), `<form #f="ngForm" (ngSubmit)="onSubmit(f)">`, submit disabled on `f.invalid`. `f.value` ko console me dekho.

**Medium:** Har field ke neeche `#ctrl="ngModel"` se error message dikhao, gated on `ctrl.invalid && ctrl.touched`. Fresh form par koi error nahi; blur karke error; type karke error clear.

**Bada:** Isi form me ek "Confirm password" field add karo jo password se match hona chahiye. Template-driven me ye kitna awkward hai note karo (form-level directive banani padegi). Phir socho aur likho — 4 line — ki reactive forms me ye ek `group validator` se kaise clean hota.

</Callout>
