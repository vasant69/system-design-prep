<SimpleDefinition>

The delete flow: a reusable `ConfirmModal` (not `window.confirm`) gathers intent, then the row is removed one of two ways — **refetch** the list after `DELETE` (simple, always consistent, one extra request) or **optimistic**: remove the row from local state immediately, call `DELETE`, and restore it on failure (instant UX, rollback logic). Both need a loading indicator on the action and a clear error path.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Delete chhota lagta hai par isme 3 real decisions hain: confirm kaise, list update kaise, aur failure kaise.

### 1. Confirm — a reusable modal, not `window.confirm`

```ts
@Component({ selector: "app-confirm-modal", changeDetection: ChangeDetectionStrategy.OnPush, /* ... */ })
export class ConfirmModal {
  open = input(false);
  title = input("Are you sure?");
  message = input("");
  confirmText = input("Delete");
  danger = input(true);
  confirmed = output<void>();
  cancelled = output<void>();
}
```

Parent:

```ts
pendingDelete = signal<Employee | null>(null);

askDelete(emp: Employee) { this.pendingDelete.set(emp); }

confirmDelete() {
  const emp = this.pendingDelete();
  if (emp) this.doDelete(emp);
  this.pendingDelete.set(null);
}
```

```html
<app-confirm-modal
  [open]="pendingDelete() !== null"
  [title]="'Delete employee?'"
  [message]="pendingDelete()?.fullName + ' will be removed.'"
  (confirmed)="confirmDelete()"
  (cancelled)="pendingDelete.set(null)" />
```

`window.confirm` blocks the thread, can't be styled, isn't testable, and looks out of place. A modal component is reusable across delete/discard/leave flows.

### 2a. Refetch approach (simple, recommended default)

```ts
doDelete(emp: Employee) {
  this.deletingId.set(emp.id);
  this.api.remove(emp.id).pipe(finalize(() => this.deletingId.set(null))).subscribe({
    next: () => { this.toast.success("Deleted"); this.reload(); },
    error: (e: AppError) => this.toast.error(e.message),
  });
}
```

- `deletingId` signal -> a spinner on that row's delete button.
- After success, `reload()` refetches the current page (server is the source of truth).
- Downside: a network round-trip before the row disappears; the current page/count can shift.

### 2b. Optimistic approach (instant, more code)

```ts
doDelete(emp: Employee) {
  const snapshot = this.employees();
  this.employees.update(list => list.filter(e => e.id !== emp.id));   // remove now

  this.api.remove(emp.id).subscribe({
    next: () => this.toast.success("Deleted"),
    error: (e: AppError) => {
      this.employees.set(snapshot);                                   // rollback
      this.toast.error("Couldn't delete — restored");
    },
  });
}
```

- The row vanishes immediately — feels instant.
- On failure, restore the snapshot and tell the user.
- Edge cases: the user may have paged/filtered before the error returns (restore into a now-different view), and pagination totals need adjusting. Encapsulate this in a store so every list doesn't reinvent it.

### 3. Bulk delete

Same choice, scaled: confirm "Delete 12 employees?", then either `forkJoin(ids.map(id => api.remove(id)))` + refetch, or optimistic removal of all selected + rollback the ones that failed. Show partial-failure results ("10 deleted, 2 failed").

### Which to use

- **Refetch**: default. Simple, always consistent, fine for admin CRUD where a 300ms delay is invisible.
- **Optimistic**: high-interaction lists, slow networks, or where instant feedback matters (mobile). Worth the rollback code only when the UX gain is real.

### Show it in our project

EMS `EmployeeListPage`: a shared `ConfirmModal`, a `deletingId` signal for the row spinner, and **refetch** after delete by default. The `EmployeesStore` also exposes an optimistic `deleteEmployee(id)` used in the bulk-actions bar, with snapshot rollback.

### Where is it used in day-to-day development

Every list with a delete action, every "archive", every bulk action. The confirm-modal + list-update + error pattern repeats constantly — worth putting in a store or a small helper.

### Pros and cons

**Refetch — Pros:** trivial, always matches the server, no rollback logic. **Cons:** a visible delay; page/count can jump.

**Optimistic — Pros:** instant, feels native. **Cons:** snapshot/rollback code, edge cases (paged away, totals, concurrent edits), harder to test.

</Hinglish>

## Real World Example

<RealWorld company="EMS delete + bulk archive">

Clicking the trash icon on an employee row opens the app's `ConfirmModal` ("Delete Aarav Sharma?"). Confirm -> the button shows a spinner (`deletingId`), `DELETE /employees/42` runs, a "Deleted" toast appears, and the list refetches — the row is gone and the count updates from the server. In the bulk-actions bar, "Archive 8 selected" uses the store's optimistic path: all 8 rows disappear instantly, `forkJoin` fires the requests, and if 2 fail those 2 reappear with a "6 archived, 2 failed" toast. Same confirm modal, two update strategies chosen per context.

</RealWorld>

## Numbers That Matter

<Numbers>

- `window.confirm()` blocks the JS thread and can't be styled or unit-tested — use a modal component.
- Refetch after delete = **one extra request**; always consistent with the server.
- Optimistic delete = **zero perceived delay**, but needs a snapshot + rollback and total/pagination adjustments.
- Bulk delete: `forkJoin(ids.map(remove))` runs them in parallel; report partial failures ("10 ok, 2 failed").
- Put a per-row `deletingId` signal so only the affected button shows a spinner.

</Numbers>

## Common Mistakes

<Mistake>

**`window.confirm()` in production.** Blocks the thread, unstyleable, untestable, off-brand. Use a modal component.

</Mistake>

<Mistake>

**Optimistic delete without a snapshot.** On failure you can't restore the exact previous state (order, pagination). Capture `const snapshot = this.employees()` first.

</Mistake>

<Mistake>

**A global "loading" spinner for a single row delete.** Blanks the whole list. Use a per-row `deletingId`.

</Mistake>

<Mistake>

**Optimistic delete but ignoring pagination totals.** The row is gone but "Showing 20 of 84" still says 84. Adjust the total or refetch.

</Mistake>

<Mistake>

**Bulk delete that stops on the first failure.** `forkJoin` errors if any inner errors. Use per-request `catchError` and report which ones failed.

</Mistake>

## Quick Revision

<QuickRevision>

- Confirm with a reusable `ConfirmModal` (`open` input, `confirmed`/`cancelled` outputs) — never `window.confirm` in production.
- Default: **refetch** the list after `DELETE` — simple, always consistent, one extra request.
- Optimistic: capture `const snapshot = state()`, remove the row now, `DELETE`, `state.set(snapshot)` + error toast on failure. Instant UX, more edge cases (paged away, totals, testing).
- Per-row `deletingId` signal for a targeted spinner, not a global one.
- Bulk: `forkJoin(ids.map(id => remove(id).pipe(catchError(...))))`, then report partial failures.
- Encapsulate the optimistic delete + rollback in a store so lists don't reinvent it.

</QuickRevision>
