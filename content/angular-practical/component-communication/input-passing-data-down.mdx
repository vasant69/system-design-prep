<SimpleDefinition>

An input lets a parent component pass a value into a child via a template binding: `<app-employee-card [employee]="selected" />`. The classic form is the `@Input()` decorator on a property; modern Angular adds `input()` — a signal-based input supporting `input.required()`, default values, aliases, and value transforms. Data flows one way: parent to child.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Ab tak humne single components dekhe. Real apps me components ek tree banate hain — parent apne children ko data deta hai. Wo "data neeche bhejna" **inputs** se hota hai.

### What is it — classic `@Input()`

```ts
import { Component, Input } from "@angular/core";

@Component({ selector: "app-employee-card", templateUrl: "./employee-card.html" })
export class EmployeeCard {
  @Input() employee!: Employee;
  @Input() showActions = false;
}
```

Parent:

```html
<app-employee-card [employee]="selectedEmployee" [showActions]="true" />
```

- `@Input() employee` — parent `[employee]="..."` se value bhejta hai.
- `!` (definite assignment) — batata hai "parent zaroor dega".
- `showActions = false` — default value agar parent na de.

### Modern — `input()` signal function

```ts
import { Component, input } from "@angular/core";

@Component({ selector: "app-employee-card", templateUrl: "./employee-card.html" })
export class EmployeeCard {
  employee = input.required<Employee>();
  showActions = input(false);
  badgeColor = input("grey", { alias: "color" });
}
```

- `input.required<Employee>()` — mandatory; parent na de to **compile error**.
- `input(false)` — optional, default `false`.
- `input("grey", { alias: "color" })` — bahar naam `color`, andar `badgeColor`.
- Ye **signals** hain — template me `employee()`, class me `this.employee()`.

Template:

```html
<h3>{{ employee().firstName }} {{ employee().lastName }}</h3>
@if (showActions()) { <button>Edit</button> }
```

### `input()` ke faayde `@Input()` par

- **Required inputs** compile-time enforced.
- Signal hai — `computed()` me directly use, OnPush ke saath perfect.
- **Transform** built-in: `input(0, { transform: numberAttribute })` — string `"5"` ko number `5`.
- No `ngOnChanges` boilerplate — signal change par `computed`/`effect` react karte hain.

### Why do we need inputs — kyun

Reusability. Ek `EmployeeCard` banao jo koi bhi employee dikha sake. List me 50 cards, dashboard me 3, search results me N — sab same component, alag `[employee]`. Bina input ke aapko har jagah alag component likhna padta.

### Data flow — one way, parent se child

Input **one-way** hai. Child ko `employee` ka naam badalna ho to wo parent ko **event** (`@Output`) bhejta hai — child directly parent ki state nahi badalta. Ye "unidirectional data flow" predictable debugging deta hai.

### `@Input` transforms aur setters

Classic:

```ts
@Input({ transform: booleanAttribute }) disabled = false;
// <app-x disabled>  ->  disabled === true (no value needed)
```

Setter form (react on change, classic):

```ts
private _id = 0;
@Input() set employeeId(value: number) {
  this._id = value;
  this.loadEmployee(value);
}
```

Modern equivalent: `id = input.required<number>()` + `effect(() => this.loadEmployee(this.id()))` — ya better, ek `computed`/resource.

### Show it in our project

`EmployeeCard`:

```ts
export class EmployeeCard {
  employee = input.required<Employee>();
  selectable = input(false, { transform: booleanAttribute });
  fullName = computed(() => `${this.employee().firstName} ${this.employee().lastName}`);
}
```

Used in the list:

```html
@for (emp of pageItems(); track emp.id) {
  <app-employee-card [employee]="emp" selectable />
}
```

### Where is it used in day-to-day development

Har reusable component: cards, tables, rows, badges, form fields, modals (title/body), charts (data). Practically har non-page component ke paas 1–6 inputs hote hain.

### Pros and cons

**Pros**

- Reusable components — ek definition, N uses.
- One-way flow — predictable, debuggable.
- `input()` — required enforced, signal-native, transforms built-in.

**Cons**

- `@Input()` + `ngOnChanges` (classic) verbose for reacting to changes.
- Bahut saare inputs (8+) = component doing too much; group into one config object or split.
- Mutating an input object inside the child (`employee().name = "x"`) — parent ko surprise, OnPush breaks.

</Hinglish>

<Callout type="tip">

Naye code me `input()` use karo. `@Input()` samajhna zaroori hai (existing codebases, tutorials), par greenfield me signal inputs cleaner hain — khaaskar `input.required()` aur OnPush ke saath.

</Callout>

## Numbers That Matter

<Numbers>

- `input.required<T>()` — parent binding missing -> **build-time** error (not a runtime surprise).
- Signal input read: `this.x()` in class, `x()` in template — always called, never bare `x`.
- Built-in transforms: `booleanAttribute` (`<x disabled>` -> `true`), `numberAttribute` (`"5"` -> `5`).
- A component with more than ~7 inputs is a common "split me" smell.

</Numbers>

## Interview Angle

<InterviewAngle>

Very common: "`@Input` kaise kaam karta hai?", "`input()` signal vs `@Input()` decorator?", "input change pe react kaise?", "required input?".

Strong answer:

1. `@Input()` / `input()` — parent se child, one-way, via `[prop]="expr"`.
2. `input.required<T>()` — mandatory, compile-enforced; `input(default)` — optional.
3. Signal input: read with `x()`, use in `computed`/`effect`; no `ngOnChanges` needed.
4. Classic reaction: `ngOnChanges(SimpleChanges)` or an `@Input set`.
5. Never mutate the input object in the child — emit an event instead.

Red flag: "child input ko directly modify karke parent update kar deta hoon" — breaks one-way flow and OnPush.

</InterviewAngle>

## Common Mistakes

<Mistake>

**Signal input ko bare use karna: `{{ employee.firstName }}`.** Signal hai — call karna padta hai: `{{ employee().firstName }}`. Bare `employee` ek function reference deta hai.

</Mistake>

<Mistake>

**Input object ko child me mutate karna.** `this.employee().isActive = false` — parent ki state chupke se badli, OnPush parents update nahi honge, aur data flow trace karna impossible. Event emit karo.

</Mistake>

<Mistake>

**`@Input() x!: T` par `!` laga kar parent ko dena bhoolna.** Runtime `undefined`, template crash. `input.required()` ye compile-time catch karta hai.

</Mistake>

<Mistake>

**`ngOnInit` me input use karna assume karke wo constructor me set hai.** Inputs `ngOnInit` se pehle set hote hain (theek), par `constructor` me nahi. Signal inputs se ye confusion khatam.

</Mistake>

<Mistake>

**8+ inputs ek component pe.** Component overloaded. Ek `config` object input, ya component ko chhote pieces me todo.

</Mistake>

## Quick Revision

<QuickRevision>

- Input = parent -> child data via `[prop]="expr"`; one-way.
- Classic: `@Input() x` (+ `!` or default). Modern: `x = input(default)` / `input.required<T>()`.
- Signal input: read as `x()` everywhere; works in `computed`/`effect`; no `ngOnChanges` needed.
- Alias: `input(v, { alias: "outer" })`. Transform: `input(0, { transform: numberAttribute })`, `booleanAttribute`.
- React to change (classic): `ngOnChanges(SimpleChanges)` or `@Input set`.
- Never mutate the input object in the child — emit an event.
- More than ~7 inputs = split the component or pass one config object.

</QuickRevision>

## Practice

<Callout type="tip">

**Chhota:** `EmployeeCard` ko `employee = input.required<Employee>()` do. `EmployeeList` se `@for` me `[employee]="emp"` bind karo. Template me `employee().firstName` etc. Ek jagah `[employee]` hata ke compile error dekho.

**Medium:** `EmployeeCard` me `selectable = input(false, { transform: booleanAttribute })` add karo. `<app-employee-card selectable [employee]="emp" />` (no value) se `selectable()` `true` hona chahiye. `computed()` `fullName` add karo aur template me use karo.

**Bada:** `StatCard` component banao `label`, `value`, `trend` (number) inputs ke saath. `trend` par `[class.up]="trend() > 0"` `[class.down]="trend() < 0"`. Dashboard me 4 stat cards render karo alag data se. Phir jaan-boojh ke child me `this.value` mutate karne ki koshish karo (signal input read-only hai) — dekho TypeScript kya bolta hai, aur likho kyun ye by-design safe hai.

</Callout>
