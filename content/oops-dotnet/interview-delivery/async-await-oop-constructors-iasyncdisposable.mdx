<SimpleDefinition>

C# does not allow async constructors because a constructor must return a fully-constructed object synchronously, while async fundamentally means "returns a `Task` representing future completion" — the two contracts are incompatible; the standard workaround is a static async factory method, and `IAsyncDisposable`/`await using` provide the async equivalent of deterministic cleanup for resources whose dispose logic itself needs to be asynchronous.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Ye topic OOP aur async/await ke intersection pe hai — aur yahin par bahut candidates surprise ho jaate hain jab unhe pata chalta hai ki `public async Task MyClass()` jaisa constructor likhna hi possible nahi hai. Interviewer isko specifically isliye poochta hai kyunki iska jawaab test karta hai ki tumhe C#'s type contracts ki actual samajh hai, sirf syntax memorize nahi kiya.

### Async constructor kyun nahi ban sakta

Ek constructor ka contract fixed hai: jab `new MyClass()` return karta hai, object **fully constructed** hona chahiye — synchronously, usi call ke andar. Koi bhi cheez jo constructor return karta hai wo hamesha `MyClass` hi hota hai, kabhi `Task<MyClass>` nahi ho sakta — C# me constructors ka koi return type declare karne ka syntax hi nahi hai, wo implicitly instance type hi return karte hain.

Ab `async` ka fundamental contract dekho: ek `async` method turant return **nahi** karta actual result — wo ek `Task` (ya `Task<T>`) return karta hai jo represent karta hai "ye kaam future me kabhi complete hoga." Ye do contracts directly conflict karte hain — constructor ko object ABHI, fully-ready chahiye; async method sirf ek "promise" deta hai ki result baad me aayega. Isliye compiler `async` keyword ko constructor ke saath allow hi nahi karta — ye ek language-level restriction hai, workaround nahi hai.

### Real-world workaround — static async factory method

Jab constructor ke andar genuinely async kaam karna ho (jaise ek remote config load karna, ek async DB connection open karna), standard pattern hai: constructor ko **private** rakho (ya minimal sync setup tak limit karo), aur ek `public static async Task<T>` factory method expose karo jo actual async initialization karke fully-ready object return kare. Caller `await MyClass.CreateAsync(...)` call karta hai, `new MyClass()` nahi.

Ye pattern itna common hai ki isko almost ek naming convention mil gaya hai — `CreateAsync`, `InitAsync`, `ConnectAsync` jaise method names. Interviewer ke liye ye ek acha signal hai agar tum bina soche is pattern ka naam bol sako.

### IAsyncDisposable aur await using

`IDisposable.Dispose()` hamesha synchronous hai — agar cleanup logic khud async hai (jaise ek network connection ko gracefully close karna, jisme ek async flush call lagta hai), to `Dispose()` ke andar `.Wait()` ya `.Result` call karna padta, jo **blocking** hai aur deadlock risk create karta hai (especially ASP.NET Core jaise sync-context-sensitive environments me, though modern ASP.NET Core sync context nahi use karta, phir bhi thread-pool starvation ka risk rehta hai).

`IAsyncDisposable` isko solve karta hai — ek `DisposeAsync()` method jo `ValueTask` return karta hai, genuinely async cleanup allow karta hai. `await using` statement (`using` ka async version) automatically `DisposeAsync()` call karta hai jab scope khatam ho, bilkul `using` ki tarah lekin non-blocking.

Ek class dono `IDisposable` aur `IAsyncDisposable` implement kar sakti hai — sync callers ke liye `Dispose()`, async callers ke liye `DisposeAsync()`, dono paths available rehte hain.

### Code Examples

**Minimal example — async factory pattern:**

```csharp
public class RemoteConfigClient
{
    private readonly string _config;

    // Constructor stays private/sync-only — no async work here
    private RemoteConfigClient(string config) => _config = config;

    public static async Task<RemoteConfigClient> CreateAsync(string url)
    {
        using var http = new HttpClient();
        var config = await http.GetStringAsync(url);
        return new RemoteConfigClient(config); // fully ready before returning
    }
}

// Usage — no "new", always via the factory
var client = await RemoteConfigClient.CreateAsync("https://config.internal/app");
```

**Real ASP.NET Core example — IAsyncDisposable for an async DB session wrapper:**

```csharp
public class AsyncOrderSession : IAsyncDisposable
{
    private readonly AppDbContext _db;
    public AsyncOrderSession(AppDbContext db) => _db = db;

    public async Task<Order> PlaceOrderAsync(CreateOrderDto dto)
    {
        var order = new Order { ProductId = dto.ProductId, Quantity = dto.Quantity };
        _db.Orders.Add(order);
        await _db.SaveChangesAsync();
        return order;
    }

    public async ValueTask DisposeAsync()
    {
        // e.g. flushing a buffered audit log asynchronously before closing
        await _db.DisposeAsync();
    }
}

// Controller usage
[HttpPost]
public async Task<IActionResult> Create(CreateOrderDto dto)
{
    await using var session = new AsyncOrderSession(_dbContext);
    var order = await session.PlaceOrderAsync(dto);
    return CreatedAtAction(nameof(Create), new { id = order.Id }, order);
}

// If DisposeAsync() were skipped and .Dispose() called .Result internally instead:
// risk of thread-pool starvation under load — blocking calls inside async paths
// don't scale the same way non-blocking await chains do
```

## Interview Angle

<InterviewAngle>

**Say this out loud:** "Constructor ka contract hai — return hote hi object fully-ready hona chahiye, synchronously. `async` method fundamentally ek `Task` return karta hai jo future completion represent karta hai — ye do contracts incompatible hain, isliye C# async constructors allow hi nahi karta. Jab mujhe genuinely async initialization chahiye hoti hai, main ek private constructor rakhta hoon aur ek `public static async Task<T> CreateAsync()` factory method expose karta hoon. Aur agar cleanup khud async hai — jaise ek connection ko gracefully close karna — to main `IAsyncDisposable` implement karta hoon aur `await using` use karta hoon, taaki blocking `.Wait()`/`.Result` calls se bachoon jo thread-pool starvation cause kar sakte hain."

**Almost-guaranteed follow-up:** "Agar tumhare paas ek class hai jo dono sync aur async callers serve karti hai, to `IDisposable` aur `IAsyncDisposable` dono implement kaise karoge bina code duplicate kiye?" — jawaab: `Dispose()` ke andar `DisposeAsyncCore()` jaisa shared helper call karo (sync context me `.GetAwaiter().GetResult()` ke through, sparingly), ya dono paths ko explicitly alag rakho agar underlying resource genuinely dono support karta hai.

</InterviewAngle>

## Common Mistakes

<Mistake>

`public async MyClass()` jaisa syntax likhne ki koshish karna — ye compile hi nahi hota, kyunki constructors return type declare hi nahi karte, `async` ke liye jagah hi nahi hai syntax me.

</Mistake>

<Mistake>

`Dispose()` ke andar async cleanup ko `.Result` ya `.Wait()` se force-synchronous banana — ye deadlock/thread-pool-starvation risk create karta hai, especially high-throughput API paths me.

</Mistake>

<Mistake>

Static factory method ko `New` jaisa naam dena instead of `CreateAsync`/`InitAsync` — koi hard rule nahi hai lekin `Async` suffix na hona teammates ko confuse karta hai ki method blocking hai ya not.

</Mistake>

<Mistake>

`IAsyncDisposable` implement karke bhi `await using` ki jagah plain `using` likh dena — is case me `Dispose()` call hoga agar wo bhi implemented hai, ya compile error agar sirf `IAsyncDisposable` hai — dono ka syntax alag hai, mix mat karo.

</Mistake>

<Mistake>

Ye maan lena ki har class jo async work karti hai usko `IAsyncDisposable` chahiye — agar cleanup khud sync hai (bas ek in-memory list clear karna), plain `IDisposable` hi kaafi hai, unnecessary complexity mat add karo.

</Mistake>

## Quick Revision

<QuickRevision>

- C# has no async constructors — a constructor must return a fully-built object synchronously, `async` returns a `Task` instead
- Standard workaround: private/minimal constructor + `public static async Task<T> CreateAsync(...)` factory method
- `IAsyncDisposable.DisposeAsync()` returns `ValueTask`, enabling genuinely async cleanup logic
- `await using` is the async equivalent of `using` — calls `DisposeAsync()` non-blocking when scope ends
- Never call `.Wait()`/`.Result` inside `Dispose()` to force-sync an async cleanup — real deadlock/starvation risk
- A class can implement both `IDisposable` and `IAsyncDisposable` for dual sync/async callers
- `IAsyncDisposable`/`await using` shipped in C# 8.0 / .NET Core 3.0 (2019)
- `EF Core`'s `DbContext` is a real-world `IAsyncDisposable` example you'll already have used

</QuickRevision>
