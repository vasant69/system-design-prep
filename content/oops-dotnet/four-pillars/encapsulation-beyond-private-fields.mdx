<SimpleDefinition>

Encapsulation is the OOP principle of bundling an object's state with the behavior that operates on it, and restricting direct external access to that state so the object can enforce its own invariants — guaranteeing it can never be observed in an invalid state.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Bahut candidates encapsulation ko "fields ko private karo, upar se getter-setter laga do" bol ke khatam kar dete hain. Ye definition technically galat nahi hai, lekin ye **incomplete** hai — aur interviewer isi incompleteness ko turant pakad leta hai. Sirf private field + public auto-property (`{ get; set; }`) likh dena encapsulation nahi hai agar setter me koi validation nahi hai — wo sirf ek zyada verbose public field hai. Real encapsulation ka payoff ek hi cheez hai: **invariant protection** — object hamesha guarantee de sake ki wo kabhi bhi invalid state me exist hi nahi kar sakta, kyunki state ko modify karne ka ek hi raasta hai: khud object ke apne validated methods/properties.

### Invariant kya hota hai, aur kyun matter karta hai

Invariant ek aisa rule hai jo object ke poore lifetime me hamesha true rehna chahiye — jaise "Order.Total kabhi negative nahi ho sakta", ya "Percentage.Value hamesha 0 aur 100 ke beech ho". Agar `Total` ek public settable field hai, koi bhi caller kahin se bhi `order.Total = -500` likh sakta hai — koi validation nahi, invariant silently toot jaata hai, aur bug production me kahin aur surface hota hai jahan se debug karna mushkil hota hai. Encapsulation isko ek jagah pe lock karta hai: `Total` ka set sirf `private` hai, aur external code sirf `AddItem()`, `RemoveItem()`, `ApplyDiscount()` jaise methods ke through interact kar sakta hai — jinke andar validation logic hai. Ab invariant violate karna **compile-time pe hi impossible** ho jaata hai, kisi runtime check ki zaroorat nahi.

### Trivial getter-setter vs real encapsulation

Ye distinction crisp bolna zaroori hai: agar tumhara property sirf `public int Age { get; set; }` hai, koi validation nahi, to ye Java-style boilerplate hai jo kuch protect nahi karta — field ko directly public rakhne jaisa hi hai, bas ek extra method call ka overhead. Real encapsulation tab shuru hota hai jab setter (ya koi method) me **logic** ho — validation, recalculation, ya side effect. C# me isko likhne ke teen tareeke hain: (1) `private set` — sirf class ke andar hi set ho sakta hai, external world ke liye read-only; (2) `init` — sirf construction ke time set ho sakta hai (C# 9); (3) full property with a body — jahan setter ke andar explicit validation ho. Kaunsa use karna hai, depend karta hai ki invariant construction-time hai (use `init` ya constructor validation) ya lifetime ke through hi baar-baar enforce hona hai (use a method ya validated setter).

### Encapsulation kahan zyada ho jaata hai

Ek real senior-level nuance: har single field ko "encapsulate" karne ke naam pe trivial `private` field + pointless public getter-setter pair banana bhi ek anti-pattern hai — isse sirf boilerplate badhta hai, koi invariant protect nahi hota. Encapsulation sirf tab lagao jahan actually ek invariant hai jo protect karna zaroori hai. Doosri taraf, agar ek class me bahut saari inter-dependent invariants hain jo saath me enforce karni padti hain, class bahut bada aur "God object" jaisa ho sakta hai — us case me responsibility ko chhote, focused classes me split karna better design hota hai.

### Code Examples

**Minimal example — invariant enforced at construction, no invalid instance can ever exist:**

```csharp
public class Percentage
{
    public int Value { get; }

    public Percentage(int value)
    {
        if (value < 0 || value > 100)
            throw new ArgumentOutOfRangeException(nameof(value), "Percentage must be 0-100");
        Value = value;
    }
}

var discount = new Percentage(15);   // fine
var bad = new Percentage(150);       // throws — a Percentage(150) object can NEVER exist
```

**Real ASP.NET Core example — Order enforcing invariants across multiple mutating methods:**

```csharp
public class Order
{
    private readonly List<OrderItem> _items = new();
    public IReadOnlyList<OrderItem> Items => _items;
    public decimal Total { get; private set; }

    public void AddItem(string productId, int quantity, decimal unitPrice)
    {
        if (quantity <= 0) throw new ArgumentException("Quantity must be positive");
        _items.Add(new OrderItem(productId, quantity, unitPrice));
        Total += quantity * unitPrice;
    }

    public void ApplyDiscount(decimal amount)
    {
        if (amount > Total) throw new InvalidOperationException("Discount can't exceed order total");
        Total -= amount;
    }
}

// If Total were `public decimal Total { get; set; }` instead:
// var order = new Order();
// order.Total = -999;
// No exception, no warning — the invariant "Total is never negative" is silently gone,
// and any code downstream (invoicing, payment capture) that trusted this invariant now breaks.
```

`OrderService` sirf `AddItem`/`ApplyDiscount` ke through hi `Order` ko modify karta hai — kabhi bhi directly `Total` set nahi karta, kyunki compiler hi allow nahi karega (`private set`). Ye hi encapsulation ka real, production-grade payoff hai.

</Hinglish>

### Kab Kya Depth Chahiye

<Callout type="tip">

**SDE-1 level answer:** "Fields private rakho, public properties/methods ke through access do" — ek simple example ke saath (jaise `private set`).

**SDE-3/Senior level answer:** Invariant-protection framing use karo — "encapsulation guarantee deta hai ki object kabhi invalid state me exist nahi kar sakta, kyunki mutation sirf validated code paths se hoti hai." Ye bhi bata do ki trivial getter-setter (bina validation ke) encapsulation nahi hai, aur over-encapsulation (har field ke liye pointless wrapper) bhi ek anti-pattern hai — balance dikhana signal deta hai ki tumne isko production code me actually socha hai, textbook se copy nahi kiya.

</Callout>

## Real World Example

<RealWorld company="Microsoft">

.NET ka `System.String` class encapsulation ka ek canonical example hai — string immutable hai, matlab ek baar create hone ke baad uska internal character buffer kabhi external code se mutate nahi ho sakta. Koi bhi "mutating" operation (`Replace`, `ToUpper`, `Substring`) actually ek naya `string` instance return karta hai, original ko touch nahi karta. Ye ek invariant hai — "is exact string value ke baad kabhi change nahi hoga" — jo poori tarah encapsulation se enforce hoti hai, aur isi wajah se strings thread-safe hain bina kisi lock ke.

</RealWorld>

<RealWorld company="A Fintech Wallet API">

Ek typical Indian fintech wallet backend (Paytm/PhonePe-style) me `Wallet.Balance` kabhi bhi public settable property nahi hoti — sirf `Credit(decimal amount)` aur `Debit(decimal amount)` methods se hi change hoti hai, jinke andar "balance kabhi negative nahi ho sakta" invariant enforce hota hai, aur har mutation ek audit log entry bhi generate karti hai. Agar `Balance` public settable hoti, ek buggy background job ya ek missed validation kisi user ka balance silently negative ya galat kar sakta tha — regulatory audit me ye seedha compliance failure ban jaata.

</RealWorld>

## Numbers That Matter

<Numbers>

- Auto-implemented properties (`{ get; set; }`) shipped in C# 3.0 (2007) — before that, every property needed a manually written backing field
- `private set` and `init` (C# 9, 2020) generate no public setter in the compiled IL at all — invalid mutation is a compile-time error, not a runtime check
- `System.String` has been immutable since .NET's first release — every "mutating" string method allocates a new string object
- A class with zero enforced invariants (all public settable auto-properties) behaves identically, at the type-safety level, to a plain data struct with no OOP benefit
- `readonly` fields (assignable only in the constructor or at declaration) are a stronger construction-time guarantee than `private set`, which can still change from inside the class after construction

</Numbers>

## Interview Angle

<InterviewAngle>

**Say this out loud:** "Encapsulation sirf 'fields private karo' nahi hai — real payoff ye hai ki object apne invariants khud enforce kar sake, matlab wo kabhi bhi invalid state me exist hi nahi kar sakta. Isliye main state ko private/protected rakhta hoon aur sirf validated methods ya properties (`private set`, `init`, ya explicit validation waala setter) ke through mutation allow karta hoon — jaise ek `Order.Total` kabhi negative nahi ho sakta agar sirf `AddItem`/`ApplyDiscount` hi usko touch karte hain. Trivial getter-setter jisme koi validation na ho, wo technically encapsulation nahi hai, wo bas ek relabeled public field hai."

Ye answer signal karta hai ki tumhe "why" pata hai, sirf "how" nahi. **Almost-guaranteed follow-up:** "Agar do properties ko hamesha sync me rehna hai (jaise `Total` aur `Items`), sirf auto-properties se ye kaise enforce karoge?" — jiska jawaab hai: auto-properties se nahi, ek method (jaise `AddItem`) chahiye jo dono ko atomically update kare.

</InterviewAngle>

## Common Mistakes

<Mistake>

Sochna ki `private` field + bina-validation-waali public auto-property = encapsulation. Agar setter me koi logic hi nahi hai, ye sirf ek verbose public field hai — koi invariant protect nahi ho rahi.

</Mistake>

<Mistake>

Interview me "invariant" word use na kar paana — bas "data hide karna" bolte reh jaana. Interviewer specifically ye sunna chahta hai ki tumhe pata hai encapsulation ka concrete, measurable payoff kya hai.

</Mistake>

<Mistake>

Har single field ke liye ek trivial `private` field + wrapper property bana dena, chahe koi invariant enforce ho ya na ho — ye sirf boilerplate hai. Encapsulation tabhi lagao jahan actually kuch protect karna hai.

</Mistake>

<Mistake>

Encapsulation aur abstraction ko same samajh lena — encapsulation state ko protect karta hai (kaun modify kar sakta hai), abstraction complexity ko chhupata hai (kya expose hota hai). Dono related hain lekin alag concerns hain — agla topic isi distinction pe hai.

</Mistake>

<Mistake>

`readonly` aur `private set` ko interchangeable samajhna. `readonly` field sirf constructor/declaration me set ho sakti hai — uske baad class ke andar se bhi nahi. `private set` waali property class ke andar kahin bhi (koi bhi method se) reassign ho sakti hai, sirf external world se nahi.

</Mistake>

## Quick Revision

<QuickRevision>

- Encapsulation's real payoff is invariant protection — an object can never be observed in an invalid state
- Private field + auto-property with no validation is NOT encapsulation, it's a relabeled public field
- Use `private set`/`init` for construction-time guarantees, a validated method for lifetime-long invariants
- Invalid mutation attempts should fail at compile time (no public setter exists), not just at runtime
- Don't over-encapsulate — a trivial wrapper property with no logic adds boilerplate without benefit
- `readonly` is stricter than `private set`: readonly can't change even from inside the class after construction
- Encapsulation protects STATE; abstraction (next topic) hides COMPLEXITY — don't conflate the two
- Always have a concrete invariant example ready (e.g. balance never negative) for the interview

</QuickRevision>
