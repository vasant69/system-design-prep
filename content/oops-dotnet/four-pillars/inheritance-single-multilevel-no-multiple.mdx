<SimpleDefinition>

Inheritance is the OOP mechanism by which a class (the derived class) acquires the members of another class (the base class), enabling code reuse and an is-a relationship; C# allows a class to inherit from exactly one base class, but permits implementing any number of interfaces.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Inheritance ka basic idea sabko pata hota hai — "ek class doosri class se properties/methods reuse kar leti hai." Interview me interesting part yahan se shuru hota hai: single aur multilevel inheritance ka syntax easy hai, lekin real question ye hota hai — "C# multiple class inheritance kyun allow nahi karta, aur agar wahi reuse chahiye to kaise karoge?" Isi ka jawaab crisp dena hi is topic ka asli test hai.

### Single aur multilevel — syntax revision

**Single inheritance**: ek class, ek hi direct base class.

```csharp
public class Employee
{
    public string Name { get; init; } = "";
    public virtual decimal CalculateSalary() => 30000;
}

public class Manager : Employee
{
    public decimal TeamBonus { get; init; }
    public override decimal CalculateSalary() => base.CalculateSalary() + TeamBonus;
}
```

**Multilevel inheritance**: ek chain — A se B inherit, B se C inherit. Har level pichhle level ka sab kuch (jo `private` nahi hai) paata hai.

```csharp
public class Employee { /* ... */ }
public class Manager : Employee { /* ... */ }
public class SeniorManager : Manager
{
    public int DirectReportsCount { get; init; }
}
```

`SeniorManager` object Employee aur Manager dono ke members access kar sakta hai (jo `public`/`protected` hain) — chain top se bottom tak flow karti hai.

### Multiple class inheritance — C# ne isko clearly mana kyun kiya

C# me `class C : A, B` (do classes se ek saath inherit) syntax hi invalid hai — compile error. Wajah hai **diamond problem**: socho `A` aur `B` dono ek method `Describe()` define karte hain, aur `C` dono se inherit karta hai. Ab jab `C` ka object `Describe()` call kare, compiler kis wale `Describe()` ko chuне — `A` ka ya `B` ka? Dono valid candidates hain, koi unambiguous answer nahi hai. C++ jaisi languages me ye allowed hai (aur genuinely confusing bugs create karta hai — "virtual inheritance" jaisa complex workaround chahiye hota hai), C# ne design-time hi isko disallow kar diya taaki ye ambiguity kabhi exist hi na kare.

### Interfaces se same reuse goal, bina ambiguity ke

Yahan interesting part hai: C# ek class ko **multiple interfaces** implement karne deta hai bina kisi ambiguity ke — kyunki interface method me (default interface methods se pehle) koi implementation hoti hi nahi thi, sirf signature. Agar `IA` aur `IB` dono `Describe()` declare karte hain, aur `C` dono implement karta hai, `C` khud apna ek `Describe()` likhta hai jo dono contracts satisfy karta hai — koi ambiguity nahi, kyunki implementation ek hi jagah (C ke andar) hai. Default interface methods (C# 8+) ke saath ye thoda tricky ho sakta hai agar dono interfaces apna default implementation dein — us case me compiler explicit resolution maangta hai (poora detail Module 3 ke diamond-problem topic me).

Practical takeaway: agar tumhe multiple sources se behavior chahiye, C# ka idiomatic tareeka hai — ek base class se inherit karo (agar genuinely "is-a" hai aur shared implementation chahiye), aur baaki capabilities ke liye interfaces implement karo. Jaise `class Manager : Employee, IReportable, IAuditable` — ek base class, do interfaces, koi ambiguity nahi.

### Kab inheritance use karna, kab nahi

Inheritance sabse zyada misuse hone waala OOP tool hai. Rule of thumb: sirf tab use karo jab genuinely ek "is-a" relationship ho AND derived class ko base class ka poora behavior "honor" karna chahiye (Liskov Substitution — agla module). Agar sirf code reuse chahiye bina real "is-a" ke, **composition** better hota hai — ek class doosri class ko field ke through hold kare, uske methods delegate kare. Deep inheritance chains (4-5 levels) fragile ho jaate hain — base class me ek chhota change neeche har derived class ko unpredictably affect kar sakta hai ("fragile base class problem").

### Code Examples

**Minimal example — multilevel chain:**

```csharp
public class Vehicle
{
    public string Brand { get; init; } = "";
    public virtual string Describe() => $"{Brand} vehicle";
}

public class Car : Vehicle
{
    public int Doors { get; init; }
}

public class SportsCar : Car
{
    public int TopSpeedKmph { get; init; }
    public override string Describe() => $"{base.Describe()}, sports car, top speed {TopSpeedKmph} km/h";
}

var sc = new SportsCar { Brand = "Tata", Doors = 2, TopSpeedKmph = 260 };
Console.WriteLine(sc.Describe());
// "Tata vehicle, sports car, top speed 260 km/h" — SportsCar has Vehicle's Brand,
// Car's Doors, and its own TopSpeedKmph, all via a 3-level chain
```

**Real ASP.NET Core example — one base class, multiple interface capabilities:**

```csharp
public interface IAuditable
{
    DateTime CreatedAt { get; }
}

public interface ISoftDeletable
{
    bool IsDeleted { get; set; }
}

public abstract class EntityBase
{
    public int Id { get; init; }
}

public class Order : EntityBase, IAuditable, ISoftDeletable
{
    public DateTime CreatedAt { get; init; } = DateTime.UtcNow;
    public bool IsDeleted { get; set; }
    public decimal Total { get; set; }
}
```

`Order` ek hi base class (`EntityBase`) se inherit karta hai — is-a relationship, `Id` shared implementation — aur do interfaces implement karta hai, jo cross-cutting capabilities hain (audit tracking, soft-delete) jo kayi unrelated entities me common ho sakti hain bina inheritance chain share kiye.

</Hinglish>

### Kab Kya Depth Chahiye

<Callout type="tip">

**SDE-1 level answer:** Single/multilevel syntax bata do, aur "C# multiple class inheritance allow nahi karta, interfaces use karte hain uske liye" — itna kaafi hai.

**SDE-3/Senior level answer:** Diamond problem ko exact mechanism ke saath explain karo (ambiguous method resolution), interfaces kyun ye problem avoid karte hain (implementation ek hi jagah — implementing class — hoti hai), aur "fragile base class" ka real-world consequence bolo — deep inheritance chains ko production me maintain karna kyun mushkil hota hai, aur kab composition better choice hoti hai.

</Callout>

## Real World Example

<RealWorld company="Microsoft">

ASP.NET Core ka `ControllerBase`/`Controller` hierarchy khud single inheritance ka example hai — har API controller `ControllerBase` se (ya MVC views chahiye to `Controller` se, jo `ControllerBase` se hi derive karta hai — ek multilevel chain) extend karta hai, aur `ActionResult`, `ModelState`, `User` jaisi shared functionality free me milti hai. Microsoft ne is hierarchy ko shallow rakha hai (2-3 levels max) — deliberately, taaki fragile base class problem na aaye.

</RealWorld>

<RealWorld company="A BFSI Loan Processing System">

Ek typical Indian NBFC/lending platform me `LoanApplication` base class hoti hai jisse `PersonalLoanApplication`, `HomeLoanApplication` derive karte hain (single inheritance, shared fields jaise `ApplicantId`, `RequestedAmount`). Lekin cross-cutting concerns jaise "ye application audit trail maintain kare" ya "ye KYC-verified honi chahiye" interfaces (`IAuditable`, `IKycRequired`) ke through add hote hain — kyunki ye capabilities loan applications ke alawa doosre unrelated entities (jaise `CustomerProfile`) me bhi chahiye hoti hain, jinka loan se koi inheritance relationship nahi hai.

</RealWorld>

## Numbers That Matter

<Numbers>

- C# has supported single class inheritance since version 1.0 (2002) — multiple class inheritance has never been allowed, by deliberate design
- A class can implement an unlimited number of interfaces but extend exactly one base class — this 1-vs-many asymmetry is unchanged across every C# version
- Default interface methods (C# 8, 2019) introduced the first scenario where interface-vs-interface diamond ambiguity can occur, requiring explicit resolution
- Every class in C# implicitly inherits from `System.Object` if no other base class is specified — there is no such thing as a class with zero inheritance chain
- `sealed` (available since C# 1.0) lets a class explicitly opt out of being a base class at all, at any depth

</Numbers>

## Interview Angle

<InterviewAngle>

**Say this out loud:** "C# single aur multilevel class inheritance support karta hai, lekin multiple class inheritance nahi — kyunki agar do base classes same method define karein, compiler ko pata nahi chalega kaunsa version use kare, ye diamond problem hai. Isi reuse-goal ko C# interfaces se achieve karta hai — ek class multiple interfaces implement kar sakti hai bina ambiguity ke, kyunki implementation ek hi jagah, implementing class ke andar, hoti hai. Main practically ek base class (jab genuinely is-a relationship ho) plus multiple interfaces (cross-cutting capabilities ke liye) combine karta hoon."

Ye answer diamond problem ka exact mechanism bataata hai, sirf naam nahi. **Almost-guaranteed follow-up:** "Agar do interfaces dono me same-signature default method ho aur ek class dono implement kare, tab kya hota hai?" — jiska jawaab hai: compile error, explicit interface implementation se resolve karna padta hai (Module 3 me poora example).

</InterviewAngle>

## Common Mistakes

<Mistake>

Sirf itna bolna ki "C# multiple inheritance support nahi karta" bina "kyun" explain kiye — diamond problem ka mechanism batana hi wo cheez hai jo interviewer actually test karna chahta hai.

</Mistake>

<Mistake>

Interfaces ko bhi "multiple inheritance" bol dena bina qualify kiye. Technically ye "multiple interface implementation" hai, jo ambiguity-free hai kyunki (default interface methods ke edge case ko chhodkar) implementation ek hi jagah hoti hai — ye distinction crisp bolna chahiye.

</Mistake>

<Mistake>

Deep inheritance chains ko "good code reuse" samajh lena bina fragile base class problem consider kiye — 4-5 level deep hierarchies production me maintain karna genuinely mushkil hota hai.

</Mistake>

<Mistake>

Har "reuse chahiye" situation me inheritance reach kar lena, jabki genuine "is-a" relationship exist hi nahi karta. Agar sirf behavior reuse karna hai bina true is-a ke, composition better fit hota hai.

</Mistake>

<Mistake>

Ye bhool jaana ki har C# class implicitly `System.Object` se hi inherit karti hai agar koi explicit base class na ho — "iska koi base class nahi hai" kehna technically galat hai.

</Mistake>

## Quick Revision

<QuickRevision>

- Single inheritance: one direct base class. Multilevel: a chain (A to B to C), each level inherits everything public/protected above it
- C# disallows multiple class inheritance (`class C : A, B` is a compile error) specifically to avoid the diamond problem
- Diamond problem: if two base classes both define the same member, the compiler can't unambiguously pick which one to use
- Interfaces solve the same reuse goal without ambiguity — a class can implement unlimited interfaces because implementation lives only in the implementing class
- Default interface methods (C# 8+) reintroduce a narrow diamond-ambiguity case, requiring explicit resolution
- Idiomatic C# pattern: one base class (for genuine is-a + shared implementation) plus multiple interfaces (for cross-cutting capabilities)
- Every class implicitly inherits from `System.Object` even with no explicit base class
- Deep inheritance chains (4-5+ levels) are fragile — prefer composition when there's no true is-a relationship

</QuickRevision>
