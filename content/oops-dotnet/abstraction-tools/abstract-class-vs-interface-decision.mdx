<SimpleDefinition>

The choice between an abstract class and an interface comes down to one decisive question: do the implementers need to share instance state or constructor-run initialization logic (abstract class, the only option that can hold fields) — everything else, including "is-a versus can-do" framing, is a softer signal that in modern C# usually still resolves to preferring an interface.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Ye sabse zyada poocha jaane wala .NET OOP interview question hai, aur sabse zyada diya jaane wala jawaab bhi sabse kam useful hota hai: **"it depends."** Interviewer ko "it depends" nahi chahiye — usse ek clear, defensible rule of thumb chahiye jo tum apply kar sako. To seedha rule of thumb se shuru karte hain.

### The one deciding question

**Kya implementers ko genuinely shared instance state (fields) ya shared constructor logic chahiye?** Agar haan — abstract class, koi doosra option nahi hai. Interface, default interface methods (DIM, C# 8) hone ke baad bhi, instance fields kabhi nahi rakh sakta. Ye ek hard technical limit hai, opinion nahi.

Agar nahi — **default interface pe jao.** Modern C# me interface zyada flexible hai: ek class unlimited interfaces implement kar sakti hai (single-class-inheritance ka limit nahi lagta), interfaces mock/test karna aasan hai (unit testing me `Moq`-style fakes banana trivial hai), aur composition-first design (jo aaj ka .NET/ASP.NET Core style hai) interfaces ke around hi bana hai.

### "Is-a vs can-do" — traditional framing, still useful lekin secondary

Classic textbook rule: abstract class "is-a" relationship model karta hai (`Circle IS-A Shape`), interface "can-do" capability model karta hai (`Order CAN-BE Auditable`). Ye framing directionally sahi hai lekin akela decision nahi le sakta — kyunki bahut saari "is-a" relationships bhi bina shared state ke perfectly interface se model ho sakti hain. Isliye main "shared state" question ko primary rakhta hoon, "is-a vs can-do" ko secondary confirming signal.

### Single inheritance limit — jab ye forcing function ban jaata hai

Agar tumhara type already kisi aur class se inherit karta hai (jaise EF Core ka `ControllerBase`, ya koi framework base class), aur ab tumhe ek naya capability chahiye — tumhare paas koi choice nahi bacha, interface hi lena padega, kyunki ek class sirf ek hi base class extend kar sakti hai. Ye scenario khud-ba-khud decision le leta hai.

### DIM ne gap kam kiya hai, khatam nahi kiya

C# 8 se pehle, "concrete shared implementation" akele abstract class ka territory tha. DIM ke baad, interface bhi ek default method BODY de sakta hai — gap genuinely narrow hua hai. Lekin state (fields) ka gap wahi ka wahi hai. Isliye modern rule thoda evolve hua hai: agar tumhe sirf shared **behavior** (koi bhi field access kiye bina) chahiye, DIM se interface me bhi de sakte ho — abstract class sirf tabhi zaroori hai jab shared **state** chahiye ho.

### Practical checklist — interview me isi order me bolo

1. Implementers ke beech shared mutable state/constructor logic hai? → **abstract class**, non-negotiable.
2. Type already kisi doosri class se inherit karta hai? → **interface** hi option hai.
3. Genuinely unrelated types (jaise `Order` aur `User` dono) ko same capability chahiye? → **interface** (capabilities across unrelated hierarchies).
4. Sab kuch equal hai, koi strong signal nahi? → **default interface** — zyada flexible, testable, aur modern .NET idiom ke saath align karta hai.

### Code Examples

**Minimal example — same problem, two approaches, showing why state decides it:**

```csharp
// Interface — works fine, NO shared state needed
public interface IAuditable
{
    void MarkAudited(DateTime auditedAtUtc);
}

// Any unrelated type can implement it
public class Order : IAuditable
{
    public void MarkAudited(DateTime auditedAtUtc) { /* set a property */ }
}
public class UserProfile : IAuditable
{
    public void MarkAudited(DateTime auditedAtUtc) { /* set a property */ }
}

// Abstract class — needed because CreatedAt/Id are SHARED STATE,
// set once via a shared constructor, not just a shared method signature
public abstract class BaseEntity
{
    public Guid Id { get; } = Guid.NewGuid();
    public DateTime CreatedAtUtc { get; } = DateTime.UtcNow;
}

public class Product : BaseEntity { /* Id and CreatedAtUtc inherited, already initialized */ }
```

**Real ASP.NET Core example — combining both, correctly:**

```csharp
// Shared STATE across all entities -> abstract class
public abstract class AuditableEntity
{
    public Guid Id { get; } = Guid.NewGuid();
    public DateTime CreatedAtUtc { get; protected set; } = DateTime.UtcNow;
    public DateTime? ModifiedAtUtc { get; protected set; }

    public void Touch() => ModifiedAtUtc = DateTime.UtcNow;
}

// Cross-cutting CAPABILITY, unrelated to the entity hierarchy -> interface
public interface ISoftDeletable
{
    bool IsDeleted { get; }
    void SoftDelete();
}

public class Order : AuditableEntity, ISoftDeletable
{
    public bool IsDeleted { get; private set; }
    public void SoftDelete() => IsDeleted = true;
}
```

`Order` ek hi abstract class (`AuditableEntity`) se state inherit karta hai, aur ek interface (`ISoftDeletable`) se ek independent capability implement karta hai — ye exactly wo pattern hai jo real ASP.NET Core/EF Core codebases me dikhta hai: shared state ke liye ek base class, cross-cutting capabilities ke liye interfaces.

</Hinglish>

### Kab Kya Depth Chahiye

<Callout type="tip">

**SDE-1 level answer:** "Is-a" ke liye abstract class, "can-do" ke liye interface — ek simple example ke saath bol do (jaise `Shape`/`Circle` vs `IComparable`).

**SDE-3/Senior level answer:** "It depends" mat bolo — seedha "shared state" ko deciding factor bolo, DIM ke baad gap kaise narrow hua hai wo explain karo, aur bolo ki default me interface prefer karte ho (testability, multiple-implementation flexibility) — abstract class sirf tab jab genuinely shared state ho. Ek real example do jahan tumne dono ko combine kiya (jaise base entity class + capability interface) — ye sabse zyada senior signal deta hai.

</Callout>

## Real World Example

<RealWorld company="Microsoft">

.NET BCL isi pattern ka best example hai: `Stream` ek abstract class hai (shared buffer-handling state aur `CopyToAsync`-style shared implementation ki wajah se), jabki `IDisposable`, `IComparable<T>`, `IEquatable<T>` sab interfaces hain — kyunki ye capabilities hain jo completely unrelated types (a `Stream`, a `string`, a custom `Order` class) sab implement kar sakte hain, koi shared state ki zaroorat nahi.

</RealWorld>

<RealWorld company="A Food Delivery Platform">

Ek Swiggy/Zomato-style backend me `RestaurantEntity`, `OrderEntity`, `RiderEntity` sab ek `BaseEntity` abstract class se `Id`/`CreatedAtUtc` shared state inherit karte hain — sabko same audit fields chahiye. Lekin `INotifiable` (push notification bhej sakta hai) interface hai jo sirf `RiderEntity` aur `UserProfile` implement karte hain — do completely unrelated hierarchies ke types, ek shared capability ke saath, koi shared state nahi.

</RealWorld>

## Numbers That Matter

<Numbers>

- A class can implement any number of interfaces, but extend only ONE base/abstract class — this asymmetry alone often decides the choice
- Default interface methods (C# 8, 2019) let interfaces ship behavior, but instance fields remain abstract-class-exclusive even today
- Mocking frameworks like Moq generate proxies primarily off interfaces — a heavily interface-based design is measurably easier to unit test
- .NET's own BCL uses far more interfaces (`IDisposable`, `IEnumerable<T>`, `IComparable<T>`, ...) than abstract classes for cross-cutting capabilities — abstract classes appear mainly where real shared state exists (`Stream`, `ValueType`)

</Numbers>

## Interview Angle

<InterviewAngle>

**Say this out loud:** "Main sabse pehle poochta hoon: kya implementers ko genuinely shared state ya constructor logic chahiye? Agar haan, abstract class — koi doosra option nahi, kyunki interface aaj bhi instance fields nahi rakh sakta, default interface methods hone ke baad bhi. Agar nahi, main default interface choose karta hoon — zyada flexible hai, multiple implement ho sakte hain, aur testing/mocking me aasan hai. 'Is-a vs can-do' ek useful secondary signal hai lekin main state ko primary decision factor rakhta hoon."

Ye answer "it depends" ke traps se bachta hai aur ek concrete, defensible rule deta hai. **Almost-guaranteed follow-up:** "Ek real example do jahan tumne dono ek saath use kiye" — jiska jawaab `AuditableEntity` + `ISoftDeletable` jaisa combined pattern hai (upar dekha gaya).

</InterviewAngle>

## Common Mistakes

<Mistake>

"It depends" bolke ruk jaana bina ek concrete deciding factor diye — interviewer ko lagta hai candidate ke paas ek clear mental model nahi hai, sirf donon options ke facts yaad hain.

</Mistake>

<Mistake>

"Is-a vs can-do" ko akela, sufficient rule samajhna — bahut saari valid "is-a" relationships (jaise `Order IS-A Auditable`) bina kisi shared state ke perfectly interface se model ho sakti hain. Is framing ko primary factor banana galat decisions deta hai.

</Mistake>

<Mistake>

Ye bolna ki DIM (default interface methods) ne abstract classes ko obsolete kar diya — galat hai, state (fields) ka gap wahi ka wahi hai, sirf shared-behavior-without-state ka gap narrow hua hai.

</Mistake>

<Mistake>

Har entity/domain class ke liye ek common base class force karna sirf "consistency" ke naam pe, jab actual shared state minimal ho — over-engineering ka classic example, jo unnecessary coupling create karta hai unrelated types ke beech.

</Mistake>

<Mistake>

Dono ko mutually exclusive samajhna — ek class ek abstract base class se extend AND multiple interfaces implement dono kar sakti hai simultaneously, jaisa `Order : AuditableEntity, ISoftDeletable` example me dikhaya gaya.

</Mistake>

## Quick Revision

<QuickRevision>

- The one deciding question: do implementers need shared instance STATE (fields) or shared constructor logic? Only abstract class can provide that
- No shared state needed → default to interface: more flexible, unlimited implementers, easier to mock/test
- "Is-a vs can-do" is a useful secondary signal, not the primary decision factor — many valid "is-a" relationships still fit interfaces fine
- Single inheritance limit can force the choice: if the type already extends another class, interface is the only remaining option
- DIM (C# 8) narrowed the SHARED BEHAVIOR gap between interface and abstract class — it did NOT narrow the shared STATE gap
- A class can extend one abstract class AND implement many interfaces at the same time — they're not mutually exclusive
- Never answer this question with just "it depends" — give the state-based rule of thumb explicitly
- .NET's own BCL leans heavily interface-first for capabilities (`IDisposable`, `IComparable<T>`) and reserves abstract classes for real shared state (`Stream`)

</QuickRevision>
