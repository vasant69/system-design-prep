<SimpleDefinition>

Inversion of Control (IoC) is a design principle where an object's dependencies are supplied from the outside instead of being created internally by the object itself; Dependency Injection (DI) is ASP.NET Core's built-in implementation of IoC, where a container resolves interface-typed constructor parameters into concrete implementations, letting consuming code depend on abstractions it never has to construct.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Ye woh topic hai jahan interviewer dekhna chahta hai ki tumhe sirf `services.AddScoped<...>()` likhna aata hai ya tumhe pata hai ye line **kyun** kaam karti hai. Chalo dono clear karte hain.

### IoC — pehle principle, phir tool

Inversion of Control ka matlab hai: control ka flow **invert** ho jaata hai. Normal (non-IoC) code me, `OrdersController` khud decide karta hai ki `OrderService` kaise banega — `var service = new OrderService(new AppDbContext(...))`. Controller yahan **control me hai** — wo apni dependency khud create kar raha hai, aur usko pata hai `OrderService` exactly kis concrete class ka object hai.

IoC isko palat deta hai: controller sirf itna kehta hai "mujhe kisi `IOrderService` ki zaroorat hai" — kaun banayega, kaise banayega, ye decide karna controller ka kaam nahi raha. Ye control kisi external cheez ko mil jaata hai. **Dependency Injection sirf ek specific technique hai IoC ko achieve karne ki** — dependency ko constructor (ya method/property) ke through "inject" kar diya jaata hai, object khud nahi banata. ASP.NET Core me ye external cheez ek **built-in DI container** hai (`IServiceProvider`), jo ASP.NET Core 1.0 (2016) se framework ka first-class part hai — koi third-party library (Autofac, Ninject) zaroori nahi.

### Ye "OOP ka real payoff" kyun hai

Yahan interview me zyada candidates sirf mechanics bata dete hain, "kyun" nahi. DI sirf tabhi useful hai jab do OOP pillars pehle se present hon:

1. **Abstraction** — agar `OrderService` ka koi interface (`IOrderService`) na ho, DI container ke paas inject karne ke liye kuch "swappable" hai hi nahi, wo sirf ek concrete class inject karega, jo `new OrderService()` likhne se barabar hi useful hai.
2. **Polymorphism** — container runtime pe decide karta hai kaunsi concrete implementation `IOrderService` ke peeche khadi hai. Aaj `OrderService`, kal `CachedOrderService` (jo pehle Redis check kare) — controller ka code ek line bhi change nahi hota.

Isliye DI OOP ki theory (abstraction + polymorphism) ko ek **daily-use, production pattern** me convert karta hai — ye sirf ek framework feature nahi, ye OOP ka practical proof hai.

### DI container mechanics — registration se resolution tak

Container do phases me kaam karta hai:

**Registration** (`Program.cs` me, startup pe) — tum container ko batate ho kaunsa interface kaunsi concrete class se resolve hoga:

```csharp
builder.Services.AddScoped<IOrderService, OrderService>();
builder.Services.AddScoped<INotificationService, EmailNotificationService>();
```

**Resolution** (jab ek request aati hai) — jab `OrdersController` chahiye hota hai (kyunki ek incoming HTTP request usko route kar rahi hai), container **reflection** use karke uska constructor dekhta hai, har parameter type ke liye recursively resolve karta hai, aur poora object graph bana ke deta hai. Agar `OrderService` khud `INotificationService` maangta hai constructor me, container usko bhi resolve karega — automatically, recursively — tumhe kahin manually `new` nahi likhna padta.

### Constructor injection hi standard kyun hai

DI teen tareekon se ho sakti hai — constructor, property, method injection — lekin ASP.NET Core **constructor injection** ko strongly favor karta hai (built-in container property/method injection natively support hi nahi karta):

- Dependency `readonly` field me store hoti hai — ek baar set hone ke baad change nahi ho sakti, immutability milti hai.
- Agar zaroori dependency missing hai, app **startup pe hi fail** hoti hai (ya pehli request pe), runtime ke beech me kahin `NullReferenceException` nahi aata.
- Class ka constructor signature khud dikhata hai uski saari dependencies — koi hidden requirement nahi.

### Code Examples

**Minimal example — control ka inversion, bina container ke bhi:**

```csharp
// Without IoC — class controls its own dependency
public class ReportGenerator
{
    private readonly SqlLogger _logger = new SqlLogger(); // hardcoded, not swappable
}

// With IoC — dependency comes from outside
public class ReportGenerator
{
    private readonly ILogger _logger;
    public ReportGenerator(ILogger logger) => _logger = logger; // caller decides which ILogger
}
```

**Real ASP.NET Core example — building on the reference topic's `IOrderService`, now with a nested dependency:**

```csharp
public interface INotificationService
{
    Task NotifyAsync(string userId, string message);
}

public class EmailNotificationService : INotificationService
{
    public Task NotifyAsync(string userId, string message) =>
        Task.CompletedTask; // sends an email in real life
}

public class OrderService : IOrderService
{
    private readonly AppDbContext _db;
    private readonly INotificationService _notifier;

    public OrderService(AppDbContext db, INotificationService notifier)
    {
        _db = db;
        _notifier = notifier;
    }

    public async Task<Order> PlaceOrderAsync(CreateOrderDto dto)
    {
        var order = new Order { ProductId = dto.ProductId, Quantity = dto.Quantity };
        _db.Orders.Add(order);
        await _db.SaveChangesAsync();
        await _notifier.NotifyAsync(dto.UserId, "Order placed!");
        return order;
    }
}

// Program.cs
builder.Services.AddScoped<IOrderService, OrderService>();
builder.Services.AddScoped<INotificationService, EmailNotificationService>();
```

Jab `OrdersController` maangta hai `IOrderService`, container `OrderService` banata hai — aur `OrderService` ka constructor khud `INotificationService` maangta hai, jo container **recursively** resolve kar deta hai. Controller ko `EmailNotificationService` ka naam tak nahi pata — pure abstraction, pure polymorphism, wired automatically.

</Hinglish>

### Kab Kya Depth Chahiye

<Callout type="tip">

**SDE-1 level answer:** DI ka matlab bata do — dependencies constructor ke through inject hoti hain, `new` khud nahi likhna padta, `Program.cs` me `AddScoped`/`AddSingleton`/`AddTransient` register karte hain.

**SDE-3/Senior level answer:** IoC ko principle ki tarah define karo, DI ko uska ek implementation batao, explain karo container reflection se recursively object graph banata hai, aur ye connect karo ki DI sirf isliye kaam karta hai kyunki abstraction (interfaces) aur polymorphism (swappable implementations) pehle se hain — DI in dono pillars ka practical, production use hai, na ki inse alag koi framework magic.

</Callout>

## Real World Example

<RealWorld company="Microsoft">

ASP.NET Core ne (starting ASP.NET Core 1.0, 2016) DI ko framework ke core me hi built-in kar diya — ye industry me bada shift tha, kyunki pehle .NET developers Autofac/Ninject/Unity jaisi third-party libraries pe depend karte the. Har `Startup.cs`/`Program.cs` me `IServiceCollection` DI ka registration surface hai — pura ASP.NET Core framework khud (logging, `DbContext`, `HttpClient`) isi container ke through wire hota hai, ye sirf application code ke liye nahi hai.

</RealWorld>

<RealWorld company="A Food Delivery Backend">

Ek Swiggy/Zomato-style order-tracking service me `IDeliveryPartnerMatcher` interface hota hai. Shuru me ek simple `NearestPartnerMatcher` implementation hoti hai. Baad me business team bolti hai "ab ek smarter algorithm chahiye jo partner rating bhi consider kare" — team ek naya `RatingWeightedMatcher` likhti hai, `IDeliveryPartnerMatcher` implement karta hai, aur `Program.cs` me sirf ek registration line change hoti hai. Controller, order service — kuch bhi touch nahi hota. Ye DI ka real production payoff hai, feature ship karne ki speed me directly dikhta hai.

</RealWorld>

## Numbers That Matter

<Numbers>

- ASP.NET Core has shipped a built-in DI container since ASP.NET Core 1.0 (2016) — no third-party library required for basic use
- Exactly 3 built-in service lifetimes: `Singleton`, `Scoped`, `Transient` (full deep-dive in the next topic)
- Constructor injection is the only injection style the built-in container supports natively — property/method injection needs a third-party container
- Missing/unregistered dependency throws `InvalidOperationException` — for a `Scoped`/`Transient` service, this surfaces on first request; a genuinely missing type can also be caught earlier via `builder.Services.BuildServiceProvider().GetService<T>()`-style validation
- The container resolves the full object graph via reflection at request time — this has a small, usually negligible perf cost compared to a hand-written `new`

</Numbers>

## Common Mistakes

<Mistake>

IoC aur DI ko same cheez samajh lena aur interchange bol dena. IoC ek broader principle hai (Service Locator bhi IoC ka ek doosra implementation hai); DI usmein se sirf ek specific technique hai. Interviewer jab "IoC define karo" poochta hai aur candidate seedha "DI matlab..." bol deta hai, ye distinction miss ho jaata hai.

</Mistake>

<Mistake>

Sirf concrete class register/inject karna, interface na banana — `builder.Services.AddScoped<OrderService>()` (bina `IOrderService` ke) technically compile hota hai, lekin DI ka pura point miss kar deta hai, kyunki ab swap karna hai to consuming code change karna padega.

</Mistake>

<Mistake>

Constructor me itni saari dependencies inject karte jaana (6-7+) bina isse "too many responsibilities" ka signal maanna — interview me isse pehchan na pana ki ye Single Responsibility Principle violation ka symptom hai, ek red flag hai.

</Mistake>

<Mistake>

Ye sochna ki container "magic" se sab kuch resolve kar deta hai — actual mechanism (reflection-based constructor inspection, recursive graph building) explain na kar paana, jab interviewer "container ke andar hota kya hai" poochta hai.

</Mistake>

<Mistake>

`new` keyword ko completely avoid karna poore codebase me, "DI hamesha use karna chahiye" jaisa absolute statement bolna — DTOs, value objects, aur simple helper types ko `new` se banana bilkul sahi hai; DI sirf **dependencies** (services, repositories) ke liye hai, har object ke liye nahi.

</Mistake>

## Quick Revision

<QuickRevision>

- IoC = principle (control of object creation moves outside the object); DI = the specific technique ASP.NET Core uses to implement IoC
- The built-in container (`IServiceProvider`) is native to ASP.NET Core since version 1.0 (2016), no third-party library needed for basic use
- Registration happens in `Program.cs` (`AddScoped`/`AddSingleton`/`AddTransient`); resolution happens per-request via reflection on constructors
- Constructor injection is the standard — it's the only style the built-in container supports natively, gives immutability and fail-fast behavior
- DI only pays off because abstraction (interfaces) and polymorphism (swappable implementations) already exist — it's OOP's real, everyday production use
- The container resolves dependencies recursively — a service's own dependencies get resolved automatically, no manual wiring
- Don't inject everything — DTOs and simple value objects should still just be `new`'d directly
- A missing registration throws `InvalidOperationException`, typically on first request for Scoped/Transient services

</QuickRevision>
