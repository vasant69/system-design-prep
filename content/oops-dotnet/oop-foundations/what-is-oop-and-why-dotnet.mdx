<SimpleDefinition>

Object-Oriented Programming is a paradigm that models a program as a collection of objects — bundles of state and behavior — rather than a sequence of instructions acting on shared global data; .NET is OOP-first at the CLR level, where every type, including primitives like `int`, ultimately derives from `System.Object`.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Interview me "OOP kya hai" poochne ka matlab textbook definition sunna nahi hota — interviewer check karna chahta hai ki tumhe pata hai OOP **kyun** exist karta hai, aur .NET jaisi language ne apna poora type system isi ke around kyun design kiya. Definition ek line me: OOP ek programming paradigm hai jisme program ko **objects** ke through model karte hain — har object apna **state** (fields/properties) aur **behavior** (methods) khud carry karta hai, na ki poora program ek shared, global data pe operate karne wale functions ka dher ho.

### OOP se pehle kya tha, aur kyun tootta tha

Procedural programming (C jaisi languages) me functions aur data alag hote hain — koi enforced boundary nahi ki kaunsa function kis data ko touch kar sakta hai. Chhote scripts me ye theek chalta hai, lekin jaise-jaise codebase badhta hai, koi bhi function kahin bhi shared/global state modify kar sakta hai. Result: "spaghetti state" — ek jagah change karo, kahin aur silently kuch toot jaata hai, kyunki data aur usko modify karne wale logic ke beech koi ownership nahi hai. OOP isko solve karta hai: data ko uske related behavior ke saath **bundle** karke, aur external world ko sirf defined methods ke through access dekar.

### .NET OOP-first kyun hai — CLR ka design decision

Ye wahi jagah hai jahan zyada candidates surface-level reh jaate hain. .NET ka **CTS (Common Type System)** ek fundamental rule follow karta hai: **har type — chahe reference type ho ya value type — ultimately `System.Object` se derive karta hai.** Haan, `int` bhi — wo technically `System.Int32` hai, ek `struct` jo `System.ValueType` se derive karta hai, jo khud `System.Object` se derive karta hai. Isi wajah se tum kisi bhi variable pe `.ToString()`, `.Equals()`, `.GetHashCode()`, `.GetType()` call kar sakte ho, chahe wo ek custom class ho ya ek plain `int` — kyunki ye chaaron `System.Object` se inherited hain, universally.

Ye design decision jaan-boojh kar liya gaya tha: ek uniform object model isliye zaroori hai taaki C#, F#, VB.NET jaisi alag-alag languages **same CLR pe interoperate** kar sakein — ek C# library ka object seedha F# code me use ho sakta hai, kyunki dono ka underlying type system same hai. Reflection, generics constraints, aur boxing/unboxing — sab isi single-root hierarchy ki wajah se consistently kaam karte hain.

### Chaar pillars — ek-line summary (deep dive agle module me)

Yahan sirf naam aur ek-line intuition — har ek ka poora deep dive Module 2 me hai: **Encapsulation** (state ko bundle karke control karo kaun modify kar sakta hai), **Abstraction** (complexity chhupao, sirf zaroori interface expose karo), **Inheritance** (shared behavior ek common base se reuse karo), **Polymorphism** (ek hi interface, alag-alag concrete implementations).

### OOP na hota to kya toota — ek concrete scenario

Socho ek e-commerce API bina OOP ke likhi gayi hai — order processing, discount calculation, aur tax calculation sab ek hi giant procedure me, ek shared mutable variable (`currentOrderTotal`) use karte hue. Kal koi discount logic change kare — accidentally tax calculation bhi break ho sakta hai, kyunki dono same shared state pe depend kar rahe the, aur koi boundary nahi thi jo batati "ye variable sirf discount logic ka hai." OOP isko `Order` class me encapsulate karta hai — apna state khud manage karta hai (`private` fields), external code sirf defined public methods (`ApplyDiscount()`, `CalculateTax()`) ke through interact karta hai. Ab ek method ka internal change doosre ko silently nahi tod sakta.

### Code Examples

**Minimal example — class vs object, independent state:**

```csharp
public class BankAccount
{
    public string Owner { get; init; } = "";
    public decimal Balance { get; private set; }

    public void Deposit(decimal amount) => Balance += amount;
}

var acc1 = new BankAccount { Owner = "Asha" };
var acc2 = new BankAccount { Owner = "Rohit" };
acc1.Deposit(500);

// acc1.Balance == 500, acc2.Balance == 0
// Same class, same method — lekin har OBJECT apna independent state carry karta hai
```

**Real ASP.NET Core example — DTO, interface-based service, controller:**

```csharp
public record CreateOrderDto(string ProductId, int Quantity);

public interface IOrderService
{
    Task<Order> PlaceOrderAsync(CreateOrderDto dto);
}

public class OrderService : IOrderService
{
    private readonly AppDbContext _db;
    public OrderService(AppDbContext db) => _db = db;

    public async Task<Order> PlaceOrderAsync(CreateOrderDto dto)
    {
        var order = new Order { ProductId = dto.ProductId, Quantity = dto.Quantity };
        _db.Orders.Add(order);
        await _db.SaveChangesAsync();
        return order;
    }
}

[ApiController]
[Route("api/orders")]
public class OrdersController : ControllerBase
{
    private readonly IOrderService _orderService;
    public OrdersController(IOrderService orderService) => _orderService = orderService;

    [HttpPost]
    public async Task<IActionResult> Create(CreateOrderDto dto)
    {
        var order = await _orderService.PlaceOrderAsync(dto);
        return CreatedAtAction(nameof(Create), new { id = order.Id }, order);
    }
}
```

Ye teeno OOP concepts ek saath dikha raha hai: `CreateOrderDto` ek chhota data-only object hai, `OrderService` apna business logic **encapsulate** karta hai aur `IOrderService` ke peeche **abstract** ho jaata hai, aur `OrdersController` seedha `OrderService` pe nahi, `IOrderService` (abstraction) pe depend karta hai — ye pattern hi aage DI aur SOLID modules ki bunyaad hai.

</Hinglish>

### Kab Kya Depth Chahiye

<Callout type="tip">

**SDE-1 level answer:** Chaar pillars ko naam aur ek-line definition ke saath bol do, ek simple class ka example do (jaise `BankAccount`). Itna kaafi hai.

**SDE-3/Senior level answer:** Ye bhi connect karo ki .NET ka CLR isi principle pe design hua hai (CTS, `System.Object` root), OOP kahan break down hota hai (deep inheritance chains fragile ho jaate hain — composition often better hai), aur apne production code se ek real example do (jaise ek interface-based service jo DI ke through inject hota hai) — isse pata chalta hai ki theory sirf textbook nahi, apne kaam me use ki hai.

</Callout>

## Real World Example

<RealWorld company="Microsoft">

.NET/CLR team ne shuru se hi ye decision liya tha ki poore type system ka ek single root ho — `System.Object`. Iski wajah se `int`, `bool`, `DateTime` jaisi value types bhi `.ToString()`/`.Equals()` jaisi methods "free" me milti hain, aur `ArrayList`/generic `List<T>` jaisi collections kisi bhi type ko uniformly store kar sakti hain (boxing ke through, jab tak generics nahi aaye the). Ye single-root design .NET ko multi-language platform banata hai — C#, F#, VB.NET sab ek hi object model share karte hain.

</RealWorld>

<RealWorld company="A Fintech Payments API">

Ek typical Indian fintech backend (Razorpay/Paytm-style payment flow) me `IPaymentGateway` jaisa interface likha jaata hai jisse `RazorpayGateway` aur `PayUGateway` dono implement karte hain. Controller sirf `IPaymentGateway` pe depend karta hai — production me Razorpay use ho ya kal PayU pe switch karna pade, controller ka code ek line bhi change nahi hota. Ye pure OOP (abstraction + polymorphism) hai, koi framework magic nahi — sirf ek interface aur do implementations.

</RealWorld>

## Numbers That Matter

<Numbers>

- Every single type in the CLR — reference or value — ultimately derives from `System.Object`, no exceptions
- 4 methods every type inherits automatically from `System.Object`: `ToString()`, `Equals()`, `GetHashCode()`, `GetType()`
- C# 1.0 shipped in 2002; OOP ergonomics have kept evolving since — `init`-only setters (C# 9, 2020), `required` members (C# 11, 2022)
- ASP.NET Core's own `ControllerBase`/`Controller` classes are themselves an inheritance-based design — every API controller you write extends one of them
- Boxing a value type (e.g. storing an `int` in an `object` variable) allocates on the heap — a real, measurable perf cost that pure reference types don't pay

</Numbers>

## Interview Angle

<InterviewAngle>

**Say this out loud:** "OOP ek paradigm hai jisme hum program ko real-world entities jaise objects ke through model karte hain — har object apna state aur behavior khud carry karta hai. .NET isko CLR level pe enforce karta hai — `System.Object` poore type system ka single root hai, `int` jaisi value types bhi isi se derive karti hain. Ye four pillars ke through implement hota hai: encapsulation, abstraction, inheritance, polymorphism — aur main apne projects me isko interface-based services aur dependency injection ke through use karta hoon, na ki deep inheritance chains ke through."

Ye answer teen cheezein signal karta hai: definition clear hai, CLR-level "why" pata hai (sirf definition nahi), aur modern .NET me OOP kaise actually likha jaata hai (composition/DI-first, inheritance-heavy nahi) — ye teesra point interviewer ko sabse zyada impress karta hai kyunki bahut candidates isse miss karte hain. **Almost-guaranteed follow-up:** "Achha, ye chaar pillars mujhe ek-ek karke detail me samjhao, real example ke saath" — jiska jawaab Module 2 ke topics dete hain.

</InterviewAngle>

## Common Mistakes

<Mistake>

Sirf "encapsulation, abstraction, inheritance, polymorphism" naam bol dena bina ye explain kiye ki har ek **kyun** zaroori hai — interviewer turant "achha, encapsulation se exactly kya problem solve hoti hai" jaisa follow-up poochta hai, aur yahan zyada candidates atak jaate hain.

</Mistake>

<Mistake>

Interview me casually "class" aur "object" ko interchange karke bolna (jaise "object" bolna jab class definition ka reference de rahe ho) — chhota sa slip lagta hai lekin interviewer ko turant signal deta hai ki concepts crisp nahi hain.

</Mistake>

<Mistake>

OOP ko sirf class hierarchies (deep inheritance chains) samajhna — modern .NET code, especially ASP.NET Core me, interfaces + composition + dependency injection heavily use karta hai, deep inheritance nahi. Isko na jaanna dated knowledge signal karta hai.

</Mistake>

<Mistake>

Theory ko apne khud ke project se connect na kar paana — agar interviewer poochhe "tumne apne project me OOP kahan use kiya," aur candidate ke paas koi concrete example (jaise ek interface-based service) na ho, to poori theoretical knowledge ka weight kam ho jaata hai.

</Mistake>

<Mistake>

"Sab kuch C# me object hai" ko bina caveat ke bolna — value types (`int`, `struct`) technically `System.Object` se derive to karte hain, lekin unka default behavior stack-allocated hota hai, object nahi banta jab tak boxing na ho. Ye nuance na jaanna ek common gap hai.

</Mistake>

## Quick Revision

<QuickRevision>

- OOP models a program as objects — bundled state + behavior — instead of functions operating on shared global data
- .NET's CTS makes `System.Object` the single root of every type, reference or value — this is a deliberate CLR design decision, not an accident
- `int`, `bool`, and every value type still derive from `System.Object` via `System.ValueType`, which is why `.ToString()`/`.Equals()` work on them
- The single-root object model is what lets C#, F#, and VB.NET interoperate on the same CLR
- Four pillars: encapsulation, abstraction, inheritance, polymorphism — full deep dive in Module 2
- Modern ASP.NET Core code leans on interfaces + composition + DI far more than deep inheritance chains
- Boxing a value type into `object` allocates on the heap — a real, measurable cost
- Always connect the theory to a concrete example from your own project when answering this in an interview

</QuickRevision>
