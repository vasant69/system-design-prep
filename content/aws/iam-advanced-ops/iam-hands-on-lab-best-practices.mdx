## Hinglish Deep Explanation

<Hinglish>

### Lab scenario

Ek Node.js service (`report-generator`) EC2 par chalti hai aur usse ek S3 bucket ke `reports/` prefix se padhna hai. Hum ek role banayenge, uspar least-privilege policy lagayenge, EC2 se attach karenge, verify karenge, aur cleanup karenge. Resources: S3 bucket `jmfs-lab-reports-<random>`, IAM policy `LabReportReadPolicy`, IAM role `LabReportRole`, instance profile `LabReportProfile`.

### Console walkthrough (summary)

1. S3 → Create bucket → `jmfs-lab-reports-8x2k`, Block Public Access sab ON → folder `reports/` banao, ek test file upload karo.
2. IAM → Policies → Create policy → JSON tab me least-privilege policy paste karo (neeche CLI section me same JSON hai) → naam `LabReportReadPolicy`.
3. IAM → Roles → Create role → Trusted entity **AWS service** → use case **EC2** → `LabReportReadPolicy` attach karo → naam `LabReportRole`. Console chupchaap same naam se instance profile bhi bana deta hai.
4. EC2 → Instance select karo → Actions → Security → Modify IAM role → `LabReportRole` chuno. Instance restart karne ki zaroorat **nahi** — IMDS kuch seconds me naye credentials dene lagta hai.
5. Verify (instance par SSH karke):

```bash
aws sts get-caller-identity
# → "Arn": "arn:aws:sts::123456789012:assumed-role/LabReportRole/i-0abc123"

aws s3 ls s3://jmfs-lab-reports-8x2k/reports/     # ✅ chalega
aws s3 ls s3://jmfs-lab-reports-8x2k/             # ❌ AccessDenied (prefix condition)
aws s3 cp s3://jmfs-lab-reports-8x2k/reports/test.csv .   # ✅ chalega
aws s3 cp test.csv s3://jmfs-lab-reports-8x2k/reports/    # ❌ AccessDenied (no PutObject)
```

### CLI walkthrough (full script)

```bash
set -euo pipefail
export AWS_REGION=ap-south-1
BUCKET="jmfs-lab-reports-$(openssl rand -hex 3)"
ACCOUNT=$(aws sts get-caller-identity --query Account --output text)

# 1. Bucket banao
aws s3api create-bucket --bucket "$BUCKET" --region ap-south-1 \
  --create-bucket-configuration LocationConstraint=ap-south-1
aws s3api put-public-access-block --bucket "$BUCKET" \
  --public-access-block-configuration \
  "BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true"
echo "order_id,amount" > /tmp/test.csv
aws s3 cp /tmp/test.csv "s3://$BUCKET/reports/test.csv"

# 2. Trust policy
cat > /tmp/trust-policy.json <<EOF
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "ec2.amazonaws.com" },
    "Action": "sts:AssumeRole"
  }]
}
EOF

# 3. Permission policy — least privilege, prefix-scoped
cat > /tmp/permission-policy.json <<EOF
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ListOnlyReportsPrefix",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::$BUCKET",
      "Condition": { "StringLike": { "s3:prefix": ["reports/*", "reports"] } }
    },
    {
      "Sid": "ReadReportObjects",
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::$BUCKET/reports/*"
    }
  ]
}
EOF

# 4. Validate DEPLOY SE PEHLE (free)
aws accessanalyzer validate-policy \
  --policy-type IDENTITY_POLICY \
  --policy-document file:///tmp/permission-policy.json \
  --query 'findings[].{Type:findingType,Issue:issueCode,Detail:findingDetails}' \
  --output table

# 5. Policy create
POLICY_ARN=$(aws iam create-policy \
  --policy-name LabReportReadPolicy \
  --policy-document file:///tmp/permission-policy.json \
  --query 'Policy.Arn' --output text)

# 6. Role create + attach
aws iam create-role --role-name LabReportRole \
  --assume-role-policy-document file:///tmp/trust-policy.json \
  --max-session-duration 3600 \
  --tags Key=Project,Value=lab
aws iam attach-role-policy --role-name LabReportRole --policy-arn "$POLICY_ARN"

# 7. Instance profile (EC2 ke liye zaroori)
aws iam create-instance-profile --instance-profile-name LabReportProfile
aws iam add-role-to-instance-profile \
  --instance-profile-name LabReportProfile --role-name LabReportRole

sleep 15   # eventual consistency — propagation ka wait

# 8. EC2 se attach
aws ec2 associate-iam-instance-profile \
  --instance-id "$INSTANCE_ID" \
  --iam-instance-profile Name=LabReportProfile

# 9. Verify BINA deploy kiye — simulator
aws iam simulate-principal-policy \
  --policy-source-arn "arn:aws:iam::$ACCOUNT:role/LabReportRole" \
  --action-names s3:GetObject s3:PutObject s3:DeleteObject \
  --resource-arns "arn:aws:s3:::$BUCKET/reports/test.csv" \
  --query 'EvaluationResults[].{Action:EvalActionName,Decision:EvalDecision}' \
  --output table
# GetObject → allowed, PutObject → implicitDeny, DeleteObject → implicitDeny
```

### CDK equivalent (TypeScript)

```typescript
import * as cdk from "aws-cdk-lib";
import { Construct } from "constructs";
import * as s3 from "aws-cdk-lib/aws-s3";
import * as iam from "aws-cdk-lib/aws-iam";
import * as ec2 from "aws-cdk-lib/aws-ec2";

export class IamLabStack extends cdk.Stack {
  constructor(scope: Construct, id: string, props?: cdk.StackProps) {
    super(scope, id, props);

    const bucket = new s3.Bucket(this, "ReportsBucket", {
      bucketName: `jmfs-lab-reports-${this.account}`,
      blockPublicAccess: s3.BlockPublicAccess.BLOCK_ALL,
      encryption: s3.BucketEncryption.S3_MANAGED,
      enforceSSL: true,
      removalPolicy: cdk.RemovalPolicy.DESTROY,   // sirf lab ke liye!
      autoDeleteObjects: true,                     // sirf lab ke liye!
    });

    const role = new iam.Role(this, "LabReportRole", {
      roleName: "LabReportRole",
      assumedBy: new iam.ServicePrincipal("ec2.amazonaws.com"),
      maxSessionDuration: cdk.Duration.hours(1),
    });

    role.addToPolicy(new iam.PolicyStatement({
      sid: "ListOnlyReportsPrefix",
      effect: iam.Effect.ALLOW,
      actions: ["s3:ListBucket"],
      resources: [bucket.bucketArn],
      conditions: { StringLike: { "s3:prefix": ["reports/*", "reports"] } },
    }));
    role.addToPolicy(new iam.PolicyStatement({
      sid: "ReadReportObjects",
      effect: iam.Effect.ALLOW,
      actions: ["s3:GetObject"],
      resources: [bucket.arnForObjects("reports/*")],
    }));
    // Production me prefer karo: bucket.grantRead(role, "reports/*")
    // — CDK ka grant helper KMS permissions bhi khud add karta hai, kam galtiyaan.

    const vpc = ec2.Vpc.fromLookup(this, "Vpc", { isDefault: true });
    new ec2.Instance(this, "ReportInstance", {
      vpc,
      instanceType: ec2.InstanceType.of(ec2.InstanceClass.T3, ec2.InstanceSize.MICRO),
      machineImage: ec2.MachineImage.latestAmazonLinux2023(),
      role,                        // instance profile auto-create hoga
      requireImdsv2: true,         // ZAROORI — SSRF protection
    });
  }
}
```

Deploy: `npx cdk bootstrap aws://<ACCOUNT>/ap-south-1` (ek baar), `npx cdk synth` (generated CloudFormation + cdk-nag warnings dekho), `npx cdk diff`, `npx cdk deploy`.

### Cleanup — order matter karta hai

**CDK:** `npx cdk destroy` (bucket bhi delete hoga kyunki `removalPolicy: DESTROY` + `autoDeleteObjects: true`).

**CLI (manual):**

```bash
# 1. EC2 se instance profile detach
ASSOC=$(aws ec2 describe-iam-instance-profile-associations \
  --filters Name=instance-id,Values=$INSTANCE_ID \
  --query 'IamInstanceProfileAssociations[0].AssociationId' --output text)
aws ec2 disassociate-iam-instance-profile --association-id "$ASSOC"

# 2. Instance profile se role hatao, phir profile delete
aws iam remove-role-from-instance-profile \
  --instance-profile-name LabReportProfile --role-name LabReportRole
aws iam delete-instance-profile --instance-profile-name LabReportProfile

# 3. Role se policy detach, phir role delete
aws iam detach-role-policy --role-name LabReportRole --policy-arn "$POLICY_ARN"
aws iam delete-role --role-name LabReportRole

# 4. Policy ke sab non-default versions delete karo, phir policy
for V in $(aws iam list-policy-versions --policy-arn "$POLICY_ARN" \
    --query 'Versions[?!IsDefaultVersion].VersionId' --output text); do
  aws iam delete-policy-version --policy-arn "$POLICY_ARN" --version-id "$V"
done
aws iam delete-policy --policy-arn "$POLICY_ARN"

# 5. Bucket khaali karo, phir delete
aws s3 rm "s3://$BUCKET" --recursive
aws s3api delete-bucket --bucket "$BUCKET"
```

**Order kyun matter karta hai:** IAM `DeleteConflict` error deta hai agar entity abhi bhi kahin attached hai. Order hamesha: **detach/disassociate → delete child → delete parent.**

### CDK/CloudFormation ka IAM se relationship

Do alag identities involve hoti hain. **Deployment identity** — jo `cdk deploy` chalata hai, bootstrap ke baad chaar roles use karta hai (`deploy-role`, `file-publishing-role`, `image-publishing-role`, `lookup-role`). Aur **`cfn-exec-role`** — ye wo role hai jo CloudFormation **actually resources banane ke liye use karta hai**, aur default bootstrap me isko `AdministratorAccess` milta hai. Ye important hai: tumhare developer ke paas admin nahi hai, lekin CFN exec role ke paas hai — isliye jo bhi `cdk deploy` kar sakta hai, wo effectively admin hai. Production me lock karo:

```bash
cdk bootstrap aws://123456789012/ap-south-1 \
  --cloudformation-execution-policies "arn:aws:iam::123456789012:policy/CdkDeployBoundary" \
  --trust 999988887777
```

CDK ke `grant*()` methods (`bucket.grantRead(fn)`, `table.grantWriteData(fn)`) least-privilege policies auto-generate karte hain, raw `addToPolicy()` se kaafi better — CDK jaanta hai kaunse actions chahiye (including KMS agar resource encrypted hai). `grantFullAccess()` se bacho, wo `*` deta hai. `resources: ['*']` likhne par `cdk synth` warning nahi deta — isliye pipeline me `cdk-nag` add karo, wo pakad lega.

### Least privilege — actual process, theory nahi

**Phase 1 — Broad start, monitored:** naye service ke liye thodi broad policy do (jaise `s3:*` on specific bucket), lekin CloudTrail on rakho. Perfect policy pehle din likhne ki koshish mat karo.

**Phase 2 — Observe (2-4 weeks, ek full business cycle cover karo):**

```bash
aws iam generate-service-last-accessed-details --arn arn:aws:iam::123:role/PaymentRole
aws iam get-service-last-accessed-details --job-id <job-id>
aws iam generate-service-last-accessed-details \
  --arn arn:aws:iam::123:role/PaymentRole --granularity ACTION_LEVEL
```

**Phase 3 — CloudTrail se policy generate karo:**

```bash
aws accessanalyzer start-policy-generation \
  --policy-generation-details principalArn=arn:aws:iam::123:role/PaymentRole \
  --cloud-trail-details '{
    "trails":[{"cloudTrailArn":"arn:aws:cloudtrail:ap-south-1:123:trail/main","allRegions":true}],
    "accessRole":"arn:aws:iam::123:role/AccessAnalyzerPolicyGenRole",
    "startTime":"2026-07-01T00:00:00Z"
  }'
aws accessanalyzer get-generated-policy --job-id <id>
```

**Phase 4 — Narrow, validate, deploy:** generated policy manually review karo (rare code paths — error handling, quarterly batch jobs, DR — miss ho sakte hain). `check-no-new-access` se verify karo. Staging me deploy, ek full business cycle chalao.

**Phase 5 — Continuous:** unused access analyzer on rakho, har quarter findings review karo. DR/break-glass roles ko tag-based exclusion se analysis se explicitly exclude karo — warna production incident ke din pata chalega ki DR role hi toota hua hai.

### IAM alternatives — kab NAHI use karna

IAM khud "use na karne" ka option nahi hai (AWS API access ke liye mandatory) — sawal ye hai ki **kaunsi feature kahan**, aur kahan IAM **galat layer** hai:

| Problem | IAM sahi tool hai? | Sahi tool |
|---|---|---|
| AWS API access control | ✅ Haan | IAM |
| App ke andar end-user permissions (SaaS customers) | ❌ Nahi | Cognito, Auth0, ya apna RBAC DB me |
| Database row/column level access | ❌ Nahi | DB ka apna GRANT / RLS, ya Lake Formation |
| Kubernetes RBAC | ❌ Nahi | K8s RBAC (IAM sirf cluster access deta hai) |
| Network access control | ❌ Nahi | Security groups, NACLs, VPC endpoints |
| API rate limiting per customer | ❌ Nahi | API Gateway usage plans |

**Sabse common mistake:** SaaS end-users ke liye IAM users banana — 5,000 users ki hard limit hai, IAM eventually consistent hai, API rate limits hain, scale nahi karega. **Doosri common mistake:** IAM ko network security ki jagah use karna — `aws:SourceIp` primary control nahi honi chahiye, VPC endpoints + security groups use karo. **Grey area:** multi-tenant SaaS jahan har tenant ka apna data hai — session policies + tag-based isolation se IAM ko tenant isolation ke liye use karna legitimate pattern hai, lekin app ke end users ke liye nahi. Line: agar entity **AWS resources directly** access kar rahi hai to IAM; app ke through jaa rahi hai to app-level authz.

</Hinglish>

## CLI Cheat-Sheet

<Hinglish>

Ye commands sabse zyada use hote hain — audit, debug, aur day-to-day operations ke liye.

**Identity aur account summary:**

```bash
aws sts get-caller-identity                     # main kaun hoon? #1 command
aws iam get-account-summary                     # sab quotas ka usage ek nazar me
aws iam get-account-authorization-details > iam-dump.json   # poora IAM export
```

**Roles:**

```bash
aws iam get-role --role-name X                  # trust policy + boundary + last used
aws iam list-attached-role-policies --role-name X
aws iam attach-role-policy --role-name X --policy-arn arn:...
aws iam put-role-policy --role-name X --policy-name Y --policy-document file://p.json
```

**Policies (versioning + rollback):**

```bash
aws iam create-policy-version --policy-arn arn:... \
    --policy-document file://p.json --set-as-default
aws iam set-policy-version --policy-arn arn:... --version-id v2    # ROLLBACK
aws iam list-entities-for-policy --policy-arn arn:...   # kaun-kaun use kar raha hai
```

**Simulation aur validation (deploy se pehle):**

```bash
aws iam simulate-principal-policy \
  --policy-source-arn arn:aws:iam::123:role/X \
  --action-names s3:GetObject s3:PutObject --resource-arns arn:aws:s3:::bucket/key

aws accessanalyzer validate-policy \
  --policy-type IDENTITY_POLICY --policy-document file://p.json    # FREE

aws accessanalyzer check-no-new-access \
  --new-policy-document file://new.json --existing-policy-document file://old.json \
  --policy-type IDENTITY_POLICY    # PAID, automated reasoning
```

**Audit aur least-privilege:**

```bash
aws iam generate-credential-report && \
  aws iam get-credential-report --query Content --output text | base64 -d > report.csv
aws accessanalyzer list-findings --analyzer-arn arn:... --filter '{"status":{"eq":["ACTIVE"]}}'
```

**Emergency:**

```bash
# Role ki SAB active sessions turant revoke karo
aws iam put-role-policy --role-name CompromisedRole --policy-name RevokeOldSessions \
  --policy-document '{"Version":"2012-10-17","Statement":[{
    "Effect":"Deny","Action":"*","Resource":"*",
    "Condition":{"DateLessThan":{"aws:TokenIssueTime":"'"$(date -u +%Y-%m-%dT%H:%M:%SZ)"'"}}}]}'

# Ek key turant band karo
aws iam update-access-key --user-name X --access-key-id AKIA... --status Inactive
```

**Handy one-liners:**

```bash
# 90+ din se unused roles
aws iam list-roles --query 'Roles[].RoleName' --output text | tr '\t' '\n' | \
while read R; do
  L=$(aws iam get-role --role-name "$R" --query 'Role.RoleLastUsed.LastUsedDate' --output text)
  echo "${L:-NEVER}  $R"
done | sort

# Kaun se roles ke paas iam:PassRole with * hai — audit checklist ka top item
aws iam get-account-authorization-details --filter Role \
  | jq -r '.RoleDetailList[] | select(
      .RolePolicyList[]?.PolicyDocument.Statement[]? |
        select(.Action == "iam:PassRole" and .Resource == "*")
    ) | .RoleName'
```

## Quotas Reference

<Hinglish>

**Adjustable (Service Quotas se, auto-approved):** customer managed policies 1,500 → 10,000; roles per account 1,000 → 10,000; managed policies per role 10 → 25; role trust policy 2,048 → 8,192 chars; OIDC providers 100 → 700; STS requests/sec 600 (Support ticket se).

**Hard limits (badh nahi sakte):** users per account **5,000**; access keys per user 2; MFA devices 8; managed policy versions 5; managed policy size 6,144 chars; inline policy aggregate — role 10,240 / user 2,048 / group 5,120 chars; session duration 900–43,200s; role chaining session 3,600s max.

**Apne account me check karo:**

```bash
aws iam get-account-summary
aws service-quotas list-service-quotas --service-code iam --region us-east-1 \
  --query 'Quotas[].{Name:QuotaName,Value:Value,Adjustable:Adjustable}' --output table
```

Quota increase requests **sirf us-east-1** se submit ho sakte hain, chahe kaam kisi bhi region me ho raha ho.

</Hinglish>

## Numbers That Matter

<Numbers>

- Least-privilege observation window: minimum **2-4 weeks**, must cover a full business cycle (quarterly jobs, month-end batches)
- Customer managed policies: 1,500 default, 10,000 maximum (adjustable)
- Roles per account: 1,000 default, 10,000 maximum (adjustable)
- Users per account: **5,000 — hard limit, not adjustable**
- Session duration: 900s (15 min) to 43,200s (12 hours); role chaining caps at 3,600s
- Managed policy size: 6,144 characters (whitespace excluded); inline policy aggregate on a role: 10,240 characters
- CDK bootstrap's `cfn-exec-role` gets `AdministratorAccess` by default — lock it down with `--cloudformation-execution-policies` in production

</Numbers>

## Interview Angle

<InterviewAngle>

Hands-on questions test whether you've actually run the commands, not just read about them — "how would you audit an AWS account's IAM for unused access" should produce the concrete `generate-service-last-accessed-details` → `start-policy-generation` → `check-no-new-access` pipeline, not a vague "review permissions" answer. ## Common Mistakes

<Mistake>

Deleting an IAM role or policy before detaching it from everything that references it — `DeleteConflict` errors are IAM enforcing dependency order: detach/disassociate → delete child → delete parent, always in that sequence.

</Mistake>

<Mistake>

Trusting a CloudTrail-generated least-privilege policy as complete — the observation window misses rare code paths like error handling, quarterly reports, and disaster-recovery scripts, which then silently break the first time they actually run.

</Mistake>

<Mistake>

Leaving CDK's default bootstrap in place for a production account — the `cfn-exec-role` has `AdministratorAccess` by default, meaning anyone who can run `cdk deploy` is effectively an admin regardless of their own IAM permissions.

</Mistake>

<Mistake>

Building per-tenant IAM users or roles for a SaaS product's end customers instead of session policies or app-level RBAC — this runs into IAM's hard 5,000-user limit and its eventual-consistency/rate-limit characteristics long before the business scales that far.

</Mistake>

<Mistake>

Submitting an IAM quota increase request from the working region instead of `us-east-1` — Service Quotas for IAM only accepts requests from `us-east-1`, regardless of which region the resources actually live in.

</Mistake>

## Quick Revision

<QuickRevision>

- The lab pattern — bucket, prefix-scoped policy, role, instance profile — is identical across Console, CLI, and CDK; only the mechanics differ
- CDK's `bucket.grantRead(role, "prefix/*")` beats hand-written `addToPolicy()` in production — it computes the correct actions including KMS permissions
- Cleanup order is always detach/disassociate → delete child → delete parent, or `DeleteConflict` errors block you
- CDK's `cfn-exec-role` gets `AdministratorAccess` by default on bootstrap — lock it down with `--cloudformation-execution-policies` before production use
- Least privilege is a 5-phase process: broad-and-monitored, observe a full business cycle, generate from CloudTrail, review-and-validate, then continuous quarterly review
- IAM is mandatory for AWS API access, but not for app-level authorization, database row-level security, Kubernetes RBAC, or network control — use the purpose-built tool for those
- Key audit commands to run against your own account: `get-account-summary`, `generate-credential-report`, `generate-service-last-accessed-details`, and the `iam:PassRole with *` one-liner
- Quota increase requests for IAM must be submitted from `us-east-1`, and the 5,000-user hard limit is the one number in this whole space that no ticket can raise

</QuickRevision>
