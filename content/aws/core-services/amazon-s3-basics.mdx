<SimpleDefinition>

S3 is AWS's object storage service — a key-value store (not a filesystem) that holds files of up to 5 TB with 99.999999999% (11 nines) durability by replicating across at least 3 Availability Zones, at a per-GB price that varies by storage class.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

S3 me koi bhi file — image, video, PDF, backup, log — daal sakte ho aur wo virtually unlimited scale pe store hoti hai. Sabse important cheez samajhne wali: **S3 ek file system nahi hai, ye ek key-value store hai.** Console me jo folders dikhte hain wo actually exist nahi karte — jo key ka naam hai usme bas `/` characters hain, jise UI folder ki tarah render karta hai. `photos/2024/goa.jpg` ek single object hai jiski poori key wahi string hai, koi "photos" folder object exist nahi karta. Isi wajah se S3 me "folder rename" jaisa operation hai hi nahi — har object copy karke purana delete karna padta hai.

### Kyun zaroori hai

Server disk ki apni limitations hain: EC2 pe EBS volume fixed size ka hai, disk fail ho sakti hai (hard disk ka annual failure rate ~2%), aur traffic badhne pe scaling manual kaam hai. S3 automatically data ko **kam se kam 3 Availability Zones** me replicate karta hai — 11 nines durability ka practical matlab ye hai ki 10 million objects ho to statistically ek khone me ~10,000 saal lagenge. Aur sirf static HTML/CSS/JS serve karne ke liye poora EC2 server 24×7 chalana waste hai — S3 me server hi nahi chahiye.

### Key components

**Bucket** globally unique naam wala top-level container hai (poore AWS me, saare accounts me unique), 3-63 characters, ek region me create hota hai aur naam banane ke baad change nahi ho sakta. **Object** ka max size 5 TB hai, aur wo immutable hai — "edit" ka matlab poora replace karna hai. **Key** object ka full path/naam hai, aur **Prefix** uska shuruaati hissa (`photos/2024/`).

### Storage classes — basic mental model

Sabse zyada use hone wali classes: **S3 Standard** (frequently accessed, ~$0.023/GB/month, active website assets), **S3 Standard-IA** (Infrequent Access — ~45% sasta, lekin retrieval fee aur 30 din ka minimum storage duration hai), aur **Glacier family** (archival — Instant Retrieval se Deep Archive tak, jahan Deep Archive sabse sasta hai ~$0.001/GB lekin retrieval me 12-48 ghante lagte hain). Interview me bolne layak insight: sirf per-GB price mat dekho — agar data har hafte access hota hai to IA actually Standard se mehnga pad sakta hai kyunki retrieval charge lagta hai. Frequently accessed data Standard pe rakho, sirf purana kam-access wala data hi sasti class me bhejo. (S3's deeper indexing, lifecycle automation aur replication is site ke dedicated S3 modules me cover hote hain — yahan sirf mental model banana hai.)

### Versioning — basic concept

Versioning on karne se S3 har object ke saare versions rakhta hai — accidental overwrite ya delete se recovery mil jaati hai. Bina version ID ke DELETE karoge to object actually delete nahi hota, ek "delete marker" version create hota hai jo latest ban jaata hai (GET pe 404 aayega); us marker ko delete karo to object wapas aa jaata hai. Cost warning: S3 diffs store nahi karta, har version ka **poora storage** charge hota hai — is topic ki gehrai (lifecycle rules se purane versions clean karna, MFA Delete, replication requirements) dedicated S3 modules me hai.

### REST endpoint vs Website endpoint — CloudFront se connect hota hai

Ye distinction pichhle CloudFront topic se seedha judta hai. S3 do endpoints deta hai: **REST endpoint** (`bucket.s3.region.amazonaws.com`) HTTPS support karta hai aur OAC ke saath kaam karta hai, lekin `index.html` auto-serve ya custom error documents nahi deta. **Website endpoint** (`bucket.s3-website-region.amazonaws.com`) index-document behaviour aur redirect rules deta hai, lekin **sirf HTTP pe kaam karta hai** aur bucket ko public karna padta hai — OAC/OAI iske saath kaam nahi karta. Isliye production setups me REST endpoint + CloudFront + OAC use hota hai: bucket private rehta hai, HTTPS CloudFront handle karta hai, aur index-document wala behaviour ek CloudFront Function se implement hota hai. Missing object pe bhi ye alag react karte hain — REST endpoint 403 deta hai (agar `ListBucket` permission nahi hai, jaanbujh ke security ke liye), website endpoint 404 deta hai.

</Hinglish>

## Real World Example

<RealWorld company="A Production AWS Project">

Ek real project me static frontend ke liye bucket **REST endpoint** se serve hota hai, static website hosting feature **disabled** rakha gaya — kyunki OAC website endpoint ke saath kaam hi nahi karta. Bucket pe Block Public Access ke saare four options ON hain, versioning enabled hai (rollback ke liye), aur default encryption SSE-S3 hai. Access sirf CloudFront ke OAC ke through milta hai, jisse bucket poori tarah private rehte hue bhi content HTTPS pe serve ho paata hai.

</RealWorld>

## Numbers That Matter

<Numbers>

- Durability: 99.999999999% (11 nines) across S3 Standard, Standard-IA, and Glacier classes
- S3 Standard availability: 99.99% (SLA 99.9%)
- Max object size: 5 TB; single PUT max: 5 GB (beyond that, multipart is mandatory)
- S3 Standard: ~$0.023/GB/month; Standard-IA: ~$0.0125/GB/month (45% cheaper, but with retrieval fee + 30-day minimum duration)
- Glacier Deep Archive: ~$0.00099/GB/month — cheapest, but 12-48 hour retrieval
- Default bucket limit: 100 per account (extendable to 10,000)
- Free tier (12 months): 5 GB Standard storage, 20,000 GET, 2,000 PUT requests

</Numbers>

## Interview Angle

<InterviewAngle>

"S3 traditional file storage se kaise alag hai" ka strong answer key-value model se shuru hota hai — folder hierarchy exist hi nahi karti, jo dikhti hai wo UI rendering hai. Storage class ka sawaal aane pe sirf per-GB price bolna weak signal hai — retrieval fee aur minimum duration ka trade-off bolna strong signal hai. REST vs Website endpoint ka distinction is topic ka sabse practical interview point hai kyunki wo seedha CloudFront/OAC decision se juda hai — "maine website endpoint nahi use kiya kyunki wo HTTPS support nahi karta aur bucket public karna padta" ek complete answer hai.

</InterviewAngle>

## Common Mistakes

<Mistake>

S3 ko "folder-based" file system samajhna aur folder rename karne ki koshish karna — S3 me aisa operation exist hi nahi karta, har object copy karke purana delete karna padta hai.

</Mistake>

<Mistake>

Static website hosting ke liye website endpoint use karke bucket public kar dena, taaki HTTPS bhi mil jaaye — website endpoint sirf HTTP pe kaam karta hai, HTTPS ke liye CloudFront + REST endpoint chahiye.

</Mistake>

<Mistake>

Storage class choose karte waqt sirf per-GB price dekhna — Standard-IA jaisi class ka 30-din minimum duration aur retrieval fee frequently-accessed data pe actually Standard se mehnga pad sakta hai.

</Mistake>

<Mistake>

Bucket naam ko change karne ki koshish karna deployment ke baad — bucket naam immutable hai, naya bucket banake data copy karna padta hai.

</Mistake>

## Quick Revision

<QuickRevision>

- S3 is object storage, not a filesystem — keys are flat strings, "folders" are just a UI rendering of `/` in the key name
- Durability (11 nines) means data survives; availability (99.99%) means it's reachable right now — they're different guarantees
- Objects are immutable — there's no partial edit, only full replace
- Standard for frequently accessed data; Standard-IA/Glacier only for data accessed rarely enough that the retrieval fee and minimum duration don't outweigh the storage savings
- Versioning keeps every version's full storage cost — deletion without a version ID creates a "delete marker," it doesn't erase the object
- REST endpoint supports HTTPS and OAC but not auto index documents; website endpoint supports index documents but is HTTP-only and requires a public bucket
- Production static sites use REST endpoint + CloudFront + OAC, not the website endpoint, specifically to keep the bucket private while still serving HTTPS
- Deeper S3 topics — lifecycle policies, replication, encryption, multipart upload, CORS — live in this site's dedicated S3 modules, not here

</QuickRevision>
