<SimpleDefinition>

Interviewers routinely probe an architecture choice by asking "why not X instead" — S3+CloudFront vs EC2 vs Amplify, CloudFront vs direct S3 access, Route 53 vs GoDaddy/Cloudflare, Lambda vs EC2 vs Fargate, and SES vs SendGrid/self-hosted SMTP. A strong answer names the alternative's genuine advantages before explaining the specific, situational reason it was rejected.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

Interviewer ka favourite pattern ye hai: "Aapne X use kiya, Y kyun nahi?" Ye poori tarah trap nahi hai — ye genuinely test kar raha hai ki kya tumne alternatives evaluate kiye ya bas ek hi option pata tha. Pattern hamesha same hai: pehle alternative ki genuine strength acknowledge karo, phir apni situation-specific reason do.

### S3 + CloudFront vs EC2 vs Amplify

EC2 pe static files serve karne ke liye ek instance 24 ghante chalana waste hai — OS patching, nginx tuning, monitoring, auto-scaling sab manually manage karna padta, aur cost $15-35/month se shuru hota hai chahe traffic zero ho. Amplify actually ek genuinely acha option hai — wo internally S3 aur CloudFront hi use karta hai, aur usme CI/CD built-in milti hai (git push = deploy). Iska matlab Amplify ko "kyun nahi" bolna thoda tricky hai, kyunki ye khud hi is stack ka wrapper hai. Sahi answer ye hai: "maine deliberately S3 + CloudFront directly choose kiya kyunki main underlying components khud samajhna chahta tha — cache policies, OAC, TTL strategy, invalidation. Amplify ye sab abstract kar deta hai, jo production me faayda hai lekin seekhne ke liye main ek layer neeche jaana chahta tha. Agar SSR chahiye hota ya team ke liye fast CI/CD chahiye hoti to Amplify better choice hoti."

### CloudFront vs Direct S3 Access

Ye comparison technically ek non-choice bhi hai: S3 ka static website endpoint HTTPS support hi nahi karta custom domain pe, isliye CloudFront mandatory tha SSL ke liye. Lekin isse alag bhi CloudFront lena sahi tha — latency 200-400 ms (single region) se 20-80 ms (edge) pe aa gayi, bucket poori tarah private reh paya OAC ke saath, free Shield Standard DDoS protection mil gaya, aur ek counter-intuitive point jo interview me bolna chahiye: CloudFront cost badhata nahi, kam karta hai, kyunki S3-to-CloudFront data transfer free hai jabki S3-to-internet direct transfer ~$0.09/GB charge hota hai, aur cache hit se S3 pe requests bhi 85%+ kam ho jaati hain.

### Route 53 vs GoDaddy / Cloudflare DNS

Cloudflare ek strong option hai — uska free tier bahut generous hai aur usme free CDN aur DDoS protection built-in hai. Route 53 teen specific reasons se choose kiya jaata hai: ALIAS records (native AWS integration, zone apex pe kaam karta hai, health-check integration ke saath — Cloudflare ka CNAME flattening similar effect deta hai but AWS health-check integration nahi), routing policies aur health checks (agar multi-region jaana ho to latency-based routing with automatic failover natively milta hai), aur operational consistency (poora stack AWS pe hai to IAM, CloudTrail, Terraform ek hi provider me manage karna simpler hai). Cost negligible hai (~$1/month). Agar stack multi-cloud hota ya free CDN chahiye hoti to Cloudflare zyada sensible hota.

### Lambda vs EC2 vs ECS/Fargate

Ye decision **traffic pattern** pe depend karta hai, feature list pe nahi. Lambda ka economics tab jeetta hai jab traffic spiky ya low ho, kyunki idle cost zero hai. Agar traffic constantly high aur steady hai — jaise 24 ghante 5,000 requests/second — to Lambda ka per-request pricing add up ho jaata hai aur EC2 with Savings Plans ya Fargate aksar saste pad jaate hain. Workload event-driven aur bursty ho (contact form din me 50 baar hit hota hai) to EC2/Fargate chalana matlab 24 ghante compute ka paisa dena jabki actual compute kuch second ka hai. Lambda ki genuine limits bhi honi chahiye pata: 15 minute timeout, cold start, aur stateful ya long-lived connection (WebSocket) workloads ke liye ye fit nahi hai — un cases me Fargate sahi choice hai. Steady high throughput ho to EC2 with Savings Plans evaluate karna chahiye.

### SES vs SendGrid / SMTP / Mailgun

Self-hosted SMTP option hi nahi hai practically — EC2 pe outbound port 25 by default blocked hota hai, aur IP reputation zero se banana hafton ka kaam hai. SendGrid genuine option hai — uska template editor aur campaign management SES se kaafi better hai. SES teen reasons se choose kiya jaata hai: cost (~9x sasta — $10 vs $75-90 per 100k emails), IAM integration (koi API key store nahi karni padti, Lambda ka execution role hi authentication hai — ek pura class of secret-management problems eliminate ho jaata hai), aur native event integration (bounce/complaint events seedha SNS pe jaate hain, koi webhook endpoint banane ki zaroorat nahi). Non-technical marketing team ho jo khud campaigns banati, to SendGrid clearly better fit hota.

### Quick reference — one-liners jo yaad rakhne hain

Ye table interview se pehle scan karne layak hai: "EC2 kyun nahi" ka jawab hai static content ke liye 24x7 server waste hai — cost, patching, scaling overhead bina fayde ke; "Amplify kyun nahi" ka jawab hai Amplify internally yahi stack use karta hai, underlying components khud samajhne ke liye direct choose kiya; "Direct S3 kyun nahi" ka jawab hai S3 website endpoint HTTPS support hi nahi karta custom domain pe; "Cloudflare kyun nahi" ka jawab hai ALIAS records aur AWS-native health check integration, plus poora stack ek provider me; "Fargate kyun nahi" ka jawab hai workload event-driven aur bursty hai, idle time ka paisa lagta; "SendGrid kyun nahi" ka jawab hai 9x mehnga, aur IAM role se auth mil gaya; "API Gateway kyun, Function URL kyun nahi" ka jawab hai throttling, request validation, custom domain routing chahiye thi; "DynamoDB kyun, RDS kyun nahi" ka jawab hai Lambda ke saath connection pooling ka problem nahi aata, DynamoDB connectionless HTTP API hai.

</Hinglish>

## Numbers That Matter

<Numbers>

- EC2 static hosting minimum cost: **$15-35/month**, even at zero traffic, vs S3+CloudFront: **~$0.10-1/month**
- CloudFront (edge) latency for distant users: **20-80 ms** vs direct S3 single-region access: **200-400 ms**
- S3-to-internet direct data transfer: **~$0.09/GB**; S3-to-CloudFront transfer: **free**
- Cache hit reduces origin (S3) requests by **85%+**
- SES vs SendGrid/Mailgun at 100k emails/month: **~$10 vs ~$75-90** — roughly a 9x cost difference
- Lambda default concurrency: **1,000 per region (soft limit)**; max execution timeout: **15 minutes (900s)**

</Numbers>

## Interview Angle

<InterviewAngle>

"Why not X" questions test whether a decision was actually a decision, or just the first tool the candidate learned. The strongest answers follow a consistent shape: acknowledge the alternative's real strength first (this is what separates "I know trade-offs exist" from "I only know my own stack"), then give the specific, situational reason it was rejected — tied to a concrete constraint (cost, a hard technical limitation like HTTPS-on-website-endpoints, or a learning goal), never a vague "it's better." Interviewers also listen for whether the candidate's answer changes when the scenario changes — e.g., admitting that Amplify or Fargate would be the right call under different constraints signals the decision was contextual, not dogmatic.

</InterviewAngle>

## Common Mistakes

<Mistake>

Dismissing the alternative outright ("EC2 is bad," "SendGrid is worse") instead of naming its genuine strength first — this reads as not having actually evaluated it, just defending a default.

</Mistake>

<Mistake>

Giving a generic answer ("Lambda is cheaper and scales better") instead of a situational one tied to the actual traffic pattern — the strong Lambda-vs-EC2 answer explicitly names the break-even logic (spiky/low traffic favors Lambda, steady/high traffic favors EC2 or Fargate), not just "Lambda is better."

</Mistake>

<Mistake>

Not knowing that CloudFront was a hard technical requirement in one case (S3 website endpoints don't support HTTPS on a custom domain) and treating it purely as a preference — this misses a fact that would end the debate immediately.

</Mistake>

<Mistake>

Forgetting to mention that CloudFront's data-transfer pricing can make an architecture cheaper, not more expensive — most candidates only cite CloudFront for latency and security, missing the cost argument entirely.

</Mistake>

## Quick Revision

<QuickRevision>

- EC2 rejected for static hosting: 24/7 server cost + patching overhead for content that doesn't need it
- Amplify rejected (not because it's worse — it wraps the same stack) but to learn cache policies, OAC, and TTL strategy directly
- CloudFront wasn't optional: S3 website endpoints don't support HTTPS on a custom domain, so CloudFront was mandatory for SSL alone
- CloudFront is often cheaper, not just faster: S3-to-CloudFront transfer is free, S3-to-internet direct is ~$0.09/GB
- Route 53 over Cloudflare/GoDaddy: ALIAS + native health checks + single-provider operational consistency
- Lambda vs EC2/Fargate is a traffic-pattern decision — spiky/low traffic favors Lambda, steady/high throughput favors EC2 or Fargate
- SES over SendGrid: ~9x cheaper, IAM-role auth (no API keys to store), native SNS event integration
- Self-hosted SMTP isn't a real option: EC2 blocks outbound port 25 by default, and IP reputation takes weeks to build

</QuickRevision>
