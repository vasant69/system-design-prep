<SimpleDefinition>

STS (Security Token Service) is IAM's token-issuing endpoint — when a principal calls `AssumeRole` on an IAM role, STS checks the role's trust policy and the caller's own identity policy, and if both allow it, returns temporary credentials (access key, secret key, session token) that expire on their own, by default in one hour.

</SimpleDefinition>

## Hinglish Deep Explanation

<Hinglish>

### Access key, password, aur session token — teeno alag hain

**Password** sirf **console** login ke liye hai — API calls me kaam nahi aata, aur IAM user par optional hai. **Access key pair** (`AKIA...` + secret) sirf **API/CLI/SDK** ke liye — console login me kaam nahi aata, permanent hai aur khud expire nahi hoti; ek user ke paas max **2 active keys** ho sakti hain (yahi rotation ka mechanism hai — nayi banao, apps switch karo, purani delete karo). **Session token** temporary credentials ka teesra component hai — `ASIA...` se shuru hone wali access key ke saath aata hai, expire hoti hai, aur har request me `X-Amz-Security-Token` header me jaata hai. `AKIA` vs `ASIA` prefix se logs me turant pata chal jaata hai credential permanent hai ya temporary. Agar temporary credentials use karte waqt session token pass karna bhool gaye, error `InvalidClientTokenId` aayega — jo lagta hai key hi galat hai, jabki actually teesra piece missing hai. Env var ka naam `AWS_SESSION_TOKEN` hai (purana `AWS_SECURITY_TOKEN` deprecated hai).

### STS aur AssumeRole ka poora flow

STS ka ek hi kaam hai: **short-lived credentials issue karna** — ye IAM ka "token endpoint" hai.

```bash
# Caller ke paas already koi valid credential honi chahiye
# (IAM user key, EC2 instance role, ya koi doosri assumed role)

aws sts assume-role \
  --role-arn arn:aws:iam::999988887777:role/CrossAccountReader \
  --role-session-name shani@jmfs \
  --duration-seconds 3600
```

STS do checks karta hai: (a) target role ki **trust policy** caller ko allow karti hai (resource-side), aur (b) caller ki **identity policy** me us role ARN par `sts:AssumeRole` hai (identity-side). Dono chahiye — cross-account me ye AND strictly enforce hota hai. Pass hone par STS return karta hai:

```json
{
  "AccessKeyId": "ASIA...",
  "SecretAccessKey": "...",
  "SessionToken": "...",
  "Expiration": "2026-08-06T12:00:00Z"
}
```

Caller in credentials se naye role ki tarah API calls karta hai. Design ka reason simple hai: caller ko target account ki koi permanent credential kabhi nahi milti — trust ek policy me declare hoti hai jo target account control karta hai, aur wo kabhi bhi hata sakta hai. `RoleSessionName` CloudTrail me `userIdentity.arn` me literally dikhta hai, isliye isko meaningful rakhna (email, employee ID, pipeline run ID) — kai companies isko `sts:RoleSessionName` condition key se policy me bhi enforce karti hain. "Kisne kiya tha?" ka jawab isi field se milta hai.

### Trust policy aur External ID

Role ki trust policy uski **resource-based policy** hai — iska action hamesha `sts:AssumeRole` (ya `AssumeRoleWithWebIdentity` / `AssumeRoleWithSAML`) hota hai.

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::999988887777:root" },
    "Action": "sts:AssumeRole",
    "Condition": {
      "StringEquals": { "sts:ExternalId": "jmfs-vendor-a7f3d91c" }
    }
  }]
}
```

External ID solves the **confused deputy** problem. Scenario: you give a SaaS monitoring vendor role-assumption access to your account; that same vendor serves 500 other customers. If another customer tricks the vendor into calling `AssumeRole` against your account ID + role name, the vendor's confused call would read your data. An External ID is a secret only you and the vendor know, required in every assumption request — without it, the assume fails. External ID: **2 to 1,224 characters**, alphanumeric plus `+=,.@:/-`. Crucially, **you** generate the External ID, not the vendor — if a vendor hands you one, that pattern is wrong (it may be guessable). It doesn't need to be hidden like a password, just unguessable — a UUID is fine.

### Instance Profile — role se alag kyun hai

EC2 instance ko tum directly role attach nahi kar sakte — beech me ek wrapper object hota hai, **instance profile**, jisme exactly **ek** role hoti hai. Console me EC2 par role attach karte waqt console chupchaap same naam ka instance profile bana deta hai, isliye ye distinction dikhti hi nahi. Lekin CLI/CDK/Terraform me ye alag objects hain:

```bash
aws iam create-role --role-name AppRole --assume-role-policy-document file://trust.json
aws iam create-instance-profile --instance-profile-name AppProfile
aws iam add-role-to-instance-profile --instance-profile-name AppProfile --role-name AppRole
aws ec2 associate-iam-instance-profile --instance-id i-123 \
    --iam-instance-profile Name=AppProfile
```

Historical reason: instance profile aaya 2012 me jab plan tha ek profile me multiple roles daalne ka — wo plan implement nahi hua, lekin abstraction reh gayi. Practical gotcha: instance profile create karne ke baad EC2 ko available hone me kuch seconds lagte hain (eventual consistency) — turant instance launch karoge to `Invalid IAM Instance Profile name` mil sakta hai; Terraform/CDK me ye classic flaky-apply ka reason hai, retry ya explicit `depends_on` + delay lagta hai.

### MaxSessionDuration — default aur maximum

Role par ek setting hoti hai `MaxSessionDuration`, range **3,600 seconds (1 hour) se 43,200 seconds (12 hours)**, default **3,600 (1 hour)**. Alag se, `AssumeRole` call me `DurationSeconds` pass kar sakte ho: **900 seconds (15 min) se role ke MaxSessionDuration tak**; kuch pass na karo to default 3,600 seconds milta hai chahe role ka max 12 hours ho.

```bash
aws iam update-role --role-name DeployRole --max-session-duration 14400  # 4 hours
aws sts assume-role --role-arn ... --role-session-name x --duration-seconds 14400
```

12-hour ceiling ek risk-vs-convenience trade-off hai — long-running jobs (ETL, data migration) ko lamba session chahiye, lekin infinitely lamba credential wapas permanent key jaisa ban jaata hai; 12 hours ek working day cover karta hai. Console me "Switch Role" karne par sirf **max 1 hour** milta hai, chahe role ka MaxSessionDuration 12 hours ho — console ki apni alag limit hai. Aur agar beech me credentials expire ho gaye (long-running Node script me), `ExpiredToken` error milega — AWS SDK v3 ke credential providers automatically refresh karte hain **agar** unhe provider function di ho, static credentials object nahi.

### Role chaining aur uski 1-hour limit

Role chaining = ek assumed-role session se doosri role assume karna (Role A → Role B → Role C). Jab tum ek **assumed-role session se** AssumeRole call karte ho, maximum duration **1 hour** ho jaati hai — chahe target role ka MaxSessionDuration 12 hours ho; `DurationSeconds > 3600` pass karoge to error milega. Reason: har hop par credential ki "distance" original identity se badhti jaati hai, aur AWS chahta hai chained sessions frequently re-validate hon taaki agar beech me kisi role ki trust policy hat jaaye to chain jaldi toot jaaye. Gotcha jo audits ko affect karta hai: chaining me `aws:PrincipalArn` har hop par badal jaata hai — original identity **lose** ho jaati hai, unless session tags forward karo (`sts:TagSession` + transitive tags):

```json
"Condition": { "ForAllValues:StringEquals": { "sts:TransitiveTagKeys": ["OriginalUser"] } }
```

Agar audit requirement hai "kis insaan ne production me ye kiya", to 3-hop chain me wo answer transitive tags ke bina gayab ho sakta hai.

### STS regional vs global endpoint — token kis region me valid hai

Ye historical baggage hai jo ab mostly resolve ho chuka hai, lekin samajhna zaroori hai. **Global endpoint** (`sts.amazonaws.com`) ka token version 1 hai — default-enabled regions me valid, lekin **opt-in regions** (jaise ap-east-1 Hong Kong, me-south-1 Bahrain) me valid **nahi**, aur ye token bada hota hai. **Regional endpoint** ka token version 2 hai — **sab regions me valid**, including opt-in. Account setting: IAM console → Account settings → "Security Token Service (STS)" → "Global endpoint token version" ko **"Valid in all AWS Regions"** par set kar do — ek-baar ka kaam jo bahut logon ne nahi kiya hai. Alag se, har opt-in region ke liye STS ko explicitly **activate** karna padta hai (same Account settings page, per-region enable/disable). Agar `RegionDisabledException: STS is not activated in this region for account: xxx` dikhe, ye policy problem **nahi** hai — ye account-level region activation setting hai; log ghanton IAM policies debug karte reh jaate hain jab fix sirf console ke Account settings me ek toggle hai.

</Hinglish>

<Callout type="tip">

Rule of thumb for CloudTrail forensics: `AKIA` prefix = permanent IAM user key, `ASIA` prefix = temporary STS-issued credential. That one detail tells you instantly whether you're looking at a long-lived key that needs rotating, or a session that already expired on its own.

</Callout>

## Real World Example

<RealWorld company="A Production AWS Project">

A vendor integration used cross-account role assumption with a project-generated External ID (a UUID, never supplied by the vendor) embedded as a condition on the trust policy, so a confused-deputy call from the vendor's other customers could never succeed against this account. CI/CD pipelines assumed a `DeployRole` with `RoleSessionName` set to the pipeline run ID, so any production change could be traced in CloudTrail back to the exact pipeline execution. EC2 instances never carried access keys at all — they used an instance profile wrapping a least-privilege role, and Terraform applies occasionally hit the `Invalid IAM Instance Profile name` eventual-consistency gotcha right after profile creation, worked around with a short retry.

</RealWorld>

## Numbers That Matter

<Numbers>

- Default STS session duration: **3,600 seconds (1 hour)**; role `MaxSessionDuration` range: **3,600 to 43,200 seconds (1–12 hours)**
- `AssumeRole` `DurationSeconds` range: **900 seconds (15 min) up to the role's MaxSessionDuration**
- Console "Switch Role" session cap: **1 hour**, regardless of the role's MaxSessionDuration
- Role chaining (assumed-role calling AssumeRole again) is capped at **1 hour**, regardless of target role's MaxSessionDuration
- Max active access keys per IAM user: **2** (the rotation mechanism)
- External ID length: **2 to 1,224 characters**, alphanumeric plus `+=,.@:/-`

</Numbers>

## Interview Angle

<InterviewAngle>

"Explain the AssumeRole flow end to end" is asked constantly — the strong answer names both checks STS performs (trust policy on the resource side, `sts:AssumeRole` identity policy on the caller side, both required) and states the returned credential shape (access key, secret key, session token, expiration). A frequent follow-up scenario is the confused deputy problem: "why does a third-party SaaS vendor's cross-account role need an External ID?" — the strong answer explains that without it, another customer of the same vendor could trick the vendor into calling AssumeRole against your account. Interviewers also probe role chaining's 1-hour cap to see if the candidate has hit it in practice — a role with a 12-hour MaxSessionDuration still caps out at 1 hour the moment it's assumed from another assumed-role session.

</InterviewAngle>

## Common Mistakes

<Mistake>

Forgetting to pass the session token alongside temporary credentials, then misreading the resulting `InvalidClientTokenId` error as a bad access key when the actual key is fine — the session token is simply missing.

</Mistake>

<Mistake>

Letting a vendor supply the External ID instead of generating it yourself. A vendor-supplied External ID may be predictable or reused across customers, defeating its purpose as a confused-deputy guard.

</Mistake>

<Mistake>

Launching an EC2 instance immediately after creating its instance profile via CLI/Terraform, hitting `Invalid IAM Instance Profile name` due to eventual consistency, and assuming the IAM setup itself is broken rather than adding a short retry/delay.

</Mistake>

<Mistake>

Assuming a role's 12-hour `MaxSessionDuration` applies uniformly everywhere. Console "Switch Role" caps at 1 hour, and any role chaining hop (assumed-role calling AssumeRole again) also caps at 1 hour, regardless of what the target role allows.

</Mistake>

<Mistake>

Debugging `RegionDisabledException: STS is not activated in this region` as if it were an IAM policy problem. It's an account-level per-region STS activation toggle in IAM console Account settings, not a permissions issue.

</Mistake>

## Quick Revision

<QuickRevision>

- Password = console only; access key (`AKIA...`) = API/CLI only, permanent, max 2 active per user; session token = accompanies temporary (`ASIA...`) credentials, expires on its own
- AssumeRole needs two Allows: the role's trust policy (resource-side) and the caller's identity policy (`sts:AssumeRole` on that ARN)
- Trust policy is the role's resource-based policy; External ID (generated by you, not the vendor) prevents the confused-deputy problem in cross-account access
- Instance Profile is a separate wrapper object (holding exactly one role) that the console hides but CLI/CDK/Terraform expose directly
- `MaxSessionDuration`: 1–12 hours, default 1 hour; `AssumeRole`'s `DurationSeconds`: 15 min up to that max
- Console Switch Role always caps at 1 hour; role chaining always caps at 1 hour, regardless of the target role's configured maximum
- Role chaining loses the original principal's identity in `aws:PrincipalArn` unless transitive session tags are forwarded
- Use STS regional endpoints (and enable the "valid in all regions" token setting) — the global endpoint's v1 token doesn't work in opt-in regions

</QuickRevision>
